## 一、它替你做了什么

启动器**不是**另一个 Hunter。它调的就是你手工部署会敲的那几条 `docker compose` 命令，
只是替你把参数填对、把出错的地方讲人话。所以：

* 出了问题，日志里是真实的 docker 输出，你可以照着自己复现；
* 你随时可以绕开它，直接 `cd ~/.hunter/app && docker compose -p hunter ...`；
* 卸载启动器**不会**动你的数据。

它做的六件事：校验 key → 检测 Docker → 选镜像源 → 拉 6 个镜像 → 写配置起容器 → 开浏览器。

> 0.1.4 起 key 排在 Docker 前面：Docker 那一步是最容易卡住的，而新加的 AI 诊断助手要用这把 key 调网关，
> 所以先把 key 收了。填 key 只需要联网，本来就不依赖 Docker。
之后常驻托盘，管启动 / 停止 / 升级 / 看日志 / 反馈。

## 二、装好之后第一次打开

向导一共 5 页，左边那条竖线就是进度：**欢迎 → 输入 key → 一次授权 → 自动安装 → 完成**。

> 0.1.5 起，「检测 Docker」「选择模型」「拉取镜像」「启动」这四步不再让你一页一页点 ——
> 它们都并进了「自动安装」那一页，由 AI 连着跑完，过程实时显示给你看。

### 1. 欢迎

选界面语言（中文 / English），勾一下协议。没有别的事。

### 2. 输入 key

一把 `hunt_tools_` 开头的 key，同时用于大模型、行情数据和工具网关。
还没有的话，页面左下角有申请链接（免费，约 30 秒）。

粘贴进去会**真的去问一次网关**（`GET /api/saas/llm/quota` + `/v1/models`），
通过之后当场显示今日额度、可用模型。这几个数字是网关返回的真值，不是写死的。

> **key 存在哪**：只有 `~/.hunter/app/.env`（权限 600）和启动器的内存里。
> 它不进日志、不进诊断包、不进遥测。界面上、日志里出现时一律打码成 `hunt_tools_****`。

key 不对时只会说「网关不认这把 key」——网关对「格式错 / 不存在 / 已吊销 / 没带」
返回的响应是**一模一样**的，分不出来。分不出来就不装作分得出来。

### 3. 一次授权（0.1.5 新增）

这一页问你一件事：**要不要让 AI 替你把 Hunter 装好**。

安装中如果遇到问题，AI 会自己查原因、自己解决，你不用看懂任何报错。
页面上写清楚了它会做什么、绝不会做什么 —— **「绝不会做」的每一条在程序里都有一道硬校验，
不是靠提示词约束**：

| 它绝不会做 | 程序里怎么保证 |
|---|---|
| 删除你的任何文件 | 所有写 / 删的路径先 `canonicalize`（解开 `..` 与软链）再判断，必须落在 `~/.hunter/` 内；能删的只有启动器自己生成的那几个文件（有白名单） |
| 删除或停止你电脑上其他的容器、镜像、数据 | 每一条 docker 命令都要带 `--project-name hunter`；按 ID 操作的先 `docker inspect` 查 compose 项目标签，不是 `hunter` 一律拒绝。`docker volume rm` / `system prune` / `down -v` 根本不在它能挑的动作表里 |
| 修改你的网络设置（代理 / DNS / hosts / VPN / 防火墙） | `networksetup` / `scutil` / `pfctl` / `iptables` / `netsh` / `/etc/hosts` 一律拒绝 |
| 修改系统安全设置、使用管理员密码 | 动作表里没有任何需要 `sudo` 的动作。真碰到要管理员权限的事（例如 Linux 上启动 docker 服务），它会把命令原样写给你，请你自己在终端里执行 |
| 执行它自己编写的命令 | 它只能从一张**固定的动作表**里挑 id 并填受检的参数。表外的一律被拒绝并记进审计日志 |

**三个档位**（设置页里随时可改）：

| 档位 | 行为 |
|---|---|
| **授权 AI 自动安装（推荐）** | 只动 Hunter 自己东西的操作直接做，做完告诉你；要动你已有的 Hunter 仍然会先问 |
| 我想每一步自己确认 | 每一个会改动的操作都先弹出来给你看，你点了才做 |
| 不用 AI，只按固定规则装 | 只用内置的确定性规则，不调模型，一个 token 也不花 |

**这一页下面还有一项勾（0.1.7 新增，默认勾着）**：

> 如果电脑上没有 Docker，允许 AI 为你安装（装在 `~/.hunter/runtime` 里，不改系统，可一键卸载）

勾着的话，真碰上「这台电脑没有 Docker」时它就直接装，不再单独问你一句；
取消勾选就还是先出一张卡片问你。装的是什么、装在哪、怎么卸，见下面的
[「电脑上没有 Docker 怎么办」](#电脑上没有-docker-怎么办0117-起全自动)。

**除此之外的「需要你同意」级别动作照样每次都问** —— 比如「改为管理你已经装好的那一套
Hunter」。那件事动的是你自己的东西，没有「一次授权、以后不问」的道理。

### 复核员（0.1.7 新增）

计划里出现「需要你同意」级别的动作时，启动器会**再问一次模型** —— 换一段完全独立的
提示词，让它扮演审查者，只回答两件事：

1. 这个计划会不会伤到你**已有的**数据 / 网络 / 其他项目？
2. 它给的理由，对不对得上现场证据里的原话？

过程流里会出现一张单独的「复核」卡片，写明通过还是否决、理由是什么、花了多少 token。
**否决了就退回去重想**（带着否决理由），换一个办法再来一次。

> **复核通过不等于可以执行。** 守卫（程序里那道硬校验）与你的确认这两道照样要过 ——
> 三道是「都要过」的关系，不是投票。多一个模型把关，不是让代码那道门松一松的理由。

AI 每做一件事（**包括被拒绝的**）都写进 `~/.hunter/logs/assist-audit.log`，
设置页的「AI 都做过什么」里能直接看最近 20 条。

> 想用自己的模型 key（DeepSeek / Qwen / Claude / OpenAI…）的话，点这一页左下角的
> 「我要用自己的模型 key」，会多出一页让你填 BASE_URL、模型名、API key 三项；
> 也可以装完之后到设置里改。默认走 Hunter 网关，不用管。

### 4. 自动安装

**点完授权之后，你不需要再点任何按钮。**

界面上是一条实时过程流，每一件事一张卡片，写人话：

```
✅ 检查 Docker            OrbStack 29.4.0 正在运行
✅ 挑下载源、算端口、写配置  下载源 腾讯云 · 香港 · 端口 web 3101 · api 8101 · …
   ⚠️ 你电脑上已经在运行另一套 Hunter   hunter-fresh（6 个容器，占着端口 3100、3921、5442、6479、8100）
   ✔ 为这次安装换了一组空闲端口       web 3100→3101 · api 8100→8101 · …
      🔎 8100 原来被占着              Docker 容器 hunter-fresh-api-1（compose 项目 hunter-fresh）
✅ 下载组件               849 MB · 用时 3 分 27 秒
✅ 启动服务               6 / 6 健康
🎉 完成                   打开 http://localhost:3101
```

- 顶上一行常驻：现在在干什么、已自动解决几个问题、花了多少 token、第几个修复回合。
- 每张卡片右边的「详情」里是技术细节：执行了什么命令、原始输出、耗时、依据。
- 出问题时你会看到 AI 完整的思路：发现问题 → 分析中（查了什么）→ 找到原因 → 正在处理 →
  重新试一次刚才失败的那一步 → 已解决。**「解决了」的判据是重跑那一步真的过了，
  不是模型说「应该可以了」。**

**0.1.8 起，从点「开始安装」到装好，你一次都不用点。** 以前会停下来问你的那三件事，
现在启动器自己按最佳方案办，并在过程流里用一句人话说明做了什么决定、为什么：

| 情况 | 它自己怎么办 |
|---|---|
| 要装新软件（容器运行时 / OrbStack / Homebrew） | 按「最不打扰你」的顺序依次试，见下面「电脑上没有 Docker 怎么办」 |
| 这台电脑上已经有另一套 Hunter | 自动「两套并存、换一组端口」，你原来那套一点都不动 |
| 这次的额度用完了 | 不问你，改成只按固定规则继续；真装不上就自动生成脱敏诊断包 |
| 另一个模型复核时否决了某个方案 | 自动退回去重想一个，不问你 |

**唯一可能出现的交互是系统自己弹的密码框**（macOS 的授权框 / Linux 的 polkit / Windows 的 UAC），
而且只出现在最后一条兜底路线上 —— 前面几条路都不需要它。弹之前界面上会先用一句人话说清
「要做什么、为什么要密码」。密码交给系统，**启动器看不到、不会保存、也不会写进日志**。

> 想自己盯着每一步的，设置页 →「AI 助手」里有「每一步都问我」那一档。默认不是它。

### 电脑上已经有一套 Hunter 怎么办

启动器发现本机已经有一套 Hunter（别的 compose 项目）时，**自动选「两套并存、换一组端口」**：
新装的这一套挑一组空闲端口，你原来那套一点都不动。这是风险最小的做法，所以不问你 ——
过程流里会出一行说明，告诉你它发现了什么、定了什么。

想改成**直接用已有那一套**（不再装新的）：设置页 →「已有的 Hunter」里切换，
或者命令行 `--takeover <项目名>`。切过去之后，运行面板变成「正在管理你原有的 Hunter」：看容器状态、看日志、
打开网页。**停止 / 启动 / 重启每一次都会再问你一遍**，而且：

- 启动器**不会改它的配置**，一个字节都不改；
- **任何情况下都不删它的数据卷** —— 动作表里根本没有对它执行 `down` / `-v` 的路；
- 读不到它的 compose 文件在哪时，如实降级成**只读监控**（只能看，停不了）。

不想管了就在那一页点「不再管理它」—— 它还在原地跑着，一个字节都没动过。

### 电脑上没有 Docker 怎么办（0.1.8 起三条路自动依次走完）

以前这一步要你自己去下载 Docker Desktop / OrbStack、拖进应用程序、点开、过欢迎页。
现在 macOS 上**全程不用你点**，而且**一条路走不通会自动换下一条**：

| 顺序 | 路线 | 要下多少 | 要密码吗 |
|---|---|---|---|
| ① | **内置运行时**（Colima + Lima + docker 客户端 + compose + 虚拟机系统镜像） | 约 436 MB | **不要** |
| ② | **OrbStack 官方安装包**（下 dmg → 验苹果签名与公证 → 装进「应用程序」→ 打开 → 等就绪） | 约 200 MB | 可能要 |
| ③ | **Homebrew** —— 这台电脑上没有 brew 就**先替你把 brew 装上**，再 `brew install --cask orbstack` | 视情况 | 会要 |

排序原则是**「同样能解决问题时，优先不需要任何交互的那条」**，所以要密码的排在最后；
只有前面所有零交互的路线都失败了才会走到它。每一条开始前界面上都有一句人话 + 预计下载量。

第一条路是这样的 —— 启动器装一套**完全用户态**的容器运行时到 `~/.hunter/runtime`：

| 组件 | 版本 | 干什么 |
|---|---|---|
| Colima | v0.10.3 | 一条命令起一台跑着 docker 的虚拟机 |
| Lima | v2.2.0 | Colima 的底座 |
| docker 客户端 | 29.8.1 | 官方静态包（只有客户端，daemon 在虚拟机里） |
| docker compose | v5.5.1 | 作为 CLI 插件 |
| 虚拟机系统镜像 | colima-core v0.10.4 | `ubuntu-24.04-minimal-cloudimg-*-docker.raw.gz`（341 MB / 316 MB） |

- **版本与校验和写死在程序里**（前四个用 sha256，虚拟机镜像用它官方给的 sha512），
  下完逐个核对，对不上就删掉不用 —— 不跟着 `latest` 漂移，每台机器装到的都是同一份东西。
- 两个下载源并列测速：GitHub / docker.com（海外）与腾讯云香港（国内），哪个快用哪个。
- **虚拟机系统镜像也由启动器自己下**（0.1.8 起）。这一条是 0.1.7 在用户 Mac 上卡住的
  直接原因：`colima start` 会自己直连 GitHub 去取那 341 MB，那一次下载不受启动器控制，
  直连不通就是干等到超时。现在它进了同一条流水线（双源、校验、真实进度），
  下好之后用 `--disk-image` 交给 colima，它一个字节都不用自己下。
- **这一条路不需要管理员密码，不改系统任何地方**：不写 `/usr/local`、不改 shell 配置文件、
  不碰你的 `~/.docker`。虚拟机、docker socket、配置全在 `~/.hunter/runtime` 里面。
- 本机**已经装了 OrbStack / Docker Desktop / Colima** 的话它一个字节都不下 ——
  在跑就直接用，装了没跑就先把它点起来。
- 不想要了：设置页 →「容器运行时」→「卸载内置运行时」，删虚拟机磁盘 + 清空那个目录。
  **Hunter 自己的数据卷不受影响。**
- **上一次没装成功也没关系**（0.1.9 起）：启动器认得出自己上一次留下的东西，
  **接着上次装，不会重来一遍**。已经下好并核过校验和的文件一个字节都不重下，
  内容对不上的删掉重下，虚拟机起不来就清掉重建一次。整个过程只动
  `~/.hunter/runtime` —— 你的 `~/.colima`、`~/.lima`、`~/.docker/config.json`、
  别人的容器与数据卷一个字节都不碰。这不是一句承诺：启动器发出的每一条 colima
  命令都在**真正执行之前**被检一遍，缺隔离参数就拒绝并记进审计日志
  （`~/.hunter/logs/assist-audit.log`）。细节见《常见问题》里
  「之前装过没成功，再装会怎样」。
- **已经装好了就不会再装一遍**（0.1.11 起）：不管是重新打开启动器，还是在错误页上
  点「重试」，第一步都是**只读地看一眼现状**。六个服务都在正常跑就什么都不做，
  只有个别服务不正常就只动那几个（不重新取配置、不重新下载镜像、健康的容器一个不重建），
  确实没装才走完整安装。实测：一套装好的 Hunter 再点一次「重试」，**2 秒、零下载**。

第二条路是 **OrbStack 官方安装包**：下 dmg、验苹果的签名与公证（含 Team ID）、装进
「应用程序」、由启动器替你打开、等 docker 就绪。它装得更快，但第一次打开时
**OrbStack 自己会弹它的欢迎页** —— 那是第三方程序的界面，启动器不会替你点，
但也**不会停下来等你**：它会一直等 docker 就绪，超时就继续走下一条路。
所以它排在内置运行时后面。（另：OrbStack 个人使用免费，商用需要另外授权。）

第三条路是 **Homebrew**：这台电脑上没有 brew 的话，启动器跑它官方的安装脚本
（`NONINTERACTIVE=1`）先把 brew 装上，再 `brew install --cask orbstack`。
brew 要往系统目录里写文件，所以这一步会弹一次**系统自己的密码框** ——
弹之前界面上会先说清楚为什么。这也是整条链上唯一要密码的地方。

> **Windows / Linux 上的情况不一样。** Windows 装 WSL 或 Docker Desktop 要管理员权限，
> Linux 装 Docker Engine 要 root。启动器在这两个平台上走的是系统自己的授权界面
> （Windows 的 UAC、Linux 的 polkit），**不自绘密码框、不保存密码**；
> 系统上没有这条路（例如没装 polkit）时它会**如实说装不了**，并给出诊断包那条路。

关于端口：3100 / 8100 / 3921 / 5442 / 6479 里哪个被占了就往后找一个空的，
写进 `.env` 和覆盖文件，界面上会列出「3100 → 3101」这种，**并写明原来是被谁占着的**。
**六个服务的端口一律只绑 `127.0.0.1`**：只有这台电脑的浏览器能打开 Hunter，
同一网络里的其他设备（手机、平板、同事的电脑）打不开，也烧不到你的额度。
局域网访问（让同一网络的其他设备也能打开）是**付费版功能**，免费版里没有这个开关。

> 从旧版本升上来的机器例外：0.1.7 之前装的那一套，网页端口是对局域网开着的。
> 升级**不会**悄悄改动你已有的配置 —— 运行面板顶上会出现一条提示，
> 点「只允许本机访问」就能收紧。**收紧之后不能再放开。**

关于下载：6 个镜像合计约 810 MiB（压缩后，amd64，manifest 实测）。
源有两个 —— **GHCR**（海外）与**腾讯云 · 香港**（国内），启动器会各探一次真实响应时间选快的，
拉不动会自动换源重试。同一个 tag 重装时已有的层不会重复下载，
这时它会如实写「六个镜像本机已有，这次一个字节都没下载」，不拿镜像大小冒充下载量。

**实在修不好**的时候进最终错误页：一句话说清卡在哪、手工处理的步骤，
以及一个「**发送诊断给开发者**」按钮（0.1.7 新增）：

1. 在**你自己的机器上**生成一份脱敏诊断包（key、邮箱、IP、用户名、主机名全部抹掉）；
2. 把**将要贴出去的 issue 标题与正文原样摆给你看**；
3. 你点「打开 GitHub 提 issue」才开浏览器，内容已经预填好，改不改、发不发由你决定。

诊断包本身**不会自动上传**，它的本地路径会一并给出（想附上就自己拖进 issue）。
万一出口闸在要发出去的文字里扫到了什么，那个按钮**不会出现** —— 宁可这条路走不通，
也不把可能带隐私的东西预填进一个公开页面。

### 5. 完成

浏览器自动打开 Hunter。容器在后台跑着，关掉启动器不会停它们。

## 五、升级 Hunter

启动器每 6 小时对比一次 hunter-community 的最新 Release tag（手动点「检查更新」会绕过这个缓存）。

有新版本时：运行面板右上角出现金色角标 → 点开是更新页，上面有

* 当前版本 → 最新版本
* **Release Notes 摘要**（上游 Release 正文的前 500 字），下面有「看完整说明」跳 GitHub
* 跨大版本时（0.x → 1.x）会多一条提醒，让你先读完再升

点「升级」会再确认一次，确认框里写清楚了两件事：

### 升级前会自动备份

备份放在 `~/.hunter/backups/<时间戳>-v<旧版本>/`：

```
hunter.sql                     整库 pg_dump（--clean --if-exists --no-owner）
.env                           升级前的配置（里面有 key，所以目录是 700、文件 600）
docker-compose.yml             旧版本的 compose
docker-compose.launcher.yml    启动器生成的端口覆盖文件
meta.json                      元信息
README.txt                     这几个文件是什么、怎么手工恢复
```

**数据库没备份成功就不会往下走。** 升级最坏的结果是数据出问题，没有转储等于没有后悔药。

### 失败会自动回滚

顺序是：取新版 compose → 备份 → 写新配置 → 拉新镜像 → `up -d` → 等 180 秒健康。

* 前两步失败：什么都还没改，直接报错（**不会**谎称"已回滚"，没动过的东西没什么可回滚的）。
* 后面任何一步失败：把 `.env` 与两个 compose 文件从备份里原样写回去，用旧镜像重新 `up -d`，
  等它们健康，然后报 `E_UPDATE_FAILED` 并告诉你备份在哪。

**回滚只还原配置，不自动灌回数据。** 因为升级失败绝大多数发生在"镜像拉不下来"或
"容器起不来"，这两种情况下数据库压根没被动过；这时候灌回一份转储反而会抹掉升级中途写进去的东西。
真出现"数据被新版本迁坏了"的情况，到**更新页 → 备份**那一栏点「从这份恢复数据库」——
那是个破坏性操作，会二次确认。

手工恢复也行：

```bash
cd ~/.hunter/app
docker compose -p hunter exec -T postgres psql -U hunter -d hunter \
  < ~/.hunter/backups/<那一份>/hunter.sql
```

升级成功后备份**不会**被自动删除。确认没问题了自己删，或者在更新页看它占了多少空间。

## 六、启动器自己的更新

启动器启动 20 秒后查一次、之后每 24 小时查一次（设置里可以关）。
查到新版本：托盘 tooltip 会多一行，运行面板顶上出现一条横幅。**它不会自动装。**

点「立即更新」之后分两种情况：

| 你怎么装的 | 会发生什么 |
|---|---|
| **AppImage / Windows / macOS** | 下载 → 验签 → 就地替换 → 启动器自己重启。全自动 |
| **`.deb`**（以及别的包管理器） | 把新包下到 `~/.hunter/updates/`，然后给你**一条可以直接粘贴的命令** |

第二种不是偷懒：`.deb` 装在 `/usr` 下，换它要 root 权限，一个桌面程序不该背着你拿 root
改系统目录。启动器把能做的都做了（查、下、告诉你装哪个文件），最后那一下 `sudo` 由你给：

```bash
sudo apt install -y --allow-downgrades ~/.hunter/updates/hunter-launcher_<版本>_amd64.deb
```

> `--allow-downgrades` 不是笔误：**dpkg 对预发布版的排序和 semver 相反**。
> 在 Debian 的版本语法里 `-rc.2` 是「修订号」，所以 `0.1.0-rc.2` 在 dpkg 眼里比 `0.1.0` **新**，
> 从 rc 升到正式版会被判成降级而拒绝。加上这个开关就通了，正常升级不受影响。

装完重新打开就是新版本。**容器全程不受影响**，一直在后台跑着。

> 更新清单 `latest.json` 是 minisign 签名的，公钥编译在程序里，验不过的包不会被安装。
> 这和"安装包没有代码签名"是两件事：前者我们自己生成密钥，不花钱；后者要向 CA / Apple 买证书。

## 七、离线安装（内网）

机器连不上 ghcr.io 也连不上腾讯云时，走离线包。

### 第一步：在一台有网的机器上打包

那台机器要先把镜像拉下来（装过一次 Hunter，或者 `hunter-launcher --headless --pull-only`），然后：

```bash
hunter-launcher --export-images hunter-images-1.2.0.tar
# 也可以指定版本：--export-images out.tar --tag 1.1.0
```

产物是一个 `docker save` 出来的 tar。**1.1.0 实测 798 MB** —— 和 registry 上的压缩大小同量级，
因为新版 docker 的 `save` 存的就是压缩后的层 blob，不是解压后的文件树。

### 第二步：拷到目标机器上导入

**界面**：设置页的「从文件导入」，或者安装失败后错误页上的同名按钮
→ 选那个 tar → 等 `docker load` 跑完。

**命令行**：

```bash
hunter-launcher --import-images /path/to/hunter-images-1.2.0.tar
```

导入之后启动器会做三件事：

1. 从镜像名反推出这一包是哪个源、哪个版本，把 `HUNTER_REGISTRY` / `HUNTER_VERSION` 对齐过去；
2. 用 `docker image inspect` **逐个复核**六个镜像真的在本机（`docker load` 说成功不等于齐了）；
3. 六个都齐了才会跳过拉取那一步。缺哪个会明说缺哪个，缺的那几个仍然要联网拉。

> **跳过拉取是一次性的**：紧接着的那一次安装跳过，之后就恢复正常（照常测速、照常拉）。
> 要在同一台离线机器上重装，再 `--import-images` 一次就行（tar 就在手边，
> `docker load` 一个已经加载过的包只要十几秒）。这样设计是为了避免「装过一次离线包之后，
> 以后每次升级都悄悄跳过拉取」——升级的本意就是去取新版本。

之后照常走向导（或 `hunter-launcher --headless --key-file <路径>`），拉取那一步会整个跳过。

> key 校验仍然要连 `hunter.agentpit.io` —— 那是一次很小的 HTTPS 请求，
> 和拉 800 MB 镜像不是一回事。完全断网的环境目前用不了（key 没法校验，模型也调不通）。

## 八、设置

标题栏右边的齿轮，或托盘 →「设置」。

| 项 | 说明 |
|---|---|
| 界面语言 | 中文 / English |
| 开机自启 | 默认关。开了是**真的**去写系统的自启项（Linux 的 `.desktop`、mac 的 LaunchAgent、Windows 注册表），界面上显示的是系统里的真实状态，不是你点的那一下 |
| 自动检查更新 | 关掉之后后台不再查版本 |
| 镜像源 | 可以「自动（测速选快的）」、固定某一个、或填自建仓库的前缀。旁边有「重新测速」，显示的是**真实**响应时间，探不到的标「不可用」 |
| 模型模式 | 网关 ↔ 自带 key 随时切。切换会重写 `.env` 并**重建** api / opencode / llm-shim 三个容器（要几十秒）—— 只 `restart` 的话容器里的环境变量还是旧的 |
| AI 诊断助手 | **默认开**（0.1.4 起）。关掉之后只用内置的确定性规则，一个 token 也不花。开着时也只有在规则认不出来、或者你主动点了「让 AI 帮我看看」之后才会真的发请求。同一张卡上还写着**启动器现在实际用的是哪一个 docker** |
| 容器运行时（0.1.7 新增） | 「这台电脑上没有 Docker」时走哪条路：**内置运行时**（默认，零点击，装在 `~/.hunter/runtime`）或 **OrbStack 官方安装包**（首次启动会弹系统提示）。下面显示内置运行时装了没有、装了哪几个版本、从哪个源下的、sha256 前 12 位，以及一个**卸载内置运行时**的按钮 |
| 匿名遥测 | 默认关，**而且当前没有上报服务端**。打开也只是把事件写进本机 `~/.hunter/telemetry/queue.jsonl`，可以在设置里看原文、随时清空。关掉的那一刻队列会被删掉 |
| 出站地址 | 列的是启动器**真的会连**的几个域名 |

底下还有「检查更新」和「从文件导入」两个按钮。

### 装不上的时候：诊断助手（0.1.4 起）

Docker 检测页和任何一个错误页上都有一块诊断面板。它分两层，**顺序不能反**：

1. **确定性规则**（一直在跑，零延迟、零 token、不联网）——
   多路径探测、「装了但没起来」、端口占用、磁盘不足、拉取失败。
   规则认出来的情况到此为止，一个字都不会发出去；有对应动作的直接给一个按钮
   （例如「启动 OrbStack」「重新分配被占用的端口」）。
2. **AI 兜底** —— 规则认不出来、或者你点了「让 AI 帮我看看」／「按上面做了还是不行」，
   才会把一份结构化诊断送到 Hunter 网关问一轮。

关于第二层，有几条是写死的：

* 发出去的内容可以点「展开完整诊断」逐字看，也可以「复制诊断信息」拿走。
  里面**没有** key、没有 `Bearer` 头，路径里的用户名一律换成 `<用户目录>`；
  发之前还有一道闸，整份再扫一遍 key 的形状，命中就干脆不发。
* 模型**不能**让启动器跑任意命令。它只能从一张写死的动作表里挑，表外的一律拒绝并记日志
  （界面上也会显示「模型提了什么、为什么没执行」）。
* 只读动作（探路径、读日志尾、查端口、`docker version`、`compose config`）自动执行；
  会改动你机器的动作（启动运行时、`brew install`、写配置、重启栈、改端口）
  **必须先把完整命令原样给你看**，你点「确认执行」才跑。
* 来回最多 3 轮。三轮之后明说搞不定，给手工步骤和「复制诊断信息」。
* 界面上带「AI 建议」角标的就是模型说的，带「规则」角标的是启动器自己判的；
  底下写着这次诊断大约花了多少 token。

### docker 装在奇怪的位置

0.1.4 起启动器按「`[runtime] docker_path` → PATH → 平台已知位置」的顺序找 docker，
不再只看 PATH（macOS 的 GUI 程序拿不到你终端里的 PATH，详见《常见问题》里
`E_DOCKER_MISSING` 那一节）。清单之外的位置，在 `~/.hunter/launcher.toml` 里指一次：

```toml
[runtime]
# 指了就只认它：那个位置没有可执行文件会如实报错，不会悄悄回退到别处的 docker
docker_path = "/opt/mydocker/bin/docker"
# 或者只追加几个搜索目录（支持 ~/ 开头），内置清单仍然生效
search_paths = ["/opt/mydocker/bin"]
```

## 九、命令行模式（没有桌面的服务器）

```bash
hunter-launcher --auto --key-file ~/k            # AI 自动驾驶安装（出问题自己修，过程实时打印）
hunter-launcher --auto --assist-mode auto        # 显式指定授权档位：auto | confirm | off

hunter-launcher --headless                       # 首次安装（交互式问 key，不回显）
hunter-launcher --headless --key-file ~/k --yes  # 从文件读 key，一路不问
hunter-launcher --headless --registry tencent    # 固定国内源
hunter-launcher --headless --tag 1.1.0           # 指定 Hunter 版本
hunter-launcher --pull-only                      # 只预下载镜像，不起容器

hunter-launcher --status                         # 现在什么情况
hunter-launcher --start / --stop / --restart / --down
hunter-launcher --logs [服务名]                   # 容器日志（已脱敏）
hunter-launcher --diagnose                       # 打印脱敏诊断 + 确定性规则的结论（零 token）
hunter-launcher --diagnose --ai --key-file ~/k   # 再问一轮 AI（显式开关，会花你的额度）
hunter-launcher --check-net                      # 虚拟机有没有 DNS + 容器连不连得上模型网关（0.1.10）

hunter-launcher --check-update                   # Hunter 与启动器各查一次
hunter-launcher --self-update                    # 更新启动器自己（见下）
hunter-launcher --upgrade 1.2.0                  # 升级（自动备份，失败自动回滚）
hunter-launcher --backups                        # 列备份
hunter-launcher --import-images <tar>            # 导入离线包
hunter-launcher --export-images <tar>            # 打离线包

# 0.1.7 新增
hunter-launcher --takeover list                  # 这台机器上还有哪几套 Hunter 可以接管
hunter-launcher --takeover use hunter-community -y   # 改为管理它，不再装一套
hunter-launcher --takeover status                # 被接管那一套现在什么情况
hunter-launcher --takeover logs [服务名]          # 它的日志（只读，已脱敏）
hunter-launcher --takeover stop -y               # 动它（**每一次**都要 -y 再确认一遍）
hunter-launcher --takeover release               # 不再管理它（它原地不动）
hunter-launcher --feedback --code E_PULL_FAILED  # 生成脱敏诊断包 + 打印预填 issue 链接（不发送）
hunter-launcher --review install_runtime --review-why "…" --key-file ~/k
                                                 # 让复核员真审一遍某个计划（会花额度）
```

**和界面版跑的是同一套代码**，不是另写一遍。两边只在"进度怎么显示"上不同。

`--auto` 走的是界面上「授权 AI 自动安装」那一条路：同一个总指挥、同一张动作表、同一套守卫，
事件流同时落到 `~/.hunter/logs/assist-events.jsonl`（一行一条 JSON），
AI 的每一个动作（包括被拒绝的）落到 `~/.hunter/logs/assist-audit.log`。
**「需要你」卡片在命令行下怎么办**（0.1.7 改过）：

- **stdin 是终端**（你人就坐在那儿敲命令）→ 它把问题和两个选项打出来，等你输 `y` 或 `n`。
  「逐步确认」档在命令行下从这一版起真的能用了。
- **stdin 不是终端**（CI、管道、`nohup`、cron）→ 没有人能答，一律按「不」处理，
  并在开头就说清楚这件事。阻塞等一个永远不会来的回答等于把进程挂死。

`--takeover stop / start / restart` 的二次确认在命令行下是 `-y`：不给就只打印那句确认话、
**不执行**。这不是「省一次点击」的问题 —— 动的是你自己装的那一套。

`--upgrade` 在终端里会先给你看 Release Notes 摘要再问一句 y/N；`--yes` 跳过这个确认。

`--self-update` 是**你显式敲出来的**，所以它可以真的动手：AppImage 会被**就地替换**
（先写临时文件再 rename，中途断电不会留下半个文件）；`.deb` 仍然只下载 + 给命令。
两条路都**先验签再落地** —— 用的是编译在程序里的那把 minisign 公钥，验不过就不装。
后台的自动检查永远只提示不装，那是两回事。

工作目录可以用 `HUNTER_HOME` 换（多套并存时有用，但注意 compose 项目名目前是固定的 `hunter`，
两个工作目录会抢同一套容器 —— 这是个已知问题）。

## 十、文件都放在哪

```
~/.hunter/                        权限 700
├── launcher.toml                 启动器自己的设置（语言、镜像源、遥测开关、Hunter tag、
│                                 docker 的定位策略 [runtime]、AI 诊断助手开关 [assist]）
├── app/
│   ├── .env                      Hunter 的配置。**key 只在这里**，权限 600
│   ├── docker-compose.yml        从上游按 tag 下载的原文（带 sha256 校验）
│   ├── docker-compose.launcher.yml   启动器生成的覆盖文件（端口、绑定地址、国内源镜像地址）
│   └── VERSION                   当前部署的 tag
├── backups/<时间戳>-v<版本>/       升级前的备份（见第五节）
├── logs/launcher.log             启动器自己的滚动日志（已脱敏）
├── telemetry/queue.jsonl         遥测队列。开关关着时这个文件是空的
├── diagnostics/                  你点「导出诊断包」生成的 zip
└── updates/                      自更新下载的安装包（.deb 那条路）
```

`.env` 和覆盖文件都可以手改，启动器每次启动前会校验必填项。
但注意：**升级、换源、切模型这些操作会重写 `.env`**（`JWT_SECRET`、数据库口令、
opencode 口令会被原样保留，不会换新）。

Docker 卷（你的数据）在 docker 自己的目录里，名字是 `hunter_*`。启动器**从不**执行 `down -v`。

## 十一、卸载

```bash
# 1. 停掉并删掉容器（数据卷保留）
hunter-launcher --down
#    或者：cd ~/.hunter/app && docker compose -p hunter down

# 2. 卸载启动器
sudo apt remove hunter-launcher          # deb
rm hunter-launcher_*.AppImage            # AppImage

# 3. 要连数据一起删的话（不可恢复，想清楚）
docker volume ls | grep hunter           # 先看看有哪些
docker compose -p hunter down -v         # 删卷
rm -rf ~/.hunter                         # 删配置、备份、日志
```

只卸载启动器不做第 3 步的话，数据和配置都还在，重装之后接着用。

## 十二、隐私：它会连哪些地址、会不会传你的东西

启动器会连的地址（设置页里也列着）：

| 地址 | 干什么 | 什么时候 |
|---|---|---|
| `hunter.agentpit.io` | key 校验、额度查询；模型调用（容器连的，不是启动器） | 填 key、刷面板 |
| `ghcr.io` / `hkccr.ccs.tencentyun.com` | 拉镜像、读 manifest 算大小 | 测速、拉取 |
| `registry-1.docker.io` | postgres / redis 的 manifest | 同上 |
| `api.github.com` | 查 Hunter 与启动器的最新版本 | 每 6 / 24 小时一次 |
| `raw.githubusercontent.com` | 按 tag 下载 `docker-compose.yml` | 安装、升级 |
| `*.cos.ap-hongkong.myqcloud.com` | 国内下载源（自更新清单、compose 备用路径） | 同上 |

**不会**发生的事：

* 你的 key 不会离开这台机器（除了发给网关做校验，那正是它的用途）；
* 遥测默认关闭，而且**当前根本没有上报服务端** —— 打开它也只是往本机文件里写；
* 「反馈」不会自动上传任何东西：它生成一个**脱敏后**的诊断包让你自己看、自己决定发不发，
  以及一个预填好的 GitHub issue 链接。诊断包里没有 key（脱敏是逐行做的，导出前可以逐节预览、逐节删）。
