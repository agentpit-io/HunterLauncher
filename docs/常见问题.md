# 常见问题 · 错误码逐条

> 技术方案第 18 节列了 10 个错误码，启动器另外补了 4 个（方案没覆盖到的情况）。
> 这里每一条都写：**什么时候会出现 → 真实原因是什么 → 你该怎么办**。
>
> 每个错误页上都有「一键反馈」，会把错误码和一份**脱敏后**的诊断信息预填进 GitHub issue。
> 诊断里没有 key。

先看两条通用的：

* **日志在哪**：`~/.hunter/logs/launcher.log`（启动器自己的）；容器的用
  `hunter-launcher --logs` 或界面上的「日志」。两边都已经脱敏。
* **想绕开启动器手动查**：`cd ~/.hunter/app && docker compose -p hunter ps`，
  启动器执行的就是这些命令，没有隐藏动作。

## `E_DOCKER_MISSING`

**什么时候**：启动器跑 `docker version` 时，系统里根本没有 `docker` 这个命令。

**怎么办（0.1.7 起 macOS 上可以完全不用你管）**：

> **macOS**：授权页上那一项默认勾着的勾（「如果电脑上没有 Docker，允许 AI 为你安装」）
> 打开时，启动器会自己装一套**完全用户态**的容器运行时到 `~/.hunter/runtime`
> （Colima + Lima + docker 客户端 + compose，版本与 sha256 写死在程序里、下完逐个核对）。
> **不需要管理员密码、不改系统任何地方**，设置页 →「容器运行时」里点一下就能卸干净。
> 本机已经有 OrbStack / Docker Desktop 的话它一个字节都不下。
>
> **Windows / Linux 上做不到** —— 装 WSL / Docker Desktop / Docker Engine 都要管理员权限，
> 启动器**不替你提权**。它会把要敲的那条命令原样写给你（见下），
> 你执行完点一下「我执行完了，继续」就接着往下装。
> 命令行下 stdin 是终端时它会真的问你一句 `y/n`。

下面是自己装的办法：

* **Windows**：装 [Docker Desktop](https://www.docker.com/products/docker-desktop/)。
  需要 WSL2，装的过程里它会引导你开（见 `E_WSL_MISSING`）。
* **macOS**：[Docker Desktop](https://www.docker.com/products/docker-desktop/)，
  或者更轻的 [OrbStack](https://orbstack.dev/)（启动器认得它）。
* **Linux**：
  ```bash
  curl -fsSL https://get.docker.com | sudo sh
  sudo usermod -aG docker "$USER"   # 加完要重新登录才生效
  ```

> Docker Desktop 在**员工超过 250 人或年营收超过 1000 万美元**的公司里商用需要付费订阅。
> 个人、小团队、教育、开源用途免费。Linux 上的 Docker Engine 一直免费。

装完回到启动器点「重新检测」。

**装了却还是报这个（macOS 上尤其常见）**

0.1.4 之前这是一个真问题，用户在自己的 Mac 上第一次跑就撞上了：OrbStack 好好装着、
终端里 `docker version` 能返回 Server 29.4.0，启动器却说「没有找到 Docker」。

原因和「装没装」无关，是 **macOS GUI 程序的固有行为**：

* 从访达或程序坞启动的程序，拿到的 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`
  （`launchctl getenv PATH` 是空的 → 走系统默认），**不含 `/usr/local/bin`**；
* 而 `docker` 通常就在 `/usr/local/bin/docker`（一个指向
  `/Applications/OrbStack.app/Contents/MacOS/xbin/docker` 的软链）；
* 终端里能跑，是因为 shell 读过 `/etc/paths` 与 `~/.zshrc`——GUI 程序读不到那些。

**0.1.4 起启动器不再只看 PATH**，而是按下面这个顺序挨个探，找到第一个能执行的就用：

| 顺序 | 位置 |
|---|---|
| 1 | `~/.hunter/launcher.toml` 里 `[runtime] docker_path` 指定的那一个（指了就只认它） |
| 2 | PATH 上的每一个目录 |
| 3 | macOS：`/usr/local/bin`、`/opt/homebrew/bin`、`~/.orbstack/bin`、`~/.docker/bin`、`/Applications/Docker.app/Contents/Resources/bin`、`/Applications/OrbStack.app/Contents/MacOS/xbin`、`~/Applications/...`、`~/.colima/bin`、`~/.rd/bin`、`~/.local/bin`、`/usr/bin`、`/bin`、`/usr/sbin`、`/sbin` |
| 3 | Linux：`/usr/bin`、`/usr/local/bin`、`/bin`、`/snap/bin`、`~/.docker/bin`、`~/.local/bin`、`/opt/docker/bin`、`/usr/sbin`、`/sbin` |
| 3 | Windows：`C:\Program Files\Docker\Docker\resources\bin`、`%LOCALAPPDATA%\Programs\Docker\...`、`C:\ProgramData\DockerDesktop\version-bin`、`%USERPROFILE%\.docker\bin`、`C:\Program Files\RedHat\Podman`、`C:\Windows\System32` |

Docker 检测页上会直接写出**实际用的是哪一条路径、是从哪找到的**；
一个都没找到时，把探过的每一个位置和结果（不存在 / 没有可执行位）整份列出来。

**装在上面都没有的地方**：在 `~/.hunter/launcher.toml` 里指一次就行 ——

```toml
[runtime]
docker_path = "/opt/mydocker/bin/docker"
# 也可以只追加几个搜索目录（支持 ~/ 开头），内置清单仍然生效
search_paths = ["/opt/mydocker/bin"]
```

指定了 `docker_path` 之后启动器**只认它**：那个位置没有可执行文件就如实报错，
不会悄悄回退到别处的 docker（否则「我明明指了这一个」会变成一桩无头案）。

## `E_CRED_HELPER`（Docker 找不到它自己的凭据助手）

**什么时候**：`docker compose pull` 报

```
error getting credentials - err: exec: "docker-credential-osxkeychain":
  executable file not found in $PATH, out: ``
```

**为什么**：你的 `~/.docker/config.json` 里有一行 `"credsStore": "osxkeychain"`
（OrbStack / Docker Desktop 装的时候自己写的）。docker 每次访问镜像仓库 ——
**哪怕仓库是公开的** —— 都会先执行 `docker-credential-<名字>` 去问一句
「这个仓库有没有存过登录信息」。那个程序通常在 `/usr/local/bin`，
而从访达 / 程序坞双击起来的程序，PATH 里没有 `/usr/local/bin`（上一条讲的就是这件事）。

**和上一条的区别**：上一条是「启动器找不到 docker」，这一条是「**docker 自己**
找不到它要用的那个程序」。两层都要补，只补一层修不好。

**0.1.6 起启动器怎么处理**（都是自动的，不需要你动手）：

1. 给所有 docker 子进程补 PATH：原 PATH + docker 所在目录 + 它软链指向的目录 +
   上面那张已知位置表。日志里会记一行「子进程 PATH 补了 N 个目录：…」。
   绝大多数机器到这一步就好了。
2. 补完还是找不到，就在 `~/.hunter/docker-config/` 里另起一份**不带 `credsStore`**
   的 docker 配置给启动器自己用（Hunter 的六个镜像都是公开的，本来就不需要登录）。
   **你的 `~/.docker/config.json` 一个字节都不会被改** —— 启动器的路径守卫
   根本不允许它写 `~/.hunter` 以外的文件。

想改回用你自己的 docker 配置：

```toml
[runtime]
isolated_docker_config = false   # ~/.hunter/launcher.toml
```

**启动器不会为这件事去换镜像源** —— 这是本机配置的问题，ghcr 和腾讯云都通也没用。

## `E_DAEMON_DOWN`

**什么时候**：`docker` 命令在，但连不上 daemon —— `docker version` 能报 Client 版本，
报不出 Server 版本。

**怎么办**：

* **Linux**：启动器会先替你试一次 `systemctl start docker`。还不行：
  ```bash
  sudo systemctl status docker      # 看它为什么没起来
  sudo systemctl enable --now docker
  ```
  另一种常见情况是**你不在 `docker` 组里**，报的会是 `permission denied while trying to
  connect to the Docker daemon socket`。跑 `sudo usermod -aG docker "$USER"`，**然后重新登录**
  （`newgrp docker` 只对当前这个 shell 有效，图形界面里的启动器读不到）。
* **macOS / Windows**：启动器没法替你点 Docker Desktop 的图标（那是个 GUI 程序，
  一个后台进程去启动它不合适，也常常失败）。自己打开 Docker Desktop / OrbStack，
  等鲸鱼图标不再转圈，回来点「重新检测」。

## `E_WSL_MISSING`

**什么时候**：Windows 上 Docker Desktop 要 WSL2 做后端，而系统里没装。

**怎么办**：管理员身份打开 PowerShell：

```powershell
wsl --install
```

**装完必须重启电脑**，这不是可选的。重启后再开 Docker Desktop。

企业设备上 `wsl --install` 可能被组策略挡住，那要找 IT。
Windows 家庭版从 21H2 起也支持 WSL2，不用专业版。

## `E_KEY_INVALID`

**什么时候**：网关拒绝了这把 key。

**你会看到的文案只有一句「网关不认这把 key」——这是故意的。**
网关对「格式错」「不存在」「已吊销」「压根没带 key」返回的是**字节级完全相同**的 401
（`{"code": "hunter_key_required"}`），实测过。分不出来就不装作分得出来：
写一个"可能已被吊销"只会让你往错的方向查。

**怎么办**，按可能性从高到低：

1. **粘贴时少了字符或多了空格**。key 以 `hunt_tools_` 开头，很长。
   重新复制一次（启动器会自己 trim 首尾空白，但中间的换行不会）。
2. **这把 key 不是给这个网关的**。`hunt_tools_` 是 Hunter 的 key，
   不是 OpenAI / DeepSeek 的 key。要用自己的模型 key 请在「选择模型」页选「自带 key」。
3. **确实过期或被吊销了**。到申请页重新签一把。
4. **网络到不了网关**。这种情况会报 `E_PROXY_BLOCK` 而不是这个码；
   如果两个码轮流出现，先解决网络。

## `E_QUOTA_EXHAUSTED`

**什么时候**：网关回 402，今日免费额度用完了。

**怎么办**：

* 等第二天 00:00 重置（面板上的「今日模型额度」卡会显示重置时间）；
* 或者到「设置 → 模型」切成**自带 key**，用自己的 OpenAI 兼容服务，不占额度。

> **坦白一点**：402 的响应体我们**没有实测过**——要触发它得真烧掉 30 万 token。
> 处理逻辑是照着网关的代码写的，但真出现的时候文案可能不够准。
> 撞上了麻烦开个 issue 把原文贴出来，我们照着改。

## `E_PULL_FAILED`

**什么时候**：`docker compose pull` 失败，且**自动换源重试 3 次之后仍然失败**。

启动器已经替你做过的：两个源（GHCR / 腾讯云香港）各探过、拉失败自动换另一个、
一共试了 3 次。所以走到这一步说明两个源都用不了。

**怎么办**：

1. **看错误页上「详情」那一行的原文**，它是 docker 的真实输出。常见的几种：
   * `TLS handshake timeout` / `i/o timeout` → 网络到不了 registry。国内直连 ghcr.io
     基本不可用（实测 17 KB/s），到**设置 → 镜像源**手动固定成「腾讯云 · 香港」。
   * `denied` / `unauthorized` → 那个 tag 在那个源上不存在。国内源的同步有滞后，
     换回 GHCR 试试；或者在设置里把 Hunter 版本固定到一个确定存在的 tag。
   * `no space left on device` → 磁盘满了。六个镜像解压后要 2 GB 出头，
     加上容器和数据卷，留 10 GB 比较稳。`docker system df` 看看占用，
     `docker system prune` 清一清（**别加 `-a --volumes`**，那会删你的数据）。
2. **自建镜像仓库**：设置 → 镜像源 → 「自定义前缀」，填 `registry.example.com/agentpit`
   这种。填了就不再测速，直接用。
3. **完全没有外网**：走[离线包](使用说明.md#七离线安装内网)。
   错误页上就有「从文件导入」按钮。

## `E_PORT_IN_USE`

**什么时候**：其实**你基本看不到这个码** —— 端口冲突是自动处理的。

启动器在写配置之前会挨个探 3100 / 8100 / 3921 / 5442 / 6479，
被占了就往后找一个空的，写进 `.env` 与覆盖文件，界面上列出来「3100 → 3101」。
只有**连着找不到可用端口**（极少见）才会报这个码。

**注意**：它会认出"占着那个端口的是我们自己上一次装的容器"，那种不算冲突。

**想固定端口**：手改 `~/.hunter/app/.env` 里的 `WEB_HOST_PORT` 等，
然后 `hunter-launcher --restart`。但要知道**升级、换源、切模型会重写 `.env`**（端口会保留，
因为启动器是按当前配置重写的；但如果你改的是别的字段就会被覆盖）。

## `E_START_TIMEOUT`

**什么时候**：`up -d` 成功了，但 180 秒内 6 个服务没有全部报健康。错误里会指出是**哪几个**没就绪。

**怎么办**：

1. **先看是哪个服务**，再看它的日志：
   ```bash
   hunter-launcher --logs api        # 或 web / opencode / llm-shim / postgres / redis
   ```
2. **最常见的几种**：
   * **postgres 没起来** → 十有八九是数据卷里的密码和 `.env` 里的 `POSTGRES_PASSWORD` 对不上。
     启动器**不会**换这个密码（它是 sticky 的），但如果你手工删过 `.env` 又重装过就会。
     日志里会写 `password authentication failed`。
   * **api 一直 starting** → 它在等 postgres 跑迁移。大版本升级时迁移可能要一两分钟，
     再等一轮（`hunter-launcher --restart` 然后看日志）。
   * **机器太慢 / 内存不够**。6 个容器加起来要 3–4 GB 内存。`free -g` 看看。
     2 核 8G 的机器上首次启动实测 40 秒左右，比这慢很多说明资源不够。
   * **opencode 起不来** → 检查 `.env` 里的 `OPENCODE_PASS` 不是空的。
3. 还是不行就点「一键反馈」，它会把六个服务的状态和最近的日志（脱敏后）一起带上。

## `E_PROXY_BLOCK`

**什么时候**：判断出网络请求是被代理 / 防火墙挡住的。

**怎么办**：

* **启动器自己走代理**：它用系统代理设置。Linux 上是 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量 ——
  注意从桌面图标启动的程序读不到你在 `.bashrc` 里设的那些。
* **容器走代理**：这是另一件事。容器里的进程要连 `hunter.agentpit.io`，
  它们不读宿主的环境变量。要给 Docker daemon 配代理：
  ```bash
  sudo mkdir -p /etc/systemd/system/docker.service.d
  sudo tee /etc/systemd/system/docker.service.d/proxy.conf <<'EOF'
  [Service]
  Environment="HTTP_PROXY=http://代理地址:端口"
  Environment="HTTPS_PROXY=http://代理地址:端口"
  Environment="NO_PROXY=localhost,127.0.0.1"
  EOF
  sudo systemctl daemon-reload && sudo systemctl restart docker
  ```
  `NO_PROXY` 里一定要有 `localhost,127.0.0.1`，否则容器之间互相调用也会走代理，
  表现是"服务都起来了但互相连不上"。
* **公司的 TLS 中间人**：自签 CA 会让 TLS 握手失败。要把公司的根证书装进系统信任库。

## `E_UPDATE_FAILED`

**什么时候**：升级 Hunter 的过程中出错了。

**启动器已经替你做过的事**（这些都写在错误信息里）：

* 升级前的**备份还在** `~/.hunter/backups/<时间戳>-v<旧版本>/`（数据库转储 + 配置）；
* 如果失败发生在"已经写了新配置"之后，**配置已经被写回旧版本那一整套**，并且用旧镜像
  重新 `up -d` 过了 —— 服务应该已经恢复。错误信息里会写清楚回滚做成了没有。

**怎么办**：

1. **先确认服务真的恢复了**：`hunter-launcher --status`，6 个应该都健康。
   没恢复就 `hunter-launcher --start` 再看一次日志。
2. **看失败在哪一步**（更新页的进度框里逐行都在）：
   * **"取不到 vX.Y.Z 的 docker-compose.yml"** → 那个版本可能不存在。
     这一步失败时**什么都还没改**。到
     [上游的 Releases](https://github.com/agentpit-io/hunter-community/releases) 确认版本号。
   * **"数据库没备份成功"** → 升级被中止了，同样什么都没改。
     多半是 postgres 没起来；先把它弄起来再升。
   * **拉镜像失败** → 那个 tag 的镜像没发布，或者网络问题。参考 `E_PULL_FAILED`。
     这是最常见的一种：**git tag 存在不等于镜像存在**。
   * **健康检查超时** → 新版本起不来。参考 `E_START_TIMEOUT` 看是哪个服务、看它的日志，
     很可能是新版本要改 `.env`（上游的升级须知里会写）。
3. **数据看起来不对**（升级跑过迁移之后才可能）：到**更新页 → 备份**，
   对着那次升级的备份点「从这份恢复数据库」。这是破坏性操作，会二次确认。
   手工做也一样：
   ```bash
   cd ~/.hunter/app
   docker compose -p hunter exec -T postgres psql -U hunter -d hunter \
     < ~/.hunter/backups/<那一份>/hunter.sql
   ```

> **为什么回滚不自动恢复数据库**：升级失败绝大多数发生在"镜像拉不到"或"容器起不来"，
> 这两种情况下数据库根本没被动过；这时候自动灌回一份转储，反而会抹掉升级中途写进去的东西。
> 所以配置自动回滚，数据等你确认之后再说。

## `E_COMPOSE_FETCH`

**什么时候**：取不到 `docker-compose.yml`。方案原本假设从 Release 资产下载，
实测上游的 Release **没有任何 assets**，所以改走 `raw.githubusercontent.com` 的固定 tag 路径，
国内备用走腾讯云香港。

**安装时**：两个地址都失败会退回**启动器内置的 1.2.0 副本**（带 sha256 校验），
界面上会明说"用的是内置副本"。所以安装时你基本不会看到这个码。

**升级时**：**不会**退回内置副本。你点的是某个具体版本，悄悄换成内置的 1.2.0 就是
拿另一件事冒充你要的事。所以升级时取不到就报这个码并中止，**什么都不改**。

**怎么办**：确认版本号真的存在（去上游的 Releases 页看）；
确认能访问 `raw.githubusercontent.com`（国内经常不行，这时走腾讯云那条备用路径，
它每 6 小时同步一次，新版本可能有几小时的滞后）。

---

## `E_CONFIG_WRITE`

**什么时候**：写 `~/.hunter/` 下的文件失败。

**怎么办**：

* **磁盘满了** → `df -h ~`。
* **权限不对** → `~/.hunter` 应该是 700、`app/.env` 应该是 600，属主是你。
  如果你曾经用 `sudo` 跑过启动器，里面会混进 root 拥有的文件：
  ```bash
  sudo chown -R "$USER:$USER" ~/.hunter
  chmod 700 ~/.hunter && chmod 600 ~/.hunter/app/.env
  ```
  **不要用 sudo 跑启动器** —— 它不需要 root，跑过一次反而会把工作目录弄乱。
* **`~` 在只读挂载 / 网络文件系统上** → 用 `HUNTER_HOME=/some/local/path` 换个地方。

这个码还会在一种**故意**的情况下出现：启动器写完覆盖文件后会用
`docker compose config --format json` 复核一遍"发布出来的端口是不是**都**绑在 127.0.0.1"，
没绑住就拒绝继续。那是安全底线，不是 bug。

（0.1.7 起 web 也算在这道自查里面。唯一的例外是从旧版本升上来、
升级前就对局域网开着的那种机器 —— 那是有意不动它，运行面板上给一键收紧。）

---

## `E_NOT_IMPLEMENTED`

**什么时候**：你摸到了一个还没做完的功能。当前版本里**不应该出现**。

**怎么办**：开 issue，写清楚点了什么。

## `E_UNKNOWN`

**什么时候**：没归类的意外。

**怎么办**：错误页上有原始信息。点「一键反馈」，它会带上脱敏后的诊断（Docker 版本、
服务状态、最近的日志、配置里的非敏感项）。这个码出现就是我们的漏，值得一个 issue。

## 不属于错误码的常见困惑

### 界面上一堆「—」

按设计。拿不到真实数据时启动器显示 `—` 并写明原因，不编一个数字糊弄你（这是硬规矩）。
运行面板上「今日对话」「晨报」两张卡**永远**是 `—`：hunter-community 的 api 没有
对应的免登录接口（逐条实测过），要么让上游加，要么就没有。点面板右下角那行小字能看到缺哪几条。

### 托盘图标不出现（Linux）

```bash
sudo apt install libayatana-appindicator3-1
```

有些精简桌面根本没有状态栏（纯 i3、某些 Wayland 合成器），那就是显示不出来。
**不影响使用**：托盘菜单里的每一项在界面上都另有入口。

### 日志里的中文是方块

系统没装中文字体。启动器自己的界面文字是打包进去的子集，不受影响；
容器日志里的中文靠系统字体回落：

```bash
sudo apt install fonts-noto-cjk
```

### 装启动器的新 deb 时报 `Packages were downgraded`

```
E: Packages were downgraded and -y was used without --allow-downgrades
```

**dpkg 对预发布版的排序和 semver 相反**。在 Debian 的版本语法里 `-rc.2` 是「修订号」，
所以 `0.1.0-rc.2` 在 dpkg 眼里比 `0.1.0` **新** —— 从 rc 升到正式版就被判成了降级。

```bash
# 加这个开关就行，它只在真需要时起作用
sudo apt install -y --allow-downgrades ~/.hunter/updates/hunter-launcher_0.1.0_amd64.deb
```

启动器 0.1.0 之后打印的命令里已经自动带上它了。

### macOS 上「已损坏，无法打开」

这是 quarantine 属性导致的，不是文件真的坏了。终端里跑一次（**路径里有空格，引号别漏**——
`.app` 的名字来自 `productName`，是 `Hunter Launcher.app` 而不是 `hunter-launcher.app`）：

```bash
xattr -dr com.apple.quarantine "/Applications/Hunter Launcher.app"
```

### 窗口是直角的，和截图里的圆角不一样

已知差异。要做圆角得开窗口透明并依赖桌面合成器，Linux 上不是所有环境都支持，
做不好会出现黑色直角。目前选择了"到处都正常"而不是"有的地方好看有的地方难看"。

### Windows 上三个圆点在左上角，和别的 Windows 程序相反

已知差异。视觉稿是 mac 风格（三个点在左），当前三平台都照着稿实现。
Windows 用户的肌肉记忆是右上角，这条记在待办里。

### AppImage 有 75 MB，不是说好 40 MB 以内吗

AppImage 要把整套 WebKitGTK 塞进去（光 `usr/lib` 就 232 MB，压缩后 75 MB），
这是格式的固有代价，和代码量无关。**`.deb` 只有 3 MB 左右** —— 介意体积就用 deb。
设计目标里那个 "20–40 MB" 对 deb/exe/dmg 是成立的，对 AppImage 不成立，
这一点 README 里已经改掉了。

### `.deb` 装的启动器为什么不能自己更新自己

`.deb` 装在 `/usr/bin` 和 `/usr/lib` 下，换那里的文件要 root。一个桌面程序不该背着你拿 root
改系统目录。所以点「更新」时启动器把新包下到 `~/.hunter/updates/` 并给你一条
`sudo apt install` 命令，最后那一下由你给授权。AppImage / Windows / macOS 是全自动的。

没有桌面的服务器上用 `hunter-launcher --self-update`，行为一样（AppImage 就地换、
`.deb` 只下载），而且同样会验签。

### 两个工作目录会互相顶掉

**已知问题**：用 `HUNTER_HOME` 开了第二套工作目录时，两套会抢同一个 compose 项目名
（`hunter`），后 `up -d` 的那一套会把先装好的连配置带端口一起顶掉（**数据卷不会丢**，
重装一次就回来）。在修好之前，一台机器上只跑一套。

### AI 诊断助手到底会把什么发出去

0.1.4 加的「让 AI 帮我看看」分两层，**顺序不能反**：

1. **确定性规则**（默认一直在跑，零延迟、零 token、不联网）：多路径探测、
   「装了但没起来」、端口占用、磁盘不足、拉取失败。规则认出来的情况到此为止，
   一个字都不会发出去。
2. **AI 兜底**：只有规则认不出来、或者你主动点了「让 AI 帮我看看」／「按上面做了还是不行」，
   才会把一份**结构化诊断**发到 `hunter.agentpit.io` 的模型网关（用你自己那把 hunter key）。

发出去的内容你可以点「展开完整诊断」逐字看，也可以「复制诊断信息」拿走。里面有：
系统与架构、Docker 与 compose 版本、探过哪些路径及结果、`docker version` 的原始输出、
错误码、启动器日志最后 40 行、5 个端口的占用情况、磁盘余量。

**不会有的**：你的 hunter key、任何 `Bearer` 头、路径里的用户名
（`/Users/zhangsan/...` 一律换成 `<用户目录>/...`）。发之前还有一道闸，
整份报文再扫一遍 key 的形状，命中就干脆不发。

模型**不能**让启动器跑任意命令。它只能从一张写死的动作表里挑（探路径、读日志尾、查端口、
`docker version`、`compose config`、启动运行时、换镜像源、改端口、写 `docker_path`、
`brew install` 几个指定的 formula），表外的一律拒绝并在日志里记一条。
只读的会自动执行；会改动你机器的**必须先把完整命令原样给你看**，你点「确认执行」才跑。

来回最多 3 轮，之后明说搞不定并给手工步骤。不想用就到「设置 → AI 诊断助手」关掉，
关掉之后只剩第一层。

### 命令行下怎么用诊断助手

```bash
hunter-launcher --diagnose            # 只跑确定性规则，零 token，不联网
hunter-launcher --diagnose --ai --key-file ~/key   # 再问一轮 AI（会花你的额度）
```

`--ai` 是显式开关：`--diagnose` 常被写进脚本，不能在你没要求的时候悄悄花掉额度。
命令行下**不会替你执行会改动机器的动作**，只把将要执行的完整命令打出来。

### 我电脑上已经有一套 Hunter，启动器会不会把它弄坏（0.1.7）

不会。它连**改**都不会改。

发现本机已有别的 Hunter（别的 compose 项目）时，过程流里会出现一张卡片，两个按钮：

- **和它并存（推荐，不动它）** —— 默认。新装的这一套换一组空闲端口，两套互不影响。
  **不点这张卡片也是这个结果** —— 它不拦着安装，下面的步骤照样在跑。
- **直接用「xxx」，不再装一套** —— 启动器不装了，改成管理你原有的那一套。

选了后者之后：

| 它会做 | 它不会做 |
|---|---|
| 看容器状态、看日志、打开网页 | 改它的配置（一个字节都不改） |
| 停止 / 启动 / 重启（**每一次都先问你**） | 删它的数据卷（动作表里根本没有对它 `down` / `-v` 的路） |
| — | 读不到它的 compose 文件时硬猜（如实降级成只读监控） |

不想管了就点「不再管理它」—— 它还在原地跑着，一个字节都没动过。

命令行：`--takeover list | use <项目名> -y | status | logs | stop -y | start -y | restart -y | release`。
改动类的那几个**必须给 `-y`**，那是二次确认在命令行下的形态。

### 内置运行时到底装了什么、装在哪、怎么卸（0.1.7）

只有 macOS 上、而且这台机器上一个 Docker 都没有的时候才会装。装的是：

| 组件 | 版本 |
|---|---|
| Colima | v0.10.3 |
| Lima | v2.2.0 |
| docker 客户端（官方静态包） | 29.8.1 |
| docker compose | v5.5.1 |

全部落在 `~/.hunter/runtime/`：

```
~/.hunter/runtime/
  bin/            docker、colima
  dist/lima/      lima 整包
  docker-config/  我们自己的 DOCKER_CONFIG，compose 插件在它的 cli-plugins 下
  lima/           LIMA_HOME —— 虚拟机磁盘在这里面
  colima/         COLIMA_HOME —— profile 与 docker.sock
  installed.json  装了哪几个版本、从哪个源下的
```

**不写 `/usr/local`、不改任何 shell 配置文件、不碰你的 `~/.docker`、不要管理员密码。**
虚拟机的 profile 名是 `hunter`，不会碰你自己可能已经有的 `default`。

**卸载**：设置页 →「容器运行时」→「卸载内置运行时」。
它会 `colima delete --profile hunter`（删掉那台虚拟机与它的磁盘）再清空 `~/.hunter/runtime`。
**Hunter 自己的数据卷不受影响** —— 那是 docker 的卷，不在这个目录里。

**为什么不直接装 OrbStack**：OrbStack 装得更快，但**第一次打开它的时候
macOS 与它自己会弹欢迎页、可能还要你输一次管理员密码**。那是系统与 OrbStack 的交互，
启动器不会、也不应该替你点 —— 而这一整套的目标是「授权之后一下都不用点」。
想用 OrbStack 的话设置页里可以切过去（下 dmg → 验苹果签名与公证 → 装进「应用程序」），
界面上会写明首启要你点几下。OrbStack 个人使用免费，商用需另外授权。

### 「发送诊断给开发者」会把什么发出去（0.1.7）

**它自己什么都不发。** 点下去之后发生三件事：

1. 在**你自己的机器上**生成一份脱敏诊断包（`~/.hunter/diagnostics/` 下的 zip）；
2. 把**将要贴进 GitHub issue 的标题与正文原样摆给你看**；
3. 你点「打开 GitHub 提 issue」才开浏览器，内容已经预填好 —— 改不改、发不发由你。

诊断包**不会自动上传**（启动器根本没有上报地址），它的本地路径会一并给出，
想附上就自己把那个 zip 拖进 issue。

出门前那段文字还会再被扫一遍：key 形状、完整邮箱、完整 IP、**你的用户名**、**你的主机名**。
扫到任何一样，**那个「打开 GitHub」的按钮就不会出现** —— 宁可这条路走不通，
也不把可能带隐私的东西预填进一个公开页面。

### 手机 / 同一网络里的另一台电脑打不开 Hunter（0.1.7）

**这是有意的。** 0.1.7 起，Hunter 的六个服务端口**全部**绑在 `127.0.0.1` 上 ——
只有装它的那台电脑的浏览器能打开，同一网络里的其他设备一律打不开。

为什么：Hunter 的聊天界面**不需要任何口令**。上游的 api 保护住了 `/api/setup/*`
那些配置接口，但**没有保护使用界面** —— I1 的实测是从另一台机器打
`http://<这台机器的 IP>:3101`，直接进了聊天界面，问了一句股价，
工具真调、答案真出、网关的 `used_today` 跟着涨。

**局域网访问（让同一网络的其他设备也能打开）是付费版功能**，
免费版里没有这个开关：设置页「谁能打开 Hunter」那一栏是一行只读的说明，
`launcher.toml` 里手写 `web_bind = "all"` 或 `"0.0.0.0"` 也不会生效 ——
覆盖文件照样按 `127.0.0.1` 生成，并在 `~/.hunter/logs/` 里记一条说明它被忽略了。

**从 0.1.7 之前升上来的机器例外**：那一套装的时候网页端口是对局域网开着的，
升级**不会**悄悄把它关掉（不然「昨天手机上还能开」会突然失效，而且是在你不知道的情况下）。
运行面板顶上会出现一条提示，点「只允许本机访问」就收紧。
**收紧是单向的** —— 收完不能再放开。

想确认现在到底绑在哪，直接问 docker：

```bash
cd ~/.hunter/app && docker compose -p hunter ps --format json \
  | python3 -c 'import sys,json;[print(d["Service"], [p["URL"] for p in d.get("Publishers") or []]) for d in map(json.loads, filter(str.strip, sys.stdin))]'
```

### 我能不能直接用 docker compose，不用启动器

能，而且推荐懂命令行的人这么做。启动器生成的东西是标准的：

```bash
cd ~/.hunter/app
docker compose -p hunter -f docker-compose.yml -f docker-compose.launcher.yml ps
```

启动器执行的就是这条命令的各种变体，没有任何隐藏动作。

> ⚠️ **两个 `-f` 都要带上。** `docker-compose.launcher.yml` 这个名字**不在** compose
> 的自动发现列表里（它只认 `docker-compose.override.yml`），漏掉它不会报错，
> 只会**安静地**按上游的原始配置来 —— 于是 api / postgres / redis 会从
> `127.0.0.1` 变回 `0.0.0.0`，端口冲突改写过的值也会丢。
>
> 这不是猜的：I7 收尾测试时，我自己在测试机上敲少了一个 `-f`，
> `docker ps` 当场就从 `127.0.0.1:8101->8000/tcp` 变成了 `0.0.0.0:8101->8000/tcp`。
>
> 嫌长就把它存成一个别名：
>
> ```bash
> alias hc='docker compose -p hunter -f ~/.hunter/app/docker-compose.yml -f ~/.hunter/app/docker-compose.launcher.yml --project-directory ~/.hunter/app'
> ```

启动器里的「反馈」按钮会生成预填好的内容，附带一份脱敏诊断包（**不含 key**，
导出前可以逐节预览、逐节删掉不想带的部分）。
