# 常见问题 · 错误码逐条

> 技术方案第 18 节列了 10 个错误码，启动器另外补了 4 个（方案没覆盖到的情况）。
> 这里每一条都写：**什么时候会出现 → 真实原因是什么 → 你该怎么办**。
>
> 每个错误页上都有「一键反馈」，会把错误码和一份**脱敏后**的诊断信息预填进 GitHub issue。
> 诊断里没有 key。

先看两条通用的：

* **日志在哪**：`~/.hunter/logs/launcher.log`（启动器自己的）；容器的用
  `hunter-launcher --logs` 或界面上的「日志」。两边都已经脱敏。
* **想绕开启动器手动查**：`cd ~/.hunter/app && docker compose -p hunter ps`，
  启动器执行的就是这些命令，没有隐藏动作。

## `E_DOCKER_MISSING`

**什么时候**：启动器跑 `docker version` 时，系统里根本没有 `docker` 这个命令。

**怎么办（0.1.8 起 macOS 上三条路自动依次走完，完全不用你管）**：

> 授权页上那一项默认勾着的勾（「如果电脑上没有 Docker，允许启动器替你装一套」）打开时，
> 启动器会**按顺序自动试这三条路，前一条失败才走下一条，每一条都是它自己执行**：
>
> 1. **内置运行时**（约 436 MB）—— Colima + Lima + docker 客户端 + compose + 虚拟机系统镜像，
>    全部装进 `~/.hunter/runtime`，版本与校验和写死在程序里、下完逐个核对。
>    **不需要密码、不改系统任何地方**，设置页 →「容器运行时」里点一下就能卸干净。
> 2. **OrbStack 官方安装包**（约 200 MB）—— 下 dmg、验苹果的签名与公证、装进「应用程序」、
>    由启动器替你打开、等 docker 就绪（超时就继续下一条，不要求你去点它的窗口）。
> 3. **Homebrew** —— 这台电脑上没有 brew 就**先替你把 brew 装上**（跑它官方的安装脚本），
>    再 `brew install --cask orbstack`。这一步要往系统目录里写文件，
>    所以会弹一次**系统自己的密码框**；弹之前界面上会先说清楚为什么。
>
> 排序原则是「同样能解决问题时，优先不需要任何交互的那条」，所以要密码的排在最后。
> 本机已经有 OrbStack / Docker Desktop / Colima 的话它一条都不走，一个字节都不下。
>
> **Windows / Linux**：走的是系统自己的授权界面（Windows 的 UAC、Linux 的 polkit），
> 启动器**不自绘密码框、不保存密码、不把密码写进日志**。
> 系统上没有这条路（例如没装 polkit）时它会**如实说装不了**，不会把活儿丢回给你。

下面是**自己装**的办法（用不到，留着备查）：

* **Windows**：装 [Docker Desktop](https://www.docker.com/products/docker-desktop/)。
  需要 WSL2，装的过程里它会引导你开（见 `E_WSL_MISSING`）。
* **macOS**：[Docker Desktop](https://www.docker.com/products/docker-desktop/)，
  或者更轻的 [OrbStack](https://orbstack.dev/)（启动器认得它）。
* **Linux**：
  ```bash
  curl -fsSL https://get.docker.com | sudo sh
  sudo usermod -aG docker "$USER"   # 加完要重新登录才生效
  ```

> Docker Desktop 在**员工超过 250 人或年营收超过 1000 万美元**的公司里商用需要付费订阅。
> 个人、小团队、教育、开源用途免费。Linux 上的 Docker Engine 一直免费。

装完回到启动器点「重新检测」。

**装了却还是报这个（macOS 上尤其常见）**

0.1.4 之前这是一个真问题，用户在自己的 Mac 上第一次跑就撞上了：OrbStack 好好装着、
终端里 `docker version` 能返回 Server 29.4.0，启动器却说「没有找到 Docker」。

原因和「装没装」无关，是 **macOS GUI 程序的固有行为**：

* 从访达或程序坞启动的程序，拿到的 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`
  （`launchctl getenv PATH` 是空的 → 走系统默认），**不含 `/usr/local/bin`**；
* 而 `docker` 通常就在 `/usr/local/bin/docker`（一个指向
  `/Applications/OrbStack.app/Contents/MacOS/xbin/docker` 的软链）；
* 终端里能跑，是因为 shell 读过 `/etc/paths` 与 `~/.zshrc`——GUI 程序读不到那些。

**0.1.4 起启动器不再只看 PATH**，而是按下面这个顺序挨个探，找到第一个能执行的就用：

| 顺序 | 位置 |
|---|---|
| 1 | `~/.hunter/launcher.toml` 里 `[runtime] docker_path` 指定的那一个（指了就只认它） |
| 2 | PATH 上的每一个目录 |
| 3 | macOS：`/usr/local/bin`、`/opt/homebrew/bin`、`~/.orbstack/bin`、`~/.docker/bin`、`/Applications/Docker.app/Contents/Resources/bin`、`/Applications/OrbStack.app/Contents/MacOS/xbin`、`~/Applications/...`、`~/.colima/bin`、`~/.rd/bin`、`~/.local/bin`、`/usr/bin`、`/bin`、`/usr/sbin`、`/sbin` |
| 3 | Linux：`/usr/bin`、`/usr/local/bin`、`/bin`、`/snap/bin`、`~/.docker/bin`、`~/.local/bin`、`/opt/docker/bin`、`/usr/sbin`、`/sbin` |
| 3 | Windows：`C:\Program Files\Docker\Docker\resources\bin`、`%LOCALAPPDATA%\Programs\Docker\...`、`C:\ProgramData\DockerDesktop\version-bin`、`%USERPROFILE%\.docker\bin`、`C:\Program Files\RedHat\Podman`、`C:\Windows\System32` |

Docker 检测页上会直接写出**实际用的是哪一条路径、是从哪找到的**；
一个都没找到时，把探过的每一个位置和结果（不存在 / 没有可执行位）整份列出来。

**装在上面都没有的地方**：在 `~/.hunter/launcher.toml` 里指一次就行 ——

```toml
[runtime]
docker_path = "/opt/mydocker/bin/docker"
# 也可以只追加几个搜索目录（支持 ~/ 开头），内置清单仍然生效
search_paths = ["/opt/mydocker/bin"]
```

指定了 `docker_path` 之后启动器**只认它**：那个位置没有可执行文件就如实报错，
不会悄悄回退到别处的 docker（否则「我明明指了这一个」会变成一桩无头案）。

## `E_CRED_HELPER`（Docker 找不到它自己的凭据助手）

**什么时候**：`docker compose pull` 报

```
error getting credentials - err: exec: "docker-credential-osxkeychain":
  executable file not found in $PATH, out: ``
```

**为什么**：你的 `~/.docker/config.json` 里有一行 `"credsStore": "osxkeychain"`
（OrbStack / Docker Desktop 装的时候自己写的）。docker 每次访问镜像仓库 ——
**哪怕仓库是公开的** —— 都会先执行 `docker-credential-<名字>` 去问一句
「这个仓库有没有存过登录信息」。那个程序通常在 `/usr/local/bin`，
而从访达 / 程序坞双击起来的程序，PATH 里没有 `/usr/local/bin`（上一条讲的就是这件事）。

**和上一条的区别**：上一条是「启动器找不到 docker」，这一条是「**docker 自己**
找不到它要用的那个程序」。两层都要补，只补一层修不好。

**0.1.6 起启动器怎么处理**（都是自动的，不需要你动手）：

1. 给所有 docker 子进程补 PATH：原 PATH + docker 所在目录 + 它软链指向的目录 +
   上面那张已知位置表。日志里会记一行「子进程 PATH 补了 N 个目录：…」。
   绝大多数机器到这一步就好了。
2. 补完还是找不到，就在 `~/.hunter/docker-config/` 里另起一份**不带 `credsStore`**
   的 docker 配置给启动器自己用（Hunter 的六个镜像都是公开的，本来就不需要登录）。
   **你的 `~/.docker/config.json` 一个字节都不会被改** —— 启动器的路径守卫
   根本不允许它写 `~/.hunter` 以外的文件。

想改回用你自己的 docker 配置：

```toml
[runtime]
isolated_docker_config = false   # ~/.hunter/launcher.toml
```

**启动器不会为这件事去换镜像源** —— 这是本机配置的问题，ghcr 和腾讯云都通也没用。

## `E_DAEMON_DOWN`

**什么时候**：`docker` 命令在，但连不上 daemon —— `docker version` 能报 Client 版本，
报不出 Server 版本。

**怎么办**：

* **Linux**：启动器会先替你试一次 `systemctl start docker`。还不行：
  ```bash
  sudo systemctl status docker      # 看它为什么没起来
  sudo systemctl enable --now docker
  ```
  另一种常见情况是**你不在 `docker` 组里**，报的会是 `permission denied while trying to
  connect to the Docker daemon socket`。跑 `sudo usermod -aG docker "$USER"`，**然后重新登录**
  （`newgrp docker` 只对当前这个 shell 有效，图形界面里的启动器读不到）。
* **macOS**：启动器会替你 `open -a OrbStack` / `open -a Docker`，再等它就绪。
  等不到就如实写在错误页上（它自己的欢迎页可能还等着你点一下）。
* **Windows**：Docker Desktop 没有可靠的命令行启动方式，这一步启动器替不了你。

**如果报的是这一条、而你从来没装过 Docker**：多半是 `~/.hunter/runtime` 里
留着上一次没装成功的内置运行时 —— 0.1.9 起那种情况会正确地报
[`E_BUILTIN_DOWN`](#e_builtin_down) 而不是这一条。

## `E_BUILTIN_DOWN`

> 0.1.9 新增。在这之前这个情况会被误判成 [`E_DAEMON_DOWN`](#e_daemon_down)，
> 而两者的处理办法完全相反 —— 详见下面「之前装过没成功，再装会怎样」。

**什么时候**：`~/.hunter/runtime` 里有一套**启动器自己装的**容器运行时
（Colima + Lima + docker 客户端 + compose + 虚拟机镜像），但它的虚拟机没在跑。

**要点**：这不是你电脑上的 Docker，也不是你装的 Colima。
它是上一次安装下到 Hunter 自己文件夹里的一套，只服务 Hunter。

**怎么办**：不用你管。启动器会按顺序自己走：

1. 文件缺了几个（上一次没装完）→ 只补齐缺的那几个，已经下好并按 sha256 / sha512
   核过的文件一个字节都不重下；
2. 文件齐了 → 用本机那份已经核过的系统镜像启动 `hunter` 这台虚拟机；
3. 起不来 → 说明上次留下了残骸，**清掉那台虚拟机重建一次**再起。

清的范围只在 `~/.hunter/runtime` 里：`colima` 的 `hunter` profile、
它对应的 lima 实例目录、以及内容对不上清单的下载文件。
**你的 `~/.colima`、`~/.lima`、别的容器与数据卷一个字节都不会碰。**

三步都没成时，错误页上会写清每一步的原话，并给「发送诊断给开发者」那条路。

## `E_WSL_MISSING`

**什么时候**：Windows 上 Docker Desktop 要 WSL2 做后端，而系统里没装。

**怎么办**：管理员身份打开 PowerShell：

```powershell
wsl --install
```

**装完必须重启电脑**，这不是可选的。重启后再开 Docker Desktop。

企业设备上 `wsl --install` 可能被组策略挡住，那要找 IT。
Windows 家庭版从 21H2 起也支持 WSL2，不用专业版。

## `E_KEY_INVALID`

**什么时候**：网关拒绝了这把 key。

**你会看到的文案只有一句「网关不认这把 key」——这是故意的。**
网关对「格式错」「不存在」「已吊销」「压根没带 key」返回的是**字节级完全相同**的 401
（`{"code": "hunter_key_required"}`），实测过。分不出来就不装作分得出来：
写一个"可能已被吊销"只会让你往错的方向查。

**怎么办**，按可能性从高到低：

1. **粘贴时少了字符或多了空格**。key 以 `hunt_tools_` 开头，很长。
   重新复制一次（启动器会自己 trim 首尾空白，但中间的换行不会）。
2. **这把 key 不是给这个网关的**。`hunt_tools_` 是 Hunter 的 key，
   不是 OpenAI / DeepSeek 的 key。要用自己的模型 key 请在「选择模型」页选「自带 key」。
3. **确实过期或被吊销了**。到申请页重新签一把。
4. **网络到不了网关**。这种情况会报 `E_PROXY_BLOCK` 而不是这个码；
   如果两个码轮流出现，先解决网络。

## `E_QUOTA_EXHAUSTED`

**什么时候**：网关回 402，今日免费额度用完了。

**怎么办**：

* 等第二天 00:00 重置（面板上的「今日模型额度」卡会显示重置时间）；
* 或者到「设置 → 模型」切成**自带 key**，用自己的 OpenAI 兼容服务，不占额度。

> **坦白一点**：402 的响应体我们**没有实测过**——要触发它得真烧掉 30 万 token。
> 处理逻辑是照着网关的代码写的，但真出现的时候文案可能不够准。
> 撞上了麻烦开个 issue 把原文贴出来，我们照着改。

## `E_PULL_FAILED`

**什么时候**：`docker compose pull` 失败，且**自动换源重试 3 次之后仍然失败**。

启动器已经替你做过的：两个源（GHCR / 腾讯云香港）各探过、拉失败自动换另一个、
一共试了 3 次。所以走到这一步说明两个源都用不了。

**怎么办**：

1. **看错误页上「详情」那一行的原文**，它是 docker 的真实输出。常见的几种：
   * `TLS handshake timeout` / `i/o timeout` → 网络到不了 registry。国内直连 ghcr.io
     基本不可用（实测 17 KB/s），到**设置 → 镜像源**手动固定成「腾讯云 · 香港」。
   * `denied` / `unauthorized` → 那个 tag 在那个源上不存在。国内源的同步有滞后，
     换回 GHCR 试试；或者在设置里把 Hunter 版本固定到一个确定存在的 tag。
   * `no space left on device` → 磁盘满了。六个镜像解压后要 2 GB 出头，
     加上容器和数据卷，留 10 GB 比较稳。`docker system df` 看看占用，
     `docker system prune` 清一清（**别加 `-a --volumes`**，那会删你的数据）。
2. **自建镜像仓库**：设置 → 镜像源 → 「自定义前缀」，填 `registry.example.com/agentpit`
   这种。填了就不再测速，直接用。
3. **完全没有外网**：走[离线包](使用说明.md#七离线安装内网)。
   错误页上就有「从文件导入」按钮。

## `E_PULL_STALLED`

**什么时候**：`docker compose pull` **没有报错**，但 90 秒里一个新字节都没有进来。
启动器主动把它杀掉了，并换另一个镜像源重试；两个源都这样才会走到这一页。

**这和 `E_PULL_FAILED` 不是一回事。** 那一条是「连不上 / 认证不过 / 磁盘满」——
docker 自己报了错。这一条是**连上了，但对面不给数据**：镜像列表读得到
（界面上那个「六个镜像合计约 xxx MB」就是这么算出来的），拉层的时候一个字节都不来。
这种连接不会报错，只会一直等下去 —— 0.1.15 及之前的启动器就会陪着它一直等，
用户看到的是「正在拉取镜像…」几十分钟不动（2026-09-25 有客户真撞上了，等了一个多小时）。

**怎么办**（按先后顺序）：

1. **换个网络最快验。** 手机开热点连一下，如果立刻就拉动了，那就是原来那条网络上
   有人在中间掐（运营商、公司网关、某些代理的 TUN 模式）。
2. **看错误页「详情」里写的是哪个源、下了多少。**「一个字节都没下到」说明从一开始
   就没通；「已下载 120 MB / 共 748 MB」说明中途断的，那多半是中间设备的连接超时。
3. **这台机器配了代理的话，试着临时关掉再拉一次。** 不少代理客户端对大文件的长连接
   有静默超时。启动器会沿用你的系统代理设置，但不会去改它。
4. **用[离线包](使用说明.md#七离线安装内网)**：在一台网络正常的机器上
   `hunter-launcher --export-images hunter.tar`，拷过来
   `hunter-launcher --import-images hunter.tar`，再装。错误页上就有「从文件导入」。
5. **网络本来就慢得离谱**（比如卫星链路）：`~/.hunter/launcher.toml` 里
   `[hunter]` 下加一行 `pull_stall_secs = 300`，把「多久没进展算卡死」调长。
   这个值夹在 20–1800 秒之间。

> 顺带一提：**这一条不是「超时」。** 启动器没有给拉取设总时长上限 ——
> 748 MB 在好网上 52 秒、在慢网上二十分钟，写死哪个数都是错的。
> 它数的是「多久没有任何新进展」，那个量和你的网速无关。

## `E_PORT_IN_USE`

**什么时候**：其实**你基本看不到这个码** —— 端口冲突是自动处理的。

启动器在写配置之前会挨个探 3100 / 8100 / 3921 / 5442 / 6479，
被占了就往后找一个空的，写进 `.env` 与覆盖文件，界面上列出来「3100 → 3101」。
只有**连着找不到可用端口**（极少见）才会报这个码。

**注意**：它会认出"占着那个端口的是我们自己上一次装的容器"，那种不算冲突。

**想固定端口**：手改 `~/.hunter/app/.env` 里的 `WEB_HOST_PORT` 等，
然后 `hunter-launcher --restart`。但要知道**升级、换源、切模型会重写 `.env`**（端口会保留，
因为启动器是按当前配置重写的；但如果你改的是别的字段就会被覆盖）。

## `E_RUNTIME_NO_DNS`

> 0.1.10 新增。只可能出现在 **macOS + 内置运行时**这条路上。

**什么时候**：Hunter 自己那台虚拟机（`colima-hunter`）里解析不了任何域名。

**为什么会这样**：这台虚拟机用的系统镜像是 Ubuntu 24.04 minimal。
Ubuntu 24.04 把 `systemd-resolved` 拆成了一个单独的包，minimal 镜像不装它；
而镜像里那条 `/etc/resolv.conf` 符号链接照旧指向它 ——
**链接在，被链接的人不在**，于是这台虚拟机（以及它里面的每一个容器）从出生起就没有 DNS。
这不是你电脑的问题，也不是你网络的问题。

**怎么办**：**通常你什么都不用做。** 0.1.10 起，启动器每次启动、以及每次安装走到
「检查 Docker」那一步，都会在那台虚拟机里真的解析一次域名；解析不动就自己把
`/etc/resolv.conf` 写好（写的是 lima 的网关 `192.168.5.2` + 国内可用的
`223.6.6.6` / `119.29.29.29`），并装一个开机重写它的服务，之后重启也不会掉。

**它只动那台虚拟机**：你 Mac 自己的 DNS、hosts、代理、防火墙一个字节都不会被改动 ——
这一条是写在程序里的（动作表里根本没有「改本机网络设置」这类动作，
而「在虚拟机里写文件」那条路只认一张逐字写死的命令表）。

想自己看一眼的话：

```bash
hunter-launcher --check-net
```

它会把那台虚拟机的 DNS 现状和 `/etc/resolv.conf` 的原文一起打出来。

## `E_CONTAINER_OFFLINE`

> 0.1.10 新增。

**什么时候**：启动器起了一个一次性容器（`--rm`，用的是刚拉下来的 Hunter 镜像），
从容器里连一次 `hunter.agentpit.io`，没连上。

**为什么这也算安装失败**：因为**六个服务全绿不等于能用**。
Hunter 的对话要经过那个模型网关，容器连不上它，你一句话都问不出来。
0.1.9 在真机上就是这样：五个服务健康、一个不健康，而真正致命的是
「就算全健康也不能对话」。所以从 0.1.10 起这是一项必检，不通就不算装完。

**怎么办**：

1. **跑在 macOS 的内置运行时上**：多半就是上面那条 `E_RUNTIME_NO_DNS`，
   启动器会自己修，不用你动手。
2. **跑在你自己装的 Docker 上**（OrbStack / Docker Desktop / Linux 的系统 docker）：
   启动器**不会**去改你电脑的网络设置，只能告诉你往哪儿查。最常见的两种：
   * **代理只放行了本机、没放行容器网段** —— Clash / Surge 这类工具的 TUN 模式很常见。
     给 Docker 配上代理，或者把容器网段放行；
   * **网络挡了 443**（公司网络、某些校园网）。

   想确认到底是哪一种，跑一次：

   ```bash
   hunter-launcher --check-net
   ```

   它会把真实跑过的那条命令和 curl 的原话一起打出来 ——
   `Could not resolve host` / `Resolving timed out` 是 DNS 的事，
   `Connection refused` / `Received HTTP code 403 from proxy` 是代理或防火墙的事。

## `E_START_TIMEOUT`

**什么时候**：`up -d` 成功了，但 180 秒内 6 个服务没有全部报健康。错误里会指出是**哪几个**没就绪。

**怎么办**：

1. **先看是哪个服务**，再看它的日志：
   ```bash
   hunter-launcher --logs api        # 或 web / opencode / llm-shim / postgres / redis
   ```
2. **最常见的几种**：
   * **postgres 没起来** → 十有八九是数据卷里的密码和 `.env` 里的 `POSTGRES_PASSWORD` 对不上。
     启动器**不会**换这个密码（它是 sticky 的），但如果你手工删过 `.env` 又重装过就会。
     日志里会写 `password authentication failed`。
   * **api 一直 starting** → 它在等 postgres 跑迁移。大版本升级时迁移可能要一两分钟，
     再等一轮（`hunter-launcher --restart` 然后看日志）。
   * **机器太慢 / 内存不够**。6 个容器加起来要 3–4 GB 内存。`free -g` 看看。
     2 核 8G 的机器上首次启动实测 40 秒左右，比这慢很多说明资源不够。
   * **opencode 起不来** → 检查 `.env` 里的 `OPENCODE_PASS` 不是空的。
   * **opencode 一直不健康，别的都健康（0.1.10 补）** → 先怀疑**容器没有 DNS**。
     opencode 的健康检查请求的是它自己的 `/`，而那个页面要去外网取东西；
     容器解析不了域名时它会慢到十几秒才返回 500，健康检查（5 秒超时）永远过不去。
     0.1.10 起启动器会在这一步之前就把「容器能不能连上模型网关」查一遍，
     所以你更可能看到的是 [`E_CONTAINER_OFFLINE`](#e_container_offline) 而不是这一条。
3. 还是不行就点「一键反馈」，它会把六个服务的状态和最近的日志（脱敏后）一起带上。

## `E_PROXY_BLOCK`

**什么时候**：判断出网络请求是被代理 / 防火墙挡住的。

**怎么办**：

* **启动器自己走代理**：它用系统代理设置。Linux 上是 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量 ——
  注意从桌面图标启动的程序读不到你在 `.bashrc` 里设的那些。
* **容器走代理**：这是另一件事。容器里的进程要连 `hunter.agentpit.io`，
  它们不读宿主的环境变量。要给 Docker daemon 配代理：
  ```bash
  sudo mkdir -p /etc/systemd/system/docker.service.d
  sudo tee /etc/systemd/system/docker.service.d/proxy.conf <<'EOF'
  [Service]
  Environment="HTTP_PROXY=http://代理地址:端口"
  Environment="HTTPS_PROXY=http://代理地址:端口"
  Environment="NO_PROXY=localhost,127.0.0.1"
  EOF
  sudo systemctl daemon-reload && sudo systemctl restart docker
  ```
  `NO_PROXY` 里一定要有 `localhost,127.0.0.1`，否则容器之间互相调用也会走代理，
  表现是"服务都起来了但互相连不上"。
* **公司的 TLS 中间人**：自签 CA 会让 TLS 握手失败。要把公司的根证书装进系统信任库。

## `E_UPDATE_FAILED`

**什么时候**：升级 Hunter 的过程中出错了。

**启动器已经替你做过的事**（这些都写在错误信息里）：

* 升级前的**备份还在** `~/.hunter/backups/<时间戳>-v<旧版本>/`（数据库转储 + 配置）；
* 如果失败发生在"已经写了新配置"之后，**配置已经被写回旧版本那一整套**，并且用旧镜像
  重新 `up -d` 过了 —— 服务应该已经恢复。错误信息里会写清楚回滚做成了没有。

**怎么办**：

1. **先确认服务真的恢复了**：`hunter-launcher --status`，6 个应该都健康。
   没恢复就 `hunter-launcher --start` 再看一次日志。
2. **看失败在哪一步**（更新页的进度框里逐行都在）：
   * **"取不到 vX.Y.Z 的 docker-compose.yml"** → 那个版本可能不存在。
     这一步失败时**什么都还没改**。到
     [上游的 Releases](https://github.com/agentpit-io/hunter-community/releases) 确认版本号。
   * **"数据库没备份成功"** → 升级被中止了，同样什么都没改。
     多半是 postgres 没起来；先把它弄起来再升。
   * **拉镜像失败** → 那个 tag 的镜像没发布，或者网络问题。参考 `E_PULL_FAILED`。
     这是最常见的一种：**git tag 存在不等于镜像存在**。
   * **健康检查超时** → 新版本起不来。参考 `E_START_TIMEOUT` 看是哪个服务、看它的日志，
     很可能是新版本要改 `.env`（上游的升级须知里会写）。
3. **数据看起来不对**（升级跑过迁移之后才可能）：到**更新页 → 备份**，
   对着那次升级的备份点「从这份恢复数据库」。这是破坏性操作，会二次确认。
   手工做也一样：
   ```bash
   cd ~/.hunter/app
   docker compose -p hunter exec -T postgres psql -U hunter -d hunter \
     < ~/.hunter/backups/<那一份>/hunter.sql
   ```

> **为什么回滚不自动恢复数据库**：升级失败绝大多数发生在"镜像拉不到"或"容器起不来"，
> 这两种情况下数据库根本没被动过；这时候自动灌回一份转储，反而会抹掉升级中途写进去的东西。
> 所以配置自动回滚，数据等你确认之后再说。

> **0.1.14 起这三条路都在真机上走过一遍了**（在此之前从来没有）：
> 升上去（含升级前自动备份并当场校验）、版本号根本不存在、镜像拉不到。
> 第二种**不会**说"已回滚"—— 那时候还什么都没动，说了就是假话；
> 第三种会把 `.env` 与两份 compose 整套写回，实测下来**连容器都不用重建**
> （期望状态和现状一样，docker 一个都没动），你正在用的 Hunter 全程无感。

## `E_COMPOSE_FETCH`

**什么时候**：取不到 `docker-compose.yml`。方案原本假设从 Release 资产下载，
实测上游的 Release **没有任何 assets**，所以改走 `raw.githubusercontent.com` 的固定 tag 路径，
国内备用走腾讯云香港。

**安装时**：两个地址都失败会退回**启动器内置的 1.2.0 副本**（带 sha256 校验），
界面上会明说"用的是内置副本"。所以安装时你基本不会看到这个码。

**升级时**：**不会**退回内置副本。你点的是某个具体版本，悄悄换成内置的 1.2.0 就是
拿另一件事冒充你要的事。所以升级时取不到就报这个码并中止，**什么都不改**。

**怎么办**：确认版本号真的存在（去上游的 Releases 页看）；
确认能访问 `raw.githubusercontent.com`（国内经常不行，这时走腾讯云那条备用路径，
它每 6 小时同步一次，新版本可能有几小时的滞后）。

## `E_CONFIG_WRITE`

**什么时候**：写 `~/.hunter/` 下的文件失败。

**怎么办**：

* **磁盘满了** → `df -h ~`。
* **权限不对** → `~/.hunter` 应该是 700、`app/.env` 应该是 600，属主是你。
  如果你曾经用 `sudo` 跑过启动器，里面会混进 root 拥有的文件：
  ```bash
  sudo chown -R "$USER:$USER" ~/.hunter
  chmod 700 ~/.hunter && chmod 600 ~/.hunter/app/.env
  ```
  **不要用 sudo 跑启动器** —— 它不需要 root，跑过一次反而会把工作目录弄乱。
* **`~` 在只读挂载 / 网络文件系统上** → 用 `HUNTER_HOME=/some/local/path` 换个地方。

这个码还会在一种**故意**的情况下出现：启动器写完覆盖文件后会用
`docker compose config --format json` 复核一遍"发布出来的端口是不是**都**绑在 127.0.0.1"，
没绑住就拒绝继续。那是安全底线，不是 bug。

（0.1.7 起 web 也算在这道自查里面。唯一的例外是从旧版本升上来、
升级前就对局域网开着的那种机器 —— 那是有意不动它，运行面板上给一键收紧。）

## `E_DATA_DOWNGRADE`

**什么时候**：0.1.12 起，安装流程在写配置之前会先只读地看一眼「这台电脑上还有没有
上一次的数据」。如果留下来的数据是**比现在要装的这一版更新的 Hunter** 写出来的，
安装会停在这里 —— 那时候一个字节都还没动。

判据有两条，命中任意一条就算：

* 数据卷里的 PostgreSQL 大版本比要装的镜像高（比如卷里是 17、镜像是 16）；
* 数据库里已经应用到的迁移编号比目标镜像里最大的那个还大。

**为什么要拦**：这两种情况硬装下去都会真的把数据弄坏，而且没法撤销。
这是唯一一档「宁可装不上，也要保住数据」的情况 —— 其余任何情况（缺密钥卷、
只有备份、全新机器）都不会拦你。

**怎么办**：错误页上写着两边分别是什么版本。两条路：

1. 把要装的 Hunter 版本换回数据原来那一版（设置页里能改 tag）；
2. 从备份恢复。

**不要**手工去删数据卷 —— 那正是这一档想帮你避免的事。

**怎么办**：开 issue，写清楚点了什么。

## 不属于错误码的常见困惑

### 出错了，可我明明已经能打开 Hunter 了（0.1.11 起不会再这样）

0.1.9 及之前有这个毛病：报错之后界面就停在那张卡片上，哪怕问题在外面被修好了、
六个服务都健康了，它也不会变。

0.1.11 起，**错误页会自己去看现状**：每 20 秒只读地问一次
（`docker compose ps` + 对本机网页发一次请求，不改任何东西）。
一旦六个服务全就绪、网页也打得开，界面**自己回到运行面板**，
顶上会有一条绿色横幅告诉你刚才发生了什么。你什么都不用点。

错误卡片下面那张「现在是什么情况」也是同一份实测结果，
想立刻再查一次就点它上面的「重新查一次」。

### 装好了，重新打开启动器却又从欢迎页开始（0.1.12 起不会再这样）

0.1.11 及之前有这个毛病，而且有人真的撞上了：Hunter 六个服务好好跑着，
重新打开启动器看到的却是「欢迎使用 Hunter 启动器」。

根子在判据上：那时候启动器只看 `~/.hunter/launcher.toml` 里的 `[install] done` 这一行标记，
**而那一行只在安装流程自己成功走完时才写**。那一次安装在启动器看来是失败的
（最后是在外面修好的），没有人回来把标记补上。

0.1.12 起改成「**现状优先**」：打开启动器先花不到一秒只读地查一次
（`docker compose ps` + 对本机网页发一次请求），六个容器在就是装过 ——
标记写的是什么都不影响这个判断，而且启动器会顺手把标记补上，
面板顶上说一句「检测到 Hunter 已在运行，已记录为已安装」。

想自己看这一次判定：命令行跑 `hunter-launcher --boot-state`。

### 停止之后内存没降下来（0.1.12 起会问你一句）

用内置运行时的机器（macOS 默认就是）上，Hunter 跑在一台只服务它的虚拟机里。
只停容器的话，那台虚拟机还占着分给它的内存（默认 4 GB）。

0.1.12 起点「停止」会弹一句确认，上面有一个**默认勾上**的选项
「顺便把 Hunter 的运行环境也停了（释放约 4 GB 内存）」。数据在虚拟机的磁盘里，
停机不会丢，下次点「启动」时启动器会先把它起回来。

### 电脑重启之后 Hunter 没自己回来（0.1.12 起会）

三道：

1. 启动器生成的覆盖文件给六个服务都写了 `restart: unless-stopped`，
   Docker 自己重启之后容器会回来；
2. 万一没回来（比如内置运行时的虚拟机停过一次），**打开启动器就会自动拉起**，
   不需要你点任何按钮；
3. **你自己点过「停止」的那一次不算** —— 启动器记着那是你的决定，不会跟你对着干。
   想让它回来，点「启动」就行。

### 重装会不会把我的数据清掉（不会）

0.1.12 起，安装流程在写配置之前多了一步「看看有没有上一次的数据」，这一步**只读**。

数据库 + 密钥卷 + 登录用的 `JWT_SECRET` 都在、而且版本不比要装的这一版新时，
启动器会**直接沿用**：不删卷、不重建库、不重新生成密钥，你也不会掉登录。
过程流里会写明「检测到你以前的数据（N 张表，最近更新于 …），将直接沿用，不会重建」。

只有一种情况会停下来：[你的数据比要装的这一版新](#e_data_downgrade)。

容器被删掉、数据卷还留着的时候，打开启动器会先进一页「**检测到上次的数据**」，
上面列着留下来的是什么、多大。点「看看里面有什么」会起一个**用完就删**的 postgres，
把表数、最近一次写入时间问出来（十几秒）。那一页上**没有**删除按钮。

**0.1.14 补上的两件事**（0.1.13 之前承诺了但没做到）：

* **key 也一起沿用。** 「只删除应用，保留数据」保留了 `~/.hunter/app/.env`，
  里面就有你的 `hunt_tools_` key。现在重装时会先读它、当场验一次，
  验得过就直接用，界面与命令行上都会说一句「沿用上次保留的 key（`hunt_tools_****`）」。
  验不过才会问你要一把新的，并且写清楚是为什么。
  留着的那一项要是被手改过、或者粘贴时少了一截（不是 `hunt_tools_` 开头的 43 位），
  也会明说「它不是一把 hunter key 的样子，沿用不了」—— 而不是当没看见。
* **每天自动备份的定时任务会自己装回来。** 它在删除应用时被一并移除
  （那是启动器装到你账号下的东西，删干净才对），
  重装的最后一步会按你的备份设置把它重新挂上，并**在过程里说出来** ——
  装上了、没装上（连原因）、还是「你自己在设置里关掉了所以没装」，三种结局各说各的。

### 运行面板上的三层资源分别是什么（0.1.12 新增）

| 层 | 数字从哪来 | 多久刷一次 |
|---|---|---|
| 这台电脑 | 系统接口（macOS 的 `host_statistics` / Linux 的 `/proc` / Windows 的 Win32） | 5 秒 |
| Hunter 运行环境 | 在那台虚拟机里跑 `free -b` 与 `df -B1 /var/lib/docker` | 30 秒 |
| Hunter 各服务 | `docker stats --no-stream` + `docker inspect` | 10 秒 |
| 数据卷与镜像 | `docker volume ls` + `docker system df -v` + `docker image inspect` | 5 分钟 |

* **窗口看不见（最小化、收进托盘）时全部停掉** —— 这几条命令要起子进程，没人看的时候采它只是费电。
* 用户自己的 Docker 上没有「运行环境」这一层，那张卡会说明原因，不会给你一组 0。
* 任何一项拿不到都显示 `—`，鼠标停上去能看到具体原因。
* 想在命令行里看同一组数字：`hunter-launcher --monitor`。

**「内存压力」是哪来的**：macOS 上读 `kern.memorystatus_vm_pressure_level`
（就是「活动监视器」里那个内存压力图的来源），Linux 上读 `/proc/pressure/memory` 的 PSI。
Windows 没有这个概念，那一行会说清楚而不是拿占用率冒充。

### 点「重试」会不会把已经装好的东西重新下载一遍（不会）

0.1.9 及之前会。0.1.11 起，「重试」的第一步是**只读探测**，然后分三种走法：

| 探到什么 | 启动器做什么 |
|---|---|
| 六个服务都在正常跑 | **什么都不做**，直接告诉你「Hunter 已经在运行」 |
| 只有个别服务不正常 | **只动那几个**（起它 / 重启它）。不重新取配置、不重新下载镜像、健康的容器一个都不重建 |
| 这台机器上确实没有一套能用的 | 才走完整安装 |

实测（测试机）：一套装好的 Hunter 再点一次「重试」用时 **2 秒**、
一条 `docker` 下载命令都没跑、六个容器的创建时间一秒都没变。

顺便：启动器**自己上一次装的那一套**，永远是复用或修好，不会再并出第二套占你的盘和内存。
（「本机已有另一套 Hunter 就并存、换端口」那条规矩只对**你自己另外装的**那些成立。）

### 错误页上的「关闭」会把 Hunter 停掉吗（不会）

不会。它只是把启动器窗口收回托盘：

* **不退出**启动器（托盘图标还在，点它就能把窗口叫回来）；
* **不停**任何容器，正在跑的服务一个都不动。

复查说没异常的时候，「关闭」会变成那一页的主按钮 —— 那种情况下你要的就是关掉它。

### 我能自己在 `~/.hunter/app` 里敲 `docker compose` 吗（0.1.11 起可以）

可以。`~/.hunter/app/.env` 里写着 `COMPOSE_PROJECT_NAME` 与 `COMPOSE_FILE`，
所以在那个目录直接：

```bash
cd ~/.hunter/app
docker compose up -d
```

会自动带上启动器的覆盖文件 —— 项目名是 `hunter`，端口只绑 `127.0.0.1`。

**为什么要有这一条**：2026-09-22 有人在一台 Mac 上手工跑了
`docker compose -p hunter up -d`（漏了 `-f docker-compose.launcher.yml`），
容器被重建成 `0.0.0.0`，五个端口在局域网里可达了约 50 分钟。

另外，启动器每次启动都会对一遍：**跑着的容器**绑在哪，和配置说的一不一样。
不一样就按配置把那几个容器收回本机，并在日志里写清楚做了什么。

### 装启动器的新 deb 时报 `Packages were downgraded`

### AppImage 有 75 MB，不是说好 40 MB 以内吗

AppImage 要把整套 WebKitGTK 塞进去（光 `usr/lib` 就 232 MB，压缩后 75 MB），
这是格式的固有代价，和代码量无关。**`.deb` 只有 3 MB 左右** —— 介意体积就用 deb。
设计目标里那个 "20–40 MB" 对 deb/exe/dmg 是成立的，对 AppImage 不成立，
这一点 README 里已经改掉了。

### 启动器更新自己的时候会做什么（0.1.14 修好了 macOS 那条）

**先说 0.1.13 及更早的一个真问题**：那几版在 **macOS 上 `--self-update` 是坏的** ——
它会去下一个 Linux 的 `.deb`，然后报 `dpkg: command not found`。
界面上点「更新」那条路不受影响（走的是另一套）。**0.1.14 起两条路都对了。**

现在该下哪个包，由 `latest.json` 里**这台机器自己那一项**说了算，不是按名字拼的：

| 你装的是 | 下什么 | 怎么装 | 要不要密码 |
|---|---|---|---|
| macOS 的 `.app` | `*_universal.app.tar.gz` | 验签后**就地换掉那个 `.app`** | `/Applications` 默认就写得了，**通常不用**；真写不了才弹 macOS 自己的授权框 |
| Windows | `*_x64-setup.exe` | 被动模式跑一遍（只有进度条，不问问题） | 安装器自己按需要弹 UAC |
| Linux AppImage | `*.AppImage` | 换掉那个文件 | 不用 |
| Linux `.deb` | `*.deb` | 下到 `~/.hunter/updates/`，再弹系统自己的授权框装上 | 要（系统弹的框，密码不经过启动器） |

`.deb` 那一档要密码是因为它装在 `/usr/bin` 与 `/usr/lib` 下 ——
一个桌面程序不该背着你拿 root 改系统目录。

换 `.app` 的那一步是「先把旧的挪开，再把新的搬进来」：
**搬不进去就把旧的放回原位**，宁可这次没更新成，也不会让你下次打不开启动器。

所有平台都是**先验签再落地**：签名验不过一个字节都不会装。
没有桌面的服务器上用 `hunter-launcher --self-update`，行为完全一样。

### 两个工作目录会互相顶掉

**已知问题**：用 `HUNTER_HOME` 开了第二套工作目录时，两套会抢同一个 compose 项目名
（`hunter`），后 `up -d` 的那一套会把先装好的连配置带端口一起顶掉（**数据卷不会丢**，
重装一次就回来）。在修好之前，一台机器上只跑一套。

### AI 诊断助手到底会把什么发出去

0.1.4 加的「让 AI 帮我看看」分两层，**顺序不能反**：

1. **确定性规则**（默认一直在跑，零延迟、零 token、不联网）：多路径探测、
   「装了但没起来」、端口占用、磁盘不足、拉取失败。规则认出来的情况到此为止，
   一个字都不会发出去。
2. **AI 兜底**：只有规则认不出来、或者你主动点了「让 AI 帮我看看」／「按上面做了还是不行」，
   才会把一份**结构化诊断**发到 `hunter.agentpit.io` 的模型网关（用你自己那把 hunter key）。

发出去的内容你可以点「展开完整诊断」逐字看，也可以「复制诊断信息」拿走。里面有：
系统与架构、Docker 与 compose 版本、探过哪些路径及结果、`docker version` 的原始输出、
错误码、启动器日志最后 40 行、5 个端口的占用情况、磁盘余量。

**不会有的**：你的 hunter key、任何 `Bearer` 头、路径里的用户名
（`/Users/zhangsan/...` 一律换成 `<用户目录>/...`）。发之前还有一道闸，
整份报文再扫一遍 key 的形状，命中就干脆不发。

模型**不能**让启动器跑任意命令。它只能从一张写死的动作表里挑（探路径、读日志尾、查端口、
`docker version`、`compose config`、启动运行时、换镜像源、改端口、写 `docker_path`、
`brew install` 几个指定的 formula），表外的一律拒绝并在日志里记一条。
只读的会自动执行；会改动你机器的**必须先把完整命令原样给你看**，你点「确认执行」才跑。

来回最多 3 轮，之后明说搞不定并给手工步骤。不想用就到「设置 → AI 诊断助手」关掉，
关掉之后只剩第一层。

### 命令行下怎么用诊断助手

```bash
hunter-launcher --diagnose            # 只跑确定性规则，零 token，不联网
hunter-launcher --diagnose --ai --key-file ~/key   # 再问一轮 AI（会花你的额度）
```

`--ai` 是显式开关：`--diagnose` 常被写进脚本，不能在你没要求的时候悄悄花掉额度。
命令行下**不会替你执行会改动机器的动作**，只把将要执行的完整命令打出来。

### 我电脑上已经有一套 Hunter，启动器会不会把它弄坏（0.1.7）

不会。它连**改**都不会改。

发现本机已有别的 Hunter（别的 compose 项目）时，过程流里会出现一张卡片，两个按钮：

- **和它并存（推荐，不动它）** —— 默认。新装的这一套换一组空闲端口，两套互不影响。
  **不点这张卡片也是这个结果** —— 它不拦着安装，下面的步骤照样在跑。
- **直接用「xxx」，不再装一套** —— 启动器不装了，改成管理你原有的那一套。

选了后者之后：

| 它会做 | 它不会做 |
|---|---|
| 看容器状态、看日志、打开网页 | 改它的配置（一个字节都不改） |
| 停止 / 启动 / 重启（**每一次都先问你**） | 删它的数据卷（动作表里根本没有对它 `down` / `-v` 的路） |
| — | 读不到它的 compose 文件时硬猜（如实降级成只读监控） |

不想管了就点「不再管理它」—— 它还在原地跑着，一个字节都没动过。

命令行：`--takeover list | use <项目名> -y | status | logs | stop -y | start -y | restart -y | release`。
改动类的那几个**必须给 `-y`**，那是二次确认在命令行下的形态。

### 内置运行时到底装了什么、装在哪、怎么卸（0.1.7）

只有 macOS 上、而且这台机器上一个 Docker 都没有的时候才会装。装的是：

| 组件 | 版本 |
|---|---|
| Colima | v0.10.3 |
| Lima | v2.2.0 |
| docker 客户端（官方静态包） | 29.8.1 |
| docker compose | v5.5.1 |

全部落在 `~/.hunter/runtime/`：

```
~/.hunter/runtime/
  bin/            docker、colima
  dist/lima/      lima 整包
  docker-config/  我们自己的 DOCKER_CONFIG，compose 插件在它的 cli-plugins 下
  lima/           LIMA_HOME —— 虚拟机磁盘在这里面
  colima/         COLIMA_HOME —— profile 与 docker.sock
  installed.json  装了哪几个版本、从哪个源下的
```

**不写 `/usr/local`、不改任何 shell 配置文件、不碰你的 `~/.docker`、这一条路不要密码。**
虚拟机的 profile 名是 `hunter`，不会碰你自己可能已经有的 `default`。

**卸载**：设置页 →「容器运行时」→「卸载内置运行时」。
它会 `colima delete --profile hunter`（删掉那台虚拟机与它的磁盘）再清空 `~/.hunter/runtime`。
**Hunter 自己的数据卷不受影响** —— 那是 docker 的卷，不在这个目录里。

**为什么内置运行时排在 OrbStack 前面**：OrbStack 装得更快，但**第一次打开它的时候
它自己会弹欢迎页，可能还要一次管理员密码**。内置运行时这条路全程不需要任何交互 ——
「同样能解决问题时，优先不需要任何交互的那条」，所以它排第一。
OrbStack 并没有被放弃：内置运行时这条路走不通时，启动器会**自动**改走它
（下 dmg → 验苹果签名与公证 → 装进「应用程序」→ 替你打开 → 等 docker 就绪），
它自己的窗口弹出来时启动器不会停下来等你点，而是一直等 docker 就绪、超时就走下一条。
OrbStack 个人使用免费，商用需另外授权。

### 「发送诊断给开发者」会把什么发出去（0.1.7）

**它自己什么都不发。** 点下去之后发生三件事：

1. 在**你自己的机器上**生成一份脱敏诊断包（`~/.hunter/diagnostics/` 下的 zip）；
2. 把**将要贴进 GitHub issue 的标题与正文原样摆给你看**；
3. 你点「打开 GitHub 提 issue」才开浏览器，内容已经预填好 —— 改不改、发不发由你。

诊断包**不会自动上传**（启动器根本没有上报地址），它的本地路径会一并给出，
想附上就自己把那个 zip 拖进 issue。

出门前那段文字还会再被扫一遍：key 形状、完整邮箱、完整 IP、**你的用户名**、**你的主机名**。
扫到任何一样，**那个「打开 GitHub」的按钮就不会出现** —— 宁可这条路走不通，
也不把可能带隐私的东西预填进一个公开页面。

### 手机 / 同一网络里的另一台电脑打不开 Hunter（0.1.7）

**这是有意的。** 0.1.7 起，Hunter 的六个服务端口**全部**绑在 `127.0.0.1` 上 ——
只有装它的那台电脑的浏览器能打开，同一网络里的其他设备一律打不开。

为什么：Hunter 的聊天界面**不需要任何口令**。上游的 api 保护住了 `/api/setup/*`
那些配置接口，但**没有保护使用界面** —— I1 的实测是从另一台机器打
`http://<这台机器的 IP>:3101`，直接进了聊天界面，问了一句股价，
工具真调、答案真出、网关的 `used_today` 跟着涨。

**局域网访问（让同一网络的其他设备也能打开）是付费版功能**，
免费版里没有这个开关：设置页「谁能打开 Hunter」那一栏是一行只读的说明，
`launcher.toml` 里手写 `web_bind = "all"` 或 `"0.0.0.0"` 也不会生效 ——
覆盖文件照样按 `127.0.0.1` 生成，并在 `~/.hunter/logs/` 里记一条说明它被忽略了。

**从 0.1.7 之前升上来的机器例外**：那一套装的时候网页端口是对局域网开着的，
升级**不会**悄悄把它关掉（不然「昨天手机上还能开」会突然失效，而且是在你不知道的情况下）。
运行面板顶上会出现一条提示，点「只允许本机访问」就收紧。
**收紧是单向的** —— 收完不能再放开。

想确认现在到底绑在哪，直接问 docker：

```bash
cd ~/.hunter/app && docker compose -p hunter ps --format json \
  | python3 -c 'import sys,json;[print(d["Service"], [p["URL"] for p in d.get("Publishers") or []]) for d in map(json.loads, filter(str.strip, sys.stdin))]'
```

### 我能不能直接用 docker compose，不用启动器

能，而且推荐懂命令行的人这么做。启动器生成的东西是标准的：

```bash
cd ~/.hunter/app
docker compose -p hunter -f docker-compose.yml -f docker-compose.launcher.yml ps
```

启动器执行的就是这条命令的各种变体，没有任何隐藏动作。

> ⚠️ **两个 `-f` 都要带上。** `docker-compose.launcher.yml` 这个名字**不在** compose
> 的自动发现列表里（它只认 `docker-compose.override.yml`），漏掉它不会报错，
> 只会**安静地**按上游的原始配置来 —— 于是 api / postgres / redis 会从
> `127.0.0.1` 变回 `0.0.0.0`，端口冲突改写过的值也会丢。
>
> 这不是猜的：I7 收尾测试时，我自己在测试机上敲少了一个 `-f`，
> `docker ps` 当场就从 `127.0.0.1:8101->8000/tcp` 变成了 `0.0.0.0:8101->8000/tcp`。
>
> 嫌长就把它存成一个别名：
>
> ```bash
> alias hc='docker compose -p hunter -f ~/.hunter/app/docker-compose.yml -f ~/.hunter/app/docker-compose.launcher.yml --project-directory ~/.hunter/app'
> ```

### 一键上传日志与追踪码（0.1.16）

**它是干什么的**：排障原来的路是「你导一个诊断包 zip → 发给我们 → 我们翻」。
中间两步都要你在场。0.1.16 起多了一条：**你点一下，脱敏后的日志直接进我们的排障库，
你只要把一个 8 位追踪码念给我们。**

**按钮在哪**：错误页、设置页（「隐私」那一节）、运行面板的按钮区，
三处文案一样 ——「上传日志给我们（不含 key 与口令）」。

**点下去会发生什么**：

1. 启动器在本机收一份脱敏后的正文，**这一步不发任何请求**；
2. 弹窗里把**那份正文原样摆出来**给你看（连同发到哪、机器标识、还附带哪几项），
   你看到的就是会发出去的字节，一字不差；
3. 你点「确认上传」才真的发。传完屏幕上是一行大字的追踪码，比如 `HL-7K3Q9F`，
   旁边一个复制按钮。

**追踪码怎么用**：把它发给我们（GitHub issue、邮件、群里都行），
我们按这个码就能在库里找到那份日志。它同时写进了你本机的日志与 `launcher.toml`，
关掉窗口也找得回来 —— 设置页「隐私」那一节会显示「上一次上传：HL-XXXXXX（时间）」。

**它不会传什么**：

* **hunter key 一个字节都不传。** 正文里出现的 key 一律是 `hunt_tools_****` 的样子；
* 数据库口令、`JWT_SECRET`、连接串里的口令、Bearer、邮箱、手机号、IP 末段，全部抹掉；
* **你的用户名与主机名也抹掉**（换成 `<用户名>` / `<主机名>`）；
* 容器日志里的 `content` / `text` 字段（也就是你和模型说过的话）整段换成 `[redacted]`；
* 出门前整份还会再扫一遍，扫出上面任何一样就**不给上传**（连按钮都不给）。

**「这台机器的标识」是什么**：一串随机 UUID，第一次用到时生成、存在 `launcher.toml` 里。
**它不含任何硬件信息** —— 网卡地址、序列号、主机名一律没读。
它的唯一用处是把同一台机器的几次上报串起来。删掉 `launcher.toml` 就会换一个。

**会不会偷偷传**：不会。默认只有你点了才传。设置页里有一个
「出错时自动上传日志」的开关，**默认关**；打开之后也只在**出错时**传，
正常安装、正常运行一个字节都不出门。

**传不上去怎么办**：

| 你看到 | 意思 | 怎么办 |
|---|---|---|
| 「今天传得有点多」 | 同一台机器每小时最多 5 次、每天 20 次 | 过一个小时再点；日志就在你本机，路径界面上写了 |
| 「这一份日志太大」 | 超过服务端 2 MB 的上限 | 启动器已经当场给你导了一个诊断包，路径在弹窗里 |
| 「我们这边的服务器出错了」 | 是我们的问题，不是你的 | 同上，把那个诊断包发给我们 |
| 「传不上去」 | 网络到不了 www.agentpit.io | 同上 |

### 「上一次升级没做完」是什么意思（0.1.16）

**你会在运行面板顶上看到这张卡片**，说的是：配置文件里写的是一个版本，
正在跑的容器却是另一个版本，而**新版本的镜像在这台机器上还不齐**。

**它怎么来的**：升级过程中拉镜像那一步被打断了 —— 强退应用、断电、关机，
都会留下这个状态。正常的失败会自动回滚，强退不会。

**为什么不自动接着装**：照着新配置去 `docker compose up`，docker 会去拉那个
还没下完的镜像 —— 你会**再看一次「卡住」**。所以启动器停下来问你。

**两个按钮**：

* **继续升到 v1.2.2** —— 打开更新页，走正常的升级流程（会先备份）；
* **回退到正在跑的 v1.2.0** —— 只把配置写回去，**不动正在跑的容器、
  不动数据、不拉任何镜像**。那六个容器本来就在正常跑，回退之后配置和它们重新对上。

命令行上同样看得到：`hunter-launcher --boot-state` 会打印这一条，
`hunter-launcher --revert-to-running -y` 就是那个「回退」按钮。

### 面板上说「Hunter 装好了，但容器都停着」（0.1.16 起会这么说）

**这一句和「还没就绪」不是一回事，该做的事也不一样：**

| 面板上说 | 实际是 | 你该做什么 |
|---|---|---|
| 「**N 个容器都停着** —— 点「启动」就能用」 | 容器**退出了**（`exited`），进程不在了 | 点「启动」 |
| 「web、api **还没就绪**」 | 容器在跑，只是健康检查还没过 | 等一会儿；一直不过就看日志 |
| 「这几个容器**退出了**（不是「还没就绪」）：…」 | 一部分停了、一部分在跑 | 点「启动」把停的那几个拉起来 |

**0.1.15 及之前会说错。** 那时候六个容器全都 `exited`，面板上写的却是
「Hunter 在跑，但 web、api、opencode、llm-shim、postgres、redis 还没就绪、网页打不开」，
顶上那行还是大字的「Hunter 运行中」—— 而下一行副标题写着「容器已停止」，
自相矛盾。一位 Windows 用户 2026-09-26 的诊断包里就是这一屏。
0.1.16 起顶上那行大字跟着「现在到底有没有容器在跑」走，不会再和副标题打架。

**容器为什么会全停着**：电脑重启过而 Docker Desktop 没设开机自启、
手动 `docker compose stop` 过、Docker 引擎重启过。数据一点没丢
（数据在卷里，见[我的数据在哪](#我的数据在哪删除应用会不会把它删了0113)），点「启动」就回来了。

### 面板上出现红条「每日自动备份没有挂上」（0.1.16 起会说出来）

**这条的意思是：定时备份一次都不会跑。** 不是「某一次备份失败了」——
是那个定时任务压根没装进系统。

**0.1.15 及之前不会告诉你。** 装机时它只往日志里写一行
「装完挂定时备份没成（不影响安装）」，界面上一个字都没有 ——
于是你以为自己有每日自动备份，实际上从第一天起就没跑过。
2026-09-26 那位 Windows 用户就是这样。**对用户来说「备份没了」不是小事，
所以 0.1.16 把它摆到面板上，还给了一个「再挂一次」的按钮。**

**怎么办**：

1. 先点红条上的「**再挂一次**」。0.1.16 在 Windows 上会依次试三条路
   （`schtasks /Create /XML` → 先删旧任务再试一次 → 不用 XML 的
   `schtasks /Create /SC DAILY /ST HH:MM`），任何一条成了红条就消失；
2. 走到第三条路时，面板会**明说**「这条路装出来的任务**错过了不补跑**」——
   电脑在设定的那个时刻是关着的话，那一天就没有自动备份。想要「错过补跑」，
   把备份时间设成一个电脑肯定开着的时间点；
3. 还是装不上：红条上会显示系统报的**原话**（0.1.16 起 Windows 上的中文
   不会再变成 `����` 那样的乱码，见下一条）。把那句话连同追踪码一起发给我们；
4. 在此期间**手动备份照常可用**：面板上的「立即备份一次」，
   或者命令行 `hunter-launcher --backup`。

**不想要自动备份**：到备份设置里把开关关掉，红条会一起消失
（那是你自己的决定，不是故障）。

## 我的数据在哪？删除应用会不会把它删了？（0.1.13）

**数据不在 `~/.hunter` 里**，在 Docker 的数据卷里（compose 项目名 `hunter`）：

| 数据卷 | 装着什么 | 丢了会怎样 |
|---|---|---|
| `hunter_pg_data` | 账号、配置、自选股、历史分析 | **核心数据** |
| `hunter_secrets` | 密钥卷 | 数据库里加密过的配置**解不开**。必须和数据库成对保留或成对删除 |
| `hunter_opencode_data` | 历史对话 | 对话记录丢失 |
| `hunter_user_skills` | 你自己建的技能 | 自建技能丢失 |
| `hunter_packages` · `hunter_redis_data` | 缓存 | 可再生 |

另有 `~/.hunter/app/.env`（里面有你的 key、数据库口令与 `JWT_SECRET`，权限 600）。

> macOS 上 Hunter 跑在一台只服务它的虚拟机里，**上面那些数据卷在虚拟机的磁盘镜像里**，
> 在访达里看不到。这也是「删除运行环境」这个勾选在「保留数据」那一档下点不了的原因。

「删除应用」有两档，**默认选中的是「只删除应用，保留数据」**：容器与启动器配置删掉，
数据库、密钥卷、历史对话、自建技能全留着，重装直接沿用、登录也不会失效。
要连数据一起删得改选第二档，而且要逐字输入「删除应用和数据」。
**备份目录在哪一档下都不会被删。**

## 自动备份是什么时候跑的？我没开启动器它也跑吗？（0.1.13）

跑。装好 Hunter 的那一刻，启动器就在**你自己的账号下**挂了一个每天 00:00 的定时任务
（macOS 用 LaunchAgent、Linux 用 `systemd --user`、Windows 用任务计划）。
不需要管理员密码，删除应用时会一并移除。

电脑当时关着或睡着 → 开机 / 唤醒之后补跑（三个平台各自的机制都支持这件事）。

Hunter 停着的时候也能备份：它只把 postgres 临时拉起来，做完再停回去。
**运行环境（Docker / 虚拟机）本身也没起的话记为「跳过」**，下次打开启动器时提示 ——
不会擅自把整套服务启动起来。

设置页 →「数据备份」里能看到定时任务在系统里的**真实状态**（不是配置里记的那个），
以及上次成功 / 上次失败是什么时候。

> Linux 上有个细节：`systemd --user` 的定时器默认只在你有登录会话时活着。
> 设置页里会如实写明。要让它退出登录后也跑得开 linger —— 启动器不替你改。

## 备份失败了我怎么知道？（0.1.13）

三个地方同时说：

* 运行面板顶上一条**红色横幅**，写清是哪一步出的问题；
* 右侧「最近备份」那一行变红；
* 托盘的 tooltip 与菜单上挂一条 `⚠ 备份失败：…`。

**连着失败两次**会把这件事交给诊断助手分析。最常见的三个原因：
备份目录所在盘空间不足、外接盘没接上、那个目录没有写权限。

设置页里点「立即备份一次」能当场看到是哪一步出的问题（过程逐条打出来）。

## 换电脑怎么把数据带过去？（0.1.13）

1. 老电脑：运行面板上点一次「立即备份一次」（或者用当天晚上那一份）；
2. 把那个备份目录**整个文件夹**拷到新电脑上；
3. 新电脑：装好启动器，正常装一遍 Hunter；
4. 运行面板 →「备份与恢复」→「从别的目录选一份备份」→ 指到刚拷过来的文件夹 →「恢复到这一份」。

恢复要**逐字输入「恢复数据」**，而且会先把新机器上现在的数据备份一份 —— 挑错了还能回去。

命令行：`hunter-launcher --restore <目录> --confirm 恢复数据 -y`。

> 备份里有 `.env`，里面有你的 `hunt_tools_` key 与数据库口令。
> 整个目录是 700、`.env` 是 600。**别把它分享给别人。**

## 「一键处理」到底会删什么？会不会动我别的东西？（0.1.13）

只有三样，而且每一样动手之前都先问一句「有没有容器在用它」：

| 清什么 | 判据 |
|---|---|
| 本项目的**旧**镜像 | 仓库名是 `hunter-community-{web,api,opencode,llm-shim}`，tag 不是现在这一版，**而且没有任何容器在用它** |
| **悬空**数据卷 | 带本项目标签、但不在 compose 声明的那六个卷里，而且没有容器挂着 |
| **过期**备份 | 按你设的保留天数轮换 |

`postgres` 与 `redis` 这两个公共基础镜像**刻意不在名单里** —— 你别的项目很可能也在用同一份。

启动器**从不**跑 `docker image prune` / `volume prune` / `system prune`：
那几条会删到别人的东西。守卫层（`argv_image_rm` / `argv_volume_rm`）写死了只认
「指名道姓的那一种形状」，`prune` 一律拒绝，有单测钉着。

需要删你自己的文件、给虚拟机扩容、调虚拟机内存的，启动器**只给建议**，不替你做。

## 启动器会用我自己设的网络代理吗（0.1.8）

**会，而且只读**。

直连失败时，启动器会读出这台机器上已经配好的代理，用它重试一次，并把它传给
它起的每一个子进程（colima / limactl / docker），以及（用 `colima start --env`）
虚拟机里的 docker —— 让虚拟机拉镜像也能走。界面上会说一句
「检测到你设置了网络代理（…，来自系统设置），已沿用」。

从哪儿读：

| 平台 | 读哪儿 | 怎么读 |
|---|---|---|
| 任意 | `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY` / `NO_PROXY` 环境变量 | 直接读 |
| macOS | 系统设置里那一份 | `scutil --proxy`（这个子命令只打印，不改） |
| Windows | 注册表 `HKCU\…\Internet Settings` 的 `ProxyEnable` / `ProxyServer` / `ProxyOverride` | `reg query`（只读子命令） |
| Linux | 只有环境变量 —— 各家桌面环境一套一个样，不猜 | 直接读 |

环境变量优先于系统设置：你显式设了它，那就是你的意思。

**绝不修改。** 启动器不会调 `networksetup`、不会写 `scutil --set`、不会改注册表、
不会动 `~/.docker/config.json`、不会碰 DNS / hosts / 防火墙 —— 这几条在
`assist/guard.rs` 里是写死的硬校验，改网络设置的动作在动作表里**根本不存在**。

两个会如实告诉你的例外：

- **直连能通就不绕路**。代理只在直连失败之后才用上，不是默认走。
- **只监听本机（127.0.0.1）的代理不会传进虚拟机** —— 虚拟机里的 `127.0.0.1`
  是它自己，传进去只会多一种失败方式。碰到这种情况界面上会说明，
  虚拟机改走腾讯云香港的源。

## 为什么会弹出系统的密码框（0.1.8）

0.1.7 之前的承诺是「绝不使用管理员密码」，代价是撞上要管理员权限的事只能停下来，
把要敲的命令写给你。用户 2026-09-21 的决定是**宁可弹一次系统密码框，也不要让用户自己动手**。

所以现在：需要管理员权限时，**由操作系统自己弹授权框**（macOS 的授权对话框、
Linux 的 polkit、Windows 的 UAC）。弹之前界面上会先用一句人话说清「要做什么、为什么要密码」。

- **启动器不自绘密码框**。你看到的那个框是系统进程画的。
- **密码一个字节都不经过启动器**：它交给系统，启动器不读、不存、不写日志。
- **能提权的事写死在一张表里**（目前只有两件：装启动器自己的 `.deb`、启动 Linux 上的
  docker 后台服务），参数由代码构造、提权前再过一遍守卫。模型碰不到这条路。
- **只有最后一条兜底路线会用到它**。排序原则是「同样能解决问题时，优先不需要任何交互的
  那条」，所以正常情况下你根本不会看到它。

**其余禁止项一条都没放松**：不删你的文件、不改你的网络与安全设置（代理 / DNS / hosts /
VPN / 防火墙 / Gatekeeper / SIP）、不动别的项目的容器与数据、不执行模型自己编的命令。

### 之前装过没成功，再装会怎样（0.1.9）

短答：**接着上次装，不会重来一遍，也不会在你电脑上留下第二套东西。**

长一点：上一次没装成功，机器上可能留下三种东西，启动器对它们的处置各不相同。

| 留下的东西 | 在哪 | 再装时怎么处理 |
|---|---|---|
| 内置运行时的文件（docker / colima / limactl / compose / 虚拟机镜像） | `~/.hunter/runtime` | **按清单逐个核 sha256 与 sha512**：对得上的直接用（一个字节都不重下），对不上的删掉重下，缺的补齐 |
| `hunter` 那台虚拟机的半成品 | `~/.hunter/runtime/colima/hunter`、`~/.hunter/runtime/lima/colima-hunter` | 先照常启动；起不来才**清掉重建一次**（只删这两个目录） |
| 已经拉下来的六个镜像、已经建出来的容器 | Docker 自己的存储 | 镜像直接复用（界面会写「本机已有，这次一个字节都没下载」）；「已创建未启动」的残留容器先清掉再重起 |

几条边界，写在代码里、不靠自觉：

* **只动 `~/.hunter/runtime`**。你的 `~/.colima`、`~/.lima`、`~/.docker/config.json`、
  别人的容器与数据卷，一个字节都不碰。
* 启动器发出的每一条 `colima` 命令都必须带指向 `~/.hunter/runtime` 的 `COLIMA_HOME`
  和 `--profile hunter`；缺一样就被执行层的守卫拒掉并记进审计
  （`~/.hunter/logs/assist-audit.log`）。
* 你**自己**装的 colima 只会被「启动它原有的 profile」，绝不会替你新建虚拟机。
* 数据卷从头到尾不删 —— 上次装了一半留下的数据库，这次会接着用。

> 0.1.8 在这件事上出过一次真问题：机器上留着 0.1.7 的残骸，启动器把**自己下的那份
> colima** 当成了「用户装的 Colima」，执行了一条不带 profile 的 `colima start`，
> 在用户家目录里建出了一台和 Hunter 毫无关系的虚拟机（占 1.4 GB）。
> 0.1.9 把这一条从三个方向堵死了：判定顺序（先问内置运行时、再问你的 Docker）、
> 子进程环境（`COLIMA_HOME` / `LIMA_HOME` 钉在 Hunter 自己的目录里）、
> 执行层守卫（不合规的 colima 命令到不了 `fork`）。
>
> 如果你的机器上已经被 0.1.8 建出了这样一台虚拟机：它叫 `default`，在 `~/.colima` 里。
> 启动器**不会替你删**（那是你家目录里的东西，红线）—— 要清掉的话，
> 那是你自己的 colima，用它自己的命令删即可。
