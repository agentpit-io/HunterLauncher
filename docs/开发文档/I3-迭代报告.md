## 二、详解：额度用完了，运行面板一个字都没提

### 2.1 怎么撞上的

回归的第一步（命令行从零装）里，key 校验那一行是这样的：

```
  ✓ key 有效 · 今日已用 216406 / 300000 · 剩 83594 · 每分钟 20 次 · 并发 4
```

装完之后跨机做真实对话（用例 3），第一个问题（600519 贵州茅台）**工具真调、答案真出**。
紧接着问第二个（000858 五粮液），界面停在「回答未完成」。查网关：

```json
{"ok":true,"used_today":304144,"limit_daily":300000,"remaining":0,"exhausted":true,
 "reset_at":"2026-09-21T00:00:00+08:00","reset_tz":"Asia/Shanghai",
 "rate_per_min":20,"max_concurrency":4,"enabled":true,"global_exhausted":false}
```

额度真的用完了（一次带深度思考的对话吃掉了剩下的 8 万多 token）。
**问题不在这里 —— 问题在回到启动器之后**：

![0.1.2 的运行面板](../screenshots/I3/00-问题现场-0.1.2的运行面板不提额度用完.png)

面板上只有「304,144 / 300,000」两个数字，进度条是正常的琥珀金，
**没有任何一个字说「用完了」**。用户在 Hunter 里对话被挡住，回到启动器看不出原因。

而输入 key 那一页写着（`i18n/zh-CN.ts` 的 `model.gatewayPoints`）：

> 对话模型 hunter-chat · 深度分析 hunter-deep · **额度用尽会明确提示，不会静默降级**

装之前承诺了，装之后没做到。`--status` 也一样 —— 只打「剩 0」，要用户自己做减法。

### 2.2 为什么会这样

数据一直都在：`QuotaInfo` 从 M2 起就有 `exhausted` 字段（网关给的，读不到时按
`remaining <= 0` 兜底），前端的 `QuotaInfo` 类型里也有。
**只有输入 key 那一页用了它**（I1 加的，见 `Key.tsx` 的 `key-exhausted`）。
运行面板从来没读过这个字段 —— 它只画了 `usedToday / limitDaily` 和一根进度条。

这是典型的「一处做对了就以为全做对了」：I1 修的是**安装时**的提醒，
而额度用尽这件事**绝大多数时候发生在装完很久之后**，那时用户看的是运行面板。

### 2.3 修了什么

1. **运行面板加一条横幅**（红色描边 + `bg-danger-soft`），写清三件事：用了多少 /
   什么时候重置 / 现在就想用该怎么办。只在网关明确说 `exhausted` 时出现，
   额度读不到就什么都不说（红线 1）。
2. **额度卡**副行写「已用完」（红色），进度条转警示色。
   副行不写重置时间 —— 卡片只有面板四分之一宽，写长了会被 `truncate` 截掉半句话；
   完整的一句由上面那条横幅说。
3. **`--status`** 同样：

```
额度：今日已用 304,144 / 300,000 · 已用完
      Hunter 里的对话会被网关挡住，直到 2026-09-21 00:00（上海） 重置；想现在就用就在设置里换成自带模型 key。
```

4. 重置时间的格式两边统一：Rust 侧 `gateway::pretty_reset`、前端 `format.ts` 的
   `shanghaiStamp()`，规则一样（只砍格式、**不做时区换算** —— 网关自己在
   `reset_tz` 里写明了是 `Asia/Shanghai`），两边各有一份测试盯着同样的样本。

修完的样子：

![0.1.3 的运行面板](../screenshots/I3/10-运行面板-额度已用完.png)

这张图里的额度是**真的**用完的（回归当天的真实状态），不是演示数据。

## 三、详解：Podman 到底能不能跑（待办池 P1-5 / P2-12）

这一条从 M0 挂到现在，理由一直是「装了会和 Docker 抢资源」。本轮把它做掉了，
**做法上没有动这台机器上真实的 Docker**：

* **不装 `podman-docker`** —— 它会往 `/usr/bin/docker` 上放一个指向 podman 的软链，
  把测试机上跑着的两套 Hunter（启动器的 `hunter` 与旧栈 `hunter-community`）全带下水；
* 改成 `apt install podman` 之后，在 `/tmp/podman-shim/` 里放一个叫 `docker` 的软链指向
  `/usr/bin/podman`，**只在这一次测试的 `PATH` 里生效**，测完删掉。

### 3.1 实测出来的事实，和代码里的假设正好相反

代码里原本的假设是：「`docker version --format json` 的输出**不是 JSON** 时，
看看里面有没有 `podman` 字样」。真实情况是：

```console
$ docker version --format json       # 这个 docker 其实是 podman 4.9.3
{"Client":{"APIVersion":"4.9.3","Version":"4.9.3","GoVersion":"go1.22.2",
 "GitCommit":"","BuiltTime":"Thu Jan  1 00:00:00 1970","Built":0,
 "OsArch":"linux/amd64","Os":"linux"}}
```

1. 它是**合法的 Docker 形状 JSON**，`parse_version` 解析得动 —— 于是
   「不是 JSON 才认 podman」那条分支**永远轮不到**，是死代码；
2. 整段里**一个 `podman` 字样都没有**。

结果：用户明明装着能用的 podman，启动器却说

```
✗ Docker 客户端在，但连不上后台服务（daemon）。
  在 Linux 上装 Docker
   · 官方便利脚本：curl -fsSL https://get.docker.com | sh …
```

—— 话说错了，而且把人往一条不必要的路上带。

### 3.2 第一版的修法栽了一次

第一版改成「没有 Server 时再跑一次 `docker --version`」。真机上：

```console
$ docker --version        # 通过名为 docker 的软链调用 podman
docker version 4.9.3
```

**podman 用 `argv[0]` 当程序名** —— 通过软链调用时它把自己叫「docker」。
于是 `classify_plain` 匹配到 `docker` → 判成 Docker Engine，比原来还糟。
这一次是靠真机跑出来的，单测再多也想不到。

### 3.3 最后的修法（两道，都与 `argv[0]` 无关）

1. **`OsArch` 这个键**。podman 的 Client 块有 `"OsArch":"linux/amd64"`；
   Docker 那边是分开的 `Os` + `Arch`，**从来不发 `OsArch`**。同一台机器上取的对照：

   | | podman 4.9.3 | docker 29.8.1 |
   |---|---|---|
   | Client 里的键 | `APIVersion` `Version` `GoVersion` `GitCommit` `BuiltTime` `Built` **`OsArch`** `Os` | `Platform` `Version` `ApiVersion` `DefaultAPIVersion` `GitCommit` `GoVersion` `Os` `Arch` `Context` |

   这一道**不用多跑任何进程**。

2. **`docker version`（不带 `--format`）的第一行**，作为第二道保险：

   ```
   Client:       Podman Engine          ← podman
   Client: Docker Engine - Community    ← docker
   ```

   这一行由 podman 自己写死，和 `argv[0]` 无关。只在「JSON 解析成功但没有 Server」
   这条失败路径上跑一次，正常安装一个进程都没多跑。

认出来之后说的话**不假装支持**（红线 1）：

```
✗ 命令行里的 docker 实际上是 Podman 4.9.3，不是 Docker，而且现在连不上它的服务。
  Podman 目前是**实验支持**：启动器认得出它，但整套安装从来没有在 Podman 上跑通过 ——
  `docker compose` 在 Podman 上要另外装一个 compose provider（podman-compose 或
  docker-compose），没有它 Hunter 起不来。最稳的做法是装 Docker Engine；一定要用
  Podman 的话，请先确认 `docker compose version` 有输出，再用 `podman system service`
  把服务起起来。
```

### 3.4 这一轮**没有**验到的（如实写）

| 问题 | 结论 |
|---|---|
| 启动器能不能认出 Podman | ✅ **验了**，能，退出码 1，文案是 Podman 专属的那一段 |
| Hunter 整套能不能在 Podman 上跑起来 | ❌ **没验**。要 `podman system service` 起 socket、要装 compose provider、六个容器要重新拉一遍 —— 在一台 2 核 8G、已经跑着 12 个容器的机器上做这件事会把现有两套栈挤垮 |
| Podman 上的 `docker compose` 是不是可用 | ❌ **测不出可信结论**。这台机器上 `docker compose version` 在 podman 的 PATH 下**仍然返回 v5.5.1** —— 因为 podman 4.9 会去找外部 compose provider，而它正好找到了**这台机器上真实 Docker 的** `/usr/libexec/docker/cli-plugins/docker-compose`。一台只有 podman 的机器上不会是这个结果，所以这个数字不算数 |

所以待办池里 P1-5 / P2-12 的状态从「完全未验证」变成「**识别这一步验过了，能跑起来没验过**」，
并且启动器现在**明说自己没验过**，而不是给一句含糊的「实验支持」。

## 四、本轮自审抓到的其余几条

### 4.1 更新页的卡片标题自己打自己

回归截图 `14-更新.png` 上一眼可见：

```
┌ 启动器有新版本 ─────────┐   ┌ Hunter 有新版本 ──────────┐
│ 启动器已经是最新版 · v0.1.2 │   │ Hunter 已经是最新版 v1.2.0 │
```

标题是写死的字符串，无论查出来是什么状态都是那一句。现在标题跟着状态走
（有新版本 → 「启动器有新版本」；其余 → 「启动器」），两张卡都改了。

### 4.2 更新页的发布时间是原始 UTC 时间戳

同一张图上：`发布于 2026-09-19T09:47:29Z`。总控规则要求**时间一律上海时间**，
而这一行是 GitHub Release 的 `published_at` 原样上屏。
新增 `format.ts` 的 `isoToShanghai()`，换算成「2026-09-19 17:47（上海）」。

这里是**真的做换算**（+8 小时），和额度重置时间那一个不一样 ——
网关的 `reset_at` 自己带 `reset_tz: Asia/Shanghai`，那个只砍格式不换算。
两个函数各有一组测试，样本都取自真实响应。

不用 `toLocaleString('zh-CN', {timeZone})`：WebKitGTK 上的 ICU 数据未必带得全，
而 +08:00 是个常数，自己加靠得住。解析不出来的一律原样返回，不猜。

### 4.3 额度提醒里的裸数字与多余空格

`04-输入key-已验证.png` 上（这一张是真实的额度用尽状态）：

> 这把 key 是好的，但今天的额度已经用完了（已用 **304144** / 上限 **300000**）。
> 额度在 2026-09-21 00:00（上海）**␣**重置。

两处：数字没有千分位，和旁边三张卡的 `300,000` 不是一套；中文右括号后面多一个空格。
Rust 侧补了一个 `gateway::thousands()`（与前端 `format.ts` 的同名函数同一套写法），
`--status`、`--headless` 的三处额度输出全部走它。

### 4.4 `--tray-menu` 打错一个字母会「成功」

```console
$ hunter-launcher --tray-menu stopp     # 少打一个 p 就成了多打一个
没认出这些参数：--tray-menu stopp。用 --help 看用法。
$ echo $?
0                                        # ← 什么都没做，但返回成功
```

原因是 `tray_menu_arg()` 对「没写这个参数」和「写了但认不出来」都返回 `None`，
而「有参数但不认得」这条路的既定行为是「提示一句再照常开界面」—— 那是为**双击图标**
准备的，对着命令行打字的人不该走这一条。

改成三态（`Absent` / `Id` / `Unknown`）。写了 `--tray-menu` 但值认不出来时：

```console
$ hunter-launcher --tray-menu stopp
--tray-menu 不认识「stopp」这一项，什么都没做。
  可用的菜单项：open | status | start | stop | restart | logs | update | feedback | settings | autostart | quit
$ echo $?
2
```

`--tray-menu` 后面什么都不跟也是同样的处理（退出码 2）。
**合法的那 11 项一个都没受影响**，回归里逐条跑过。

### 4.5 `--key-file` 只写建议不查权限

`--help` 里写着「文件建议权限 600」，但从来没查过。同机的其他用户读得到那个文件，
这把 key 就等于是公开的。现在提醒一句（**只提醒不中断** —— 脚本化场景里用户可能
有自己的理由，比如挂在只读的 secret 卷上）：

```console
$ chmod 644 /tmp/loose-key && hunter-launcher --headless --key-file /tmp/loose-key -y
[2/6] hunter key
  从 /tmp/loose-key 读到一把 key（hunt_tools_****）
  ⚠ /tmp/loose-key 的权限是 644，同机的其他用户也读得到这把 key。建议 chmod 600 /tmp/loose-key
```

### 4.6 一条单测会跟着开发机的真实状态走

`autostart::tests::默认没有自启项` 直接 `assert!(!status())` —— 而 `status()` 读的是
**真实用户的 `~/.config/autostart/`**。本轮回归里托盘那一步跑了 `--tray-menu autostart`，
自启项被真的打开了，之后 `cargo test` 就红了，**而代码一个字没改**。

（更普通的情形是：开发者自己把启动器设成开机自启，于是他本机的 `cargo test` 永远过不了。）

原来的注释写着「真有的话这条测试失败是对的 —— 说明环境脏了」，这个理由站不住：
单元测试不该去读用户的真实配置。改成把 `XDG_CONFIG_HOME` 指到一个空的临时目录，
断言「干净环境下没有自启项」—— 这才是这条测试本来想说的话。
同文件里两条会动环境变量的测试也加了一把锁（`cargo` 默认并行跑）。

### 4.7 待办池的三条小活

| # | 做了什么 |
|---|---|
| **P1-22** | `Candidate` 的六个字段从 `&'static str` 换成 `Cow<'static, str>`：内置两个源仍是 `Cow::Borrowed`（零分配），自定义源用 `Cow::Owned`。`registry::custom()` 与 `flow::prepare()` 里的三处 `Box::leak` 全部去掉，**代码库里一个 `Box::leak` 都不剩**。`CANDIDATES` 从 `const` 改成 `static`（`Cow` 带 drop glue，`const X: &[T]` 那种写法要靠常量提升，而带 drop glue 的类型不给提升） |
| **P2-16** | `~/.hunter/app/VERSION` 从 644 收成 600。至此 `~/.hunter` 下由启动器写出来的**五个**文件全是 600、七个目录全是 700。单测从「四个文件」扩到「五个文件」 |
| **P2-17** | CI 里给安装包改名不再把版本号拼进源文件名（`Hunter Launcher_${V}_amd64.deb`），改成和 `release.yml` 完全一样的「按前缀替换、不猜版本号」，后面加一句 `ls` 保证改完真的存在 |

### 4.8 I2 报告里建议的两件事

**建议 4：`.env` 写完读回来对账。** I2 修「模型名里的换行会注入」用的是「写之前查」，
拦得住已知形状，拦不住没想到的形状 —— 而这个文件里有 hunter key、数据库口令、JWT secret。
现在加了一道结果校验：

* 落盘**之前**先对一遍（渲染错了就根本不碰磁盘上那一份，旧的 `.env` 还在）；
* 落盘**之后**把文件读回来再对一遍（盘满、被截断、编码出岔子都在这里露馅）；
* 规则：① 每个键只能出现一次（注入最典型的后果就是多出一行同名键，而 `parse_env`
  是后写覆盖先写，只看解析结果反而看不出来）；② 用户能左右的那 11 项值一字不差（含五个端口）；
* **报错只说键名不说值**（红线 2）—— 有一条测试专门盯着报错里不许出现 key 明文。

**建议 5：GUI 回归的点击断言。** 见 §5.2 —— 本轮第一遍就当场抓到一次。

## 十、可交付，等待用户决定

按 I3 的要求（第 6 条）：**待办池里已经只剩需要用户决定、花钱、或者需要一台本项目拿不到的机器的事项了。**
下面每一条都写清「启动器这一侧已经做到哪」和「需要用户定什么」。

### 10.1 web 端口默认值（待办池 P1-20）—— 唯一一条纯产品决策

**启动器这一侧全做完了**（I2）：`launcher.toml` 的 `hunter.web_bind`、设置页的
「谁能打开 Hunter」、覆盖文件渲染、端口探测、单测，一样不缺。想收紧的用户点一下就能收紧。
**默认值一个字节没动**（仍然对外）。

要用户拍板的是两件事：

1. **默认该是「只有这台电脑」还是「同一网络里的设备都可以」？**
   现状（对外）的代价是实测过的：从**另一台机器**打 `http://34.133.8.3:3101`，
   不需要任何凭证就进了聊天界面，问了一句「600519 最新收盘价」，工具真调、答案真出，
   网关 `used_today` 跟着涨（I1 用例、I2 用例 3、本轮用例 3 都是这样跑的）。
   上游 api 保护住了 `/api/setup/*`，**但聊天界面本身没有**。
2. **已经装好的机器要不要在升级时自动收紧？** 收紧会让「昨天手机上还能开」突然失效。

我的建议（**是建议不是决定**）：默认收紧 + 设置页给开关 + 升级时不动已有配置。

### 10.2 代码签名证书（红线 7）

Windows 代码签名证书与 Apple 开发者账号都要花钱，按红线 7**没有申请、没有购买**。
CI 里签名步骤已经写好，没有 secrets 时自动跳过并产出未签名包。
后果是每个 Release 都标 prerelease，而且：

* Windows 上会弹 SmartScreen，用户要点「更多信息 → 仍要运行」；
* macOS 上会说「无法验证开发者」，要右键打开或去隐私设置里放行；
* **自更新的第二个端点（GitHub）一直是 404**（§7.2）—— 它解析的是「最新的正式 Release」。

要不要买、买哪一种，由用户定。

### 10.3 第三方模型 key（待办池 P1-10）

自带模型 key 模式的参数校验、早退、DeepSeek 自动 sanitize 都有单测，连通性检查的代码路径也审过，
但手上**没有 DeepSeek / OpenAI 的 key**，没法端到端验一次。要用户提供一把。

### 10.4 一台 Windows 或 macOS 真机（待办池 P1-15 / P1-13）

| 事项 | 现状 |
|---|---|
| updater 的就地安装 | AppImage 真机走通过（本轮又走了一遍）；Windows 的 NSIS `passive`、macOS 的 `.app.tar.gz` 替换**只有代码路径审阅 + CI 编译** |
| 托盘图标的可见性与菜单渲染 | Xvfb 下 `TrayIconBuilder::build()` 返回 Ok、11 个动作都真跑过，但**图标长什么样、菜单怎么排、右键什么行为，Xvfb 里看不见** |
| Windows 上窗口按钮挪到右上角 | I1 改的，**没有真机验证** |

### 10.5 一台干净机器

「完全干净的机器上首次安装要多久」（P1-9）、「解压那一段的体感」（P1-12）、
「Hunter 整套在 Podman 上跑起来」（§3.4）都卡在同一件事上：
测试机上跑着的旧栈用着同样的六个镜像，层全在本地内容存储里，
而把它 `down` 掉再 `docker rmi` 之后不保证能原样恢复（旧栈没有 `.env`，不知道当初怎么起的），
风险不值得。

### 10.6 测试机上的 pnpm 供应链策略（待办池 P2-9）

测试机的 pnpm 12 默认拒绝 24 小时内发布的包，会挡住**一切** pnpm 入口（连 `pnpm exec` 都挡）。
本项目的绕法是完全不经过 pnpm（直接 `node node_modules/vite/bin/vite.js build`）。
长期解法是在测试机上 `pnpm config set minimumReleaseAge 0` —— 但那是**放松一条供应链策略**，
值不值得由用户定。CI 用 pnpm 10，不受影响。

## 附、本轮的三个「差点没发现」

留给以后翻这份文档的人：

1. **额度用完那一条，是靠「回归当天额度真的被用光」撞出来的。** 如果那天额度还剩得多，
   这个洞会一直留着 —— 而它恰恰是**装完之后最常遇到**的一种状态。
   教训：构造一遍极端状态（额度 0、磁盘满、网断）比多读十遍代码有用。
2. **Podman 那一条，第一版修法在真机上又错了一次**（`argv[0]`）。
   单测写得再多也想不到「podman 会把自己叫 docker」。
   教训：凡是和外部程序打交道的判断，必须在真机上跑一遍。
3. **GUI 回归的点击断言，第一次用就抓到了。** I2 报告里它只是「建议 5」，
   做出来当天就省下了一整轮白跑。
