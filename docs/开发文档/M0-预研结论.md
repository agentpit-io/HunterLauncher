### 1.3 ⚠️ 四类错误 key 的响应**完全相同**（本轮最重要的负面结论）

四种输入各调一次 `quota` 与 `models`：

| 输入 | HTTP | 响应体 |
|---|---|---|
| 格式错（`sk-totally-wrong-format-123`） | **401** | 见下 |
| 格式对但不存在（随机 `hunt_tools_` + 32 位） | **401** | **与上一行逐字节相同** |
| 完全不带 `Authorization` 头 | **401** | **相同** |
| 空 `Bearer` | **401** | **相同** |

统一的响应体（`/api/saas/llm/*`）：

```json
{"error":{"message":"这个地址是 HunterCode 的内置模型额度网关，需要一把 Hunter 平台 key 才能用。到 https://hunter.agentpit.io/dev/api-keys 免费申请（约 30 秒），把 hunt_tools_ 开头的那串填进「大模型 API Key」即可 —— 它和工具、数据源共用同一把，不需要第二把。也可以在设置里改用你自己的大模型 key（任何 OpenAI 兼容服务都行）。","type":"invalid_api_key","code":"hunter_key_required","param":null,"apply_url":"https://hunter.agentpit.io/dev/api-keys"}}
```

**「已吊销」没有实测**（会污染生产数据，红线 6 只允许新增一条 key 记录）。
但从 hermes 代码可以确定结果一样：`saas_key.verify()` 的 SQL 是
`WHERE key_hash = %s AND status = 'active'` —— 吊销的 key 查不到行，
与「不存在」走**同一个** `return None` 分支，因此响应必然也是同一个 401。

**对 M2 的影响**：方案第 18 节要求 `E_KEY_INVALID` 区分四种原因，**网关侧做不到**。M2 的实现定为：

1. **本地先判格式**：`key.starts_with("hunt_tools_") && key.len() == 43` —— 不满足就直接报「key 格式不对，应该是 `hunt_tools_` 开头的 43 位字符串」，**不发请求**；
2. 格式对、网关回 401 → 统一文案「这把 key 网关不认（可能填错了、或者已被吊销）」+ 申请链接；
3. **不能**假装区分出「已吊销」——那会是编造的诊断结论。

已列入 [待办池](待办池.md) **P0-1**，并在本文 §8「需上游配合」提出诉求。

### 1.4 一把 key 通吃三个网关（**产品承诺成立**）

同一把 key，三个网关各调一次：

| 网关 | 请求 | HTTP | 响应 |
|---|---|---|---|
| 大模型 | `GET /api/saas/llm/quota` | **200** | 见 §1.2 |
| 工具 | `GET /api/saas/verify` | **200** | `{"ok":true,"scopes":["tools"],"quota_daily":null,"used_today":0}` |
| 数据 | `GET /api/saas/data/api/v1/kline/600519?period=daily&limit=3` | **200** | 真实 K 线数组（见下） |

```
$ curl -H "Authorization: Bearer hunt_tools_****" \
    "https://hunter.agentpit.io/api/saas/data/api/v1/kline/600519?period=daily&limit=3"
[{"ts":"2024-09-18T16:00:00+00:00","open":1262.0,"high":1292.88,"low":1245.83,
  "close":1261.0,"volume":59988,"amount":7623739900.0}, ...]
HTTP 200 · 1.409s
```

数据网关是**路径白名单**制（`saas_data.py` 的 `_ALLOWED_PREFIXES`），不在白名单里的路径回 **403**：

```
$ curl ... https://hunter.agentpit.io/api/saas/data/health
{"error":"path_not_allowed","path":"health","message":"health 不在数据网关白名单里。"}

```

白名单：`api/v1/news`、`api/v1/cninfo`、`api/v1/quote/`、`api/v1/kline/`、`api/v1/financial/`、
`api/v1/orderbook/`、`api/v1/money_flow/`、`api/v1/lhb/`、`api/v1/fund_holders/`、
`api/v1/governance/`、`api/v1/peers/`、`api/v1/research/`。

> 注意：数据网关的 401 体与大模型网关**不同结构**（扁平 `{"error":"hunter_key_required","message":...}`，
> 不是嵌套的 `{"error":{...}}`）。M2 的错误解析要按网关分别处理，不能共用一个反序列化结构体。

### 1.6 额度用尽（402）**未实测**

要触发需要烧掉 30 万 token，本轮没做。从 hermes 代码（`saas_llm.py` 的 `_deny_to_response`
+ `llm_quota.py`）可确定：日额度用尽 → `code: "daily_quota_exceeded"`、

## 三、hunter-community 的 compose 与配置（方案 §7 / 附录 E）

来源：`agentpit-io/hunter-community` 最新 Release **`v1.2.0`**（发布于 2026-09-19T09:47:29Z）。

### 3.1 服务清单（六个服务，全部实测自运行中的栈）

| 服务 | 镜像 | 宿主端口 → 容器端口 | 健康检查 | 卷 |
|---|---|---|---|---|
| web | `ghcr.io/agentpit-io/hunter-community-web:1.2.0` | `3100 → 3000` | **镜像内置**：`curl -fsS http://127.0.0.1:3000`（30s/5s/start 15s/retry 3） | `hunter_secrets:ro` |
| api | `ghcr.io/agentpit-io/hunter-community-api:1.2.0` | `8100 → 8000` | **镜像内置**：`curl -fsS http://127.0.0.1:8000/api/health`（30s/5s/start 10s/retry 3） | `hunter_user_skills`、`hunter_packages`、`hunter_secrets` |
| opencode | `ghcr.io/agentpit-io/hunter-community-opencode:1.2.0` | `3921 → 3901` | **镜像内置**：`curl -fsS -u $OPENCODE_SERVER_USERNAME:$OPENCODE_SERVER_PASSWORD http://127.0.0.1:3901/` | `hunter_opencode_data`、`hunter_secrets:ro` |
| llm-shim | `ghcr.io/agentpit-io/hunter-community-llm-shim:1.2.0` | **不对外** | **镜像内置**：`python3 -c urllib.request.urlopen('http://127.0.0.1:3999/health')`（15s/5s/start 5s/retry 5） | — |
| postgres | `postgres:16-alpine` | `5442 → 5432` | **compose 里写的**：`pg_isready -U $POSTGRES_USER` | `hunter_pg_data` |
| redis | `redis:7-alpine` | `6479 → 6379` | **compose 里写的**：`redis-cli ping` | `hunter_redis_data` |

**关键发现：`docker-compose.yml` 里只有 postgres 和 redis 写了 `healthcheck:`，另外四个服务的健康检查烧在镜像里。**
所以启动器**不能**靠读 compose 文件判断「哪些服务有健康检查」，必须读 `docker compose ps --format json` 的 `Health` 字段。

证据（`docker inspect -f '{{json .Config.Healthcheck}}'`）：

```
hunter-community-api-1   {"Test":["CMD-SHELL","curl -fsS http://127.0.0.1:8000/api/health || exit 1"],"Interval":30000000000,"Timeout":5000000000,"StartPeriod":10000000000,"Retries":3}
hunter-community-web-1   {"Test":["CMD-SHELL","curl -fsS http://127.0.0.1:3000 || exit 1"], ...}
hunter-community-opencode-1 {"Test":["CMD-SHELL","curl -fsS -u ${OPENCODE_SERVER_USERNAME:-opencode}:${OPENCODE_SERVER_PASSWORD:-changeme} http://127.0.0.1:3901/ || exit 1"], ...}
hunter-community-llm-shim-1 {"Test":["CMD-SHELL","python3 -c \"import urllib.request;urllib.request.urlopen('http://127.0.0.1:3999/health',timeout=3)\""], ...}
```

**`/api/health` 存在且可用**（api 镜像的健康检查就在打它），所以方案第 5.2 节
「对 `localhost:3100/api/health` 做 HTTP 探测」可行 —— 但要注意那是 **api 的 8100**，不是 web 的 3100。

实测响应里还有一个意外收获：

```
$ curl http://127.0.0.1:8100/api/health
{"status":"ok","service":"hunter","hunter_api_key":"missing"}
HTTP 200 · 0.010s
```

`hunter_api_key` 字段会告诉调用方**这个实例到底有没有配上 key**。
M3 写完 `.env` 起完容器后，可以用这一个字段确认「key 确实落进容器了」，
而不是只看服务健康就当成功 —— 少一整类「服务全绿但工具全 403」的排查。
（测试机旧栈是 `missing`，因为它的 key 配在数据库里而不是 `.env`。）

web 与 llm-shim 也实测可用：`http://127.0.0.1:3100/` → HTTP 200；
llm-shim 容器内 `http://127.0.0.1:3999/health` → `{"ok":true}`。

启动依赖顺序（compose `depends_on`）：`postgres`+`redis` healthy → `api` healthy + `llm-shim` healthy → `opencode`；`web` 只 `depends_on: api`（不等健康）。

## 五、Docker 进度输出与状态解析（方案 §5.2）

测试机：Docker **29.8.1**（containerd 快照器 + overlayfs）· Compose **v5.5.1**。
测试方法：拉一个本机从未有过的镜像（`golang:1.22-bookworm`）保证是**冷拉**。

> 踩过的坑：`docker rmi` 在 containerd 镜像存储下不清内容存储，重拉是秒级且**不产生任何进度事件**。
> 第一次试验就是因为这个得出了「compose json 只有 2 行」的错误结论，换成从未拉过的镜像才拿到真实数据。

### 5.1 `docker compose --progress json pull` —— **选定方案**

`--progress` 的合法取值：`auto, tty, plain, json, quiet`。

冷拉一个 7 层镜像共 **457 行** JSON，字段全集：
`id` · `parent_id` · `status` · `text` · `details` · `current` · `total` · `percent`

| `text` | 行数 | 带 `current` | 带 `total` | 带 `percent` |
|---|---|---|---|---|
| `Pulling` / `Pulled`（镜像级） | 1 / 1 | — | — | — |
| `Pulling fs layer` | 7 | — | — | — |
| `Downloading` | **142** | **142** | **142** | **142** |
| `Download complete` | 8 | — | — | — |
| `Extracting` | **290** | 290 | **0** | 0 |
| `Pull complete` | 7 | — | — | ✅ 100 |
| `Already exists` | 1 | — | — | — |

真实行样例：

```json
{"id":"Image golang:1.22-bookworm","status":"Working","text":"Pulling"}
{"id":"4f4fb700ef54","parent_id":"Image golang:1.22-bookworm","status":"Working","text":"Pulling fs layer","details":"0B"}
{"id":"35af2a7690f2","parent_id":"Image golang:1.22-bookworm","status":"Working","text":"Downloading","details":"1.049MB","current":1048576,"total":64394292,"percent":1}
{"id":"a492eee5e559","parent_id":"Image golang:1.22-bookworm","status":"Working","text":"Downloading","details":"42.99MB","current":42991616,"total":48479687,"percent":88}
{"id":"a492eee5e559","parent_id":"Image golang:1.22-bookworm","status":"Working","text":"Extracting","details":"1B","current":1}
{"id":"1451027d3c0e","parent_id":"Image golang:1.22-bookworm","status":"Done","text":"Pull complete","details":"0B","percent":100}
{"id":"Image golang:1.22-bookworm","status":"Done","text":"Pulled"}
```

**这一条满足视觉稿第 2 张的全部需要**：`parent_id` 就是 `"Image <完整镜像引用>"`，
按它分组即可得到每个镜像一条进度条；层级 `current`/`total` 求和得到每镜像百分比；
所有镜像求和得到总百分比与「1.36 GB / 2.12 GB」那一行。

**M2 的解析方案**（定稿）：

```
docker compose -p hunter -f docker-compose.yml -f docker-compose.launcher.yml \
  --progress json pull
```

- 逐行读 stdout，`serde_json` 解析，**解析失败的行直接丢弃不报错**（未来 compose 加新行型不会炸）
- 按 `parent_id` 分组到镜像；维护 `HashMap<layer_id, (current, total)>`
- 每镜像百分比 = `Σcurrent / Σtotal`；**总大小从 manifest 预先算好**（§4.1 已证明可读），
  这样进度条从第一秒就有正确的分母，不用等所有层的 `total` 都到齐
- `text == "Pull complete"` → 该层记为 100%；`text == "Pulled"` → 该镜像完成
- `--progress` 是 **`docker compose` 的全局参数**，要写在 `pull` 前面

### 5.2 ⚠️ `docker pull` 在非 TTY 下完全没有进度

```
$ docker pull traefik:v2.10          # stdout 不是终端时
v2.10: Pulling from library/traefik
Digest: sha256:6341b98aec5ec8969b99e9730f4c5b22cca3103d42b6bbe4b7a3c910758fe565
Status: Downloaded newer image for traefik:v2.10
docker.io/library/traefik:v2.10
```

就这四行，**没有任何逐层信息**。`docker pull` 也**没有** `--progress` 参数
（`docker pull --help` 只有 `--platform` 和 `-q/--quiet`；`--progress` 是 `docker compose` 独有的）。
启动器是拿管道读子进程 stdout 的，必然是非 TTY —— 所以方案第 5.2 节的
「`docker pull` 逐镜像 + `--progress plain`」这条路**走不通**，除非在 Rust 侧分配伪终端再解析 ANSI，没必要。

作为对照，Engine API `POST /images/create` 的 JSON 流确实带精确字节
（`{"id":"7c897fde901f","status":"Downloading","progressDetail":{"current":1048576,"total":248755360}}`），
但它要求直连 docker socket / Windows 命名管道，三平台路径各不相同 ——
正是方案第 2 节选 CLI 的原因。**既然 compose 的 json 进度已经够用，就不引入这条依赖。**

其余两种格式供参考：`--progress plain` 是人读的文本行（`" 35af2a7690f2 Downloading 15.73MB"`，
**没有分母**，解析不出百分比）；`--progress quiet` 是**零输出**。

`docker compose pull` 自己的选项：`--dry-run`、`--ignore-buildable`、`--ignore-pull-failures`、
`--include-deps`、`--policy missing|always`、`-q/--quiet`。
其中 **`--ignore-pull-failures`** 对 M2 的「失败重试/换源」有用：可以先尽量拉，再针对失败的单独重试。

### 5.3 `docker compose ps --format json` 的字段

每个容器一行 JSON（**不是**一个 JSON 数组）。完整字段：

`Command` · `CreatedAt` · `Engine` · `ExitCode` · **`Health`** · `ID` · `Image` · `Labels` ·
`LocalVolumes` · `Mounts` · `Name` · `Names` · `Networks` · `Ports` · `Project` · **`Publishers`** ·
`RunningFor` · **`Service`** · `Size` · **`State`** · `Status`

启动器要用的（运行面板 + 启动轮询）：

```json
{"Name":"hunter-community-api-1","Service":"api","State":"running","Health":"healthy","ExitCode":0,
 "Publishers":[{"TargetPort":8000,"PublishedPort":8100,"URL":"0.0.0.0"},
               {"TargetPort":8000,"PublishedPort":8100,"URL":"::"}]}
```

实测六个服务全部 `State: running` / `Health: healthy`。

三个坑：

1. **`Publishers` 每个端口有两条**（IPv4 `0.0.0.0` 和 IPv6 `::`）。运行面板显示端口时要去重，否则视觉稿第 3 张的服务网格会出现重复端口。
2. **没有容器时 stdout 是空字符串，退出码仍是 0**。解析器要把空输入当成「还没起」，不能当错误（[待办池](待办池.md) P1-6）。
3. `llm-shim` 不发布端口，它的 `Publishers` 是 `[{"TargetPort":3999,"PublishedPort":0,"URL":""}]` —— `PublishedPort: 0` 要显示成「内部」而不是端口 0。

### 5.4 Docker / daemon 检测（方案 §5.1）

| 场景 | 命令 | 退出码 | stdout | stderr |
|---|---|---|---|---|
| 一切正常 | `docker version --format json` | **0** | `{"Client":{...},"Server":{"Version":"29.8.1",...}}` | — |
| **daemon 没起** | 同上 | **1** | `{"Client":{...},"Server":null}` ← **Client 段仍在** | `failed to connect to the docker API at unix://...; check if the path is correct and if the daemon is running: ...` |
| 没装 docker | 同上 | — | — | 进程起不来（`ENOENT`） |

**判定逻辑（M2 定稿）**：进程起不来 → `E_DOCKER_MISSING`；
退出码非 0 但 stdout 能解析出 `Client` 且 `Server` 为 `null` → `E_DAEMON_DOWN`；
退出码 0 → 读 `Server.Version` 比最低版本。
**关键：不能只看退出码**，退出码 1 的两种含义靠 `Server == null` 区分。

compose 插件：`docker compose version --format json` → `{"version":"v5.5.1"}`。
daemon 不可达时 `docker compose ps` 退出码 1，stderr 同上。

方案的目标是「安装包 ≤ 40 MB」。最小模板只有 2.3 MB，**即使加上完整的前端、字体（本地打包）
与全部插件，离 40 MB 也有很大余量**。技术选型（Tauri 而不是 Electron）在体积上成立。

**对 CI 的影响（M4）**：GitHub Actions 的 `ubuntu-latest` 是 2 核 / 7 GB / 14 GB SSD，
与测试机规格基本一致，所以可以直接按实测值定预算：

- 单平台冷构建按 **15 分钟**算，三平台矩阵并行则总时长仍约 15–20 分钟；**job timeout 设 40 分钟**留余量
- 峰值内存 1.64 GiB，7 GB 的 runner 绰绰有余，**不需要**调 `CARGO_BUILD_JOBS` 限并发
- `target/` 1.5 GB，14 GB 的 runner 磁盘够用，但**必须**配 `Swatinem/rust-cache`，否则每次 PR 都等 15 分钟

### 6.3 ⚠️ 踩到的坑：AppImage 打包需要 `xdg-open`，默认镜像里没有

第一次 `pnpm tauri build`（只装了官方文档列的依赖）时，`.deb` 与 `.rpm` 都打出来了，
**AppImage 在最后一步失败**：

```
    Bundling hunter-probe_0.1.0_amd64.deb   （成功）
    Bundling hunter-probe-0.1.0-1.x86_64.rpm（成功）
    Bundling hunter-probe_0.1.0_amd64.AppImage
failed to bundle project: xdg-open binary not found /usr/bin/xdg-open: No such file or directory (os error 2)
       Error failed to bundle project: xdg-open binary not found
```

Tauri 官方的 Linux 依赖清单里**没有** `xdg-utils`，但 AppImage 的 bundler 要把 `xdg-open`
打进 AppDir。装上 `xdg-utils`（以及运行 AppImage 需要的 `fuse` / `libfuse2t64`）后重打通过。

**这条对 M4 是硬性的**：CI 的 Linux job 必须装 `xdg-utils`，否则 `.deb` 出得来、
`.AppImage` 静默缺失 —— 而这是个**只在打包最后一步才暴露**的错误，本地只打 deb 的话永远发现不了。

### 7.3 托盘：能建，但在纯 Xvfb 下**看不见**

代码层面（`tauri = { features = ["tray-icon"] }` + `TrayIconBuilder`）的编译与构建结论见 §7.4。

**运行层面的结论**：Xvfb 是一个裸 X server，**没有任何 StatusNotifierItem host**
（没有 GNOME Shell / KDE plasmashell / `snixembed` 之类的托盘宿主）。
`libayatana-appindicator3` 走的是 D-Bus 的 `org.kde.StatusNotifierWatcher`，
无宿主时它**不会报错，只是图标不出现** —— 这正是「托盘静默失效」这类 bug 难查的原因。

**对 M3 的要求**（托盘是那一期的交付物）：

1. **不能靠 Xvfb 截图验收托盘**。托盘只能靠「`TrayIconBuilder::build()` 返回 `Ok`」+ 代码审阅确认，
   报告里必须写明「托盘图标在无桌面环境下未能目视确认」。
2. **托盘必须是增强而不是唯一入口**。方案第 5.8 节把「启动 / 停止 / 重启 / 日志 / 反馈」
   全放在托盘里，而 Linux 服务器、部分精简桌面、以及 GNOME 40+ 原生（不装扩展）都没有托盘宿主 ——
   这些功能**必须在主窗口里也各有一个入口**。视觉稿第 3 张的运行面板右下角已经有
   「停止 / 重启 / 日志 / 反馈」四个按钮，正好满足这一条，照着做即可。
3. `.deb` 要把 `libayatana-appindicator3-1` 列进 `Depends`（见 §7.5：Tauri 自动生成的 `Depends`
   里**没有**它，需要在 `tauri.conf.json` 的 `bundle.linux.deb.depends` 手动补）。

## 八、需上游（hunter-community / hermes）配合的事

总控规则：本项目**不改** hunter-community，需要配合的写在这里，由上游自己决定改不改。

| # | 诉求 | 对象 | 为什么 | 不改的话启动器怎么办 |

| 国内网络下 GHCR 的真实速度 | 测试机在美国 GCP，测了也不代表国内 | 无法在现有基础设施上测。若用户能提供一台国内机器，可补测 |

**本轮踩过、值得记下的坑**：

1. `docker rmi` 在 containerd 镜像存储下不清内容存储 —— 重拉是秒级且零进度事件。测进度解析必须用**本机从未拉过**的镜像。
2. `ssh ... | tee log | head -N`：`head` 关管道会 SIGPIPE 把远端脚本打断，日志是截断的。要么在远端 `> log` 再 `cat`，要么不加 `head`。
3. 从开发机（34.133.47.117）查 crates.io API 一律返回空，同样的 curl 在测试机上正常。疑似 UA 或出口 IP 被限速（待办池 P2-4）。
