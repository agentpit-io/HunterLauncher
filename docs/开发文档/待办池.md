# HunterLauncher · 待办池

> 发现了、但当期里程碑不做的事。迭代轮（I1–I3）从这里取活。
> 优先级：**P0** = 会让用户跑不起来或有安全风险，必须做；**P1** = 明显影响体验，应该做；**P2** = 锦上添花。
> 每条都要写清「为什么现在不做」，否则会变成永远不做。

最后更新：2026-09-20（M2 收尾）

## P0

| # | 事项 | 背景 | 为什么现在不做 |
|---|---|---|---|
| P0-5 | **两个工作目录会抢同一个 compose 项目名 `hunter`** | M2 测试时用另一个 `HUNTER_HOME` 跑了一次安装，`docker compose -p hunter up -d` 把已经装好的那一套连配置带端口一起顶掉了（数据卷没丢，重装一次就回来）。真实用户也可能撞上：换过工作目录、或者同时开了两个启动器 | 拦截逻辑不难（`up -d` 前比对现有容器的 `com.docker.compose.project.config_files` 标签，不一致就停下来问用户），但 M2 已经到收尾，改动会影响刚测完的启动路径。M3 做托盘/升级时一起加 |
| P0-1 | **key 无效的四种原因无法区分** | 网关对「格式错 / 不存在 / 已吊销 / 未带 key」返回**字节级完全相同**的 401（`code: hunter_key_required`）。方案第 18 节的 `E_KEY_INVALID` 要求区分原因给不同文案，做不到 | 需要上游网关配合加错误码。M2 先按「本地判格式 + 401 一律当无效」实现，并把上游诉求写进 M0 报告「需上游配合」 |
| P0-2 | **额度用尽（402）的响应体没有实测过** | 只从 hermes 代码读到 `code=daily_quota_exceeded` / `type=insufficient_quota`。实测要烧掉 30 万 token，M0 没做 | 代价太大。M2 做 key 校验时，用 hermes 上 `llm_key_admin.sh --quota <id> 1` 把测试 key 额度临时压到 1 token 触发 402，测完改回 |
| P0-4 | **运行面板有两张卡片没有数据来源** | 视觉稿第 3 张的「今日对话 17 次 · 深度分析 3 次」与「晨报 已开启」，依赖方案第 13 节的 `/api/system/metrics/daily`，而该接口**实测不存在**（M0 §3.6）。红线 1 禁止编数字 | M3 做运行面板时才需要决定。届时要么显示 `—` 并给原因，要么去掉这两张卡 —— 需用户拍板 |
| P0-3 | **`.env.example` 里的 `HUNTER_INTERNAL_KEY=hunter-internal-local` 是公开字符串** | compose 的注释明确说不该有兜底值，但 `.env.example` 仍然预填了它。启动器照抄会把一个写在公开仓库里的 secret 带进每个用户的部署 | 启动器生成的 `.env` 留空即可绕过（M3 会这么做）。但上游的 `.env.example` 仍然误导手工部署的用户，需要提 issue |

## P1

| # | 事项 | 背景 | 为什么现在不做 |
|---|---|---|---|
| P1-9 | **「完全干净的机器上首次安装要多久」测不出来** | 测试机上跑着的 hunter-community 旧栈用着同样的六个镜像，层全在本地内容存储里。要造出干净条件必须把旧栈 `down` 掉再 `docker rmi`，而旧栈没有 `.env`（不知道当初怎么起的），`down` 之后不保证能原样恢复 | 风险不值得。M2 用「同样六个镜像、换一个本机没有的 tag」冷拉，测出 61 秒 / 网卡实收 408 MiB 的有效吞吐；完整 849 MB 的时间只有推算值。要真数字得换一台干净机器 |
| P1-10 | **自带模型 key 模式没有拿真实第三方 key 跑过完整安装** | 参数校验、早退、DeepSeek 自动 sanitize 都有单测，连通性检查的代码路径也审过，但手上没有 DeepSeek / OpenAI 的 key，没法端到端验一次 | 要用户提供一把第三方 key。写进「需要用户决定」 |
| P1-11 | **额度用尽（402）与限流（429）仍未实测**（P0-2 的延期） | 要把测试 key 的额度压到 1 token 才能触发，会影响这把 key 的后续使用 | M2 全程都在用这把 key 做真实安装与真实对话，压额度会把自己卡死。迭代轮里单独找一个时间窗做 |
| P1-12 | **拉取页「解压中」那一段没有在慢机器上验证过体感** | 本机已有层时几乎瞬间跳过 | 需要一台层全都没有的机器，同 P1-9 |
| P1-7 | **Windows 上自绘的三个圆点在标题栏左侧，与系统习惯相反** | 视觉稿把三个点画在左边（mac 风格），M1 按稿实现，Windows / Linux 都在左边。Windows 用户的肌肉记忆是右上角 | M1 的任务是「按视觉稿 1:1」，改位置等于改稿。M4 发布前按平台加一个 `order` 反转即可，顺手把关闭按钮的悬停色也按平台调 |
| P1-8 | **窗口是直角的，视觉稿的窗体是圆角** | `decorations(false)` 之后窗口没有系统圆角；要做圆角得开窗口透明 + 依赖 WM 合成，Linux 上不是所有桌面环境都支持，做不好会出现黑色直角 | M1 不引入透明窗口这类会影响稳定性的改动。M4 评估三平台的实际表现后再定 |
| P1-0 | **AppImage 74 MiB,超出「≤ 40 MB」目标近一倍** | 实测 77,548,024 B。原因是要自带整套 WebKitGTK(AppDir 的 usr/lib 就 232 MB),与代码量无关,压不下去。`.deb` 只有 2.28 MiB | M0 已确认这是格式的固有代价,不是 bug。M4 定发布策略时按格式分开设目标,README 不能笼统写「20–40 MB」 |
| P1-1 | **`Extracting` 阶段没有百分比** | `--progress json` 的 `Extracting` 行只有 `current`，没有 `total`，算不出解压进度。视觉稿里镜像进度条在解压阶段会卡住不动 | 属于 M2 的 UI 决策：解压阶段改显示「解压中」而不是百分比条，或按「下载 90% + 解压 10%」加权 |
| P1-2 | **没有国内镜像源** | 阿里云 ACR 与 Docker Hub 实测都是 `denied`，只有 GHCR 一个源。视觉稿第 2 张写的「已自动选择最快的镜像源（阿里云·杭州）」目前是做不到的 | 建源要花钱、要用户决策。M2 先做成「只有 GHCR + 可手填自定义 registry」，并在报告里列为需用户决定 |
| P1-3 | **Release 没有 assets，compose 只能走 raw.githubusercontent** | 方案第 5.2 节假设从 Release 资产下载 compose，实测 `v1.2.0` 的 `assets` 是空数组 | M3 改成 raw 按 tag 取 + 随启动器内置一份兜底。另可给上游提「Release 挂 compose 资产」的 issue |
| P1-4 | **离线包导入（`docker save` / `load`）未验证** | 方案第 9 节承诺给内网用户的能力，M0 没测 | 不在 M0 范围。M2 或迭代轮验证 |
| P1-5 | **Podman 兼容性完全未验证** | 方案把 Podman 列为「实验支持」 | 测试机上没装 Podman，装了会和 Docker 抢资源。迭代轮单独验证 |
| P1-6 | **`compose ps --format json` 在无容器时输出空** | 退出码仍是 0、stdout 为空字符串。解析器要能吃空输入，不能当成错误 | 实现细节，M3 写解析器时注意即可 |

| # | 事项 | 背景 | 为什么现在不做 |
|---|---|---|---|
| P2-8 | **字体子集没有「文案里的字都在子集里」的 CI 校验** | 子集是按当前源码里出现过的字生成的（853 字符 / 717 汉字）。以后加了新文案忘了重跑 `scripts/build-fonts.py`，新字会回落到系统字体 —— 在有中文字体的机器上看不出来 | 需要在 CI 里加一步「扫源码字符集 ∈ woff2 的 cmap」。M4 做发布流水线时一起加 |

| P2-11 | **`launcher.toml` 与覆盖文件是 644** | 目录已经收成 700（M2 加的），这两个文件里也确实没有 secret（key 只在 600 的 `.env` 里），但统一收成 600 更省心 | 不影响安全底线，顺手改的时候一起做 |
| P2-12 | **Podman 仍未验证** | M2 写了识别与「实验支持」的提示文案，但测试机上没装 Podman | 装了会和 Docker 抢资源，同 M0 的判断 |
