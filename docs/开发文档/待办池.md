## P0

**I4 之后 P0 回到零。** 本轮开工时有一个 **P0**，而且不是自审找出来的 ——
是**用户在自己的 Mac 上第一次真机运行 0.1.3** 当场撞出来的：
装着 OrbStack 却报「没有找到 Docker」。根因是 macOS GUI 程序拿不到 shell 的 PATH，
和用户装没装毫无关系（详见 [I4-迭代报告.md](I4-迭代报告.md) 第二节）。**本轮已修。**

这件事的教训值得记一笔：**三个里程碑 + 三轮迭代的自审都没有找到它，
因为开发机与测试机都是 Linux，而这个问题只在 macOS 的 GUI 启动路径上出现。**
「没有真机」不是一句免责声明 —— 它是一类问题的温床。

I1 清零之后，I2、I3 各通读了一遍代码找 P0，都没有找到新的。
I3 抓出来的几条（额度用尽不提示、Podman 误判、更新页文案自相矛盾、`--tray-menu` 打错字返回 0、
`--key-file` 不查权限、一条跟着机器状态走的单测）**都不是 P0**：
不影响功能正确性，也不是远程可打的洞 —— 但「该说的话没说」这一类离红线 1 很近，所以都当轮修了。

> **本项目自己能做的事已经基本做完。** 待办池里剩下的条目，要么需要用户拍板、
> 要么需要花钱、要么需要一台本项目拿不到的机器（Windows / macOS / 干净机器）。
> 详见 [I3-迭代报告.md](I3-迭代报告.md) 第十节「可交付，等待用户决定」。

**I5 之后 P0 又回到零。** 本轮开工时又有一个 **P0**，来源和上一次一模一样 ——
**用户在自己的 Mac 上真机运行 0.1.4** 撞出来的：端口探测把被占死的端口判成了空闲。
根因是 `std::net::TcpListener::bind` 在 Unix 上默认开 `SO_REUSEADDR`，
而 macOS 的 BSD 语义下这个选项会让「绑 `127.0.0.1:P`」在「`*:P` 已被占」时照样成功；
Linux 内核不会。**连着两轮的 P0 都是「只有 macOS 才错」的那一类。**

这一次专门为它加了一条 CI 回归：macOS runner 上真起一个带 `SO_REUSEADDR` 的 `*:port` 监听，
断言探测判它为「占用」（`ports::tests::带_so_reuseaddr_的通配监听必须被判为占用`）。
**「没有真机」的补救办法不是更仔细地读代码，是把那台机器的差异写成一条会红的测试。**

**I6 之后 P0 再次回到零。连着三轮了，来源一模一样 —— 用户在自己的 Mac 上跑上一版。**
这一次是 I4 那个 PATH 问题的**下一层**：I4 让启动器找得到 docker，但 docker 自己
去 `$PATH` 上找 `docker-credential-osxkeychain` 时，用的还是子进程继承的那份受限 PATH。
**修好一层不等于修好一类** —— 「谁的 PATH」这件事，凡是会 `exec` 别人的程序都要问一遍。
本轮也把它写成了 CI 的 macOS 回归（`runtime::env::tests`），并且**在测试机上用真的
0.1.5 二进制把失败复现了一次**（`docs/开发文档/I6-证据/a-015.log`）——
以后再有「只有 mac 才炸」的猜测，先问一句「能不能在 Linux 上造出同样的现场」。

**I10 之后 P0 回到零。本轮开工时那个 P0 是第六次来自「用户在自己的 Mac 上跑上一版」。**
这一次的根因**不在我们的代码里**，在我们下发的那份虚拟机镜像里：
Ubuntu 24.04 把 systemd-resolved 拆成了单独的包，minimal 镜像不装它，
而基础根文件系统里那条 `/etc/resolv.conf → …/stub-resolv.conf` 符号链接照旧躺着 ——
**链接在，被链接的人不在**，虚拟机从出生起就没有 DNS。

这一条的教训和前五次不同：前五次都是「只有那台机器上才会错的代码」，
这一次是**我们把一个第三方产物当成黑盒交付了**。清单里钉死了它的
版本、文件名、sha256、sha512 —— 钉住了「拿到的是不是同一个文件」，
但没有人问过「这个文件里装的是什么」。I10 花了不到一小时把它挂起来逐条查清
（`I10-证据/0-镜像为什么没有DNS-逐条实查.log`），答案一目了然。
**下一次往清单里加一个几百 MB 的第三方镜像时，先把它解开看一眼。**

**I8 之后 P0 仍然是零，但本轮的来源第四次是「用户在自己的 Mac 上跑上一版」。**
0.1.7 装到一半停在一张「请在终端里执行 `brew install --cask orbstack`」+「我执行完了，继续」的卡片上。
两个根因：① 虚拟机系统镜像是 colima **自己**直连 GitHub 去下的，那一次下载不在我们控制里；
② 用户系统设置里配着代理，启动器（和它拉起来的每一个子进程）谁都没去看一眼。两条都修了。

这一次还多出一条**自审抓不到、回归抓到了**的：本轮把「Sensitive 要用户点一下」那道门拿掉之后，
「方向该由用户定」的那一类动作（`reuse_existing_hunter`）跟着裸奔了 ——
模型提一句「你已经有一套了，用它吧」，全自动档下就真的不装了。
抓到它的不是通读代码，是**把 I5–I7 的回归原封不动再跑一遍**
（详见 [I8-迭代报告.md](I8-迭代报告.md) 6.3）。
**回归不只是确认「没搞坏」，它也会抓出「新加的东西自己有个洞」。**

**I9 之后 P0 回到零。本轮的来源第五次是「用户在自己的 Mac 上跑上一版」，
但这一次的肇事者是我们自己 —— 0.1.8 被它自己上一次留下的残骸骗了。**

`~/.hunter/runtime/bin/docker` 与 `colima` 都在（0.1.7 装了一半留下的），
0.1.8 把它们认成了「用户装的 Docker / Colima」，于是：内置主线一步没走到；
执行了一条不带 `--profile`、不带 `COLIMA_HOME` 的裸 `colima start`，
**在用户家目录里建出了一台和 Hunter 毫无关系的虚拟机（1.4 GB）**；
修好之后不接着装；那 5 分钟里所有 `docker ps` 都打在 `/var/run/docker.sock` 上。

这一轮的教训和前四轮不太一样，值得单记一笔：

* **前四次是「那台机器和我们的不一样」，这一次是「那台机器上有我们自己的上一版」。**
  真机不只带来平台差异，还带来**时间**：用户机器上叠着我们自己历次失败的沉积层。
  「全新机器能装上」和「装过一半的机器能装上」是两道题。
* **判定分散在各处就一定会各自猜错。** 本轮把「现在生效的运行时是谁」收成一个模块
  （`runtime/effective.rs`），三个 P0 里有三个是同一个缺口的三种表现。
* **守卫要挂在最后一刻。** 0.1.8 那条闯祸的命令是**动作表自己规划出来的** ——
  提案那一侧没有任何人觉得它有问题，所以只在提案侧设卡是拦不住的。
  I9 把 colima 的隔离检查挂到了 `proc` 层（真正 `spawn` 之前），
  不管命令是谁写的、走哪条路，都要先回答「你动的是哪一台虚拟机」。

以及一条真跑才撞得出来的（[I9-迭代报告.md](I9-迭代报告.md) 6.1）：
**我们的残骸会把用户一套好好的 Docker 弄坏** —— `DOCKER_CONFIG` 原来是
「内置运行时装着就用它那一份」，于是残骸里那个坏掉的 compose 插件被用上了。
读代码时那一行看起来完全合理。
