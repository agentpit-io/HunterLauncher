## 二、设计令牌（要求 2）

完整清单在 [`docs/design/设计令牌.md`](../design/设计令牌.md)，这里只说方法与几个关键结论。

**方法**：写了 [`scripts/sample-mockup.py`](../../scripts/sample-mockup.py)，对三张视觉稿逐像素采样 ——
纯色区域取众数（避开 JPEG 噪点），文字取区域内最亮像素（抗锯齿的峰值最接近真实字色），
尺寸沿行/列扫亮度跃迁找边界。**视觉稿是 2 倍图**（2360×1520 对应约 1180×760 逻辑像素），
所有像素测量值 ÷2 才是令牌值。这个脚本提交进了仓库，改令牌前可以重跑对账。

**四层底色**（同色相的四级明度）：

| 令牌 | 值 | 用在哪 |
|---|---|---|
| `--hl-bg-app` | `#05080f` | 窗外画布 |
| `--hl-bg-window` | `#0a101c` | 窗口、内容区、标题栏 |
| `--hl-bg-sidebar` | `#0b0f1a` | 左侧步骤条栏 |
| `--hl-bg-card` | `#0f1626` | 卡片、输入框、服务格子 |
| `--hl-bg-log` | `#090d16` | 日志框（比窗口还暗一档） |

**琥珀金 `#daa442`**。两个半透明变体是**反解**出来的，不是猜的：
「已验证」按钮底实测 `#232220`，按 `0.12×218 + 0.88×10 = 35 = 0x23` 反推，正好是 12% 透明度叠在窗口底色上；
K 线金蜡烛实测 `#574827`，同法反推是 36%。

**一个容易漏的事实：视觉稿里「健康 / 运行中」的状态点用的是琥珀金，不是绿色。**
实现照做了；绿色 `#35c08a` 只留给「完成」这类一次性结果。

**七档文字色**：`#edf3fb`（主标题）→ `#bfcae2`（镜像名、环境值）→ `#8ea6c2`（正文）→
`#94a2b8`（日志、数值）→ `#8f95a3`（环境键、窗口标题）→ `#626d7f`（副标题）→ `#5f6b87`（版本号、未到步骤）。

**字体（本地打包，离线可用）**：

| | 字体 | 许可证 | 子集大小 |
|---|---|---|---|
| 中文无衬线 | Noto Sans SC（可变） | SIL OFL 1.1 | **199 KB** |
| 等宽 | JetBrains Mono（可变） | SIL OFL 1.1 | **30 KB** |

两个都是**可变字体的子集**：一个文件覆盖 400–700 全部字重，比每档一个文件小得多。
子集范围是「扫描 `src/` 下所有源码里出现过的字符」= 853 个字符（汉字 717 个）。
完整的 Noto Sans SC 一档就约 10 MB，三档会把 `.deb` 从 2.3 MB 撑到几十 MB；
而界面文案是有限且写死在仓库里的，子集足够。子集没覆盖的字（比如 Docker 报错里的生僻字）
按 font-family 回落到系统中文字体，不会变豆腐块。
**两份 OFL 许可证全文随字体提交进了 `src/assets/fonts/`**（OFL 要求随分发附带）；
OFL 允许子集化与嵌入，唯一的硬限制是不能改用保留字体名发布修改版 —— 子集不改名，不触发。

生成脚本 [`scripts/build-fonts.py`](../../scripts/build-fonts.py)（用 fontTools），
产物已提交，**CI 与日常开发都不需要跑它**。

**字号阶梯**由文字高度反推（汉字字面约占 0.88em）：12 / 13 / 14 / 15 / 17 / 20 / 24 / 26 / 30 / 42 px。
**间距**：12（卡片间隙）/ 20（卡片内边距）/ 24（侧栏左）/ 40（向导底）/ 44（面板左右）/ 48（向导左右）px。
**圆角**：卡片 12px、按钮与输入框 10px、角标 6px（由左上角圆弧每行的收敛速度反推）。
**结构**：标题栏 44px、侧栏 250px、步骤点 12px、状态点 8px、进度条 6px、输入框 45px、主按钮 40px。

### key 输入框与红线 2

`KeyInput` 里 key 只以受控值的形式活在内存里：失焦时渲染 `maskKey()` 的结果（长度与原串一致，界面不跳宽），
聚焦时才显明文方便用户核对。组件自己不打日志、不往外抛整串 key。
`src/lib/mask.ts` 另外提供 `maskKeyShort()`（写进文档/报告的 `hunt_tools_****`）与 `redact()`
（日志/诊断包脱敏，规则来自方案 §12.3：key、Bearer、邮箱、手机号、IP 末段），
两者都有单测覆盖，测试里用的是**编造的假 key**，不是测试机上那把真 key。

## 五、状态机（要求 5 · 方案 §4）

[`src/state/machine.ts`](../../src/state/machine.ts) 是**纯函数**：不 import React、不 import Tauri、不做副作用。

```ts
transition(state: State, event: Event): State
```

17 个状态 + 1 个带 `code` / `from` / `detail` 的 `Error` 状态；27 种事件。
配套三个派生函数：`pageOf()`（状态 → 渲染哪一页）、`stepperOf()`（状态 → 步骤条六项各是什么状态）、`isWizard()`。

**与方案 §4 的两处增补**（都写在源码注释里）：

1. 方案从 `Idle` 直接进 `CheckDocker`，这里在前面补了 `Welcome` —— 视觉稿的步骤条第一项就是「欢迎」。
2. 方案里 `Starting` 成功后直接进 `Ready`，这里中间补了 `Done` —— 打开浏览器应该是用户点的。

**一条刻意的设计**：收到当前状态下不该出现的事件时**原样返回**，既不抛异常也不乱跳。
界面上一个慢回来的异步结果不应该把用户从别的页面拽走。有专门的测试覆盖（18 个状态 × 27 个事件全排列）。

### 单测

`pnpm test` → **47 个测试全绿**（状态机 28 + 打码/脱敏 12 + 格式化 7）。

覆盖的不只是主路径：
- 18 × 27 全排列不抛异常、结果永远是合法状态；
- `transition` 不修改传入的状态对象（纯函数性质）；
- 每个错误码都有确定的重试去向、且重试后不会停在 `Error` 上；
- 没有 `detail` 时不写 `detail` 字段（避免 `{detail: undefined}` 这种脏对象）；
- 每个向导状态都能映射到步骤条的某一步（漏了会失败）；
- 「同一屏里三种步骤状态都会出现」—— 视觉稿要求的三种样式确实都被用到。

## 六、IPC 与演示数据（要求 6 · 红线 1）

[`src/lib/ipc.ts`](../../src/lib/ipc.ts) 是前后端唯一通道，两条路径：

- 正常构建 → 真的 `invoke` 到 Tauri command。M1 的 Rust 侧只有 `app_info`、三个窗口控制、
  `open_external` 是真实现，其余一律返回 `E_NOT_IMPLEMENTED: xx 要到 M2/M3 才实现`。
- `VITE_DEMO=1` 的开发构建 → 走 `demo.ts` 的演示数据，界面右上角常驻「演示数据」角标。

**除了失败时抛 `IpcError`，这一层不做任何降级**。页面拿到失败就显示「—」加上 `错误码 · 说明`。
`useAsync` 这个钩子的关键点也在这：**失败时 `data` 保持 `null`，不做假数据兜底**。

### 「发布包里不可能进入演示模式」是被机器保证的，不是靠人记住

三道闸：

1. `DEMO` 是编译期常量 `import.meta.env.VITE_DEMO === '1'`；不设这个变量时整个演示分支被摇掉。
2. `vite.config.ts` 顶部有断言：`HUNTER_CHANNEL=release` 时若还带着 `VITE_DEMO=1` **直接让构建失败**。CI 里 `HUNTER_CHANNEL=release` 是全局环境变量。
3. CI 有两步互为对照的检查：
   - 发布构建的 `dist/` 里 `grep HUNTER_DEMO_DATA_MARKER` **必须搜不到**；
   - 演示构建的 `dist-demo/` 里**必须搜得到** —— 这一步是为了保证上一步不是空跑。

开发机上实测：

```
$ pnpm exec vite build && grep -c "HUNTER_DEMO_DATA_MARKER" dist/assets/*.js
0
$ grep -o "hunt_tools_9f2c7a41[a-z]*" dist/assets/*.js
（无输出）
```

## 七、i18n（要求 7）

`src/i18n/zh-CN.ts` 是基准，`en.ts` 声明成 `const en: Dict = {...}`，
**类型上强制与中文字典逐字段对齐** —— 漏一个键、名字写错、或者把带参数的文案写成常量，都编译不过。

覆盖范围：向导 7 页的全部文案（标题、说明、字段名、按钮、提示、错误文案）、运行面板、
设置 / 日志 / 反馈三页、以及方案 §18 十二个错误码各自的标题与建议。
带参数的文案是函数（`versionLabel(v)`、`healthy(ok, total)`、`sizeLine(done, total)`），
不做字符串插值模板，少一层运行时解析也少一类拼错。

默认语言：中文。`guessLocale()` 只在系统语言明确不是中文时预选英文；
**演示数据模式固定中文**，否则截图对不上视觉稿。

### 三个圆点在三平台上的行为

```rust
#[cfg(target_os = "macos")]
win = win.decorations(true)
         .title_bar_style(tauri::TitleBarStyle::Overlay)
         .hidden_title(true);

#[cfg(not(target_os = "macos"))]
win = win.decorations(false);
```

- **macOS**：保留系统装饰，`Overlay` + `hidden_title` 让内容顶到窗口最上面，
  红绿灯仍是系统原生的那三颗。mac 用户对它们的位置、悬停时的符号、双击标题栏的行为都有肌肉记忆，
  自绘一套只会哪里都不对。前端拿到 `windowChrome: "native"` 后不画圆点，只在左边留 70px 空位。
- **Windows / Linux**：`decorations(false)`，前端自绘视觉稿上那三个点。
  语义与 macOS 一致：**左=关闭、中=最小化、右=最大化**；平时是 `#1c2b40` 的灰蓝（视觉稿里就是灰的），
  鼠标移到整组上才显出红 / 黄 / 绿。标题栏带 `data-tauri-drag-region`，拖拽照常。
  Windows 用户会觉得按钮在左边不习惯 —— 但这是视觉稿定的，本轮按稿实现，
  已列进待办池，M4 发布前可以按平台把这一组挪到右侧（同一个组件加个 `order` 就行）。

`windowChrome` 由 Rust 的 `cfg!(target_os = "macos")` 决定并通过 `app_info` 命令告诉前端，
不是前端靠 `navigator.platform` 猜的。

### Rust 侧只暴露了该暴露的

`src-tauri/capabilities/default.json` 按最小集给权限：
`core:default` + 窗口的 start-dragging / minimize / toggle-maximize / close / set-focus + `opener:allow-open-url`。
没有 fs、没有 shell、没有 http —— 这些要到 M2 / M3 用到时再逐条加。

`open_external` 只放行 `https://` 与 `http://localhost` / `http://127.0.0.1`，
防止这个命令被当成任意程序启动器。

| 命令 | 状态 |
|---|---|
| `app_info` | **真实**：版本来自 `CARGO_PKG_VERSION`，平台/架构来自 `std::env::consts` |
| `window_minimize` / `window_toggle_maximize` / `window_close` | **真实** |
| `open_external` | **真实**（带协议白名单） |

## 九、CI（要求 9）

[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml)，三个 job：

| job | 机器 | 做什么 | 超时 |
|---|---|---|---|
| `frontend` | ubuntu-22.04 | `pnpm lint` → `typecheck` → `test` → `vite build` → **两步红线 1 检查** | 15 分钟 |
| `rust` | ubuntu-22.04 | 装 Linux 依赖 → `cargo fmt --check` → `cargo check --locked` → `cargo clippy -D warnings` → `tauri build --no-bundle` | 40 分钟 |
| `cross` | windows-latest · macos-latest | `cargo check --locked` | 40 分钟 |

几处按 M0 实测定下来的细节：

- **`xdg-utils` 必须装**。Tauri 官方 Linux 依赖清单里没有它，但 AppImage 的 bundler 要把 `xdg-open`
  塞进 AppDir，缺了会在打包最后一步才失败（M0 §6.3 踩过）。虽然本轮 CI 只跑 `--no-bundle`，
  依赖先装齐，M4 打 AppImage 时不用再改。
- **`Swatinem/rust-cache` 是必须的**。M0 §6.2 实测冷编译 14 分 24 秒、`target/` 1.5 GB；
  不加缓存每个 PR 都要等一刻钟。job timeout 设 40 分钟留余量（同样按 M0 的实测值定的）。
- **Windows / macOS 只做 `cargo check`**，不做完整 build —— 这两个平台没有真机测试环境，
  按总控规则的默认决策，以「CI 能编译通过 + 代码路径审阅」为准，报告里写明未真机测试。
- `HUNTER_CHANNEL: release` 是 workflow 级环境变量，配合 `vite.config.ts` 的断言构成红线 1 的第二道闸。

### 一个踩了一轮的坑：`cargo build` 与 `tauri build` 不等价

第一次在测试机上用 `cargo build --release` 出了可执行文件，Xvfb 下窗口起来了、
尺寸也对，但**整片白**。排查过程：

1. 截图是 1180×760 的**灰度**图，99.8% 是纯白 —— 说明 HTML 加载了但 CSS / JS 没生效；
2. 先怀疑 CSP（`default-src 'self'` 没有显式 `script-src`，Tauri 会往 `script-src` 里塞 nonce，
   结果 `'self'` 反而没了）。补上 `script-src 'self'` 重编，**还是白的**；
3. `strings` 二进制发现新的 CSP 字符串确实进去了，但**找不到 `/assets/index-*.js` 这些资源键**，
   只有 `/index.html`；
4. 换成 `pnpm exec tauri build --no-bundle`，它先重编了 `tauri` 这个 crate 本身 —— **特性不一样**。

根因：`tauri build` 会带上 **`custom-protocol`** 特性；不带它时产物走的是 `devUrl`
（`http://localhost:1420`）而不是内嵌前端，而那个开发服务器根本没在跑，于是白屏。

两处修正已经进仓库：

- `src-tauri/Cargo.toml` 显式声明 `custom-protocol = ["tauri/custom-protocol"]`（带注释说明原因）；
- `scripts/screenshot.sh` 顶部写明可执行文件必须由 `tauri build --no-bundle` 产出。

顺带把 CSP 也留成了显式写 `script-src 'self'` 的版本 —— 虽然不是白屏的根因，但那样写更明确。

### 截图脚本的「白屏检测」

第一轮白屏时，截图脚本原来的检查（颜色数 > 50）**是通过的** —— 一张纯白页面也有 216 个灰阶。
这正是 M0 §7.2 提醒过的「白屏在 CI 上只会表现成一张看起来正常的图片」。
现在改成三道校验，任何一条不过就让脚本退出非零：

| 检查 | 阈值 | 抓的是什么 |
|---|---|---|
| 颜色数 | ≥ 200 | 纯色块 |
| 平均亮度 | ≤ 350‰ | **白屏**（本项目界面是深海军蓝，亮度一定很低） |
| 平均饱和度 | ≥ 20‰ | 灰度图 = 底色没上（`#0a101c` 不是灰色） |

第一轮那张白屏的实测值是「亮度 998‰ / 饱和度 0」，三条里中两条。

## 十四、给 M2 的交接

1. **Rust 侧的命令签名已经定好**（`src-tauri/src/commands.rs`），M2 要做的是把
   `detect_docker` / `validate_key` / `pull_progress` 三个的 `Err(E_NOT_IMPLEMENTED)` 换成真实现，
   返回结构按 `src/lib/types.ts` 里的 `DockerInfo` / `KeyCheckResult` / `PullProgress`
   （serde 用 camelCase 重命名即可对上）。**前端一行都不用改**。
2. **判定逻辑照 M0 §5.4**：进程起不来 → `E_DOCKER_MISSING`；退出码非 0 但 stdout 能解析出
   `Client` 且 `Server` 为 `null` → `E_DAEMON_DOWN`；退出码 0 → 读 `Server.Version` 比最低版本。
   **不能只看退出码。**
3. **key 校验照 M0 §1.3**：本地先判 `hunt_tools_` 前缀 + 43 长度（`src/lib/mask.ts` 的 `isKeyShape`
   已经写好并有单测），不满足就不发请求；格式对、网关回 401 → 统一文案，**不要假装区分「已吊销」**。
4. **拉取进度照 M0 §5.1**：`docker compose --progress json pull`，按 `parent_id` 分组，
   层级 `current`/`total` 求和；总大小从 manifest 预先算好当分母。
   `Extracting` 行没有 `total`（待办池 P1-1），UI 那一段要显示「解压中」而不是百分比。
5. **额度接口是 `GET /api/saas/llm/quota`**，返回 `{ok, used_today, limit_daily, remaining, ...}`；
   模型列表走 `GET /api/saas/llm/v1/models`。没有 `keys/validate`。
6. 演示数据在 `src/lib/demo.ts`，改真实接口时对着它调返回结构最省事。
7. 测试用 key 明文在测试机 `~/.hunter-launcher-test/key`（600），M0 已签发，直接复用。
