# I19 迭代报告 · 升级这条路要能自己站起来

> 时间一律**上海时间**。本轮不开源发版、不打 tag。
> **凡没在真机上验过的一律写「未验证」**，不写「已验证」。
> 需求来源：用户 2026-10-05 原话（见 `plan/参考-I19-方案.md` 顶部）。

## 〇、一句话

客户那台 Windows「点启动能起来、点升级还是撞同一堵墙」—— I18 做的「装了没跑就替你拉起来」
只挂在「启动服务」按钮上，升级这条路一个字都没挂；而且升级失败后产品一点自救都没有
（界面上只有一行红字）。本轮补三格：**升级开场先把该在跑的东西弄起来**（P0-A）、
**升级卡住先自己修、整轮最多 5 个修复回合**（P0-B）、**修不好就停下来把话说清楚 + 给一个交日志的按钮**（P1-C）。

用户 2026-10-05 拍板的三条口径（本轮边界）：

1. 「循环 5 次」按**整轮升级最多 5 个修复回合**算 —— 任何一步失败触发的自愈都算进同一个计数器；
2. 「交日志」**只在 5 轮用完后给一个手点按钮**，循环中一律不自动上传；
3. 本轮**不发版**（不打 tag）。

## 一、改了什么（按文件）

### 1. P0-A · 升级开场「运行环境就绪」（确定性，零 AI）

| 文件 | 改动 |
|---|---|
| `src-tauri/src/commands.rs` | `ensure_runtime_up`（原私有）提成 `pub(crate)`，加注释说明它现在也挂在升级那条路上 —— **口径 A 只有这一份，升级不另抄** |
| `src-tauri/src/upgrade.rs` | `upgrade()` 在第 ① 步之前插「⓪ 运行环境就绪」：复用 `ensure_runtime_up`（把每一句过程 `note` 进升级步骤流）→ 之后用 `runtime::effective::current().running` 如实判引擎能不能用；**不能用时直接返回 `Code::DaemonDown`**（`E_DAEMON_DOWN`），不再让内层错误（`拉起 postgres 失败：failed to connect to the docker API`）从第 ② 步漏出来 |

口径与 I18 一致：**只在「装了、只是没在跑」时动手**；「没装」不插手。
「等就绪」由 `ensure_runtime_up` 内部复用 `builtin::start` / `try_start_daemon`（后者复用 `chain::wait_daemon`）完成，本轮不另写轮询。

**数据库那一格本来就被覆盖**：第 ② 步备份内部是 `PostgresLease`（`get` 时临时 `up -d postgres`、`Drop` 时停回去），
只要引擎在跑，备份会自己把 postgres 起好再停回 —— 本卡的关键就是**引擎先起来**。

新增 `UpgradeStep` 枚举（八步）与 `UPGRADE_STEP_ORDER` 常量：顺序声明在一处，单测钉住「运行环境就绪排在最前」。

### 2. P0-B · 升级自愈（抽中间层 + 升级专用编排）

**抽中间层**（`src-tauri/src/assist/auto.rs`）：

- 新增 `Stage` 结构（`title` / `id` / `net_like` / `start_like`）与 `Step::stage()`；
  `scout` / `rule_plan` / `rule_plan_raw` / `ask_model` / `repair` 全部改成只认 `impl Into<Stage>`，
  与安装的 `Step`、`InstallOptions` **彻底解耦**（升级那边传 `Stage`，安装那边传 `Step`）；
- `Budget` 结构（`per_issue` / `total` / `tokens`），`Orchestrator` 新增 `set_budget` 与 `tokens()` 取值器；
  安装仍用设计文档 §八 那三个数，**升级另配**；
- 把 `repair` 里那段「规则 → 模型 → 复核员」抽成 `plan_for()`，返回 `(动作串, 原因, Proposer)`；
  `repair` 通过 `by` 把「这一步是谁判的」写进事件流（`Kind::Analyze` 的 `by` 字段）；
- 新增 `pub(crate) fn repair_round(state, stage, e, issue_rounds) -> bool` —— **不依赖安装语义**的修复回合入口。

**升级专用编排**（新增 `src-tauri/src/upgrade_repair.rs`）：

- `MAX_UPGRADE_REPAIR_ROUNDS: usize = 5`（**不共用** `MAX_ROUNDS_PER_ISSUE=4` / `MAX_ROUNDS_TOTAL=10`）；
- `RepairBudget` —— **整轮升级共用一个计数器**，`take()` 用满 5 次返回 `None`；
- `UpgradeRepairer` —— 包一个 `Orchestrator`（事件走 `assist://event` 的同一条总线），
  `repair()` 取一个回合号 → `Orchestrator::repair_round` → `Repaired / Exhausted / Rejected`；
- `stopped_config_state()` 纯函数：过第 ③ 步必回滚、没过如实说「什么都没改」。

**接线**（`src-tauri/src/upgrade.rs`）：`do_upgrade` 的 ③④⑤⑥ 四步每步外面套 `run_step`，
失败 → `UpgradeRepairer::repair` → 修好则**重跑失败那一步**（= 验证，沿用「不问模型『好了吗』」那条纪律）。
`FailedStep { step, err }` 把「卡在哪一步」带回 `upgrade()`。
`UpgradeResult` 补 `repairRounds` / `exhausted` / `errorCode` 三个字段；
失败**不再返回 `Err`**，而是返回一份 `ok: false` 的结果（带 backupId / rolledBack / repairRounds）。

**接线（两条入口）**：`commands.rs::upgrade_hunter` 与 `headless.rs::cmd_upgrade` 都建
`UpgradeRepairer`（前者用 `TauriSink`，后者用 `Stdout` sink），把事件推到 `assist://event` / stdout。
`upgrade_hunter` 里 `Ok(res)` 且 `!res.ok` 的那一支**不设 `g.error`**（那一份结果自己带着完整 message 与自愈信息），
只在「还没开始就停了」的 `Err` 分支才设 `g.error`。

## 二、「用 AI」的正确姿势（规则优先、模型兜底）

用户要的是「先自动用 AI 分析处理」，但产品一直的原则是**确定性的事不交给模型**。所以：

- 规则认得出且 `confident` → **直接执行、零 token、零等待**（`plan_for` 先调 `rule_plan`）；
- 规则认不出 → 才把（已脱敏的）证据交给模型，模型**只能从 `ACTIONS`（33 条）里挑**（`actions::plan` 白名单闸）；
- 含 `Sensitive` 动作的计划过复核员；
- 守卫逐条硬校验，越界一律拒绝并记档（`guard::audit`）。

界面上「规则判的」与「模型判的」用角标分开（事件新增 `by` 字段）——
规则更快更准、也不花 token，这对用户是诚实。

**守卫一个字都没松**：动作表里根本没有 `docker volume rm` / 删用户文件 / 改 hosts 这些形状
（A7④ 的三种越界各有一条单测断言被拒）。

## 五、没做什么 / 为什么

- **A1 / A2 / A4 的真造景没做**（见 §四）。本机 `unshare` 不允许，且**红线禁止**用这台机器上跑着生产容器的真 docker 造升级现场。这不是「没测」，是**测不了**。
- **前端没加单测**：本轮前端改动集中在演示数据与两块渲染（`RepairStream` / `Update.tsx` 的失败态），
  现有 182 条前端单测都过；没有可纯函数化的新逻辑（`upgradeErrorCode` 是一行白名单映射，不值得单开一个文件）。
- **`UpgradeStep` 只声明了顺序、没有真正驱动 `upgrade()` 的控制流**：`upgrade()` 里的 ①①.5② 因为前置体检要提前 `return`，没有做成 `for step in UPGRADE_STEP_ORDER`（那样风险太大）。③④⑤⑥ 是真正驱动起来的。A7 的「第一步是运行环境就绪」是**结构断言**，配 A1 造景才能证明它真跑 —— 而 A1 本机做不了。
- **不在 Windows / Linux 上做「安装 Docker / WSL2」**、不改 `docker-compose.yml`、不动数据卷与数据库、不新增遥测、不改 I17 / I18 已定的交互 —— 任务书边界，一条没越。
