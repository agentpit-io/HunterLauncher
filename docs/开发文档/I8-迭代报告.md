## 零、一句话

0.1.7 在用户自己的 Mac 上第一次跑，四个组件从腾讯云香港装好了，虚拟机起不来，
最后停在一张卡片上：

> 请在终端里执行：`brew install --cask orbstack`（或者去 orbstack.dev 下载）
> 　　　　　　　　　　　　　　　　　　　　　　　　　　　　［我执行完了，继续］

用户当天说了两句话，这一轮就是这两句话：

> **所有能替用户解决的问题——分析异常、执行操作——都不要让用户自己去操作，这是原则。**（22:10）
>
> **需要支持全自动的安装、问题修改，不要让用户参与决策和点击确认和执行，出现问题，自主分析，按最佳方案执行。**（22:35）

落到代码上是三件事：**那张卡片没有了**（兜底链三条路自动依次走完，要管理员权限就弹系统自己的密码框）；
**安装过程中所有需要用户拿主意的地方都由启动器自己拿主意**（授权页只剩一个「开始安装」）；
**加一条流水线检查，代码里再出现这类文案就直接红**。

另外两件：0.1.7 那次失败的两个根因（虚拟机镜像不受我们控制、没沿用用户自己的系统代理）都修了；
开源协议按用户决定从 MIT 改成 Apache-2.0。

**实测撞出 7 个问题**，其中两条是这一轮自己的改动引入的：
取消「Sensitive 要用户点一下」那道门之后，「方向该由用户定」的那一类动作裸奔了（6.3）；
把代理接进子进程环境之后，`netproxy` 与 `runtime::env` 之间凑成了一个环，
**CI 的 macOS runner 上直接栈溢出**（6.7）——「只有 macOS 才炸」的第五条。
另外修 6.3 时加的那条单测又在 CI 上红了一次，根因是老一条：测试里藏着对环境的假设（6.6）。

## 一、本轮做了什么

### 1.1 全自动：安装过程里不再有需要用户点的按钮

| 原来会停下来问用户的 | I8 起怎么办 | 在哪儿 |
|---|---|---|
| 要装新软件（运行时 / OrbStack / Homebrew） | 按第 1.3 节的兜底链自动依次走 | `runtime/chain.rs` |
| 本机已有另一套 Hunter | **自动选「并存、换端口」**，出一张告知卡片说明决定与理由 | `assist/auto.rs::report_other_installs` |
| token 预算用尽 | 不问，改成只用确定性规则继续；仍失败就自动生成脱敏诊断包 | I5 起就是这样，本轮没动 |
| 复核员否决了某个计划 | 自动退回诊断员换方案 | I7 起就是这样，本轮没动 |
| `Sensitive` 级动作 | 守卫 + 复核员两道门过了就**直接执行** | `assist/guard.rs::Mode::needs_confirm` |

**把关的门一道没少，只是换了把关的人：**

| 门 | 谁 | 全自动档下 |
|---|---|---|
| ① 动作表 | 代码 | 表外的一律不执行（不变） |
| ② 守卫 | 代码 | 路径 / 删除 / 网络 / 他人容器的禁止项一条不放松（不变） |
| ③ 复核员 | 另一个模型 | 含 `Sensitive` 的计划必过，否决就退回诊断员（不变） |
| ④ 用户点一下 | 用户 | **取消**（`confirm` 档仍保留，在设置页给高级用户） |
| ⑤ `user_only` | 代码 | **本轮新增**，见 6.3 |

配置默认档位从 `confirm` 改成 `auto`。「同意」这件事没有消失，只是挪了位置：
授权页仍然要用户亲手点一次「开始安装」，**默认值替他同意的不是「要不要装」，而是「装的过程中不再打扰他」**。

### 1.2 需要管理员权限时走系统自带的授权框 · `runtime/elevate.rs`

I5–I7 的承诺是「**绝不使用管理员密码**」，代价是撞上要 root 的事只能把活儿丢回给用户。
用户 22:10 把这条推翻了，于是承诺改成：

> **需要管理员权限时会弹出系统自带的密码框，只用于安装这一步。**

三条硬规矩：

1. **只用系统自带的授权界面**。macOS 是 `do shell script … with administrator privileges`，
   Linux 是 `pkexec`（polkit），Windows 是 UAC。**启动器不自绘密码框。**
2. **密码一个字节都不经过启动器**。唯一的例外是 `SUDO_ASKPASS` 那条路（Homebrew 官方脚本
   自己要调 `sudo`），它把密码直接喂给 `sudo` 的标准输入，**也不经过启动器进程**。
3. **能提权的事写死在一张表里**（`guard::PRIVILEGED_OPS`，目前两条：装启动器自己的 `.deb`、
   启动 Linux 上的 docker 后台服务），参数由代码构造、提权前再过一遍 `guard::argv_privileged`。
   模型碰不到这条路上的任何一个字节。

**其余禁止项一条都没放松**：不删用户文件、不改用户的网络与安全设置
（代理 / DNS / hosts / VPN / 防火墙 / Gatekeeper / SIP）、不动别的项目的容器与数据、
不执行模型自编的命令。

跟着改的还有一处：Linux 上启动器自更新的 `.deb` 那条路，原来是「包下好了，这条命令你自己去敲」，
现在是下好包 → 弹 polkit 的原生授权框 → 启动器自己 `dpkg -i`。界面上那个
「复制命令」的弹窗（`ManualDialog`）连同 `ManualInstall` 这个类型一起删掉了。

### 1.3 没有 Docker 时三条路自动依次走完 · `runtime/chain.rs`

| 顺序 | 路线 | 要下多少 | 要密码吗 |
|---|---|---|---|
| ① | 内置运行时（Colima + Lima + docker CLI + compose + **虚拟机系统镜像**） | 约 436 MB | 不要 |
| ② | OrbStack 官方 dmg（下载 → 验苹果签名与公证 → 装进「应用程序」→ 打开 → 等就绪） | 约 200 MB | 可能要 |
| ③ | Homebrew（**没有 brew 就先替用户装 brew**）→ `brew install --cask orbstack` | 视情况 | 会要 |

排序原则是用户 22:35 那条的直接落地：**同样能解决问题时，优先不需要任何交互的方案**。
所以要密码的排在最后，只有前面所有零交互路线都失败才会走到它。

OrbStack 首次启动会弹它自己的窗口 —— 那是第三方程序的界面，启动器不替用户点，
但也**不停下来等**：一直等 `docker version` 真的连得上，超时就继续走下一条路。
「这条路成功了」只有一个判据：**`docker version` 真的连得上后台服务**。
装好了、打开了、进程在跑，都不算。

### 1.4 虚拟机系统镜像现在由启动器自己下

这是 0.1.7 在用户 Mac 上卡住的**直接原因**：`colima start` 会自己直连 GitHub 去取
`colima-core` v0.10.4 的 `ubuntu-24.04-minimal-cloudimg-{amd64,arm64}-docker.raw.gz`
（341 MB / 316 MB），**那一次下载不在我们的控制里**，直连不通就是干等到超时。

现在这两个文件进了内置运行时的同一条流水线：GitHub 与腾讯云香港并列择优、
版本与官方给的 `.sha512sum` 写死在 `runtime/manifest.rs`、校验不符拒绝用、下载有真实进度。
下好之后用 `colima start --disk-image <本地文件>` 交给 colima，它一个字节都不用自己下。

### 1.5 沿用用户自己配好的网络代理 · `netproxy.rs`

用户那台 Mac 的系统设置里配着 `127.0.0.1:7897`，`scutil --proxy` 显示 HTTP / HTTPS / SOCKS
都开着，直连 github.com 十秒超时、走代理两秒 200。**路是用户铺好的，是我们没走。**

| 做 | 不做 |
|---|---|
| **只读**地读出这台机器上已经配好的代理 | **绝不修改**任何网络设置 |
| 传给子进程（colima / limactl / docker） | 不写 `~/.docker/config.json`、不碰 `networksetup` |
| 用 `colima start --env` 传进虚拟机 | 不改 DNS / hosts / 防火墙 |
| 直连失败时用它重试一次 | 不默认改走代理 —— 直连能通就不绕路 |

| 平台 | 读哪儿 | 只读吗 |
|---|---|---|
| 任意 | `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY` / `NO_PROXY` 环境变量 | 是 |
| macOS | `scutil --proxy` | 是（`--proxy` 只打印） |
| Windows | `reg query HKCU\…\Internet Settings` | 是（`query` 子命令） |
| Linux | 只有环境变量（桌面环境各家一套，不猜） | 是 |

两个会**如实说明**的例外：

- **只监听本机（127.0.0.1）的代理不传进虚拟机** —— 虚拟机里的 `127.0.0.1` 是它自己。
  碰到这种情况界面上说清楚，虚拟机改走腾讯云香港的源（`builtin::vm_proxy_note`）。
- **直连能通就不绕路**。代理只在直连失败之后才用上。

解析函数全部写成**纯函数**（`scutil` 在开发机与测试机上根本不存在），
单测里抄的就是用户那台 Mac 上 `scutil --proxy` 的真实输出。

### 1.6 「已自动解决 N 个问题」如实计数

自动换下载源、自动改走代理、自动换兜底路线，每一次都算一个，并各自在过程流里留一行说明。
实测两个场景下都是 2 个（第五节），每一个都对得上一条具体的事。

### 1.7 文案扫描检查 · `scripts/check-wording.py`

**这条原则靠代码守，不靠提示词。** 0.1.7 停住的那张卡片是代码里写死的字符串，
不是模型编的，所以守它的办法只能是在流水线上扫字符串。

| 扫 | 不扫 |
|---|---|
| `src/i18n/*.ts`、`src/pages`、`src/components` 的字面量 | 注释（不会上屏） |
| 规则层、动作表、总指挥、兜底链、`netproxy`、`err.rs`、`selfupdate.rs` 的**字符串字面量** | 命令行 `--help` 与 headless 输出（本来就在终端里看） |
| | 日志与诊断包（给开发者） · 文档 `.md`（会故意引用这些话） |

七条规则（正则，不是裸子串），例如：
「在终端里执行 / 复制这条命令 / 我执行完了 / 请手动安装 / 请你选择 / 点一下继续 / 照着文档自行处理」。
规则写成正则是因为有些词单独出现是正当的 ——「设置页里点一下就能卸干净」讲的是这东西多好卸，
不是在安装过程里支使用户。

自带 `--self-test`：**9 条反例必须全被拦下，8 条正当文案一条都不许误判**。
CI 里先跑自测再扫仓库 —— 证明这条检查不是空跑。逐行豁免标记 `wording-ok`，
认命中行前后各 3 行（Rust 的多行原始字符串里插不了注释）。

## 二、偏离任务书的决策与原因

| # | 任务书写的 | 实际做法 | 为什么 |
|---|---|---|---|
| 1 | 「取消『需要你』卡片」 | `NeedUser` 卡片**留在代码里**，全自动档下不会出现 | 设置页里的「每一步都问我」那一档还要用它（任务书〇·五.5 要求保留这一档）。全自动档下 `needs_confirm` 恒为 false，这条路走不到 |
| 2 | 「`Sensitive` 级动作由守卫 + 复核员双重把关后直接执行」 | 照做，但**另加了一道 `user_only`** | 见 6.3：那句话对「风险高但方向是对的」动作成立，对「方向该由用户定」的动作不成立 |
| 3 | 「测试机上起一个 HTTP 代理（squid 或 tinyproxy）」 | tinyproxy，只听 127.0.0.1 | squid 配置面太大，tinyproxy 十行配置就够 |
| 4 | 「iptables 拦 GitHub/ghcr 直连」 | 用 **ipset + GitHub 官方 `api.github.com/meta` 的 106 个网段**，DROP 不是 REJECT，且**只拦 support 这个用户** | 第一次用 `getent` 解一次 IP 写死规则，GitHub 轮询 IP，十分钟后规则就漏了（实测漏过一次，第五节）。DROP 而不是 REJECT 是为了造出「十秒超时」而不是「立刻连接被拒」—— 用户那台机器就是超时。只拦 support 是为了让 tinyproxy（以 nobody 跑）照样出得去 |

## 四、安全边界的自查

本轮动了授权模型（取消第四道门），所以把四条禁止项各挑一个代表，确认**它们和档位毫无关系**
（`guard::tests::全自动档下四条禁止项一条不放松`）：

| 禁止项 | 代表 | 拦在哪 |
|---|---|---|
| 不删用户文件 | `rm_user_documents` | 动作表（`plan()` 直接 Err） |
| 不改网络与安全设置 | `set_system_proxy` / `disable_gatekeeper` | 动作表里根本没有这两条 |
| 不动别的项目的容器 | `compose_down_other` | 同上 |
| 不执行模型自编的命令 | `run_shell` | 同上 |
| 路径守卫 | `writable_path("/etc/hosts")` | `guard::writable_path`，不看档位 |

真实回放（回归场景 7，`docs/开发文档/I8-证据/g-*.log`）：两份诱导响应共 8 个动作，
**8 个全部被拒**，审计日志逐条留痕。这一段与 I5–I7 的结果一致，本轮没有放松。

提权这条新路的自查：

- `elevate::root_argv` 第一句就是 `guard::argv_privileged(inner)`，表外的命令提不了权
  （`elevate::tests::表外的命令提不了权`）；
- `dpkg -i <包>` 那一条还要过 `writable_path` —— **只能装我们自己下到 `~/.hunter/updates/` 的那个包**；
- 密码不经过启动器：`askpass_script` 生成的脚本里没有 `>>`、没有 `tee`，
  单测逐条断言（`elevate::tests::askpass_脚本的形状`）；
- 弹框之前界面上有「要做什么、为什么要密码」两句人话（`elevate::tests::提权前那两句人话都在`）。

## 六、实测撞出来的 7 个问题

### 6.1 `--auto` 跑出来居然是「逐步确认」

**怎么发现的**：场景 A 第一次跑，打印的是

```
授权档位：confirm（逐步确认）
⚠ 「逐步确认」档在这里等不到回答（stdin 不是终端，多半是 CI 或管道）：
凡是要你点头的动作都会按「不」处理。
```

**根因**：`--auto` 只是「进自动驾驶那条代码路径」，档位仍然从 `launcher.toml` 里取。
测试机的配置里存着 `confirm`（I5 写进去的），于是一个名字叫 `--auto` 的开关跑出来是逐步确认，
而 stdin 不是终端时所有确认都按「不」处理 —— 等于什么都不做。

**修**：档位优先级改成 `--assist-mode` > `--auto` > 配置里那一档，抽成纯函数
`headless::asked_mode` 并加单测钉死。

**这条的教训**：把「进哪条代码路径」和「用哪一档授权」当成两件事，用了三个迭代都没人发现，
因为**在此之前默认值恰好是对的**（I5 的默认是 confirm，而 `--auto` 的典型用法都显式带了
`--assist-mode auto`）。默认值一改，这个洞就露出来了。

### 6.2 探一次 GHCR 要 60.7 秒

**怎么发现的**：场景 A 的测速输出 `可用 GHCR · GitHub · 60734 ms`。

**根因**：拉 manifest 要先取 token 再取 manifest，**每一次请求**都老老实实先直连等满 20 秒
超时再走代理。第一次那 20 秒是必要的（得先知道直连不通），后面每一次都交就是浪费。

**修**：主机一旦被 `netproxy::mark_rescued` 记下，**这一次安装里对它不再试直连**。
作用域只有这一次安装（`run()` 开头 `reset_rescued`），不会跨进程留下「这个站永远走代理」的判断。

**实测**：60.7 秒 → **20.7 秒**。

### 6.3 取消「Sensitive 要用户点一下」之后，有一类动作裸奔了 ★

**这是本轮自己的改动引入的，而且是最要紧的一条。**

**怎么发现的**：I5–I7 回归的场景 7c（`--diagnose --ai`，真去问网关）里，模型提议：

> 要做什么：直接用你已经装好的「hunter-community」
> 为什么：　这台机器上已经有一套在跑，再装一套要多占几个 G 和五个端口

在 `--diagnose` 那条路上它只是被列出来（诊断是只读的，不执行）。但换到**自动安装**那条路上，
全自动档下 `needs_confirm` 恒为 false —— 这一提议会**直接执行**：启动器就不装了，
改去管用户已有的那一套。而用户 22:35 定的是**自动选「并存、换端口」**，正好相反。

**根因**：「要不要问一句」这一道门同时兜着两类完全不同的动作 ——

| 类别 | 例子 | 不问用户行不行 |
|---|---|---|
| 风险高，但**方向是对的** | `install_runtime`（装一套运行时） | 行 —— 守卫 + 复核员把关后自己做 |
| 风险不高，但**方向该由用户定** | `reuse_existing_hunter`（改成用你已有的那套） | **不行** |

把第四道门整个拿掉的时候，只想到了第一类。

**修**：动作表加一位 `Spec::user_only`，**档位管不着它** —— 三档下模型提了都拒，
而且这一道放在档位判定**之前**（放在后面就永远走不到，因为全自动档下 `needs_confirm` 恒为 false）。
总指挥碰到这类动作连 `confirmed` 都不给，事件流里如实写一行「这件事不由启动器替你定」
并说明默认做法是什么。两条单测钉死：三档全拒 + **表里只有那一条是 `user_only`**
（后一条是为了让以后再加 `user_only` 的人先想清楚「全自动档下它会怎么样」）。

**这条的教训**：**放松一道门之前，先问清楚那道门到底在拦什么。**
「Sensitive」这个级别描述的是**风险大小**，而那道门实际上还兼着**「方向归谁定」**——
两件事挤在一个判据里，拿掉判据的时候就会连带拿掉另一件。

### 6.4 删了 `~/.hunter` 但数据卷还在 → api 起不来（**本轮不修，进待办池**）

**怎么发现的**：场景 A 第一次跑，`docker compose up` 反复失败
（`docs/开发文档/I8-证据/a-*.log`、`b-*.log`）：

```
FATAL:  password authentication failed for user "hunter"
```

**根因**：`rm -rf ~/.hunter` 删掉了上一次安装随机生成的 postgres 密码，
但 docker 卷 `hunter_hunter_pg_data` 还在，里面的库还认那把旧密码；新写的 `.env` 是新密码。

**自动修复循环跑了 3 个回合都没能解决 —— 而且它不该解决**：唯一的出路是删用户的数据卷，
那是守卫写死不许做的事。这一点上它的行为是**对的**，但它**没说清楚卡在哪**，
只是反复「清残留容器 → 重试」。

**本轮不修的理由**：这不是 I8 引入的，也不在任务书范围里；改它要动「安装时怎么认出这种现场」
（读卷里的密码是做不到的，只能靠 api 容器的那句原话反推）。已写进待办池 **P1-29**。

### 6.5 场景 I5-2（Docker 装了但 daemon 没起）从「通过」变成「失败」

**这不是缺陷，是 I8 的预期行为，但它改了回归结果，必须写明。**

I7 时这一场景的结局是：启动器发一张卡片「请在终端里执行 `sudo systemctl start docker`」+
「我执行完了，继续」，用户点一下就接着装 —— 按 I7 的口径算**通过**。

I8 起这条路没有了。启动器改成试着自己做：走 polkit 的原生授权框。测试机上：

- 没装 polkit 时 → 「这台机器上没有 pkexec（polkit），没有办法弹出系统自己的授权框」；
- 装了 polkit 但会话既没有图形界面、stdin 也不是终端（`nohup` 出来的进程）→
  「polkit 没有地方问你要密码」；
- 装了 polkit 且给一个 pty → **polkit 自己的文本提示出来了**（5.4 节）。

所以 `rc=1` 是**在那个会话里能给出的唯一诚实结果**。在一台有桌面的 Linux 上，
这一步会弹 polkit 的授权框，用户输一次密码就过 —— **那一段测试机上验不了**。

顺带修了一条：`elevate::available` 原来在 Linux 上只看 `DISPLAY` / `WAYLAND_DISPLAY`，
会把「人坐在 ssh 终端前面手敲 `--headless`」也判成弹不出框，而那种情况 `pkexec`
明明能在终端里问他一句。改成「有图形会话 **或** stdin 是 tty」。

### 6.6 那条新加的单测在 CI 上红了：它偷偷依赖了「这台机器上有另一套 Hunter」

6.3 那道 `user_only` 门，第一版放在 `plan()` **后面**。`plan()` 会去看这台机器的现状 ——
`reuse_existing_hunter` 要查本机还有哪几套 Hunter。于是：

| 机器 | `plan()` | 那条断言拿到的话 |
|---|---|---|
| 开发机 / 测试机（跑着 hunter-community） | 过得去 | 「这件事的方向该由用户自己定」✓ |
| GitHub 的 runner（一套都没有） | 先报错 | 「这台机器上并没有别的 Hunter 安装」✗ |

**修法不是改断言，是改顺序**：把这一道挪到 `plan()` **之前**，并且只看动作表、
不看这台机器的现状。这样它在任何机器上给的都是同一句话 —— 语义上也更对：
「这件事不归我定」比「参数对不对」更早，参数再对也不做。
断言里跟着加了一条「连参数都不给时也是同一句话」，把这个顺序钉死。

**这是 I7 那条教训的第四次**：本地绿 ≠ CI 绿，而每一次的根因都是
**测试里藏着一个对环境的假设**。

### 6.7 CI 的 macOS runner 上 `fatal runtime error: stack overflow` ★

**这是本轮第二严重的一条，而且它只在 macOS 上炸。**

链条是这样的 —— 两个缓存都还空着，所以它一直绕：

```text
netproxy::current()        ← 缓存空
  → detect() → read_scutil() → proc::run_timeout() → base_command()
  → runtime::env::apply() → env::current()   ← 缓存也空
  → env::compute() → netproxy::current()     ← 回到第一行
```

`runtime::env::compute()` 里那一行 `e.proxy = netproxy::current().env_pairs()`
是本轮加的（要把代理传给子进程），而 `netproxy::detect()` 在 macOS 上要跑
`scutil --proxy` —— 跑子进程就会经过 `base_command`，`base_command` 又要问
`runtime::env`。**本轮在这两个模块之间各加了一条边，凑成了一个环。**

**Linux 上不会炸**：`detect()` 里 `scutil` 那一支是 `cfg!(target_os = "macos")`，
Linux 只读环境变量，不跑任何子进程，环也就不存在。所以开发机与测试机上
482 条全绿。**这是「只有 macOS 才炸」的第五条**（I4 的 PATH、I5 的 `SO_REUSEADDR`、
I6 的凭据助手 PATH、I7 没有、I8 这一条）。

**修法**：`proc` 里单开一条 `run_timeout_bare` —— **不套 `runtime::env`**。
断链的依据不是「为了不递归」，而是**这两条命令本来就不需要那份环境**：
程序用的是绝对路径 `/usr/sbin/scutil`（不需要 PATH 补全），读一份本机设置
也不需要代理变量。`read_scutil` 与 `read_windows` 都改走它。

**加的回归**：`netproxy::tests::读系统代理不会绕回自己`。它在 Linux 上抓不到
这个缺陷（那里没有环），报告里写清楚了 —— 它真正生效的地方是 CI 的 macOS runner，
`ci.yml` 里那一步会点名跑 `netproxy::tests`。真有递归时它是栈溢出而不是断言失败，
整个测试进程挂掉，一样是红的。

## 十、本轮的一条总结

**放松一道门之前，先问清楚那道门到底在拦什么。**

这一轮的任务是「把第四道门（用户点一下）拿掉」。拿掉之前，那道门看起来只在拦一件事：
风险高的动作要用户点头。拿掉之后才发现它还兼着另一件完全不同的事 ——
**方向该由谁定**。`install_runtime` 和 `reuse_existing_hunter` 都是 `Sensitive`，
但前者不问用户是对的，后者不问用户是错的，而「Sensitive」这个级别分不出这两者。

发现它靠的不是通读代码，是**把 I5–I7 的回归原封不动再跑一遍**。
那一轮回归本来只是为了确认「没搞坏」，结果它抓出来的是「新加的东西自己有个洞」。
