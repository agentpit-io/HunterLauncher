## 零、一句话

用户 2026-09-28 报：**「不起 Docker 打开软件，会重复进入安装界面。」**

装是装过的、数据都在，只是当时内置虚拟机 / Docker Desktop 没在跑。
启动器问不出容器现状，**把「问不出来」当成了「根本没有」** ——
于是又走一遍安装流程，用户要重新填 key，甚至可能重建数据卷。

这一轮就是这一件事：给复查加一档 `RuntimeDown`（装过、但运行时问不出来），
它的下游**绝不安装、绝不重填 key、绝不碰 `.env` 与数据卷**。

这不是新问题。它就是 I15 任务书里的 P0-1，2026-09-24 在另一台 Mac 上真实发生过
（`15:57:27` 装成功 → `16:30` 虚拟机是 `stopped` → 被判成「还没装过」）。

| | 0.1.16 | R1 之后 |
|---|---|---|
| **P0-1** 运行时没起来 | `docker compose ps` 一报错就判 `Absent`，下游是**完整安装** | 新档 `RuntimeDown`：进运行面板，主按钮「启动运行时」 |
| 项目名被别人占着 | 同样被并进 `Absent`（会去装，把别人的配置和端口顶掉） | 同一档，说法换成 `E_PROJECT_CONFLICT` 那一句 |
| **P0-2** 单测 | 这一档判据埋在 `review()` 里，要一台「Docker 没起」的机器才测得出来 | 判据抽成纯函数 `posture_before_containers`，4 条单测钉死 |
| **P1** 界面 | 没有这一档，没有对应文案 | 运行面板顶上一块 + 主按钮「启动运行时」 |

## 一、P0-1 · 新档 `RuntimeDown`

### 1.1 出问题的那两行（`selfcheck.rs`）

基线 `6f41acc` 的 `review()`：

```rust
if !installed_on_disk() {
    return finish(Posture::Absent, …);   // 真的没装过 —— 合理
}

let services = match compose::ps() {
    Ok(v) => v,
    Err(e) => {
        lines.push(format!("docker compose ps 问不出来：{}", e.msg));
        return finish(Posture::Absent, …);   // ← ★ 这里
    }
};
```

`installed_on_disk()` 上面**刚刚返回 `true`**（`docker-compose.yml` 与 `.env` 都在），
可 daemon 连不上就判成了 `Absent`。而 `Absent` 的含义是「磁盘上什么都没有」，
它的下游（`commands::route_of`）是 `Welcome` / `DataFound` —— **两条都是安装入口**。

还有一处同类：`compose::guard_project_owner()` 失败（`E_PROJECT_CONFLICT`，
别人占着 `hunter` 这个项目名）也被归进了 `Absent`。那更危险 —— 照着安装走，
`up -d` 会把别人那一套的配置和端口一起顶掉（M2 实测撞到过）。

**「问不出来」和「根本没有」是两回事。** 前者只是我们此刻看不到，
后者是磁盘上真的没有。把前者说成后者，用户就得重新填 key。

### 1.2 判据抽成纯函数

`review()` 是只读的，但它要跑 `docker`、读磁盘，在开发机与测试机上
**造不出「Docker 没起来 + 磁盘上装过」这个现场**（这两台机器上的 Hunter 一直好好跑着，
而且红线不许我们去动别人的容器）。所以按项目里的老规矩，把判据抽成纯函数：

```rust
pub fn posture_before_containers(
    installed_on_disk: bool,
    project_owned_by_us: bool,
    runtime: Runtime,          // Answers / Silent / NotAsked
) -> Option<Posture>
```

返回 `None` = 前两问没定局，接着去看容器现状。两条硬规矩，**顺序不能换**：

1. **项目名不是我们的 ⇒ `RuntimeDown`**（那是 `E_PROJECT_CONFLICT`，
   运行时好好的、只是它服务的是另一套）；
2. **只有磁盘上真的什么都没有，才许说 `Absent`。** 磁盘上有、运行时问不出来
   ⇒ `RuntimeDown`。

同一条思路在项目里已经用过两次：`commands::route_of`（I12 · R1 那张五行表）
与 `runtime::effective::decide`（I9）。**判定不该需要一台处在那个状态的机器才能测。**

### 1.3 项目名冲突那一支：同一档，说法不同

`guard_project_owner()` 失败时，运行时其实是好的 —— 说「运行时没在跑」就是**在编**
（红线 1）。所以那一支返回同一档 `RuntimeDown`，但**换一句 headline**：

> 另一个位置的 Hunter 正占着「hunter」这个项目名，启动器现在管不了这一套 ——
> 你的数据和配置都没动，这里也不会重新安装

行为是同一类（不安装、不重填、不碰数据），说法跟着事实走。
界面那一块的正文直接用后端给的 headline，不另编一句。

### 1.4 行为写死（任务书 P0-1 的硬要求）

| 要求 | 落在哪 |
|---|---|
| 绝不触发完整安装 | `commands::route_of` 里 `RuntimeDown => BootRoute::Dashboard`；单测 `运行时问不出来时绝不触发完整安装` 逐个数据卷数断言 `!= Welcome && != DataFound` |
| 绝不要求重新填 key | 这条路由压根不到向导；`.env` 一个字节没动（`review()` 全程只读） |
| 绝不碰 `.env` 与数据卷 | 同上。`review()` 只跑 `docker compose ps` 与一次本机 GET |
| 主按钮是「启动运行时」 | `Dashboard.tsx`：这一档把主按钮文案换成 `t.dashboard.runtimeDownStart` |

### 1.5 顺带改掉的：这一档**不写安装记录**

原来的 `boot_state` 只要进运行面板就 `mark_installed(adopted)`。
`RuntimeDown` 这一档不能这么写，两处都不成立：

* 写 `adopted_from_running=true` → 运行面板顶上会挂一条绿横幅说
  **「Hunter 已经在正常运行」**，而它明明没在跑；
* 项目名冲突那一支连我们这个工作目录下有没有文件都没确认过，
  写「装于今天、工作目录 X」等于记一条假账。

所以这一档 `mark_installed` 直接不调。**等它真的 6/6 健康了，
`selfcheck::note_healthy` 会自己补写** —— 那才是「这台机器上装好了」的成立条件。
`--boot-state` 的输出里看得见：`进来时 done=false，现在 done=false`（证据 b）。

## 二、P0-2 · 单测

任务书要的 4 条，全部落在 `selfcheck.rs` / `commands.rs`，断言都是具体的：

| 要求 | 测试 | 断言 |
|---|---|---|

| ③ `guard_project_owner()` 失败 ⇒ 不是 `Absent` | `项目名被别人占着时不算没装过` | `(true, false, NotAsked)` 与 `(false, false, NotAsked)` 都不是 `Absent` |
| ④ 新档与 `Stopped` 的区别 | `全停着与问不出来是两回事` | `Stopped` 那一边：六个容器都在手上（`services.len() == 6`）、`judge_containers` 判 `AllDown`；`RuntimeDown` 那一边：`services.is_empty()`、`missing.is_empty()`、**headline 里不许出现「个容器」**（我们根本不知道有几个）；两边 headline 不相等 |
| 额外：路由 | `运行时问不出来时绝不触发完整安装`（`commands.rs`） | `vols ∈ {0, 1, 6}` 时一律 `Dashboard` |

**没有第二条会红的测试，第一条就不算钉住** —— ② 是 ① 的反向保险：判据改宽了，
它当场就红。

## 四、真机验证：Linux 上验得了的

「Docker 没起来」这个现场在这台机器上**造得出来，而且不用停 Docker** ——
把 `DOCKER_HOST` 指向一个没人听的端口，docker 客户端自己就会报
`Cannot connect to the Docker daemon`。整棵 `docker` 是同一份代码、同一条路径，
不是我们伪造的返回值。

### 4.1 改之前 / 改之后，同一个现场

造法：`HUNTER_HOME=/tmp/r1-X`（`review()` 只读地看这个目录下的
`app/docker-compose.yml` 与 `app/.env`），`DOCKER_HOST=tcp://127.0.0.1:1`。
两台二进制都是本轮现编的（改之前那份是从另一个工作区 stash 后编出来的，见证据 a 的文件头）。

| | 改之前（0.1.16） | 改之后（R1） |
|---|---|---|
| 现状 | **这台机器上还没有装过 Hunter** | **Hunter 装在这台电脑上，只是运行时没在跑 —— 不用重新安装，也不用重新填 key** |
| 该进哪 | **欢迎页（全新安装）** | **运行面板** |
| `install.done` | `false` | `false`（没被写） |
| 用时 | 406 毫秒（含复查 254 毫秒） | 357 毫秒（含复查 255 毫秒） |

原始输出：`docs/开发文档/R1-证据/a-改之前-0.1.16-同一个现场.txt`、`b-改之后-R1-同一个现场.txt`。
**「改之前」那一栏就是用户报的那一幕**：`该进哪 = 欢迎页（全新安装）`
= 用户被带回安装向导、重新填 key。

### 4.2 反向保险：磁盘上真的什么都没有

`HUNTER_HOME=/tmp/r1-C`（空的）→ 现状「这台机器上还没有装过 Hunter」、
**该进哪 = 欢迎页（全新安装）**（证据 c）。**没把真的没装过一起改坏。**

### 4.3 回归

`cargo test --locked` 全量跑：**723 通过、0 失败、3 ignored（共 726 条）**。
比 I16 报告里那个 718 多 5 条 —— 正是本轮新增的那 5 条。
I9（残骸识别：`created` 的容器走完整流程）、I12（现状优先：`route_of` 五行表逐行钉死）、
`E_BUILTIN_DOWN`（`assist::rules` / `assist::auto` 里那几条内置主线）
全部原样通过 —— 新增档位没有碰它们。

`E_BUILTIN_DOWN` 那条通路为什么不受影响，值得写清楚：
`preflight_plan` 对 `Absent` 与 `RuntimeDown` 都是 `_ => Preflight::FullInstall`，
**和改动前完全一样**（改动前那种机器给的是 `Absent`，两者落在同一个分支上）。
「装过、只是运行时没起来」这个现场**根本不经过安装流程** —— 它进的是运行面板，
所以去动 preflight 只会白白冒破坏 I9/I12 的风险。

### 9.1 这一轮最值得记住的一句

**「问不出来」不等于「没有」。**

六轮 P0 里有五轮是「那台机器和我们的不一样」；这一轮的根子不一样 ——
**是我们在没把握的时候替用户下了一个确定的结论**，而且这个结论的代价
