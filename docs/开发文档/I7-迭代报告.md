## 零、一句话

上一轮把「docker 拉不动镜像」修好了；这一轮回答的是**再往前一步的那个问题** ——
**电脑上根本没有 Docker 的时候，还能不能让用户一下都不点。**

答案是：macOS 上能（内置运行时，全程用户态、不要管理员密码、可一键卸载），
Windows 与 Linux 上**不能**，而且我们不打算假装能 —— 那两条路都要管理员权限，
启动器不替用户提权。

另外三件：给会碰到「你已有的东西」的计划加了一道**复核员**（第二个模型），
给「本机已经有一套 Hunter」这件事加了一个「**直接用它**」的选择，
给「修不好」这件事加了一条**真的能走完的反馈路**。

### 1.1 复核员 —— 第二个模型角色 · `src-tauri/src/assist/reviewer.rs`（393 行）

设计文档 §四那张表里的「复核员」这一格，本轮落地。

**什么时候触发**：计划里含 `Sensitive` 级动作时。**只看级别，不看是谁提的** ——
规则层提的 `Sensitive` 动作一样要复核，因为规则是人写的，人也会写错。

**它看到什么**：只有「计划 + 证据」。**不带诊断员的对话历史**，
**不给工具表**（`call_gateway_plain`，不带 `tools`）。

> 为什么要另起一次调用而不是在原对话里追一句「现在请你批评自己」：
> 同一段上下文里换角色，模型多半会顺着上文继续同意。这不是提示词写得好不好的问题，
> 是上下文本身的偏置。

**它只回答两件事**：

1. 这个计划会不会伤到用户**已有的**数据 / 网络 / 其他项目？
2. 它给的理由，**对不对得上证据里的原话**？

**输出**：`{"approve": true|false, "reasons": ["…"]}`。解析器从第一个 `{` 到最后一个 `}`
截一刀再解析（模型常带 ```json 围栏或前后废话）。

**解析不出结论 = 没通过。** 这是这个模块的底线，写成了单测（`解析不出来一律判没通过`，
六种输入）。网关不通、没 key、AI 档位关着、token 到上限 —— 一律「复核做不成」，
**不是「默认通过」**。把关的人不在场时把门打开，那这道门不如不装。

**否决之后**：理由进证据（`Evidence::notes`），**退回诊断员重想一个**，
而且**跳过规则层**（规则是确定性的，原样再跑一遍只会给出同一个计划）。
退回这一趟**计一个回合、计 token** —— 否则模型可以靠不停被否决把预算绕过去。
第二趟还被否决就不再猜了。

**三道门的关系**（这一条写进了代码注释、界面文案、单测三处）：

```
诊断员给计划
   ↓
① 复核员   ← 模型说了算。只有 Sensitive 才走
   ↓
② 守卫     ← 代码说了算。模型无论如何绕不过
   ↓
③ 用户确认 ← 人说了算
```

**「都要过」，不是投票。** 复核员说可以之后，守卫照样可能拒、用户照样可能点「不用」。
单测 `复核通过不等于可以执行` 钉住这件事：造一个「复核员放行了一个表外动作」的场景，
断言 `actions::plan` 照样拒绝、`Mode::needs_confirm` 照样要求确认。

> 这一条值得单独写一笔：「多加一个模型来把关」很容易滑成
> 「有模型把关了，那道代码就可以松一松」—— 那正好是反过来的。

事件流里是一张单独的卡片（`Kind::Review`，界面上蓝色描边 + 「复核」角标），
写明通过 / 否决、理由、花了多少 token、用时多久。

### 1.2 `install_runtime` —— 没有 Homebrew 也要全自动

> 用户 2026-09-21 17:00 的原话：**「所有流程只要 AI 能协助执行，不要人去操作」**。

#### 授权页并入那一项勾

一次授权页下面多了一项**默认勾选**的勾：

> 如果电脑上没有 Docker，允许 AI 为你安装（装在 `~/.hunter/runtime` 里，不改系统，可一键卸载）

勾着 → `install_runtime` 这个 `Sensitive` 动作**不再弹「需要你」卡片**，
但事件流里**照样出一张卡片说明「为什么这次没问你」**，并写清怎么改回去
（`[assist] allow_install_runtime = false`）。已经授权过的事再问一遍不叫谨慎，叫啰嗦；
但不留痕就是另一回事了。

**这个口子只对 `install_runtime` 一个动作开**（`Orchestrator::pre_authorized`）。
`reuse_existing_hunter` 动的是用户自己装的那一套，**没有「一次授权、以后不问」的道理** ——
有一条单测专门钉这件事。

#### macOS 默认路线：内置运行时

`src-tauri/src/runtime/manifest.rs`（309 行）+ `builtin.rs`（906 行）。

| 组件 | 版本 | 文件（两个架构各一份） | 字节数 |
|---|---|---|---|
| Colima | v0.10.3 | `colima-Darwin-{x86_64,arm64}` | 16,954,240 / 15,656,320 |
| Lima | v2.2.0 | `lima-2.2.0-Darwin-{x86_64,arm64}.tar.gz` | 24,415,554 / 37,586,365 |
| docker CLI | 29.8.1 | `docker-29.8.1-{x86_64,aarch64}.tgz` | 20,888,599 / 19,613,004 |
| docker compose | v5.5.1 | `docker-compose-darwin-{x86_64,aarch64}` | 32,686,480 / 30,532,210 |

合计：Intel 机器 **94.95 MiB**，Apple Silicon **103.4 MiB**（实测字节数，不是估算）。

**版本与 sha256 写死在清单里，下完逐个核对，对不上就删掉、不使用。**
不跟 `latest` 漂移的理由不是洁癖：跟着 latest 走意味着上游哪天改了打包方式，
用户这边就是装到一半炸掉，而且每台机器装到的东西还不一样，出了事根本复现不了。
要升级运行时 = 改这个文件 + 重新同步 + 重新发一版启动器 —— 一次**有记录的改动**。

校验和的出处（这一条要能查证，写进了模块注释里的表）：

| 组件 | 上游发不发校验和 | 本文件里的值 |
|---|---|---|
| colima | 发（`<资产名>.sha256sum`） | 与上游发布值**一致**，2026-09-21 核对过 |
| lima | 发（`SHA256SUMS`） | 与上游发布值**一致** |
| docker compose | 发（`<资产名>.sha256`） | 与上游发布值**一致** |
| docker CLI 静态包 | **不发**（`download.docker.com` 的 `.sha256` / `.sha256sum` 实测都是 404） | 从官方 HTTPS 地址下载后**自算并钉住**，报告里如实写明 |

**两个下载源并列测速择优**：官方地址（GitHub / download.docker.com）与
腾讯云香港桶 `hunter-dl-hk-1253756459` 的 `runtime/<组件>/<版本>/<文件名>`。
八个文件已经同步上去并**逐个核对过与清单一致**（见第三节）。
新增 `scripts/runtime-mirror.py` 与 `.github/workflows/runtime-mirror.yml`：
每天核对一次「桶里的副本是不是还和清单逐字节相同」，对不上就红。

#### 装在哪、隔离得干净不干净

```
~/.hunter/runtime/
  bin/            docker（官方静态 CLI）、colima
  dist/lima/      lima 整包（bin/limactl + share/lima，相对位置不能拆）
  docker-config/  我们自己的 DOCKER_CONFIG，cli-plugins/docker-compose 在这儿
  lima/           LIMA_HOME —— 虚拟机磁盘在这里面
  colima/         COLIMA_HOME —— profile 与 docker.sock
  cache/          下载中转，校验通过才往外搬（装完就删）
  installed.json  装了哪几个版本、从哪个源下的（设置页显示它）
```

**一个字节都不会落在 `~/.hunter` 外面** —— 不写 `/usr/local`、不改 shell 配置文件、
不碰用户的 `~/.docker`。这不是靠「我们没写那一行」保证的：
所有写文件的地方都过 `guard::writable_path`，越界会被拒。

profile 名是 `hunter`，**不碰用户可能已经有的 `default`**。

#### 虚拟机资源：按本机配置取保守值

| 项 | 取法 | 区间 |
|---|---|---|
| CPU | 本机核数的一半 | 2–4 |
| 内存 | 本机内存的 1/4 | 4–8 GiB |
| 磁盘 | 剩余空间的 1/3 | 20–60 GiB |

任何一项读不到就用**下限**，不猜一个大的。有单测钉住这三个区间。

`vm-type` 用 `vz`（macOS 自带的虚拟化框架）。**macOS 低于 13 时直接拒绝并说清原因** ——
换 qemu 要再下一套东西，本版没做，所以不假装支持。

#### 与已有运行时共存

判定在 `builtin::decide()`，**不在界面里**：

| 现场 | 做什么 |
|---|---|
| 已有运行时**正在跑** | 一个字节都不下，直接用它 |
| 装了但**没跑** | 先 `start_runtime` 把它点起来，不另装 |
| 内置运行时**之前装过** | 起它的虚拟机就行（`start_builtin_runtime`） |
| 一个都没有 | 才走 `install_runtime` |
| 这个平台装不了 | 如实说原因，不装一半 |

#### 一键卸载

设置页 →「容器运行时」→「卸载内置运行时」= `colima delete --profile hunter --force`
+ 删掉 `~/.hunter/runtime` 整棵树 + 把设置里指向它的 `docker_path` 撤回。

守卫这一侧新增 `deletable_trees()`：**「可以整棵删掉」的清单里只有这一个目录**。
`~/.hunter` 下别的目录一个都不在里面（`app/` 有用户的 key、`backups/` 是他的备份、
`diagnostics/` 是他导出的包）。有单测逐个断言。

#### 事件流里显示什么

下载进度是**真实字节数**（`http::download_to_file` 边下边报，每 4 MB 更新一行），
然后是「校验通过」、「虚拟机起来了（用时 N 秒）」。虚拟机起好之后还要再确认一次
**socket 文件真的出现了**才算成功 —— colima 说起好了不算数。

#### macOS 备选路线：OrbStack 官方 dmg

`src-tauri/src/runtime/orbstack.rs`（424 行）。设置里可选，**不是默认**。

下 dmg（`https://orbstack.dev/download/stable/latest/{amd64,arm64}`，实测 307 到
`cdn-updates.orbstack.dev/<arch>/OrbStack_v2.2.3_20963_<arch>.dmg`）→ 验签三道 →
`hdiutil attach -readonly -nobrowse` → `ditto` 拷到 `/Applications`（不可写则
`~/Applications`）→ 拷完**再验一次签名** → 卸载镜像。

验签三道，**缺一不可**：

| 检查 | 命令 |
|---|---|
| 代码签名完整 | `codesign --verify --deep --strict` |
| 公证 / Gatekeeper 放行 | `spctl -a -t open --context context:primary-signature` |
| **签名者是不是 OrbStack** | `codesign -dv` 里的 `TeamIdentifier` 必须等于 `HUAQ24HBR6` |

第三道单独说一句：**「签名有效」不等于「签名的人是 OrbStack」**。
不比对 Team ID 的验签是假验签。

**为什么它不是默认**：OrbStack 首次启动会弹系统级提示（欢迎页、安装辅助程序要管理员
密码）——那是 macOS 与 OrbStack 自己的交互，**启动器无法也不应代点**。
所以这条路走不到「零点击」。这句话原样写在代码常量 `FIRST_RUN_NOTE` 里、
界面上、以及这份报告里，还有一条单测钉住它不许被删掉。
另：OrbStack 个人使用免费、商用需授权，界面上注明。

#### 有 Homebrew 时

**照样走内置运行时**，不再依赖 brew。理由是行为一致：同一台机器上跑两次、两台机器上
各跑一次，装到的是同一份东西，卸载方式也一样。`brew_install` 这个动作还在表里
（模型有时会想用它装别的），但「没有 Docker」这条规则不再走它。

#### Windows / Linux：做不到零操作，不假装能

- **Windows**：WSL 与 Docker Desktop 都要管理员。代码骨架在
  `builtin::supported()` 里如实拒绝并说明原因；`manifest::for_target("windows", …)` 返回空。
  一次 UAC 提权安装的设计见第六节，**本轮未实现真机**。
- **Linux**：装 Docker Engine 要 sudo。规则层给出 `curl -fsSL https://get.docker.com | sh`
  这条命令并**等用户执行完**（「需要你」卡片 →「我执行完了，继续」），不替他提权。
  rootless Docker 的评估见第六节。

### 1.3 `reuse_existing_hunter` —— 直接用你已经装好的那一套

`src-tauri/src/takeover.rs`（595 行）+ `src/pages/TakeoverPanel.tsx`。

**默认仍然是并存。** 这一条从 I5 起没变过。

#### 那张卡片**不阻塞**

发现本机已有 Hunter 时，过程流里出现一张卡片，两个结论式按钮：

- **和它并存（推荐，不动它）**
- **直接用「xxx」，不再装一套**

卡片上写着：「不点也行 —— 默认就是「和它并存」，下面这一步已经在跑了。」

> **为什么不阻塞**：并存是推荐做法，也是不点任何按钮时会发生的事 ——
> 那就没有理由把安装停在这里等一次点击。「授权之后零点击」是这一整套的底线，
> 而且测试机上的回归场景 5（旧栈占满 5 个端口）本来就要求零点击跑到 6/6。
>
> 「必须问」指的是**那个动作**：不问就不会接管。不是「每次看见别人的 Hunter 就停下来问」。

点了「直接用它」之后，项目名记进 `Handle::takeover`（**另一条通路**，不走那个会挂住的
condvar），总指挥在**下一个步骤开始前**读到就改道：走动作表 → 守卫 → 审计，
把项目名 / 工作目录 / compose 文件 / web 端口写进 `launcher.toml` 的 `[takeover]` 段，
然后以 `takeover: Some(项目名)` 结束这次安装。

装完之后才点的话，**如实说「这一下点晚了」**并告诉他去哪里改 —— 不留一句
「这就改道」却什么都不发生。

#### 接管**不等于**拥有

那一套是用户自己装的，里面有他的数据。所以三条硬规矩，**每一条都是代码**：

| 规矩 | 实现 |
|---|---|
| 任何改动类操作先二次确认 | `Op::needs_confirm` **恒为真**（不是一个可以配的开关）；`takeover::run` 不给 `confirmed` 就直接拒绝，文案由 Rust 给、界面不另写一套 |
| 任何情况下不删它的卷 | 只有 `stop` / `start` / `restart` 三个操作，**连 `down` 都没有**；守卫 `argv_takeover` 再拦一道 |
| 找不到工作目录就只读 | `manageable()` 为假时改动类操作一律拒绝并**说清原因与出路** |

第二条值得多说一句：**接管态下连 `down` 都不给做**。`docker compose down` 本身不删
命名卷，但它会删容器与网络 —— 「用户点了停止、结果容器没了」与他的预期差太远。
要停就 `stop`，能原样 `start` 回来。

#### 守卫那一侧：`argv_takeover` 比默认那道**更严**，不是更松

默认规则是「改动容器状态的 docker 命令必须 `--project-name hunter`」。接管时项目名当然
不是 `hunter`，所以要开一个口子。这个口子有四把锁：

1. `[takeover] project` 必须**非空**，且命令里指名的就是它；
2. 子命令只能是 `stop` / `start` / `restart` / `logs` / `ps`；
   `down` / `rm` / `kill` / `up` / `create` 一律拒绝；
3. **任何** `-v` / `--volumes` 写法一律拒绝（通用那道只在 `down` / `rm` 上拦，
   这一条是接管态自己加的一层）；
4. 剩下的全部检查照旧走通用那一道（`sudo`、改网络设置、`/etc/hosts`、任意 shell……一条不少）。

这一段有四条单测，包括「没接管时指向别人的项目一律拒绝」与「接管态不放松通用规则」。

#### 运行面板换成什么样

接管态下 `Dashboard` 换成 `TakeoverPanel`。与普通运行面板的三点不同：

1. **数字更少**。额度、数据源、今日对话这些要读我们自己 `.env` 才知道的东西，
   这里一概没有 —— 那一套不是启动器装的，我们没有它的 key，**也不该去猜**。
   能读到的只有 `docker ps` 给的：容器名、状态、镜像、端口。
2. **每一个改动类按钮都要二次确认**，文案由 Rust 给。
3. **没有「停止并删除」这类按钮。**

顶上一条横幅常驻：「这一套是**你自己装的**，不是启动器装的……任何情况下都不会删它的数据卷。」

### 1.4 一键反馈直达

`feedback::one_click()` + `src/pages/ErrorPage.tsx` 里的 `SendToDev`。

三步，**一步都不省**：

1. 在**本机**生成脱敏诊断包（沿用 `export_zip` 那一套 `mask_home` + 出口闸）；
2. 把**将要贴出去的 issue 标题与正文原样摆给用户看**；
3. 他点「打开 GitHub 提 issue」才开浏览器，内容已预填好。

**它不发送任何东西，也没有「已上报」这种字段。** 有一条单测断言回执里不许出现
「已上报 / 已发送 / 上传成功」这几个词（总控规则：不得假装上报成功）。

出口闸这一版加严一档（`assert_clean_strict`）：在原有的「key 形状 / 完整邮箱 /
完整 IPv4」之上，**连当前用户名与主机名都扫**。理由是 `mask_home` 只抹路径，
而用户名会以别的形态混进来（容器名前缀、compose 项目名跟着目录名走……），
主机名则出现在 `docker info` 的 `Name:` 一行里 —— 那一行本身是有用的诊断信息，
所以是**出门前这一道**负责拦住它，而不是把整段扔掉。

**扫到东西就不给「打开 GitHub」那个按钮。** 宁可让这条路走不通，
也不把可能带隐私的文字预填进一个公开页面。

### 1.5 顺手清掉的四条遗留

| # | 事项 | 怎么改的 |
|---|---|---|

## 二、偏离方案的决策与原因

| # | 方案怎么写的 | 实际怎么做的 | 原因 |
|---|---|---|---|
| 1 | `install_runtime`（mac：`brew install --cask orbstack`；无 brew 则打开官网下载页） | **有没有 brew 都走内置运行时（Colima）**；OrbStack 降为设置里的备选 | 用户 2026-09-21 17:00 明确要求零操作。`brew install --cask orbstack` 要有 brew（很多用户没有），而且装完 OrbStack 首启仍然会弹系统提示 —— 两条都走不到零点击。内置运行时是唯一一条全程用户态、不要管理员密码、可一键卸载的路 |
| 2 | 「需要你」卡片给两个结论式按钮（`reuse_existing_hunter`） | 卡片**不阻塞**，默认并存照常往下跑 | 「必须问」约束的是**那个动作**（不问就不接管），不是「每次看见别人的 Hunter 就停下来」。而且测试机的回归场景 5 要求「旧栈占满 5 个端口时授权后零点击到 6/6」——阻塞就不可能过 |
| 3 | 复核员否决 → 退回诊断员 | 退回时**跳过规则层**，直接问模型 | 规则层是确定性的，原样再跑一遍必然给出同一个计划，等于死循环 |
| 4 | docker CLI 静态包按 sha256 校验 | 校验和是**我们自算并钉住**的，不是上游发布的 | `download.docker.com` 不发布 mac 静态包的校验和（`.sha256` / `.sha256sum` 实测 404）。我们从官方 HTTPS 地址下载一次、算出来钉在清单里，并在代码注释与本报告里写明这一条与另外三个组件的区别 |
| 5 | Linux 分支评估 rootless Docker | **评估了，没做**（结论见第六节） | `dockerd-rootless-setuptool.sh` 的前提是**系统里已经装了 docker 的 rootless 包**（`docker-ce-rootless-extras`），而装那个包本身就要 root。它解决的是「有 docker 但不想用 root 跑 daemon」，不是「机器上没有 docker」——和本轮要解决的问题不是同一件事 |
| 6 | 用 tar crate 解压 | 用**系统自带的 `tar`** | 三个平台都自带（macOS / Windows 10+ 是 bsdtar，Linux 是 GNU tar），比往依赖树里再塞 `tar` + `flate2` 两个 crate 划算。安全性来自上一步：文件的 sha256 已经和清单对上了，内容是确定的，解压目标是我们自己建的空目录、`-C` 指死 |

### 3.1 复核员 —— 真实调网关，通过与否决各拿到一次

为了能在 Linux 测试机上真的跑一遍复核员（它只在「计划含 `Sensitive` 动作」时触发，
而那种现场不是随时能造出来的），新增了一条命令行入口：

```
hunter-launcher --review <动作id[:键=值;…][,动作id…]> --review-why "<诊断员给的理由>" --key-file <路径>
```

**走的是同一个 `reviewer::review()`、同一段提示词、同一次真实网关调用**，不是模拟，会花额度。
计划里的动作**必须真的在动作表里、参数也必须过校验** —— 这条路不给任何绕过
`actions::plan` 的机会。
