# I9 · 0.1.8 真机首测的三个 P0 · 「上次没装成功」这件事

> 迭代轮：I9 · 2026-09-22（上海时间）
> 依据：`plan/I9.md`、0.1.8 在用户 Mac 上的首测现场（`plan/mac-0.1.8-20260922/`）、
> `plan/AI自动驾驶安装_多智能体方案.md`、`plan/总控规则.md`
> 版本：`launcher-v0.1.9`（prerelease）
> 测试机：`34.133.8.3` · Ubuntu 24.04 · 2 核 8G · Docker Engine 29.8.1 · compose v5.5.1

## 零、一句话

0.1.8 在用户 Mac 上第一次跑（2026-09-22 14:48–14:58），**它自己上一次留下的残骸
把自己认成了别人**：

```
14:49:13  ~/.hunter/runtime/bin/docker 在 → 判成「你装了 Docker，只是 daemon 没起」
          ~/.hunter/runtime/bin/colima 在 → 判成「你装了 Colima，把它启动起来」
14:49:15  执行 <用户目录>/.hunter/runtime/bin/colima start
                              ↑ 我们自己的 colima   ↑ 没有 --profile、没有 COLIMA_HOME
          → 60 秒超时 → 「没能自动装好」
```

三个后果，都是 P0：

1. **0.1.8 的主线（没有 Docker → 内置运行时）一步都没走到**；
2. 那条裸命令用的是默认的 `~/.colima`，**在用户家目录里新建并启动了一台与 Hunter
   毫无关系的 `default` 虚拟机**（2 核 2 GB，`~/.colima` 占 1.4 GB）——
   「只在 `~/.hunter` 里动东西」这条承诺当场就破了；
3. 14:54 AI 第 1 轮给出的 `start_builtin_runtime` **62 秒就把虚拟机起来了**
   （docker 29.5.2 可用，本地 Claude 事后实测 `docker info` 正常），
   可安装一步都没往下走 —— `~/.hunter/app/` 到 14:58 还是空的，界面停在失败卡片上，
   用户只能导出诊断包。

外加两条：这 5 分钟里**每一条 `docker ps` 都打在 `/var/run/docker.sock` 上**
（内置运行时的 socket 在 `~/.hunter/runtime/colima/hunter/docker.sock`），
端口冲突检测整条被跳过；以及失败之后界面掉进「每一步都要你点确认」的模式，
**用户点了四次**，而他在授权页上选的是全自动。

本轮把这五件事都修了，并在测试机上把现场一比一复现出来验过。

**实测又撞出 7 个问题**（第六节），其中一条是**打完 tag 之后**复查才发现的：
有残骸的机器上，我们自己的隔离参数会让**用户自己的 colima** 起不来（6.6）。最难看的一条：我们的**残骸会把用户一套好好的 Docker 弄坏**
（6.1）—— 那一条是复现现场时当场炸出来的，不是读代码读出来的。

## 一、本轮做了什么

### 1.1 一个新模块：「当前生效运行时」（`runtime/effective.rs`）

五个毛病里有三个是同一个缺口：**没有人问过「现在到底该用哪个运行时」**。
每个调用点各自去猜，猜出来的还不一样。

新模块把这件事收成一次判定，判定顺序按任务书 P0-1 写死：

| 顺序 | 问什么 | 判据（**全是文件系统与 socket，不跑任何子进程**） |
|---|---|---|
| ① | 内置运行时的虚拟机在跑吗 | `~/.hunter/runtime/colima/hunter/docker.sock` 连得上 |
| ② | 用户自己的 Docker 在跑吗 | 已知 socket 逐个 `connect`（系统 / Docker Desktop / OrbStack / Rancher / 他自己的 colima；`DOCKER_HOST` 排最前） |
| ③ | 内置运行时装了（哪怕只装了一半）吗 | `runtime/` 下那四件工具 |
| ④ | 用户自己的 Docker 装了没起吗 | 已知 socket 路径存在 / `.app` 在 / `~/.colima` 里有 profile |

内置运行时的状态分**四档**，「装了一半」是一个真实存在的中间态，不能和「没装」合并：

```rust
pub enum BuiltinState { Absent, Partial(Vec<String>), Stopped, Running }
```

**为什么一个子进程都不跑**：这个函数会被 `runtime::env::compute()` 调到，
而那个函数在每一次建 `Command` 的路径上。跑子进程就会凑出
`env::compute → effective::current → docker version → base_command → env::apply
→ env::current → compute` 这个环 —— I8 在 `netproxy` 与 `runtime::env` 之间
已经凑出过一模一样的一个，CI 的 macOS runner 上直接 `stack overflow`（I8 报告 6.7）。
**同一个形状的环，不踩第二遍。**

判定本身拆成纯函数 `decide(builtin, user_running, user_installed)`，理由见 6.3。

### 1.2 P0-1 · 残骸走内置主线，不再被当成「你的 Docker 没开」

| 层 | 0.1.8 | 0.1.9 |
|---|---|---|
| 总指挥 `Step::Docker` | 第一句就是 `docker::detect()`（找到的是**我们自己**那份 docker）→ `E_DAEMON_DOWN` | 先问 `effective::current()`；内置运行时是主角且没起来 → 新错误码 **`E_BUILTIN_DOWN`** |
| 规则层 | `daemon-down-app-installed`：「Colima 装着但没在运行，把它启动起来」 | 新规则 **`builtin-runtime-down`**，排在所有 docker 规则**前面** |
| 侦察员 `runtime_apps()` | 把 `~/.hunter/runtime/bin/colima` 报成「用户装的 Colima」 | 拆成两条：`builtin`（我们自己的）与 `colima`（**只认 `~/.colima` 里本来就有的 profile**）；`builtin` 被 `daemon_down` 那条规则显式排除 |
| `builtin::decide()` | 第一句 `docker::detect()` | 先问 `effective`，再问用户的 Docker |

`E_BUILTIN_DOWN` 对应三条路，全都零 token：

| 现场 | 动作 |
|---|---|
| 文件缺了几个（上次没装完） | `install_runtime` —— 只下缺的那几个 |
| 文件齐了、虚拟机没起来 | `start_builtin_runtime` |
| 这一轮已经起过一次没成 | **`repair_builtin_runtime`**（本轮新增动作，见 1.3） |

### 1.3 P0-1 续 · 残骸不可用时自动清理并重建（`repair_builtin_runtime`）

新动作，级别 `Safe`。做三件事，每一件都有明确边界：

1. `colima delete --profile hunter --force`（带全套隔离环境变量）；
2. 删掉 `~/.hunter/runtime/colima/hunter` 与 `~/.hunter/runtime/lima/colima-hunter`
   两个目录 —— **每一个都先过 `guard::writable_path`**，解析后必须落在 `~/.hunter` 里；
3. 按清单核一遍已经落地的文件（`broken_items()` / `drop_broken_items()`），
   **内容对不上的删掉重下，对得上的一个字节都不重下**。

下载回来的二进制与那份 341 MB 的虚拟机镜像**不无条件删** —— 删了就得重下。
`colima delete` 失败不算失败（残骸的定义本来就是「colima 自己也说不清它是什么状态」），
目录照样清干净。

另外 `start_argv()` 里那句 `--disk-image` 改走 `verified_disk_image()`：
**先按清单核 sha256 与 sha512，核过了才交给 colima**。
「上次下载时是好的」不等于「现在是好的」—— 用户 Mac 上那个文件已经躺了一天，
中间经历过一次装到一半被放弃、若干次 `colima start`。

### 1.4 P0-2 · 所有 colima 调用带隔离参数，三道防线

| # | 在哪 | 做什么 |
|---|---|---|
| ① 环境 | `runtime/env.rs` | 内置运行时**哪怕只装了一半**，所有子进程的 `COLIMA_HOME` / `LIMA_HOME` 就钉在 `~/.hunter/runtime` |
| ② 规划 | `actions::start_runtime_argv("colima")` | 分成两件事：我们自己那份 → **如实拒绝并指路**（走 `start_builtin_runtime`）；用户自己那份 → 必须 `--profile <他原本就有的那个>` |
| ③ 执行 | `proc::isolation_guard` → `guard::colima_call` | **挂在真正 `spawn` 之前的那一刻**，不管这条命令是谁写的、走的哪条路 |

第三道是关键。动作表那一道（`guard::argv`）只看得到 AI / 规则层**提出来**的动作，
而 0.1.8 那条闯祸的 `colima start` 是**动作表自己规划出来的** ——
提案那一侧没有任何人觉得它有问题。挂在 `proc` 这一层意味着：
只要它最终要变成一个进程，就必须先回答「你用的是谁的 `COLIMA_HOME`、动的是哪一台虚拟机」。

判据（两条路，都是代码，不是提示词）：

| 情形 | 放行条件 |
|---|---|
| 用我们自己那套 colima | `COLIMA_HOME` 解析后落在 `~/.hunter/runtime` 里，**且** profile 是 `hunter` |
| 起用户原有的 profile | `--profile <名字>` 里的名字是 `~/.colima` 里**本来就有**的目录，**且**子命令只能是 `start` |
| limactl | `LIMA_HOME` 必须落在 `~/.hunter/runtime` 里 |

两条都不满足 —— 包括「没写 `--profile`」这种最危险的写法 —— 一律拒绝并**记审计**。

还有一条容易漏的：侦察员判断「用户有没有 colima」时**一条 `colima status` 都不跑**，
改成读 `~/.colima` 的目录名 + 看它们的 `docker.sock` 在不在。
跑 `colima status` 用的是默认的 `COLIMA_HOME`，而 0.1.8 正是这样把 `~/.colima` 建起来的。

**自愈那一条没做，原因写在第八节。**

### 1.5 P0-3 · 修好之后自动续上安装

两条路，缺一不可：

| 路 | 在哪 | 做什么 |
|---|---|---|
| 总指挥这一侧 | `auto.rs::repair` | 一个动作失败**不等于**没有别的办法：下一回合规则层若能给出**不一样的**计划就接着走（6.2） |
| 诊断助手这一侧 | `assist::diagnose_and_fix` + `commands::maybe_resume_install` | 全自动档下规则层有把握的 Safe 动作**自己跑掉**；任何一步让 Docker 变成可用、而这一套还没装完 → 后端自己把安装重新跑起来，并发 `assist://resume` 让界面回到过程流那一页 |

诊断面板这条路上**只自动跑 `Safe` / `ReadOnly`**（任务书 P0-3 的原话就是「Safe 级动作」）。
`Sensitive` 不在这条路上 —— 总指挥那一侧在执行它之前还有**复核员**那道门，
这里没有；级别放宽一档、又少一道门，两件事凑一起就是「悄悄把门拆了」。
要装运行时，走的仍是总指挥那条完整通路。这一条有单测钉着
（`诊断面板这条路不自动跑_sensitive_动作`，遍历动作表里每一个 `Sensitive`）。

`can_resume_install()` 的判据写死两条，缺一不可：docker 后台服务连得上了，
**而且**这一套还没装完（compose 文件 / `.env` 没落地，或者六个容器没起齐）。
装完了还自动重装一遍是另一种毛病。

「每一步都要你点确认」那件事也从根上改了：**档位是 `auto` 就不再问**。
把关的门一道没少（动作表 + 守卫 + 级别判定），只是不再让用户去按那个按钮；
**做了什么必须看得见** —— 界面上多了一块「启动器已经替你做了这几步」，
一条条列出来（截图 `i9-error-builtin.png`）。

命令行上对应的是新开关 `--diagnose --fix`。分成两个入口是因为
不带 `--fix` 的 `--diagnose` 在文档里写的是「打印诊断信息」——
**一条印东西的命令不该顺手改这台机器。**

### 1.6 P0-4 · 端口探测走正确的 docker

| 改动 | 说明 |
|---|---|
| `DOCKER_HOST` 的来源 | 从 `builtin::docker_host()`（socket 存在才给）改成 `effective::current().docker_host` ——**内置运行时是主角时一律给**，哪怕 socket 还不存在 |
| 为什么这么改 | 指向我们自己那个还不存在的 socket，会得到一句「连不上我们自己那台虚拟机」；那正是实话。让它悄悄打到 `/var/run/docker.sock` 上，端口检测就整条无声跳过了 |
| `probe::collect` | 五个端口**共用一次** `Survey::collect()`。原来是逐个端口调 `port_free()`，而那个函数每次自己采一遍现场 —— 5 个端口就是 5 次 `docker ps` + 5 次 `lsof`（用户 Mac 日志里同一秒内那一串重复的警告就是这么来的） |
| 诊断报文 | 新增一行「当前生效运行时：…」，送给模型的那一份也有。0.1.8 那次模型拿到的证据**恰好缺了它** |

实测：场景 A 的完整日志里「docker ps 查已发布端口失败」**0 条**（0.1.8 现场是 7 条）。

## 三、测试机实测（全部真跑）

测试机上同时跑着一套 `hunter-community` 旧栈（占 3100 / 8100 / 3921 / 5442 / 6479），
所以每一场都顺带覆盖「本机已有另一套 Hunter」这个场景。

**复现手法**：造一份「内置运行时残骸」——`runtime/bin/docker` 是真的（拷系统那个），
`colima` 是一个**只记账不干活**的假程序，它把「谁调了我、带着什么 `COLIMA_HOME`」
原样写进一个文件。P0-2 要验的两件事，答案就在那个文件里。

| # | 场景 | 结果 | 证据 |
|---|---|---|---|
| A | 内置运行时残骸 + 用户自己的 Docker 在跑 | **零点击装到 6/6 健康**，106 秒，**0 token**，5 个端口自动换到 3101/8101/3922/5443/6480；假 colima **一次都没被调用** | `I9-证据/a-场景A-*.log` |
| B | 内置运行时残骸 + 没有可用 Docker（停掉 daemon） | 判成 **`E_BUILTIN_DOWN`**（不是 `E_DAEMON_DOWN`），规则层直接给内置主线、**0 token**；起不来 → 自动清残骸重建；两轮都不成后如实收场，1 秒 | `I9-证据/b-场景B-*.log` |
| B′ | 同上，**假 colima 收到的每一条命令** | 三条，**全部**带 `--profile hunter` + `COLIMA_HOME=<工作目录>/runtime/colima` + `LIMA_HOME=<工作目录>/runtime/lima`；**一条裸 `colima start` 都没有** | 同上 |
| C1 | 用户自己的 colima（`~/.colima/myprofile` 本来就有） | 规划出来的是 `/tmp/ubin/colima start --profile myprofile` —— **他自己的程序、他原有的 profile** | `I9-证据/c-场景C-*.log` |
| C2 | `~/.colima` 清空（一个 profile 都没有） | colima 这一档**根本不被提出来**（掉到 systemd）；跑完之后 **`~/.colima` 仍然不存在** —— 启动器没有把它建出来 | 同上 |
| C′ | **残骸 + 用户自己也有 colima**（6.6 那一条，最该跑通的一种机器） | 规则层认的是内置那一条（残骸是主角），用户的 colima 一次都没被碰；强制走 `start_runtime(colima)` 时执行的是 `colima start --profile myprofile`（他原有的），而且**父进程里故意塞进去的 `COLIMA_HOME` / `LIMA_HOME` / `DOCKER_HOST` 全部被摘掉**（子进程收到的是「没设」） | `I9-证据/h-场景C撇-*.log` |
| D1 | docker 可用、这一套还没装完 | `--diagnose --fix` 自动跑掉 `remap_ports`（**没有任何点击**），并打出「Docker 现在可用，而这一套还没装完 —— 界面上会自动接着往下装」 | 见下方原文 |
| D2 | 已经装好了（6/6 在跑） | **不**打那一行 —— 不会自动重装一遍 | 同上 |
| D3 | 停掉 daemon 后 `--diagnose --fix` | 自动执行了 `start_runtime(systemd)`（**零点击**）；这台机器是 SSH 无 tty 会话，polkit 没有地方问密码，于是如实报出来 | 见第七节 |
| E | 端口探测走的是哪个 docker | 场景 A 全程「docker ps 查已发布端口失败」**0 条**；日志第一行就是「当前生效运行时：系统 docker（/var/run/docker.sock 连得上）」 | `I9-证据/A-auto.log` |

## 六、实测撞出来的 7 个问题

### 6.1 我们的残骸会把用户一套好好的 Docker 弄坏（**最难看的一条**）

场景 A 第一次跑，装到「写配置」那一步炸了：

```
× 挑下载源、算端口、写配置　compose 文件校验不过：Run 'docker --help' for more information
```

根因：`runtime::env` 里那一句 ——

```rust
e.docker_config = if super::builtin::is_installed() { 内置那一份 } else { … };
```

「装着就用」。可测试机上的现场是：内置运行时是**残骸**（工具在、虚拟机起不来），
而用户自己的 Docker 好好跑着。于是 `DOCKER_CONFIG` 被指到残骸那一份，
`docker compose` 用的是**残骸里那个坏掉的 compose 插件**，安装当场卡死。

这一条比 P0-1 更难看：P0-1 是「我们没把自己的东西认出来」，
这一条是**我们的垃圾把用户一套本来能用的 Docker 弄坏了**。

修法与 `DOCKER_HOST` 同一个口径：**谁生效就用谁的配置**。

这条只有真跑才撞得出来 —— 读代码时那一行看起来完全合理。

### 6.2 「这个办法没成」被当成了「没有别的办法」

场景 B 第一次跑，`start_builtin_runtime` 失败之后当场就收场了，
第二条路（清残骸重建）**一次都没有机会跑**。

`auto.rs::repair` 里，所有动作都失败时无条件 `return Ok(false)`，而失败的动作
已经进了 `failed_actions` —— 下一回合规则层本来会换一条路。
改成：先问一句「下一回合还有没有**不一样的**办法」，有就接着走
（回合上限与 token 预算那几道闸照常管着）。

这是本轮改动自己引入的吗？不是 —— 它一直在那儿，只是在 I9 之前
**没有哪条规则会为同一个错误码给出第二种办法**，所以从来没被看见。

### 6.3 同一张错误码表抄了三份，加新码时漏改一份

场景 B 的命令行上打出来的是：

```
✗ E_UNKNOWN: Hunter 自己那套运行时装好了，虚拟机没起来。…
```

**一句话里两个互相矛盾的说法。** 根因：错误码清单在三处各抄了一份
（`err.rs` 的单测、`headless::code_from_str`、前端的 `ERROR_CODES`），
加 `E_BUILTIN_DOWN` 时漏改了中间那份。

修法：Rust 这一侧收成一份 `Code::ALL`，`code_from_str` 改用它，
并加一条 `每个错误码都能从字符串反查回来` —— 下次再加码，漏了当场红。

顺带记一笔同类的事：`effective::decide` 之所以拆成纯函数，
是因为第一版走 `current()`，而开发机与测试机都常驻着一个能连的
`/var/run/docker.sock` —— **「内置运行时是主角」那几条分支在 CI 上一次都跑不到**，
测试会绿，但绿的是「这台机器上 docker 在跑」。
I5 与 I6 的教训都是同一句话：**把那台机器的差异写成一条会红的测试。**

### 6.4 讲解员说了谎（不是故意的）

场景 B 的第 3 回合，事件流里写着：

```
✓ 找到原因　刚才起那台虚拟机没成 …… 把 Hunter 自己的这台虚拟机清掉重建一次
… 正在处理：等 Docker 起来
✓ 正在处理：等 Docker 起来　等了 121 秒，Docker 守护进程还是没起来。
```

说的是「清掉重建」，做的是「干等 121 秒」。根因：计划是
`[repair_builtin_runtime, wait_daemon]`，而 `repair_builtin_runtime`
已经失败过、被过滤掉了，只剩后面那条「等它生效」单独跑。

修法：**计划的头一条被滤掉，整条作废**。一个计划里第一条是「做事」的，
后面跟着的多半是「等它生效」；头一条没了，剩下的只会白等。
改完场景 B 从 125 秒降到 1 秒。

红线 1 说的是「不编数字」，这一条提醒了另一半：
**把两件事拼在一起讲，哪怕每一句单独看都是真的，合起来也是假的。**

### 6.5 「忘了拿 `HUNTER_HOME` 那把锁」—— 这一轮第三次，所以这次治本

I9 新加的测试会把 `HUNTER_HOME` 指到临时目录，于是**一批没拿锁的老测试当场红了**，
而且红的位置和肇事者毫无关系：

| 在哪红的 | 症状 |
|---|---|
| 开发机 | `guard::路径守卫解得开_双点_与软链`、`guard::审计能写能读` |
| CI · Ubuntu | `guard::安装脚本只能跑自己下的那一个` |
| CI · Windows | 上面几条 + `guard::删除只限启动器自己生成的文件` / `只有内置运行时目录可以整棵删` / `提权只允许表里那两件事` |
| CI · macOS | `auto::提前批过的只有装运行时那一个`（`cfg.save()` 去 chmod 一个刚被删掉的 `app/`） |

它们**一直是坏的**，只是在 I9 之前没有哪条测试会去动那个变量，所以时序从没撞上。
I7 记过一次这个教训、I9 又抓到七条 —— 逐条去补是治标，所以这次做了三件事：

1. `paths::test_home()`：**一份共用实现**（锁 + 干净临时目录 + 建好整棵目录树 +
   `Drop` 里还原），不再让每个模块各抄一遍「存旧值 → set_var → 还原」；
2. 把找到的每一条都补上（用一段脚本扫「测试体里碰了 `paths::` / `LauncherConfig` /
   `ensure_dirs` 却没拿锁」的）；
3. **治本那一条**：`#[cfg(test)]` 下，没设 `HUNTER_HOME` 时的默认工作目录
   不再是真的 `~/.hunter`，而是 `/tmp/hunter-unittest-<pid>`。

第 3 条才是关键。测试机上的 `~/.hunter` 是一套**真的、装好的** Hunter ——
里面有 `.env`（真 key）、compose 文件、跑着的容器对应的配置。
一条忘了拿锁的测试往那儿写一次，毁的是真实安装。
默认值挪出真实目录之后，忘了拿锁最坏也只是两条测试互相打架。

### 6.6 发布前最后一刻抓到的一条：我们的隔离参数会让**用户自己的 colima** 起不来

打完 tag、release 流水线正在跑的时候，回头复查 P0-2 的执行路径，发现一个洞：

`runtime::env` 会给**所有**子进程钉上我们的 `COLIMA_HOME`（这是 P0-2 的第一道防线）。
可 `start_runtime(colima)` 起的是**用户自己**那台 —— 于是这条完全正当的命令
会带着**我们的家**去找**他的 profile**，被第三道守卫当场拒掉。

场景 C 没撞到它，纯属运气：那一场的 `~/.hunter-i9c` 是空的、没有残骸，
所以 `COLIMA_HOME` 根本没被钉上。**有残骸 + 用户自己也有 colima** 才会撞上，
而那恰恰是最该跑通的一种机器。

两处一起修：

- `guard::colima_call` 判「这是谁的 colima」**看程序路径，不看环境变量** ——
  程序在 `~/.hunter/runtime` 里就是我们的，别处就是他的；
- `start_runtime` 走新的 `proc::run_timeout_user_runtime`，
  把我们那四个变量（`COLIMA_HOME` / `LIMA_HOME` / `DOCKER_HOST` / `DOCKER_CONFIG`）
  **摘掉**再执行 —— 起他的东西，就不该带我们的家。

另加两条单测：「有残骸时起用户原有的 profile 照样放行」、
「不许拿用户的 colima 去写我们自己的家」。

**这一条的教训**：守卫写得越严，越要问一句「它会不会把**正当的事**也拦下来」。
P0-2 的三道防线是对的，但第一道（给所有子进程钉环境变量）和第三道（按环境变量判归属）
凑在一起，恰好把「起用户自己那台」这件正当的事判成了越界。

### 6.7 「有一个空目录」被当成了「装了一半」

同一轮复查里发现的第二条。`builtin_state()` 判「没装」的条件写成了
「四件工具一件都没有 **而且** `runtime/` 目录不存在」。

可测试机上真实的 `~/.hunter/runtime` 里只剩一个空的 `cache/`
（更早某次装到一半留下的）—— 于是它被报成「装了一半（还缺全部四件）」。
后果：停掉 docker 之后，这台机器本该走「你的 Docker 没开 → 启动 systemd 服务」，
却会去走内置主线，而 Linux 上那条路根本走不通。

判据改成「一件工具都没有就是没装」。**一个空目录不是一次安装。**
加了一条单测（`只有空的_runtime_目录不算装了一半`），并在测试机上用**真实的**
`~/.hunter` 复验了一遍：停掉 docker → 规则层给的是 `daemon-down-app-installed`，
不是 `builtin-runtime-down`。

## 八、一个刻意没做的决定：不去碰 `~/.colima/default`

任务书 P0-2 里有一条「自愈」：检测到 `~/.colima` 里存在**由启动器创建**的 `default`
实例就停掉它，并在过程流里说明；删除只在用户确认后做。

**本轮没有做，理由是那个「由启动器创建」判不准。**

任务书给的判据是「启动器审计日志里有过裸 `colima start` 且该实例创建时间与之吻合」。
实际去写的时候有三个坎：

1. **审计日志本身可能不在了** —— 用户重装过启动器、清过 `~/.hunter/logs`，
   或者根本是从另一台机器同步过来的家目录；
2. **时间吻合不构成证据** —— 用户完全可能在同一分钟里自己也起过一台
   （0.1.8 那次前后，用户和本地 Claude 都在这台机器上敲命令）；
3. 更要紧的：**判错的代价不对称**。判对了，省用户一次 `colima stop`；
   判错了，我们停掉的是他自己在用的虚拟机 —— 那是「不动用户东西」这条红线的正面违反。

任务书自己也写了「拿不准就不动」。我们拿不准，所以不动。

**替代做法**（本轮已做）：把这件事**说清楚**而不是替他做。
常见问题里「之前装过没成功，再装会怎样」一节明写：0.1.8 可能在 `~/.colima` 里
建出过一台叫 `default` 的虚拟机、它占多少、它和 Hunter 没关系、
启动器不会替你删。用户要清掉的话，那是他自己的 colima。

**这件事需要用户拍板**：要不要在设置页里加一个「我确认这台 `default` 是启动器建的，
帮我停掉」的按钮（只停不删）？判定仍然由用户做，启动器只执行。
