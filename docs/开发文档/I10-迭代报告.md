# I10 · 0.1.9 真机：内置虚拟机没有 DNS

> 迭代轮：I10 · 2026-09-22（上海时间）
> 依据：`plan/I10.md`、0.1.9 在用户 Mac 上的现场（`plan/mac-0.1.9-20260922/`）、
> `plan/AI自动驾驶安装_多智能体方案.md`、`plan/总控规则.md`
> 版本：`launcher-v0.1.10`（prerelease）
> 测试机：`34.133.8.3` · Ubuntu 24.04 · 2 核 8G · Docker Engine 29.8.1 · compose v5.5.1
> 现场日志与截图留在 `docs/开发文档/I10-证据/` 与 `docs/screenshots/I10/`

## 零、一句话

0.1.9 在用户 Mac 上（2026-09-22 21:14–22:05）**该做的都做对了**：认出内置运行时、
走代理取到 compose、从腾讯云香港拉下 849 MB（693 秒）、`compose up` 成功、全程零点击。
然后卡在最后一米：

```
21:26–21:39  opencode 一直 unhealthy，诊断助手读了 4 次日志、up 了 4 次
21:39        E_START_TIMEOUT · 规则层 unknown · 5/6 健康
```

根因是一件**用日志永远看不出来**的事：

> 启动器自带的那份虚拟机镜像里没有 systemd-resolved，
> 而 `/etc/resolv.conf` 出厂就是一条指向它的断链 ——
> **虚拟机和它里面的每一个容器都没有任何 DNS。**

更要紧的不是健康检查：容器解析不了 `hunter.agentpit.io`，
**就算六个服务全绿，用户也一句话都问不出来**。

本轮做了三件事：把这件事治本（第一节）、把「容器能不能上网」升成一项必检（第二节）、
让已经装好的机器自己痊愈（第三节）。外加**实测当场抓出来的两条**（第五节），
其中一条是我们自己新写的代码差点把「本机没有这个镜像」报成「容器连不上网」。

这一轮还把用户 Mac 上那一幕**在 Linux 上原样复现出来了**（第四节场景 H）——
不用虚拟机、不用 macOS：5/6 健康、opencode unhealthy，和真机一模一样。

## 一、P0-1 · 这份镜像为什么没有 DNS，以及怎么治本

### 1.1 先把根因查实（不是推测）

把启动器**真正会下发的那个文件**下下来、解开、loop 挂载、逐条查。
原始输出在 `I10-证据/0-镜像为什么没有DNS-逐条实查.log`。

| # | 事实 | 怎么查的 |
|---|---|---|
| 0 | 这确实是我们下发的那一个 | `sha256 4cd967d2…15e6`，与 `manifest.rs` 里钉的一字不差 |
| 1 | `/etc/resolv.conf` → `../run/systemd/resolve/stub-resolv.conf`，**出厂就是断链** | 挂载点上 `ls -la` |
| 2 | **镜像里没有 systemd-resolved** | `dpkg -l` 里只有 `systemd` / `systemd-dev` / `systemd-sysv` / `systemd-timesyncd`；`usr/lib/systemd/systemd-resolved` 不存在，`systemd-resolved.service` 也不存在 |
| 3 | 也没有 `resolvconf` / `openresolv` | 同上，一个都没有 |
| 4 | lima 写 DNS 的第一条路（cloud-init 的 `resolv_conf` 模块）**根本不会跑** | 模板 `resolv.conf.tmpl` 在，但 `/etc/cloud/cloud.cfg` 的 `cloud_config_modules` 里**没有** `resolv_conf` 这一项（Ubuntu 的默认配置就是这样，它指望 resolved），`cloud.cfg.d/` 里也没加回来 |
| 5 | lima 写 DNS 的第二条路（netplan 的 `nameservers:`）**也到不了 `/etc/resolv.conf`** | lima v2.2.0 `pkg/cidata/cidata.TEMPLATE.d/network-config` 把 DNS 写成 netplan 的 `nameservers.addresses`，而 netplan/systemd-networkd 只是把地址交给 systemd-resolved —— 没有 resolved，这条路的终点是空的 |

为什么是「Ubuntu 24.04 minimal」这一款才有这个问题：**24.04 把 systemd-resolved
拆成了一个单独的 deb 包**，minimal 镜像不装它；而基础根文件系统里那条
`/etc/resolv.conf` 符号链接照旧躺在那儿。**链接在，被链接的人不在** —— 一台从出生起就没有 DNS 的机器。

### 1.2 结论：`colima start --dns` 治不了这个

任务书给了两条修法，允许任选一条能证明有效的。读完 lima 源码之后，第一条被排除了 ——
**不是因为麻烦，是因为它在这份镜像上不成立**：

`colima --dns` / `colima.yaml` 的 `dns:` 最终只落到 `instConfig.DNS`，
lima 拿它算出 `args.DNSAddresses`（`pkg/cidata/cidata.go`），
然后把这些地址交给上面第 4、5 条那两条路。**两条路的出口都是堵的**，
换几个地址进去没有任何区别。

顺带查实了另外两个数（都写进代码注释里了）：

* lima 的 usernet（gvisor-tap-vsock）里 **网关 `192.168.5.2` 自己就是 DNS 服务器**
  （`pkg/networks/usernet/gvproxy.go` 原话：「GatewayIP handling all request, also answers DNS queries」），
  lima 自己算的也是 `SlirpDNS = GatewayIP`；
* `192.168.5.3` 是传统 QEMU slirp 的 DNS 地址，vz + user-v2 这一路上**没有人在那儿听** ——
  和本地 Claude 在用户 Mac 上实测的结果一致。

### 1.3 修法：启动器自己在那台虚拟机里把 resolv.conf 写好

新模块 `runtime/vmdns.rs`。写进去的内容（**每一条都有理由，数值由实测决定**）：

```
# 由 Hunter 启动器写入（只作用于 Hunter 自己的这台虚拟机）。
# 这份 Ubuntu 24.04 minimal 镜像里没有 systemd-resolved，
# /etc/resolv.conf 出厂是一条指向它的断链 —— 虚拟机和容器因此没有任何 DNS。
# 你 Mac 自己的 DNS 设置没有被改动过。
nameserver 192.168.5.2   # lima user-v2 的网关，它自己就是 DNS 服务器，解析跟着你 Mac 走
nameserver 223.6.6.6     # 阿里公共 DNS，国内可直连
nameserver 119.29.29.29  # 腾讯 DNSPod 公共 DNS，再兜一层
options timeout:2 attempts:2
```

| 地址 | 依据 |
|---|---|
| `192.168.5.2` | lima 源码（上面 1.2）+ 本地 Claude 在用户 Mac 上实测可用。走它 = 走用户 Mac 自己的解析，公司 DNS / VPN 跟着生效 |
| `223.6.6.6` | 本地 Claude 在用户 Mac 上实测可用；**国内可直连**（任务书要求「必须同时对国内网络可用」） |
| `119.29.29.29` | 同为国内可用的公共 DNS，再兜一层 |

两个国内 DNS **在测试机上用真容器验过**：`--dns 223.6.6.6` → 模型网关 HTTP 401 · 0.75 秒；
`--dns 119.29.29.29` → HTTP 401 · 1.08 秒（`I10-证据/m-数值与写入内容的实测.log`）。
401 是没带 key 的正常应答 —— 能拿到任何一个 HTTP 状态码，就证明 DNS + TCP + TLS 全通。

落位用的是 `cp --remove-destination`：**先把那条断链删掉再写普通文件**。
直接 `cp` 会顺着链接去写 `/run/systemd/resolve/`，而那个目录根本不存在。

### 1.4 「持久」不是推理出来的，是三层

| 层 | 做法 | 为什么够 |
|---|---|---|
| ① 文件本身 | 写成**普通文件**（不是链接），落在虚拟机根盘上 | 这份镜像里没有任何东西会去重写它（1.1 的第 2–5 条就是证明：resolved 没有、resolvconf 没有、cloud-init 的那个模块不跑、netplan 到不了这儿） |
| ② 开机再写一遍 | 装一个 oneshot 的 `hunter-dns.service`（`Before=docker.service`），每次开机把 `/etc/hunter/resolv.conf` 拷回 `/etc/resolv.conf` | 「虚拟机重启 / `colima stop/start` / 宿主机重启后依然有效」这句话因此不靠推理 —— **每次开机都重做一遍**。这个 unit 的语法在测试机上过了 `systemd-analyze verify`（退出码 0） |
| ③ 每次启动都复查 | 启动器每一次走到「检查 Docker」那一步都重新探一次，坏了就再修 | **不假设上一次修好了。** 这一层同时也是 P0-3 |

单测钉住的是①②的形状（`vmdns::tests`：写进去的 nameserver 必须含网关 + 至少一个国内公共 DNS、
不许再出现 `192.168.5.3`、unit 必须排在 `docker.service` 前面且**不跑 shell**）。
③ 由 `ensure()` 的调用点保证。

**没能做到的一条如实写在这里**：测试机没有 `/dev/kvm`、CPU 也没有 `vmx/svm` 标志
（`I10-证据/0-…log` 第 7 节），所以**用同一份 disk-image 起一台 lima 虚拟机、
重启它、看 resolv.conf 还在不在**这件事，本项目这台机器做不了。
①②的依据是镜像内容 + lima/colima 源码 + systemd unit 语法校验，不是一次真的重启。

### 1.5 边界：只动 Hunter 自己那台虚拟机

每一条命令都指名 `colima-hunter` 这一台，`LIMA_HOME` 钉在 `~/.hunter/runtime/lima`。
**用户 Mac 自己的 DNS、hosts、代理、防火墙一个字节都不碰** —— 这一条靠的是代码，
不是提示词，见第六节。

## 二、P0-2 · 「容器能不能上网」当成必检项

### 2.1 加在哪两处

| 位置 | 查什么 | 不通怎么办 |
|---|---|---|
| 「检查 Docker」这一步的末尾 | 内置运行时的虚拟机里解析得动域名吗（`limactl shell … getent hosts hunter.agentpit.io`） | **自动修**（第一节那套），修不好 → `E_RUNTIME_NO_DNS` |
| 「下载组件」这一步的末尾（镜像刚到手） | 用**刚拉下来的那个镜像**起一个 `--rm` 的一次性容器，从容器里 `curl` 一次模型网关 | 不通 → `E_CONTAINER_OFFLINE`，整个安装不算成功 |

为什么容器那一项放在「下载组件」之后而不是「启动服务」之后：0.1.9 的教训就是
**等到健康检查超时才发现，白等 13 分钟，而且拿到的错误码指不到根上**。
放在这儿用的是刚拉下来的镜像，**一个字节都不用多下**。

探测命令（展示与执行同一个来源）：

```
docker run --rm --pull=never --entrypoint curl <api 镜像> \
  -sS -o /dev/null -w %{http_code} --max-time 20 \
  https://hunter.agentpit.io/api/saas/llm/v1/models
```

**不带 key**（红线 2）：没有 key 时网关返回 401，而任何一个 HTTP 状态码都意味着
DNS + TCP + TLS 全部走通了。

### 2.2 两个新错误码

| 码 | 什么时候 | 规则层给什么 |
|---|---|---|
| `E_RUNTIME_NO_DNS` | Hunter 自己那台虚拟机解析不了域名 | `fix_vm_dns`，`confident = true`，**零 token** |
| `E_CONTAINER_OFFLINE` | 一次性容器连不上模型网关 | 分两种：虚拟机本身就解析不动 → `fix_vm_dns`；虚拟机好好的（或者跑在用户自己的 Docker 上）→ **不给动作**，如实说清楚我们修不了 |

第二种为什么不给动作：那一类的原因是代理只放行了宿主机、或者网络挡了 443，
**而改用户电脑的网络设置是禁止项**。给一个看着像能修、其实没用的按钮，
就是 I6 那次「换了三次源、268 秒、一个问题都没解决」的重演。

### 2.3 规则层的判据是「试过了」，不是「像是」

`vm-no-dns` 这条规则的判据只有一条：侦察员**真的在那台虚拟机里解析过一次**，没解析出来。
不是「日志里看着像网络问题」。所以它 `confident = true`、零 token。

顺序也钉死了：`vm-no-dns` 排在 `pull-failed` 与「起不来」**前面**。
没有 DNS 的机器上，拉镜像（走代理）可能是成的、容器也起得来，
表现出来只是「某个服务一直不健康」—— 顺序反了就会去换镜像源。

### 2.4 「启动超时」不再是终点

`E_START_TIMEOUT` 这条路上先问一句「是不是根本没有 DNS」：
虚拟机解析不动、或者一次性容器报「解析不了域名」→ 直接给 `fix_vm_dns`（+ 重起容器）。
**0.1.9 那一幕在这里就会被截住。**

### 2.5 侦察员会自己动手探，不再指望模型从日志里看出来

0.1.9 那次诊断助手读了 4 次容器日志都没看出根因 —— 因为
「opencode 的健康检查返回 500」这句话里，看不出「它解析不了域名」。
**那条事实只有真的去解析一次才会出现**，所以现在由侦察员去做：
「起容器」这一类失败上，证据里会多出两行 ——
虚拟机的 DNS 现状、以及一次性容器的实测结果（带真实命令与耗时）。

## 三、P0-3 · 已经装好的机器自己痊愈

用户 Mac 现在的状态是：虚拟机跑着、容器跑着，而 `/etc/resolv.conf`
是本地 Claude 手工改好的。0.1.10 起来之后：

| 现场 | 做什么 |
|---|---|
| 已经修好了 | **什么都不做** —— 不把人家手工改好的推倒重来。只在「开机自动重写那层保险还没装」时补一次 |
| 还是断链 | 自动修，然后（容器已经起着的话）重启虚拟机里的 dockerd 让容器重新拿一份 DNS，再续上安装 |

两个入口：

* **启动器一起来**就在后台查一次（三道闸门：用户授权过、内置运行时的虚拟机在跑、
  查不成不当成坏）；
* **每一次安装**走到「检查 Docker」那一步都会再查一次。

为什么要重启 dockerd：容器里那份 `/etc/resolv.conf` 是**容器创建那一刻**
由 dockerd 写死的，之后不会自己更新。本地 Claude 在用户 Mac 上走的正是这一步
（`systemctl restart docker` → `compose up -d` → 6/6 健康）。

另外补了一条确定性判据：侦察员会读本项目**正跑着**的容器里那份 resolv.conf，
和现在该有的比一比；对不上的就是「在修好之前起的」，规则层给
`compose_down_own` + `restart_stack`（不带 `-v`，数据卷一个都不动）把它们重建一次。

## 四、测试（全部实测）

Rust 单测 **547 条全绿**（I9 收尾时 527 条，本轮 +20），前端 vitest **85 条全绿**，
`cargo clippy -D warnings` 与 `cargo fmt --check` 干净。

### 4.1 用「在 Docker 网络里断掉 DNS」构造出来的那几场

任务书说得对：测试机没有虚拟机，DNS 那个现场没法原样复现。
用的办法是起一台**自己的 dockerd**（`docker:28-dind`，`--dns 203.0.113.1` ——
一个路由不到的地址），它发出来的容器因此一个可用的 nameserver 都没有。
**测试机自己的网络设置一个字节都没动**（红线 9）。

| # | 场景 | 结果 | 证据 |
|---|---|---|---|
| N1 | 容器无 DNS · `--check-net` | `E_CONTAINER_OFFLINE`，归类「容器解析不了域名」，原话 `curl: (28) Resolving timed out after 20000 milliseconds`，**退出码 1** | `I10-证据/n1-容器无DNS-check-net.log` |
| N2 | 对照 · 测试机自己的 docker | 「容器能连上模型网关（HTTP 401 · 2766 毫秒）」，**退出码 0** | `n2-…log` |
| N3 | 本机没有那个镜像 | 「这一次没能做这项探测」，**退出码 0** —— 没测就说没测，**不说成不通** | `n3-…log` |
| N4 | 规则层 · `--diagnose --code E_CONTAINER_OFFLINE` | 命中 `container-offline-user-docker`，**0 个动作**，正文写明「不会去改你电脑的 DNS、hosts、代理或防火墙设置」 | `n4-…log` |
| G | **全自动安装**打在那台无 DNS 的 docker 上 | 拉取成功（daemon 自己有 DNS）→ 容器必检**当场拦下** → `E_CONTAINER_OFFLINE`。规则层如实让路（这一类我们修不了） | `G-auto-nodns.log` |

场景 H 的价值不只是「复现了」：它让第七节那条「需上游配合」有了**可重复的实验台**，
而不是一台远在别处的 Mac。

## 五、实测当场抓出来的两条（都不是读代码读出来的）

### 5.1 我们自己的新代码差点把「本机没有这个镜像」报成「容器连不上网」

第一次跑 `--check-net` 的原话是：

```
容器出网：容器连不上模型网关：容器解析不了域名（没有可用的 DNS）
         （Unable to find image 'ghcr.io/…/hunter-community-api:1.2.0' locally）
```

本机没有那个镜像，`docker run` 就先去 pull，而那台 docker 没有 DNS，pull 也失败 ——
于是**一条「镜像不在本机」被报成了「容器解析不了域名」**。
两件完全不同的事混成一条结论，正是这一轮要消灭的那一类错误，结果差点自己犯一遍。

修法：探测命令固定带 `--pull=never`，并且把「No such image / Unable to find image」
单独归成 `NotRun`（「这一次没能测」），**不算不通**。
N3 那一场就是这条修复的验收。

### 5.2 「生成一份诊断包」被当成了一次修复，空转了 4 个回合

场景 G 第一次跑的时候：规则层（正确地）判定这一类修不了、让路给模型，
模型（也合理地）选了 `export_feedback_bundle`，然后 **总指挥把「跑成了一个动作」
当成了「做了点什么，值得重跑一次」**：

```
生成诊断包 → 重跑下载组件 → 又失败 → 生成诊断包 → …   4 个回合，22,400 token
```

生成一个 zip 不会让容器多出一条 DNS。修法是把这件显然的事写进代码：
`actions::REPAIRS_NOTHING`，表里的动作跑成了也**不触发重跑**，并写一行日志说明为什么。
配一条单测钉住「真会改变现场的那几个动作一个都不许进这张表」。

### 5.3 另外一条（界面）

Xvfb 截图里当场看见错误页上原样印着 `**你自己装的 Docker**` —— 规则层那些
`detail` 是直接渲染成纯文本的，写 Markdown 只会把星号显给用户看。
i18n 那一侧早就有同样一条测试，规则层这一侧原来没有。本轮把 rules.rs 里所有
用户可见文案的星号去掉，并补了一条测试：**每一条规则的标题与正文都不许含 `**`，
也不许出现「请在终端」「复制命令」「我执行完了」**。改完之后把那一页重新拍了一遍
（`i10-08-错误页-容器连不上网关.png`）。

同一次扫尾还抓到一条同源的：**字符串的续行写法出错，界面上会出现一长串空格**。
`ensure_vm_dns` 那张「问题」卡片的正文本来是「…没有 systemd-resolved，
`<17 个空格>`/etc/resolv.conf 出厂就是一条断链」。顺手把 I7 留下的同一类
（`reuse_existing_hunter` 的 summary）也一起改了。

以及 `check-fonts.py` 抓到的一条：本轮新文案里有 4 个字（味 / 嵌 / 症 / 适）
不在打包的字体子集里，不重新生成子集的话界面上会显示成豆腐块。
已重新生成（1165 个字符全部覆盖）。

## 六、守卫：多开一道门，一条禁令都没松

「在虚拟机里写 `/etc/resolv.conf`」和总门 [`guard::argv`] 上的一条硬禁令正面相撞：
**参数里不许出现 `/etc/resolv.conf`**。

那条禁令**一个字都没动**。它防的是「改用户这台电脑的网络设置」，
而我们要改的是**自己下载、自己创建、只服务 Hunter 的那台虚拟机**里的文件。
所以走的是另开的一道窄门 `guard::argv_vm_dns`，门上三把锁，全是代码：

1. 程序必须是 `~/.hunter/runtime` 里那份 `limactl`（不是 PATH 上找到的某个）；
2. 目标实例必须是 `colima-hunter`（跟着 `builtin::PROFILE` 走）；
3. **整条参数数组必须与一张写死的表逐字相等** —— 不是「以…开头」，不是「包含…」，是全等。

那张表现在 10 条：3 条只读（`cat /etc/resolv.conf`、`getent hosts hunter.agentpit.io`、
`test -f …hunter-dns.service`）、6 条落位（`mkdir -p /etc/hunter`、三条
`cp --remove-destination`、`systemctl daemon-reload`、`systemctl enable hunter-dns.service`）、
1 条让容器重新拿 DNS（`systemctl restart docker`）。表里有 `sudo`，
所以**参数留一丝活口就等于留一个任意命令执行** —— 单测钉住「表里不许有 `*` / `{` / `$`」
以及「表长度变了要同时改这一节」。

> 这里的 `sudo` 是**虚拟机里**的 sudo（lima 给那台虚拟机的用户配了 NOPASSWD），
> 和用户 Mac 上的管理员密码毫无关系 —— 这条路不会弹任何密码框。

单测覆盖（`guard::tests`）：

* 总门**依旧拒绝**一切带 `/etc/resolv.conf` 的命令（模型永远走那一道）；
* 窄门只认表里那 10 条，「只差一点点」的全拒（`sudo rm -rf /`、`sudo cat /etc/shadow`、
  `sudo sh -c …`、`cp /tmp/evil /etc/resolv.conf`、`systemctl stop docker`、
  `systemctl restart sshd`、`getent hosts evil.example.com`…）；
* 只认 `colima-hunter` 这一台（`colima-default` / `default` / `docker-desktop` 全拒）；
* 只认我们自己那份 limactl（`/usr/local/bin/limactl`、`/opt/homebrew/bin/limactl` 全拒）；
* 送进虚拟机的文件必须是我们自己在 `~/.hunter/runtime/vm` 里生成的，落点只能是那两个。

第四节 4.2 是这一套在真二进制上的实证。

## 七、需上游配合（不改 hunter-community）

### 7.1 opencode 的健康检查依赖外网

镜像里写死的那一条（`docker image inspect`）：

```json
{"Test":["CMD-SHELL","curl -fsS -u ${OPENCODE_SERVER_USERNAME:-opencode}:${OPENCODE_SERVER_PASSWORD:-changeme} http://127.0.0.1:3901/ || exit 1"],
 "Interval":30s,"Timeout":5s,"StartPeriod":15s,"Retries":3}
```

本轮在 Linux 上把「容器没有 DNS」这个现场造出来之后，逐个端点实测
（`I10-证据/u-opencode健康检查的外网依赖.log`）：

| 端点 | 容器**没有** DNS | 容器 DNS 正常 |
|---|---|---|
| `/`（健康检查用的就是它） | **500 · 14.2 秒** | 200 · 0.21 秒 |
| `/health` | 25 秒没响应 | 200 · 0.23 秒 |
| `/app` | 500 · 7.1 秒 | 200 · 0.30 秒 |
| `/config` | 25 秒没响应 | 200 · 0.04 秒 |
| **`/doc`** | **200 · 0.012 秒** | 200 · 0.062 秒 |

健康检查自己的 `timeout` 是 5 秒，所以 `/` 那 14.2 秒连失败原话都留不下，
只有一句 `Health check exceeded timeout (5s)`。

**给上游的两条建议（都带上面这组实测数字）：**

1. **健康检查从 `/` 换成 `/doc`**。本地 Claude 在用户 Mac 上建议的 `/config`
   在 1.2.0 上过不了这一关：没有 DNS 时它 25 秒不响应。
   `/doc` 是这一版里**唯一一个既快又不碰外网**的端点（无 DNS 时 12 毫秒返回 200）。
2. 顺带把 `timeout: 5s` 放宽一点：冷启动时 `/` 实测要十几秒，5 秒的窗口
   会把「慢」和「坏」混成同一个结果。

**启动器这一侧不等上游**：容器能不能连上模型网关已经是一项必检（第二节），
不再靠健康检查顺带证明。
