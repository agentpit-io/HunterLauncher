## 一、四张卡各做了什么

### 1. F-02 · 三级授权 L1/L2/L3 + 复核员判据改法（地基）

#### 1.1 问题一：提示词里那条绝对禁令

`assist/reviewer.rs` 的判定尺度里原来写着：

```
- 只要沾上「删用户的文件 / 删数据卷 / 停或删别的项目的容器 / 改代理、DNS、hosts、防火墙 / 用管理员权限」，一律否决。
```

「用管理员权限」被和「删数据卷」并列写成了绝对禁令。后果就是 I15 那句原话：
**能力有，判官不放行** —— Windows 上装容器运行时绕不开提权，于是三条路被砍掉两条。

改成两句话（`reviewer.rs:SYSTEM_PROMPT`）：

```
- 只要沾上「删用户的文件 / 删数据卷 / 停或删别的项目的容器 / 改代理、DNS、hosts、防火墙」，一律否决。这几条**一个字都不能松**，跟用户授权到了哪一档没有关系 —— 没有哪一档授权能换来「可以删你的数据卷」。
- 需要管理员权限的动作：**看它有没有超出用户已经授权到的那一档**。下面写着用户授权到了哪一档，计划里每一步也写着它要哪一档。授权范围内的提权（例如装容器运行时本身要用到的那几步）**不是**否决理由，但要在理由里点明「这一步会弹系统授权框」；超出授权范围的一律否决，并说清缺的是哪一档授权。
```

复核员要能「对一下这两者」，所以每次调用都得把两侧都喂给它：

| 喂什么 | 从哪来 |
|---|---|
| 用户授权到哪一档 | 新增纯函数 `reviewer::grant_brief(GrantSet)`，拼进每次调用的用户消息 |
| 每一步要哪一档 | `reviewer::describe()` 每一步多打一行「需要的授权：…」 |

抓这两个函数出来的目的是**能被单测钉住** —— `review()` 只剩发请求与解析。

#### 1.2 问题二：以前没有分级授权

原来全仓只有一个 `Level{ReadOnly, Safe, Sensitive}`，而它唯一的判定消费点是
`guard::Mode::needs_confirm`。新增的这一层**是另一条轴**，这一点在代码里写死了：

| | 说的是什么 | 谁在管 |
|---|---|---|
| `Level` | 这个动作**影响面**多大 | 复核员与用户的确认 |
| `Grant`（新） | 做这件事**要用户授权到哪一档** | 执行路径上的硬校验 |

一条动作可以影响面很大（`Sensitive`）却只要二级 —— `reuse_existing_hunter` 就是
（只往 `launcher.toml` 写一行字，弹不出任何系统授权框）。把两件事塞进同一个枚举，
迟早会为了「影响面」放松「授权」，或者反过来。

**三级**（`guard::Grant`）：

| 档 | 名字 | 判据 |
|---|---|---|
| 一级 | 只读观察 | 只看不改 |
| 二级 | 本机安全操作 | 装 / 起自己那套运行时、改自己的配置 |
| 三级 | 需要系统提权 | **这一步会弹系统自己的授权框** |

配置落在 `launcher.toml [assist] grants`，写成一张清单：

```toml
[assist]
grants = ["l1", "l2"]
```

几条设计上刻意的地方：

* **默认只到二级**（`default_grants()`），三级出厂一律不勾 —— 替用户把「允许提权」
  默认打开，等于把最有代价的那一次同意替他做了；
* 解析取清单里**最高**的那一档（授权到三级，一二级当然也在内），
  写回去时把含在内的低档**列全** —— 配置文件那行字自己就该读得懂；
* 认不得的值一概丢掉，**整张清单都认不得 = 一档都没授权**。
  一份被谁改坏的配置应该少授权，不是多授权；
* 老版本的 `launcher.toml` 里根本没有这一行，读回来必须是默认的
  「一级 + 二级」—— 不能因为少一行就变成「一档都没授权」（那会让所有改动类动作
  突然都做不了），更不能变成「全授权」。

**判据落在哪一级**：`actions::required_grant(id, args)`，只有一条判据 ——
**这一步会不会弹系统自己的授权框**。现在全表只有一条是三级：
`start_runtime` 且 `app = systemd`（Linux 上起 docker 的后台服务，先原样试一次，
不成就走 `pkexec`）。Windows 上启用 WSL2 / 装 Docker Desktop 的那几个动作
（W-13 / W-14）会在后续轮次以**新增动作**的形式进来并声明三级 —— 本轮不碰。

**执行路径上的闸**：`actions::ensure_granted(call)`，插在四处入口上 ——
`execute_as`（第 4 道门，排在档位确认之后）、以及总指挥那两条带实时进度的
执行体 `run_install_runtime` / `run_builtin_action`（它们有自己的 `plan` 调用，
不补的话就是**换个入口绕过去**）。拒绝时的话是：

> 「装一套容器运行时」这一步需要「三级 · 需要系统提权」这一档授权，
> 而现在只授权到「二级 · 本机安全操作」，所以不执行。

**说人话**：二级 / 三级的动作在过程流里各出一句（`actions::grant_line`），
`detail` 上当场看得见、`tech` 里留一份永久的；只读的动作不报（那是噪音）。

**设置页与授权页**：后端两处入口都打通了 —— `assist_consent` 新增可选的 `grants`
（**没传就是出厂那一档**，界面漏传不该等于替用户勾上三级），
`write_settings` 新增可选的 `assistGrants`（`None` = 这一次不动它，
老界面不带这个字段时不会把安装能力关掉）。两处改动都**写日志 + 写审计**，
和改档位一样算一次新的授权（盖时间戳）。

#### 1.3 三条一个字不能松

任务书点名的那三条，**一条没松**，而且各有一条单测钉着（`guard.rs`）：

| 承诺 | 钉它的测试 |
|---|---|
| 不删用户文件 / 数据卷 / 别的项目的容器 | `三级授权换不来删数据卷的权限` |
| 不改用户的代理、DNS、hosts、防火墙 | `三级授权换不来改网络设置的权限` |
| 免费版只绑 `127.0.0.1` | `三级授权换不来对外开网页端口的权限` |

三条都是**跟授权档位毫无关系**的：它们各自被代码写死的硬校验拦着
（`argv` 的禁令表、`own_container` 的标签校验、`WebBind` 那条单向的绑定），
没有哪一档授权能换来其中任何一条。

### 2. S-02 · `[runtime] data_dir`

新增 `launcher.toml [runtime] data_dir`，空 = 沿用 `~/.hunter/runtime`。
落地点只有一处：`paths::runtime_dir()` 优先读它 —— `bin` / `dist` / `cache` /
`lima` / `colima` / `docker-config` / `installed.json` 全是它的子路径，
`builtin.rs` / `effective.rs` / `env_pairs()` 一个都没改，自动跟着走。

**没用 `HUNTER_HOME`**（那个会把整个 `~/.hunter` 连同 `.env`、日志、备份、
诊断包一起搬走，粒度太粗），支持 `~/` 开头。

**认不得的值一律落回默认**（`data_dir_usable`），四条否决，
每一条都对应一种真实的坏结果：

| 否决 | 为什么 |
|---|---|
| 相对路径 | 落在哪儿取决于进程当时的工作目录，等于没写 |
| 盘符 / 根目录（`/`、`C:\`） | 那是把整台机器交给启动器写 |
| 用户家目录本身 | 运行时那棵树是直接往它的根上写 `bin` / `colima` / `lima` / … 的 |
| **工作目录的祖先** | 见 S-03 —— 这条最要命 |

比对之前先**按字面把 `.` 与 `..` 消掉**（`normalize`）：不这么做的话
`~/..` 这种写法能绕过每一条前缀比对（`components()` 里那个 `..` 谁都不等于）。

### 3. S-03 · 守卫白名单 + Level 升级（安全陷阱 · 硬前置）

S-02 与 S-03 是**同批**做的 —— 只做 S-02 不做 S-03，等于把守卫开了个口子。

#### 3.1 守卫认新目录

`guard::writable_path` 原来只认 `~/.hunter` 一个根。运行时搬走之后，
`repair_builtin_runtime`（删 colima profile 与 lima 实例目录）与
`uninstall_builtin_runtime`（清空整棵树）都落到那个根之外了 —— 要么被**误拒**，
要么（更糟）「写东西必须先落在自家地盘里」这条约束**整个失守**。

新增 `guard::own_roots()`：当场读 `paths::runtime_dir()`，它搬去哪守卫就认到哪。
colima 那条隔离守卫（`guard::colima_call` → `under_runtime`）本来是当场读的，
自动跟着走 —— 现在有单测钉着这件事，免得以后有人把它改成常量。

**一条绝不能破的不变式**：白名单里不许出现一个比 `~/.hunter` **更宽**的目录。
加一个根是为了「守得住」，不是「放得开」——如果 `data_dir` 指到 `~/.hunter`
的上一层，加进去等于把 `writable_path` 那道门整个拆掉。
`paths` 那边已经把这种值挡回去了（S-02 的第四条否决），
`guard::may_add_root` 再挡一道 ——「守得住」不该建立在别的模块没被改坏上。

#### 3.2 两个动作升到 `Sensitive`

`repair_builtin_runtime` 与 `uninstall_builtin_runtime` 从 `Safe` 升到
`Sensitive`（**授权档位仍是二级** —— 它们不弹任何系统授权框，升的是影响面那一档）。
卡片上写明**实际路径**，不再写「只动 `~/.hunter/runtime`」这种想当然的默认值：

> 这会删掉 `<实际路径>` 里的东西：colima 的 hunter profile 与它的 lima 实例目录，
> 再重新起一次虚拟机…

有一条测试专门钉住「别再把它当成事实」：断言 `desc` 里**不再出现**
「只动 ~/.hunter/runtime」，且卡片摘要里必须出现**当场算出来的**那个路径。

### 4. S-01 · 卷枚举与打分（纯函数 + 单测）

新增 `src-tauri/src/runtime/disk.rs`（375 行，其中 11 条单测）。

* **没用** `assist/probe.rs::disk_free()` —— 它在 Windows 上直接返回 `None`；
  走的是 `sysinfo::Disks`（三平台同一套代码），枚举口径参考
  `backup.rs::external_suggestions()`。
* 打分（分高者胜，并列取盘符序）：

  ```
  +1000   不是系统卷
  +200    这块盘上已有 Hunter 的数据
  +free_GB
  -500    free < 需求下限 × 3
  ```

* 需求下限 **15 GiB**（`NEED_BYTES`，`0.42 + 3.90 + 1.7 + 1` 那几项实测数字算出来的），
  「勉强够」那条线是它的三倍（45 GiB）。**总量小于 40 GiB 的卷直接不看**。
* **系统卷永不被推荐**：不是「扣分够多就还能选」，而是 `eligible()` 直接滤掉。
  打分里那条 `+1000` 是第二道保险 —— 以后有人改了过滤那一段，分数这一层还拦得住。
* **全不合格返回 `None`**，不瞎选一块。

一条系统卷判据三平台各按各的规矩：Windows 看盘符是不是 `C`、
macOS 把 `/` 与 `/System/Volumes/Data` 都算系统卷、Linux 看 `/`，
另外**家目录所在的那块一律算系统卷**（由 `monitor::disk_for` 单独判）。

## 三、安全自查：这一轮有没有把哪一道门放松

这是本轮最该被问的一句话，逐条答：

| 门 | 这轮动了吗 | 结论 |
|---|---|---|
| 表外动作一律拒（`actions::plan`） | 没动 | 不变 |
| 删除白名单（`deletable_files` / `deletable_trees`） | `deletable_trees` 跟着 `runtime_dir()` 走 | **更严了**：搬盘之后旧的 `~/.hunter/runtime` 不再算自家地盘 |
| 写入必须在自家地盘内（`writable_path`） | 多了第二个根 | **有条件的放宽，且带死锁**：只放行「当场算出来的那棵运行时树」，且 `may_add_root` 拒绝任何比 `~/.hunter` 更宽的候选；有 3 条单测钉着 |
| 容器只动自己的（`own_container`） | 没动 | 不变 |
| 提权（`argv` 禁令 / `PRIVILEGED_OPS`） | **没有放松** | 通用 `argv` 照样不认 `sudo` / `pkexec` / `runas` / `osascript`；提权仍只有那条专门的通道，且新增了「要三级授权」 |
| 网络设置（代理 / DNS / hosts / 防火墙） | 没动 | 不变 |
| 免费版只绑 `127.0.0.1` | 没动 | 不变 |
| 复核员（第二道） | 判据改了 | 从「沾管理员就否决」改成「超出已授权才否决」——**这是任务书点名要改的那一条**，其余三条红线在提示词里被写得更死（「哪一档授权都换不来」） |

新增的那一条放宽（`writable_path` 的第二个根）是本轮**唯一**放宽的地方，
而它放宽的对象是「启动器自己下载、自己解压、自己创建」的那棵树 ——
和 `~/.hunter` 是同一类东西，只是换了块盘。它带来的风险（`data_dir` 指到更宽的目录）
由 `data_dir_usable` 与 `may_add_root` 两道挡着，各有单测。

## 四、没做到的（如实）

### 4.1 界面一个字没改（本轮明确不做，但后果要说清）

任务书写的「界面与文案」不在本轮范围，所以下面这几处**只有后端就绪、页面上看不到**：

* 授权页那三个勾（L1 / L2 / L3）—— `assist_consent` 已经收 `grants`，
  **没传就是一级 + 二级**，所以旧界面照跑，不传也不会误勾三级；
* 设置页那个「随时关掉某一档」—— `write_settings` 已经收 `assistGrants`
  （`None` = 不动），`read_settings` 也把当前档位返回去了，页面还没接；
* 选盘卡片（U-03）—— `runtime::disk` 的枚举与打分还没接到任何界面上。

### 4.2 选盘还没接进安装链路

`runtime/disk.rs` 是**纯函数 + 一次枚举**，`pick()` 现在没有任何非测试调用方 ——
把它接进 `builtin::vm_params()`（macOS 侧按选中盘算虚拟机磁盘）、
把选中值写进 `[runtime] data_dir`、以及卡片上那句「为什么是它」，
都是**技术方案 §4.2.2 的 S-04 / U-03**，不在本轮任务卡里。

它现在**不是死代码**（`runtime` 是 `pub mod`，`pub fn` 是库的公开接口），
但确实**还没有人调它** —— 这句话是字面意思。

### 4.3 复核员提示词改法：钉住了提示词，没跑过真模型

`提示词按授权档位判提权而不是一律否决` 这条测试断言的是**提示词文本**：
旧措辞不在了、新判据的两半都在、三条红线还在。它**不能**证明模型真的会照做。

要证明那件事得拿真 key 打一次真实复核（一份带提权的计划 + 三级已授权 ⇒ 期望放行），
本轮**没有做**，理由两条：一是这会花用户的真实 token 额度，
二是「模型这次有没有听话」本身就是概率问题，一次对照说明不了太多。
**这一条留在待验证清单里（见下表第 3 行）。**

### 4.4 本机验不了的东西（一条都没伪造）

技术方案 §4.3.2 还点名了两件事，本轮**没做**，因为没有对应的机器：

* **② `elevate::Op` 新增 Windows 项**（UAC 提权）—— Windows 真机；
* **③ `PRIVILEGED_OPS` 新增 Windows 白名单条目**（`wsl --install` 等）—— 同上。

总控规则第五节写死了「绝对禁止在 Linux 上伪造 Windows 场景」，

## 五、这一轮撞到的事

**两件，都是自己过一遍代码时抓到的，写的比改的多。**

### 5.1 「把它加进白名单」这句话本身就是一次放宽

写 S-03 的第一版时，「把运行时目录加进自家地盘」是照着技术方案那句
「A：把 `runtime::data_dir()` 加进守卫的白名单」直译的，第一版用的是
`v.retain(...)` —— 让更宽的那个根赢。自己过一遍的时候发现：
`data_dir = "~"` 会让白名单变成整个家目录，`writable_path` 那道门当场失守。
**这正是 S-03 那张卡要防的那类事，只是换了个方向**（不是「误拒」也不是
「失去保护」，而是「保护范围被一行配置撑开」）。

改成现在的形状：`paths` 那边四条否决（`data_dir_usable`）+ 守卫这边
`may_add_root` 不许候选根比现有根更宽，两边各有单测。

### 5.2 按档位套的那句「人话」，会替动作吹牛

`grant_line` 的第一版对二级动作写的是「只在本机 Hunter 自己的目录与容器里做，
不碰你别的软件和网络设置」。这句话对绝大多数二级动作是真的，
对 `install_runtime` **不是** —— 它的兜底链会去装 Homebrew / OrbStack。

顺手把判据本身也写清楚了：三级是「**这件事的目的就是改系统**」，
不是「有没有可能弹框」。按后者算的话 `install_runtime` 也得进三级，
而出厂默认（一级 + 二级）就装不了 Docker —— 那正是这个产品存在的理由。
现在那句「人话」只说授权这件事本身，动作的范围交给 `Plan::summary`
（它是逐条动作写出来的，比按档位套的通用话准得多），
并且有一条测试把这个判断钉住了（`装运行时是二级不算系统级变更`）。

写 S-03 的第一版时，「把运行时目录加进自家地盘」
是照着技术方案那句「A：把 `runtime::data_dir()` 加进守卫的白名单」直译的，
第一版用的是 `v.retain(...)` —— 让更宽的那个根赢。自己过一遍的时候发现：
`data_dir = "~"` 会让白名单变成整个家目录，`writable_path` 那道门当场失守。
**这正是 S-03 那张卡要防的那类事，只是换了个方向**（不是「误拒」也不是「失去保护」，
而是「保护范围被一行配置撑开」）。

改成现在的形状：`paths` 那边四条否决（`data_dir_usable`）+ 守卫这边
`may_add_root` 不许候选根比现有根更宽，两边各有单测。
写下来是因为它值得警惕 —— **「把它加进白名单」这句话本身就是一次放宽，
读需求的时候容易只看见「别误拒」那一半。**
