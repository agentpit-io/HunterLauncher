## 零、一句话结论

**0.1.3 在用户的 Mac 上一打开就停在「没有找到 Docker」，而他的 OrbStack 好好装着。**

根因和「装没装」毫无关系，是 macOS GUI 程序的固有行为：从访达或程序坞启动的程序，
拿到的 PATH 只有 `/usr/bin:/bin:/usr/sbin:/sbin`（`launchctl getenv PATH` 是空的 →
走系统默认），**不含 `/usr/local/bin`** —— 而 docker 恰恰就在那里（一个指向
`/Applications/OrbStack.app/Contents/MacOS/xbin/docker` 的软链）。终端里能跑，
是因为 shell 读过 `/etc/paths` 与 `~/.zshrc`，GUI 程序读不到那些。

本轮把可执行文件定位从「只看 PATH」改成「配置 → PATH → 平台已知位置，按顺序探，
全过程留痕」，并把**实际用的是哪一条路径**摆到界面上；顺带把向导顺序改成
「欢迎 → 输入 key → Docker → 选模型 → 拉镜像 → 启动」，再做了一个**两层**的诊断助手：
第一层是零 token 的确定性规则，第二层才是 AI 兜底（最多 3 轮、动作只能从写死的白名单里挑）。

**本轮还顺手抓出五个会在真实使用里咬人的 bug**（详见 §五）。
前三个都是「第一次跑好好的、第二次才炸」那一类：

1. 把模型回来的 assistant 消息**原样回灌**会让上游直接 HTTP 400 —— AI 那一层的第 2 轮**必然失败**；
2. 安装阶段的**任何**失败都被当成 `E_PULL_FAILED` —— 「项目名被另一个工作目录占着」
   会显示成「镜像拉取失败」，诊断助手据此给出「换个镜像源」这种完全跑偏的建议；
3. 规则层认出「装了但没起来」之后，如果当前平台给不出启动按钮，**整条规则会静悄悄地失效**
   并掉到优先级更低的规则上。

后两个是取错误页截图时连环暴露出来的：规则层把**自己这一套**占着的端口也算成冲突，
以及 `E_PROJECT_CONFLICT` 根本没有对应的规则。

Rust 单测 **298 → 305**，前端 67（状态机那 38 条按新顺序重写）。
`fmt` / `clippy -D warnings` / `eslint` / `tsc` / 字体子集 / 截图自查全绿。

**macOS 与 Windows 仍然没有真机。** 第一节的多路径探测为 macOS 写了专门的分支与清单，
并打出了 dmg，**但那一条路只在代码与单测层面验过**；请你在真机上试一遍并把结果告诉我（§八）。

## 二、P0 · macOS 上装着 Docker 却报「没有找到 Docker」

### 2.1 现场

用户第一次在自己的 Mac 上打开 0.1.3：Docker 检测页停在

```
没有找到 Docker
命令行里找不到 docker。          E_DOCKER_MISSING
```

而同一台机器的终端里：

```
$ which docker
/usr/local/bin/docker
$ ls -l /usr/local/bin/docker
… -> /Applications/OrbStack.app/Contents/MacOS/xbin/docker
$ docker version
Server: … 29.4.0
```

### 2.2 根因（用户在自己机器上实测，本轮不再重推）

macOS 上**从访达或程序坞启动的 GUI 程序**拿到的 PATH 只有
`/usr/bin:/bin:/usr/sbin:/sbin` —— `launchctl getenv PATH` 是空的，于是走系统默认值，
**不含 `/usr/local/bin`**。终端里之所以有，是因为 shell 会读 `/etc/paths` 与 `~/.zshrc`；
GUI 程序读不到那些。

所以 `Command::new("docker")` 在那台机器上必然 ENOENT。
**这跟用户装没装 Docker 完全无关**，是 macOS GUI 程序的固有行为 ——
换句话说，0.1.3 在 macOS 上对**所有**把 docker 装在 `/usr/local/bin`
（这是 OrbStack、Docker Desktop、Intel 版 Homebrew 的默认位置）的用户都会这样。

### 2.3 怎么修的

新模块 [`runtime::which`](../../src-tauri/src/runtime/which.rs)。给一个程序名，按固定顺序找绝对路径：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | `launcher.toml` 的 `[runtime] docker_path` | 指了就**只认它**；那个位置没有可执行文件就如实报错，**不回退** |
| 2 | PATH | 自己走一遍，不调 `which`（那个程序自己也可能不在 PATH 上，而且三平台行为不一样） |
| 3 | 平台已知位置 | 见下表，**清单只写在这一个函数里** |

macOS 的清单（顺序即探测顺序）：

```
/usr/local/bin                                       ← 用户那台机器命中的就是这一条
/opt/homebrew/bin
~/.orbstack/bin
~/.docker/bin
/Applications/Docker.app/Contents/Resources/bin
/Applications/OrbStack.app/Contents/MacOS/xbin       ← /usr/local/bin/docker 指向的地方
~/Applications/OrbStack.app/Contents/MacOS/xbin
~/Applications/Docker.app/Contents/Resources/bin
~/.colima/bin  ~/.rd/bin  ~/.local/bin
/usr/bin  /bin  /usr/sbin  /sbin                     ← GUI 默认 PATH 里的那四个，兜底也探
```

Linux：`/usr/bin`、`/usr/local/bin`、`/bin`、`/snap/bin`、`~/.docker/bin`、`~/.local/bin`、
`/opt/docker/bin`、`/usr/sbin`、`/sbin`。
Windows：Docker Desktop 的三个安装位置、`%USERPROFILE%\.docker\bin`、Podman、`System32`。

几个刻意的取舍：

* **找到第一个「存在且可执行」的就用。** 文件在但没有可执行位（mac 上从 dmg 拷出来又被
  改过权限的情况见过）算作「跳过并记一条」，不算找到。
* **全过程留痕。** 探过的每一个位置与结果（不存在 / 没有可执行位 / 可执行）都记下来，
  界面上一个都不少地列出来；软链还会写出它指向哪里。0.1.3 缺的正是这一段 ——
  一句「命令行里找不到 docker」把用户引到「是不是我没装」这条死路上去了。
* **解析不到时退回裸程序名。** 最坏情况和 0.1.3 完全一样（由操作系统自己去 PATH 上找），
  不多出一种「启动器自己不肯试」的新失败模式。
* **清单可以从配置覆盖**（`search_paths` / `use_builtin_paths` / `use_env_path`），
  装在清单之外的用户指一次就行。

compose 同理：先试 `docker compose` 插件，不行再找独立的 `docker-compose`
（返回的是「程序名 + 参数前缀」，两种形态对调用方透明）。

**之后所有调用 docker 的地方都走这条解析出来的绝对路径** —— 本轮把
`runtime/docker.rs`、`compose.rs`、`offline.rs`、`backup.rs`、`flow.rs` 里的
11 处调用点全部改掉了，`grep '"docker"'` 在非测试代码里已经搜不到裸字符串。

### 2.4 顺手查的「还有哪些地方假设 GUI 能继承 shell 的 PATH」

| 程序 | 在哪用 | 结论 |
|---|---|---|
| `docker` / `docker-compose` | 到处 | **就是这次的 P0**，已走定位器 |
| `systemctl` | Linux 上启动 daemon | 在 `/usr/bin`，各发行版 GUI 会话的默认 PATH 里都有；**仍然走了一遍定位器**统一口径 |
| `wsl` | Windows 检测 | 在 `System32`，Windows 的系统 PATH 里恒有；已走定位器 |
| `launchctl` | macOS 开机自启 | 在 `/bin`，**在 GUI 默认 PATH 的那四个目录里**，不受影响 |
| `reg` | Windows 开机自启 | 在 `System32`，不受影响 |
| `open` / `pgrep` / `df` / `sw_vers` | 诊断助手新用到的 | 全在 `/usr/bin` 或 `/bin`，**在 GUI 默认 PATH 里**；仍然走定位器 |
| `brew` | 诊断助手的 `brew_install` 动作 | **不在 GUI 默认 PATH 里**（`/opt/homebrew/bin` 或 `/usr/local/bin`）→ 必须走定位器，已走；找不到就如实拒绝这个动作 |
| 打开浏览器 / 文件管理器 | `tauri-plugin-opener` | 由插件自己处理（mac 上走 `/usr/bin/open`），不受影响 |

### 2.5 这一条属于确定性规则，不交给 AI

`runtime::which` 整个在诊断助手的**第一层**：零延迟、零 token、结果可复现，
同一个现象每次给的都是同一句话。AI 那一层永远拿它的探测结果当输入，
**不负责「猜 docker 在哪」**。

## 三、向导顺序调整

```
0.1.3   欢迎 → Docker → 输入 key → 选模型 → 拉镜像 → 启动
0.1.4   欢迎 → 输入 key → Docker → 选模型 → 拉镜像 → 启动
```

理由：Docker 那一步是整个流程里最容易卡住的一步，而新加的 AI 诊断助手要用 hunter key
调网关；填 key 本来就只需要联网、不依赖 Docker，挪到前面没有任何代价。

同步改掉的地方（一个都不能漏，漏一个用户就会看到前后矛盾的界面）：

| 处 | 改动 |
|---|---|
| 状态机 | `Welcome --ACCEPT_TERMS--> NeedKey`、`ValidateKey --KEY_VALID--> CheckDocker`、`CheckDaemon --DAEMON_UP--> ChooseModel` |
| 「上一步」回退路径 | `NeedKey→Welcome`、`CheckDocker/CheckDaemon/InstallDockerGuide→NeedKey`、`ChooseModel→CheckDaemon` |
| 步骤条 | `STEP_IDS` 改成 `welcome, key, docker, model, pull, start`；两份 i18n 字典里的顺序也跟着换 |
| 状态机单测 | 38 条全部按新顺序重写，并**新增一条不变量**：每个向导状态的「上一步」都必须落在它前面（不许往回跳到后面的步骤） |
| 无界面模式 | `--headless` 的步骤号对调：`[1/6] hunter key` → `[2/6] 检查 Docker` |
| 二次打开 | 不受影响（`install.done` 为真直接进运行面板，根本不走向导） |
| 截图脚本 | `PAGES` 顺序调整 |
| README / 使用说明 | 三处描述顺序的地方 |

**与视觉稿的偏离（有意）**：三张视觉稿的步骤条仍然是旧顺序。对照图
（`docs/screenshots/I4/对照/`）左右两侧因此能直接看出这一处差别 ——
这是本轮刻意做的产品改动，不是实现走样。

## 四、AI 诊断助手

### 4.1 两层，顺序不能反

```
用户卡住了
  │
  ├─ 第一层 · 确定性规则（rules.rs）      零延迟、零 token、不联网
  │    ├─ 认出来且有把握（confident）     → 到此为止，给动作，**不调模型**
  │    └─ 认不出来 / 用户点「还是不行」   ↓
  │
  └─ 第二层 · AI 兜底（ai.rs）           最多 3 轮，动作只能从白名单里挑
       └─ 任何一条前提不满足              → 退回第一层，并**说明是哪一条挡住了**
```

第一层认得出来的六种（顺序即优先级）：

| 规则 id | 判据 | 给的动作 | confident |
|---|---|---|---|
| `daemon-down-app-installed` | docker 客户端在、daemon 不在，且 OrbStack / Docker Desktop / Colima / systemd 之一**装了但进程没起** | 启动它 | **是**（不走 AI） |
| `docker-not-found` | 所有已知位置都探不到 | 重新探一遍 + 安装指引 + 探测明细 | 否（真没装还是装在别处，规则分不清） |
| `project-conflict` | 错误码是 `E_PROJECT_CONFLICT` | **不给动作**（三条出路里有一条会删数据卷） | 是 |
| `pull-failed-switch-registry` | 错误码是 `E_PULL_FAILED` | 换另一个镜像源 | 否 |
| `ports-taken` | 5 个端口里有**被别的程序**占着的（自己这一套占的不算） | 重新分配端口 | 是 |
| `disk-low` | 剩余 < 5 GB | **不给动作** —— `prune -a` 会连别的项目的镜像一起删，不替用户按 | 是 |

认不出来时返回一条 `confident = false` 的兜底，**如实说「认不出来」**，
界面据此把「让 AI 帮我看看」显出来。

### 4.2 AI 那一层的边界

| 项 | 取值 |
|---|---|
| 端点 | `https://hunter.agentpit.io/api/saas/llm/v1/chat/completions` |
| 模型 | `hunter-chat` |
| 凭据 | 用户自己那把 `hunt_tools_` key |
| 轮数上限 | **3**（一轮 = 一次模型调用） |
| 单轮超时 | 45 秒 |
| 单轮最多自动执行 | 4 个只读动作 |
| `max_tokens` | 2000 |

**模型能做的只有两件事**：说一段话，或者从一张**写死的表**里挑一个动作。
表外的一律拒绝并记一条 warn 日志 —— 这不是「模型大概不会这么干」的君子协定，
是执行路径上唯一的入口：

* `parse_tool_calls` 只认 `tool_calls[].function.{name,arguments}`；
* `actions::plan(call)` 按 id 查表，查不到直接 `Err`；
* 参数逐项校验：`app` 必须在四种运行时里、`registry` 必须是真有的候选源、
  `path` 必须**真实存在且可执行**、`lines` 有上下界、`formula` 必须在四个之内；
* `actions::execute(call, confirmed)` 对会改动机器的动作**在 Rust 侧**要求
  `confirmed == true`，这一道拦在界面之外（界面可以有 bug，这一层不能有）。

**没有任何一条路径会执行模型生成的命令文本** —— 连「把模型的字符串拼进命令」
这种代码都不存在。

动作白名单（12 条）：

| 只读（自动执行） | 会改动机器（必须确认） |
|---|---|
| `probe_docker_path` 重新探路径 | `start_runtime` 启动 OrbStack / Docker Desktop / Colima / systemd |
| `docker_version` | `set_docker_path` 把路径写进设置 |
| `compose_config` | `switch_registry` 换镜像源 |
| `read_log_tail{lines}` | `restart_stack` |
| `check_ports` | `remap_ports` |
| `check_disk` | `brew_install{formula}`（仅 macOS） |
| `list_runtime_apps` | |

会改动机器的动作**把将要执行的完整命令原样展示**，配一句「要做什么 + 为什么」，
用户点「确认执行」才跑。展示的那一行和真正 `spawn` 出去的参数数组是**同一个来源**
（`Plan::argv`），不存在「展示一套、执行另一套」。

### 4.3 送出去的到底是什么

一份结构化诊断（纯文本，界面上可以「展开完整诊断」逐字看、「复制诊断信息」拿走）：
系统与架构、系统版本、启动器版本、错误码与说明、卡在哪一步、Docker 与 compose 版本与形态、
**实际用的 docker 路径**、**探过的每一个位置与结果**、**本进程的 PATH 原文**、
四种容器运行时各自「装没装 / 进程起没起」、5 个端口的占用、磁盘余量、镜像源与 tag、
`docker version` 的原始输出、启动器日志最后 40 行。

**不会有的**：hunter key、任何 `Bearer` 头、路径里的用户名。三道闸：

1. 采集路径上每一个字符串都过 `redact::redact`（登记过的密文 + 形状匹配）
   再过 `redact::mask_home`（`/Users/zhangsan/...` → `<用户目录>/...`，后半截留着）；
2. 发之前整个请求体序列化出来再扫一遍 key 的形状，命中就**干脆不发**并记一条 warn；
3. 容器日志另外过一道 `mask_content_fields`（`content:` / `text:` 整段换成 `[redacted]`）。

### 4.4 降级矩阵

| 条件 | 表现 | 实测 |
|---|---|---|
| 设置里关掉（`[assist] enabled = false`） | 不显示「让 AI 帮我看看」，只用规则层 | ✅ §六 D |
| 没填 key | 说明「要用它调网关，先回去填一把」，退回规则层 | ✅ §六 A |
| 离线 / 网关不可达 | 说明连不上，退回规则层 | ✅ §六 B（1 秒） |
| 超时（45 秒） | 说明超时，可以再点一次 | ✅ §六 C（45 秒） |
| 额度用尽（402） | 说明等明天 0 点重置，规则层不花额度仍然有效 | ✅ §六 F |
| 限流（429） | 说明等一分钟 | **未实测** —— 实测限流只作用于 `POST /chat/completions`，本轮没有在一分钟内打满 20 次 |
| 网关回了别的非 200 | 说明「返回了意料之外的结果」 | ✅ 修 §五.1 之前每次第 2 轮都会走到这一条 |
| 三轮用完 | 明说搞不定，给手工步骤与「复制诊断信息」 | ✅ §六 场景 1 |

**每一条降级文案都必须告诉用户「接下来能做什么」** —— 有一条单测盯着这件事
（`每一种降级都有一句能上屏的话`）。

## 五、本轮实测撞出来的三个真 bug

这三个都是「第一次跑好好的、第二次才炸」那一类 —— 只手动点一遍根本发现不了，
所以每一条都补了单测盯着。

### 5.1 回灌 assistant 消息会让上游回 400，AI 的第 2 轮必然失败

场景 1 第一次真跑时，第 1 轮好好的（模型要了一个只读动作、我们执行了），
第 2 轮直接退化成「网关返回了意料之外的结果」。日志里的原话：

```
[warn] AI 诊断：网关返回 HTTP 400 ——
{"error":{"message":" (request id: 2026092017210168555490374212677)",
          "type":"upstream_error","param":"400","code":"bad_response_status_code"}}
```

按 OpenAI 的协议，下一轮必须把上一轮的 assistant 消息（含 `tool_calls`）连同每一条
`role: "tool"` 结果一起带回去。我原样回灌了 —— 而这个网关后面接的是 Gemini，
它在 `tool_calls[].extra_content.google.thought_signature` 里塞了一大段自己的内部状态。

**同一把 key、同一个端点，三个变体对照实测**：

| 变体 | 结果 |
|---|---|
| A · assistant 原样回灌（含 `extra_content`） | **HTTP 400** `upstream_error` |
| B · 去掉 `extra_content` | **200**，正常回答 |
| C · 去掉 `extra_content` 且补一个空 `content` | **200**，正常回答 |

修法：`sanitize_assistant()` 把回灌的消息洗成**只含协议本身有的字段**
（`role` / `content` / `tool_calls[].{id,type,function{name,arguments}}`），
厂商私有的一律丢掉 —— 它们是给那一家自己看的，我们既不需要也不该替它转发。
`content` 缺失时补一个空串（有些兼容实现不接受 `null`）。

单测里存了**那一份真实响应的原文**（`thought_signature` 截短了），
断言洗完之后 `extra_content` / `thought_signature` 都不在，而 `id` / `arguments` 一个不少。

修完之后场景 1 跑满了三轮（2809 + 1596 + 1639 ≈ 6044 tokens），
第 3 轮模型给出了正确的结论与一个白名单内的动作。

### 5.2 安装阶段的任何失败都被当成「镜像拉取失败」

取错误页截图时用「换一个工作目录再装一次」触发了项目名冲突闸门，结果界面上：

* 标题：**镜像拉取失败**
* 正文：这台机器上已经有一套 Hunter 在用 compose 项目名「hunter」…
* 诊断助手：**换一个镜像源** ← 完全跑偏

原因：`PullProgress` 只有一段错误文字，没有错误码；前端 `Pull.tsx` 对安装阶段的
**任何**失败都 `send({ type: 'PULL_FAILED' })`。这是 I3 及更早就有的问题，
本轮因为诊断助手要按错误码分流才暴露出来。

修法：`PullProgress` 加 `error_code`，`commands.rs` 失败那一支从 `AppError` 上取真实的码；
前端按它发对应的 `FAIL`，拿不到才退回 `PULL_FAILED`。

### 5.3 规则认出「装了但没起来」之后，会静悄悄地掉到别的规则上

`daemon_down` 里原来是 `let plan = actions::plan(...).ok()?;` —— 规划不出启动动作
（比如在 Linux 上遇到 OrbStack，而 `open -a` 只有 macOS 有）时，
`?` 让**整条规则**返回 `None`，于是掉到优先级更低的「端口被占」上，
用户看到的建议会完全跑偏。这一条是写单测时被测试当场抓住的。

修法：结论照给，只是没有按钮时改说「启动器在这个平台上没法替你启动它（原因），
请手动打开 X 之后再点重新检测」。

### 5.4 规则层把「自己这一套占着的端口」也算成冲突

修完 5.2 之后再取一次错误页截图，规则层给的是 `ports-taken`：
「5 个端口被别的程序占着」—— 而占着那 5 个端口的正是**同一台机器上跑得好好的那套 Hunter**。

`flow::prepare` 早就有这个概念（`own_ports`，M2 用例 9 实测撞出来的），
但 `assist::probe` 是本轮新写的，忘了带上。现在 `PortState` 多一个 `ours` 字段，
规则层只看「被**别的**程序占着」的那些，报文里也如实写「被 Hunter 自己的容器占着（正常，不是冲突）」。

### 5.5 项目名冲突没有自己的规则

同一次截图里还暴露出：`E_PROJECT_CONFLICT` 在规则表里根本没有对应的条目，
于是它会一路落到下一个能匹配的规则上（先是错误的 `pull-failed`，修完 5.2 之后是 `ports-taken`）。
本轮补了一条 `project-conflict`：三条出路都写清楚，**不给动作**
—— 其中一条会删数据卷，不替用户按。

### 5.6 另外三条（自审，都在新功能内）

* **一轮里超过 4 个动作时，多出来的没有 tool 回复** —— OpenAI 协议要求每一个
  `tool_call` 都有对应的 `role: "tool"`，少一条下一轮整个请求会被拒。
  现在超出的也回一条「没轮到，请下一轮只挑最要紧的那一个」。
* **动作全被拒时被当成「模型说完了」** —— 那恰恰说明它还在试，应该让它带着拒绝理由再来一轮。
* **模型一轮什么都没返回时界面上留一个空白轮次** —— token 是真花掉了，
  现在如实说出来，并按 `finish_reason` 分开文案（`length` 说「把输出额度用在思考上了」）；
  `max_tokens` 也从 1200 提到 2000（诊断报文本来就长，思考型模型的 thinking 算在输出里）。

### 安全：模型返回了白名单之外的命令

不是编一个假响应 —— **真去问了网关**，给它一个名叫 `run_shell` 的工具定义，
让它「直接在我机器上跑一条命令把 Docker 装了」。模型照做了：

```json
{"name": "run_shell", "arguments": "{\"cmd\":\"curl -fsSL https://get.docker.com | sh\"}"}
usage = {'completion_tokens': 28, 'prompt_tokens': 130, 'total_tokens': 437}
```

把**这一份真实响应**喂给启动器的处理路径（`--assist-replay`，离线、不联网、
走的是和真联网时完全同一段代码）：

```
动作白名单 · 离线回放
  响应文件：/tmp/i4-evil-response.json
  自动执行 0 个 · 待确认 0 个 · **拒绝 1 个**
  ✗ 拒绝「run_shell」：动作「run_shell」不在白名单里，已拒绝执行。

  日志：
  [warn] AI 诊断助手提出了白名单之外的动作，已拒绝：id=run_shell（参数 ["cmd"]）
```

`--assist-replay` 为什么做成「读本地文件」而不是「把网关地址改成本地假服务」：
后者意味着代码里要留一个能把 `Authorization: Bearer <用户的 key>` 指到任意地址的开关，
等于给自己开一道泄漏 key 的门。读本地文件不碰凭据，也不碰网络。

白名单**之内**但参数被塞了东西的情况由单测覆盖
（`start_runtime{app: "orbstack; rm -rf /"}` → 拒绝、
`read_log_tail{lines: "; cat /etc/passwd"}` → 拒绝、
`set_docker_path{path: "/opt/made/up/docker"}` → 那个位置没有可执行文件，拒绝）。

## 九、偏离方案与决策记录

| # | 偏离 | 原因 |
|---|---|---|
| 1 | 向导顺序不再是方案 §4 的「Docker → key」 | 见 §三。写进状态机的文件头注释里 |
| 2 | 三张视觉稿的步骤条仍是旧顺序 | 视觉稿是 M0 之前画的；本轮是刻意的产品改动，对照图上能看出差别 |
| 3 | AI 诊断助手不在技术方案里 | 本轮新增需求。方案 §18 只规定了「每个错误页都有一键反馈」，这一层是在它之前多加的一道 |
| 4 | `--assist-replay` 是一条只读本地文件的测试路径 | 做成「改网关地址」会开一道泄漏 key 的门，见 §六 |
| 5 | 磁盘余量走 `df -k` 而不是 `statvfs` | 这个仓库里一行 unsafe 都没有，为「顺带提一句盘还剩多少」引入 libc + unsafe 不划算。Windows 上没有 `df`，如实返回「读不到」 |
| 6 | `--diagnose` 默认**不**调 AI，要显式 `--ai` | 这条命令常被写进脚本，不能在用户没要求时悄悄花掉他的额度 |
| 7 | 一轮最多自动执行 4 个只读动作 | 模型一次要十个也不给它跑；超出的如实回一条「没轮到」 |

## 十二、下一轮的建议

1. **等你的 macOS 真机反馈**（§八）。如果探测清单还差一条，把诊断面板上那一段发我，加进 `builtin_dirs` 就行。
2. **AI 层的成本还可以再压**：场景 1 三轮花了约 6,000 tokens，其中第 2 轮是模型重复要了一次同一个只读动作（待办池 P2-18）。诊断报文里日志那 40 行占了大头，可以只在模型真的要 `read_log_tail` 时才给。
3. **规则层还能再多认几种**：`E_START_TIMEOUT`（哪个服务没就绪）、`E_PROXY_BLOCK`（容器内 DNS 不通）目前都落在「认不出来」上，而这两种其实都有很清楚的判据。
4. **GUI 回归脚本的坐标应该从截图上自动量**，而不是写死。本轮沿用 I3 的坐标，结果「反馈」和「更新」截出来是同一页 —— 靠 `check-shots.sh` 的去重才发现。
