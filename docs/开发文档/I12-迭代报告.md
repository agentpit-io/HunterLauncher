## 零、一句话

用户 2026-09-22 23:10 的截图：Mac 上 Hunter **6/6 健康**跑着、网页 `127.0.0.1:3100` 返回 200，
重新打开启动器看到的却是「欢迎使用 Hunter 启动器」。

根子是一行判据：

```rust
// 0.1.11 及之前的 boot_state
installed = cfg.install.done && crate::paths::env_file().exists()
```

`install.done` **只在安装流程自己成功走完时才写**（`flow.rs`）。那一次安装在启动器看来是
失败的（`E_START_TIMEOUT`），最后是在外部修好的 —— 没有人回来把标记补上。
同一份文件里 `[launcher] version` 还停在 `0.1.7`。

这一轮四件事（R1 / R2 / R3+R3+ / R5），每一件都能一句话说清它在回答用户的哪句原话：

| 用户原话 | 本轮做的 |
|---|---|
| 「需要保存状态到配置文件里面，重新打开应用，需要显示系统运行状态」 | **R1**：判据改成「现状优先」，`[install]` 记全，开机第一屏是「正在检查」而不是欢迎页 |
| 「CPU、内存、硬盘状态」 | **R2**：三层资源 + 数据卷与镜像，每层都写明数字从哪问来的 |
| 「可以执行：停止应用、启动应用、重启应用」 | **R3**：停止可顺带停运行环境、启动先把运行环境弄好、可只重启一个服务 |
| 「重新安装过程……如果数据库和数据都存在，不要重新安装数据库和数据」 | **R5**：写配置之前先只读检测，都在就直接沿用；只有「数据比镜像新」这一档拦下来 |

外加任务书里 2026-09-23 追加的 **R3+**：虚拟机重启之后容器不会自己回来。

## 一、R1 · 安装状态持久化 + 以现状为准

### 1.1 判据从「只看标记」改成「标记 + 现状」

`boot_state` 现在先做一次**浅查**（`selfcheck::review(false)` —— `docker compose ps`
+ 一次本机网页 GET，不起一次性容器，实测几百毫秒），再按方案 R1 那张五行表决定去哪：

| 现状探测（只读） | `install.done` | 进入 | 顺手做什么 |
|---|---|---|---|
| 本项目 6/6 健康 | **任意** | 运行面板 | `done=false` 时**补写**，`adopted_from_running=true`，刷 `last_healthy_at` |
| 本项目存在但已停止 | **任意** | 运行面板（显示「已停止」+「启动」主按钮） | 同上（不刷 `last_healthy_at` —— 那会是假时间） |
| 本项目存在但部分不健康 | **任意** | 运行面板（显示异常服务） | 同上 |
| 本项目不存在，但数据卷还在 | 任意 | 「检测到上次的数据」 | — |
| 什么都没有 | 任意 | 欢迎页 | — |

判定本身抽成了纯函数 `commands::route_of(posture, volumes) -> BootRoute`。
拆出来的理由和 I9 的 `effective::decide` 一样：**这台机器上造不出「什么都没有」
和「只剩数据卷」两行**（开发机与测试机上 Hunter 一直好好跑着），而那两行正是
2026-09-22 那次现场最需要钉死的。现在它们有单测（第五节）。

### 1.2 `[install]` 记全了

```toml
[install]
done = true
at = "2026-09-23 ..."
launcher_version = "0.1.12"     # 每次启动写当前版本
hunter_tag = "1.2.0"
project = "hunter"
app_dir = "~/.hunter/app"
runtime = "user"                # builtin | user | none（读现状，不读配置里的意图）
last_healthy_at = "2026-09-23 ..."
adopted_from_running = false
stopped_by_user = false         # 方案第四节没有这一项，是 R3+ 逼出来的，见 3.3
```

`[launcher] version` 那个从 0.1.7 起就没更新过的字段合并进 `[install] launcher_version`：
读配置时自动迁移（`LauncherConfig::migrate`），之后一律以新字段为准。
**老字段不删** —— 用户在两个版本之间来回切的时候不该被我们弄坏配置，
所以两处都写成当前版本。

`last_healthy_at` 在**任何一次**健康检查通过时刷新（`selfcheck::review` 里），
带**一分钟节流**：错误页上的复查是 20 秒一次，运行面板还更频繁，
每次都往 `launcher.toml` 里写一遍纯粹是在磨用户的盘。

这两项在运行面板右侧那一栏上屏：「安装于」（补记的会写明「检测到已在运行后补记」）、
「上次正常运行」。**摆出来才看得见它对不对** —— 2026-09-22 那次之所以拖了那么久，
正是因为「启动器认为装过没有」这件事在界面上根本看不见。

### 1.3 开机第一屏不再是欢迎页

状态机新增 `Booting` 状态与 `booting` 页。**`Idle` 也改成落到这一页** ——
那一帧（窗口出来、reducer 还没跑）原来就是欢迎页，正是「闪一下」的来源：

```
Idle ─(BOOT)→ Booting「正在检查 Hunter 状态」
                 ├─(RESUME_READY)────→ Ready（运行面板）
                 ├─(BOOT_DATA_FOUND)─→ DataFound（检测到上次的数据）
                 └─(BOOT_FRESH)──────→ Welcome（全新安装）
```

后端查不出来（`boot_state` 抛错）时前端送 `BOOT_FRESH` —— **不能卡在「正在检查」那一页上**。

## 二、R2 · 三层资源监控

### 2.1 新模块 `monitor.rs`：四层，各自的刷新频率

| 层 | 问谁 | 刷新 |
|---|---|---|
| 这台电脑 | `sysinfo`（macOS 走 `host_statistics`、Linux 读 `/proc`、Windows 走 Win32） | 5 秒 |
| Hunter 运行环境 | `limactl shell colima-hunter -- free -b` / `df -B1 /var/lib/docker` | 30 秒 |
| Hunter 各服务 | `docker stats --no-stream` + `docker inspect`（`RestartCount` / `OOMKilled`） | 10 秒 |
| 数据卷与镜像 | `docker volume ls` + `docker system df -v` + `docker image inspect` | 5 分钟 |

四条是**独立的 Tauri 命令 + 独立的轮询**，不是一条大命令。合成一条的话，
最慢的那一层（`docker system df -v` 要遍历机器上所有卷）会把最快的那一层拖住。

**为什么分三层给用户看**：在 macOS 上 Hunter 跑在一台只服务它的虚拟机里。
「这台 Mac 内存 92%」和「那台虚拟机内存 92%」是两件不同的事，该做的处理也不同
（关别的程序 / 给虚拟机多分一点）。每张卡右上角都写着这一层的数字是从哪问来的。

### 2.2 引入 `sysinfo`

`sysinfo 0.39`，只开 `system` + `disk` 两个特性（关掉网络、进程、组件温度、用户列表）。
Linux 上它只拖 `libc` + `memchr` 两个依赖。自己写这一层等于把三套平台 API 搬进来。

两个地方 sysinfo 给不了、只能自己问：

* **CPU 占用要两次采样**。第一次调用没有参照点，`global_cpu_usage()` 一定是 0 ——
  那是**假数字**。所以进程里留了一个 `static SYS`，第一次采样时隔一个
  `MINIMUM_CPU_UPDATE_INTERVAL` 再取一次，让第一屏也是真的。
* **内存压力** sysinfo 没有。macOS 读 `kern.memorystatus_vm_pressure_level`
  （1 正常 / 2 吃紧 / 4 危急 —— 这就是「活动监视器」那个内存压力图的来源，
  不是我们按占用率折算的）；Linux 读 `/proc/pressure/memory` 的 `some avg10`（PSI）；
  **Windows 没有这个概念，那一行如实说清楚，不拿占用率冒充它**。

### 2.3 虚拟机那一层：新增一张只读白名单

I9 定的隔离守卫（`proc::isolation_guard` + `guard::colima_call`）照旧生效：
`limactl` 必须是 `~/.hunter/runtime` 里那一份，`LIMA_HOME` / `COLIMA_HOME` 必须指到那里。

在它之前还多了一道：**`guard::argv_vm_metrics` + `VM_METRIC_COMMANDS`**。
和 I10 的 `argv_vm_dns` 分开，是因为两张表的性质完全不同 ——
那一张里有 `sudo`（要改 `/etc/resolv.conf`），这一张只有两条、全只读、一条 `sudo` 都没有：

```rust
pub const VM_METRIC_COMMANDS: &[&[&str]] = &[
    &["free", "-b"],
    &["df", "-B1", "/var/lib/docker"],
];
```

采指标这件事每 30 秒跑一次，不该共用一张带写权限的白名单。

### 2.4 窗口看不见就停止采集

新 hook `usePoll`：判据是 `document.visibilityState`（窗口最小化、收进托盘、
切到别的桌面都会变成 `hidden`）。重新可见时**立刻补一次**，不让用户对着一屏旧数字。

下一次采样从**这一次结束**开始算，而不是固定间隔 —— 采一次要 3 秒的机器上，
固定间隔会让请求排队越堆越多。

### 2.5 拿不到就是「—」，而且一定配一句原因

每个后端结构里都带一份 `reasons: BTreeMap<String, String>`，逐项写着「这一项为什么没有」。
界面把它挂在 `title` 上，鼠标停上去就能看到原话。三档兜底：
后端逐项原因 → 这一轮整体的错误 → 「拿不到真实数据」。**任何一档都不是空白。**

用户自己的 Docker 上「Hunter 运行环境」这一层根本不存在 —— 那张卡显示
「这台电脑用的是你自己的 Docker，没有 Hunter 专用的虚拟机这一层」+ 具体判据，
**不给一组 0**（那就是编数字）。

### 2.6 两套单位，各按各的来

docker 自己就是两套：`system df` 用 go-units 的十进制（kB = 1000），
`stats` 用 1024 进制（MiB）。`compose::parse_human_size` 与 `monitor::parse_binary_size`
分别按各自的来 —— 混用的话界面上的数字和用户敲命令看到的对不上。有单测钉住。

## 三、R3 / R3+ · 停止 / 启动 / 重启

### 3.1 新命令 `stack_op`，老的 `stack_action` 原样留着

| 操作 | 0.1.11 做的 | 0.1.12 做的 |
|---|---|---|
| **停止** | `compose stop` | `compose stop`；内置运行时场景下**多问一句**「顺便把运行环境也停了（释放约 N GB 内存）」，默认勾上 |
| **启动** | `compose up -d` | 运行环境没起**先起它**（含 I10 的 DNS 检查）→ `up -d` → 等六个健康 |
| **重启** | `compose restart` | 六个一起，或者**只重启一个**（`compose restart <服务>`，容器不换、端口映射与数据卷不动） |

「顺便停运行环境」这一问不是可有可无的：Hunter 在 macOS 上跑在一台分了 4 GB 的虚拟机里，
只停容器的话那 4 GB 还占着 —— 用户点了「停止」却发现内存没降下来，只会以为启动器在骗人。
新增 `builtin::stop()`（`colima stop --profile hunter`），**不删任何东西**，
虚拟机磁盘、数据卷、下好的组件一个都不动，下次 `start` 原样回来。

界面先问后端 `stack_plan`：这台机器到底要不要显示那个勾选（内置运行时**而且**它现在在跑）。
**问不到就不显示** —— 界面上不出现一个不知道会做什么的勾选。

操作过程中后端每做完一件事就推一条 `hunter://stack`，面板上一条条直播出来 ——
按钮置灰的那几十秒不该是一片空白。做完之后的那句结论**来自一次新的复查**，
不是「我们刚才发了什么命令」（I11 §6.1 的同一条教训：红线 1 不只管数字，也管动词）。

托盘上的「启动 / 停止 / 重启」走同一条路（`stack_start_from_tray`）。
唯一的差别是托盘上没地方问「顺便停运行环境吗」，所以那一问只在界面上有。

### 3.2 所有 compose 调用都带两份 `-f`

这件事**代码里本来就是对的**：`compose::run` / `compose::argv` / `pull_streaming`
三个出口全部走 `compose::full_args`，而它无条件拼上
`--project-name hunter --project-directory <app> -f <基础> -f <覆盖>`。
I11 的 U5 事故是**手工敲**命令造成的，已经用 `.env` 里的 `COMPOSE_FILE` 兜住了。

本轮补的是**把它钉死**：新增两条单测，逐条走一遍启动器会发出的全部 12 种子命令
（`up` / `up --no-recreate` / `up --force-recreate` / `stop` / `start` / `restart` /
`restart <服务>` / `down` / `ps` / `logs` / `config` / `pull`），断言

* 正好两份 `-f`；
* 第一份是基础 compose，**第二份是覆盖文件而且排在后面**（排前面 `!override` 就覆盖不到）；
* 带 `--project-name hunter`（漏了 compose 会按目录名猜一个，那就是另一套）。

`full_args` 是唯一的出口 —— 加新命令时绕过它的话这条测试发现不了，所以这一条写进了注释。

### 3.3 R3+ · 电脑或运行环境重启之后，容器要自己回来

**现象**（2026-09-23 本地 Claude 在用户 Mac 上实测）：内置运行时的虚拟机
`limactl stop` / `start` 之后，Hunter 的六个容器一个都没起来，`docker ps` 是空的。

三道，一道比一道兜底：

**① 覆盖文件里写死重启策略。** 六个服务（含原本一个字都没有的 `llm-shim`）
一律 `restart: unless-stopped`。

> **实测修正**：上游的 `docker-compose.yml` 其实**已经**写了这一条
> （`x-restart: &restart` 锚点，六个服务都引了）。测试机上 `docker inspect hunter-web-1`
> 报 `HostConfig.RestartPolicy.Name = unless-stopped` —— 确实在。
> 所以这一条不是「补一个缺的」，是**把它钉在我们自己的文件里**：
> 上游哪天改了锚点、或者用户拿到的是别的 tag，覆盖文件仍然保证它。
>
> **而且它管不到那个现场**：`unless-stopped` 的语义是「除非你手动停过」，
> 而虚拟机停机时容器正是被「手动停」的那一路。所以下面第 ② 条才是真正兜底的。

**② 启动器一起来就看一眼，该拉就拉。** 判据是「配置齐了 + 运行环境在跑 +
本项目的容器**存在但一个都没跑着**」→ 自己 `compose up -d`（带两份 `-f`），
在日志里说明，不需要用户点。四道闸门缺一不可：

1. 这台机器上装过（`install.done` + 两份配置文件都在）；
2. docker 现在连得上；
3. 容器**存在但一个都没跑着** —— 一个都没有（从没装过）、或者已经有在跑的，都不走这条路；
4. **不是用户刚刚自己点的「停止」**。

第 4 条是写代码时想到的，后来觉得它是这一段里最重要的一条：
用户点完停止、关掉窗口、过一会儿又打开启动器，启动器要是把容器又起回来，
那就是在跟他对着干。所以 `[install]` 里多了一项方案第四节没有的 `stopped_by_user`，
界面与托盘的「停止」都写它、「启动」都清它。

另外「六个都是 `created`」那一档**有意不拉** —— 那是上一次装到一半留下的残骸，
身上冻着当时那一组端口，`up` 起来照样撞车（I11 §1.1 的结论）。那一档归
`selfcheck` 的 `Incomplete` 走完整流程。

**③ 宿主机重启**：开了开机自启的机器上，启动器起来后走第 ② 条；没开的，
下次打开启动器时走第 ② 条。

## 四、R5 · 重装前检测已有数据

### 4.1 新模块 `datacheck.rs`，接在「写配置」之前

`Orchestrator::run()` 的完整安装那条路上，`[Docker, Prepare, Pull, Start]` 之前
多了一步 `data_precheck()`。只在**完整安装**那条路上做 —— `Reuse` / `FixOnly`
根本不会碰配置，没有要保护的东西。

### 4.2 「只读」只读到什么程度（与方案的第一处偏离）

方案 R5 写「用一次性容器**只读**挂载查询」。**实测做不到字面意义的只读**：
PostgreSQL 打开一个数据目录时必然要写（WAL 回放、`postmaster.pid`、控制文件），
数据目录挂成 `:ro` 它连启动都启不来。

所以拆成两段，把「真只读」和「不得不写一点」分得清清楚楚：

| 段 | 做什么 | 会不会写 |
|---|---|---|
| 浅查（`probe`） | `docker volume ls` 看卷在不在；一个 `--rm` 容器**`:ro`** 挂上去 `cat /data/PG_VERSION`；读 `.env` 里有没有 `JWT_SECRET` | **完全不写** |
| 深查（`probe_deep`） | 起一个 `--rm` 的 postgres 查表数、迁移版本、最近写入时间 | 会（WAL 回放） |

**大版本对不上时绝不进深查** —— 用 pg16 去打开 pg17 的数据目录正是会把它弄坏的那种操作。
那一档直接判「降级」，连查都不查。深查也**优先用已经在跑的 postgres 容器**
（`docker exec`），那是最便宜、也最不会出事的一条路；没有在跑的才起一次性的，
名字固定成 `hunter-datacheck-probe`（上一次没清干净的这次也清得掉），
用完无论成败都 `rm -f`。

### 4.3 「版本」是什么（与方案的第二处偏离）

方案 R5 写「查 Alembic 版本号」。**测试机上实查：这套库里没有 `alembic_version` 表。**
上游用的是自己的 `schema_migrations`：

```
$ docker exec hunter-postgres-1 psql -U hunter -d hunter -tAc "select * from schema_migrations order by 1" | tail -1
0022_schema_migrations.sql|d7a8d99bad3968958793bf46c74a9fdc5d13a298c49a9f1e71535abe13f7b060|2026-09-22 20:22:27.074459+00
$ docker exec hunter-api-1 sh -lc 'ls /opt/hunter-migrations | head -3'
0001_local_users.sql
0004_pred_backtest.sql
0005_backtest_share.sql
```

所以「数据的版本」= 已应用的最大迁移编号，「目标版本」= 目标 api 镜像里
`/opt/hunter-migrations/` 下最大的那个（起一个 `--rm` 容器 `ls` 一下）。
镜像还没拉下来时那一项是 `None`，**不猜**。

### 4.4 数据卷的真实名字（方案 1.3 节那张表要修正）

方案 1.3 节写的是 `pg_data` / `secrets` / …。测试机实测：

```
$ docker volume ls --filter label=com.docker.compose.project=hunter --format '{{.Name}}\t{{.Labels}}'
hunter_hunter_pg_data        … com.docker.compose.volume=hunter_pg_data
hunter_hunter_secrets        … com.docker.compose.volume=hunter_secrets
hunter_hunter_opencode_data  … com.docker.compose.volume=hunter_opencode_data
hunter_hunter_user_skills    … com.docker.compose.volume=hunter_user_skills
hunter_hunter_packages       … com.docker.compose.volume=hunter_packages
hunter_hunter_redis_data     … com.docker.compose.volume=hunter_redis_data
```

也就是说 compose 文件里声明的名字是 `hunter_pg_data`（**已经带一层 `hunter_`**），
docker 里的完整名再加一层项目名 → `hunter_hunter_pg_data`。
方案那张表少了一层。代码里按 **docker 的标签 `com.docker.compose.volume`** 取短名，
**不按前缀猜** —— 按前缀匹配会把用户另外装的 `hunter-fresh` / `hunter-community`
的卷算到我们头上，那在 I13 的「删除应用」那里就是一场事故。
标签读不到时才退回切前缀，并把 `label_missing` 置上说明这一条是猜的。

| 数据卷（声明名） | 内容 | 丢了会怎样 |
|---|---|---|
| `hunter_pg_data` | PostgreSQL：账号、配置、自选股、历史分析 | **核心数据** |
| `hunter_secrets` | 密钥卷 | 用它加密的配置解不开。**必须和数据库成对** |
| `hunter_opencode_data` | 对话引擎的会话记录 | 历史对话丢失 |
| `hunter_user_skills` | 用户自建技能 | 自建技能丢失 |
| `hunter_packages` | 依赖缓存 | 可再生 |
| `hunter_redis_data` | 缓存 | 可再生 |

### 4.5 决策表（与方案的第三处偏离）

| 检测结果 | 本轮做法 | 与方案一致？ |
|---|---|---|
| 数据库 + 密钥卷 + `JWT_SECRET` 都在，版本不高于目标 | **直接沿用**，过程流里说清「不会重建」 | ✅ |
| 数据库在，**密钥卷缺失** | **照常装**，但把后果说清楚 | ❌ 方案要求「停下来给两个选项」 |
| 数据库版本高于目标镜像 | **停在这里**（新错误码 `E_DATA_DOWNGRADE`） | ✅ |
| 没有数据卷，但备份目录里有备份 | 说明有几份备份，照常装 | 部分（没做「一键恢复」入口） |
| 什么都没有 | 全新安装 | ✅ |

**「缺密钥卷」为什么不拦**：方案给的两个选项是「从备份恢复密钥卷 / 放弃这部分加密配置」。
**前一个的能力要等 I13 的 R6** —— 现在的 `backup.rs` 只备份数据库与配置，**不备份卷**，
摆一个点不动的选项比不摆更糟。而后一个恰恰就是「照常装」：它不删任何东西，
只是那几项加密配置解不开。所以这一档如实说清后果、照常往下走：

> 数据库、会话、自建技能全都保留，登录也不会失效。只有用那把密钥加密过的几项配置解不开，
> 需要你在 Hunter 里重新填一次。

等 I13 把备份卷那条路补上，再改成两选一。这一条写进了「没做的」一节。

**「降级」为什么一定要拦**：这是唯一一档「宁可装不上，也要保住数据」的情况 ——
硬装下去会真的把数据弄坏，而且没法撤销。这也是本轮唯一新增的错误码。

**CPU 那一行对不上是采样口径不同，不是 bug**：`sysinfo` 按它自己两次采样之间的间隔算，
`top -bn2 -d0.5` 按它那 0.5 秒算，两者不是同一段时间。逐个容器的 CPU 同理

**内存、磁盘、卷、镜像这些「存量」指标则必须一模一样，实测确实一模一样。**

#### 这一节抓到的 bug：`--monitor` 的单位和界面对不上

第一次跑 `r2-compare` 时，`--monitor` 打的是 `内存 4.2 GB / 7.7 GB`，
而同一时刻界面上那张卡写的是 `4.57 GB / 8.32 GB`，`free -b` 的原值是 `4474494976 / 8319729664`。

根子：仓库里有**两个都叫 `human_bytes` 的函数** ——
`flow::human_bytes` 按 1000 进位（SI，和界面 `src/lib/format.ts` 的 `bytes()` 一套），
`assist::probe::human_bytes` 按 1024 进位**却写成 `GB`**。
`headless.rs` 的 `opt_bytes` / `opt_pair` 拿的是后者。

`--monitor` 存在的唯一理由就是拿去和界面、和 `free -b` / `df -B1` / `docker system df` 对照，
**对不上的对照工具比没有还糟**。已改成 SI 那一个，并补一条单测钉住进位基数
（`monitor_的字节格式与界面同一套单位_si`）。上表是改完之后重跑的结果。

界面那一侧从头到尾是对的 —— 这是命令行验收工具自己的毛病，没有影响用户看到的数字。

#### 本轮踩的一个坑：`cargo build --release` 不等于 `tauri build`

重跑验收时我先用 `cargo build --release` 重编了一次，结果 `r1-gui` 挂了：
界面整片空白，只有一行 `Could not connect to localhost: Connection refused`，
`boot_state` 一次都没被调用过（日志里没有「开机判定」）。

原因是 `tauri.conf.json` 里 `devUrl = http://localhost:1420`，
只有走 `tauri build` 才会把 `dist/` 嵌进去、指向嵌入资源；直接 `cargo build` 出来的是**连开发服务器的那一版**。
改回 `i12-build.sh` 的 `tauri build --no-bundle` 之后一切正常。

**这是我的构建操作失误，不是产品缺陷** —— 记在这里是因为它同时说明一件事：
`--boot-state` 全绿、Rust 单测 591 条全绿，界面仍然可以是一片空白。
**没有截图就不算验过**（总控规则「前端完成的标准」）。

## 七、没做的 / 未验证的

* **macOS 真机未验证。** 本项目只有 Linux 测试机。本轮里有三块是**只有 mac 才走得到**的代码路径：
  * `monitor::runtime()` 那一层（`limactl shell` 进虚拟机跑 `free -b` / `df -B1`）——
    Linux 测试机上 `applicable()` 恒为假，所以走的是「不适用 + 说明原因」那一支，
    **采集本身一次都没真跑过**；
  * `builtin::stop()`（`colima stop --profile hunter`）—— 同理；
  * `mem_pressure()` 的 macOS 分支（`sysctl kern.memorystatus_vm_pressure_level`）。

  这三块的守卫（`argv_vm_metrics` 白名单、`colima_call` 的 `COLIMA_HOME` 校验）
  在 Linux 上有单测，**但那三条命令本身没有在真虚拟机里跑过**。等用户真机验收。

* **R3+ 那个现场（虚拟机 `limactl stop` / `start`）在 Linux 上造不出来。**
  测试机用的是系统 Docker，没有虚拟机。本轮用 `systemctl restart docker`
  造了一个「守护进程重启」的近似现场验证第 ① 道，用 `compose stop` +
  清 `stopped_by_user` 验证第 ② 道 —— **两者合起来不等于真的虚拟机重启**。
  「虚拟机 stop/start 后 60 秒内自动回到 6/6」这条验收标准**只能在用户 Mac 上验**。

* **R5「缺密钥卷」只做了一半**（见第六节第 4 条）。I13 的 R6 把备份卷那条路补上之后，
  这一档要改成两选一。已进待办池。

* **`[monitor]` 那几个阈值只用来给界面标色**，不发通知、不做智能分析 —— R7 是 I13 的活。
  设置页这一轮**没有**加「资源提醒」分区，理由同上：没有代码读的开关不该摆出来。

* **资源采集的四个周期（5 / 30 / 10 / 300 秒）是按方案写死的**，没做成可配置。

* **`docker stats` 在容器很多的机器上有点慢。** 测试机上同时跑着三套 Hunter
  （本项目 + `hunter-community` + 两套 `hca-*`），实测一次 `docker stats --no-stream`
  指定 6 个容器名要 1–2 秒。窗口可见时每 10 秒一次，可以接受；没做缓存。

* **R1 五行表里「什么都没有 → 欢迎页」这一行没有真机证据**（见 5.2 节）。
  只要这台机器上有一套 Hunter 在跑，I9 的项目名归属守卫就会先拦下来 ——
  守卫做得对，但也因此造不出那个现场。**这一行只有单测覆盖。**

* **「开机第一屏不超过 1 秒」这条没有稳定达标。** 实测浅查耗时在
  **204 / 355 / 406 / 612 / 658 / 847 / 1206 / 1520 毫秒**之间（测试机 2 核，
  且同一时刻还跑着另外两个项目）。容器全在、要逐个问状态再 GET 一次网页时最慢。
  界面上这一屏本来就是「查完就走」，慢的时候用户多看零点几秒 ——
  但**方案写的是「不超过 1 秒」，实测会超，如实记下**。要压下去得把
  `docker compose ps` 与网页探测并发起来，已进待办池。

* **`r3plus-autoup` 的 60 秒验收标准是擦着过的。** 三次实测 **56 / 59 / 63 秒**
  （从启动器进程起来算到 6 个容器都在跑，每 5 秒采样一次）。其中 `compose up -d`
  本身占 49–56 秒 —— 这是 2 核测试机上六个容器一起起来的真实耗时，
  换台快一点的机器会好很多。**但在这台机器上它确实会偶尔超过 60 秒。**

* **I5/I7 场景 1–4 本轮没跑**（Docker 缺失 / daemon 没起 / 端口被占 / 拉取失败），
  理由见 5.3 节末尾：那几个场景要停 docker 或用 iptables 拦 ghcr，
  会波及同机另外两个项目。
