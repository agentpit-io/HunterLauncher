## 一、模块与实现（方案 §5.1–5.5、§6–9）

### 1.1 `runtime::docker`（方案 §5.1、§6）

判定逻辑严格按 M0 §5.4 的实测结论，**不能只看退出码**：

| 场景 | 判定依据 | 错误码 |
|---|---|---|
| 进程起不来（ENOENT） | `Command::spawn` 失败 | `E_DOCKER_MISSING` |
| 退出码 1，stdout 有 `Client`、`Server` 为 `null` | `Server == null` | `E_DAEMON_DOWN` |
| 退出码 0 | 读 `Server.Version` 比最低版本 | 版本不够也报 `E_DOCKER_MISSING`，并写明差在哪一项 |

- **运行时种类**：`Server.Platform.Name` + `Components[].Name` + `docker context show` 三个来源合并判断，
  认 Docker Desktop / Docker Engine / OrbStack / Colima / Podman（实验）。
  三个来源都用上是因为它们各自都会漏 —— 例如 OrbStack 有时只在 context 名里露馅。
- **最低版本**：Engine 24 / Compose v2.20（方案 §5.1）。不满足时文案会点名是哪一项，
  例如「Docker Compose 版本太低（需要 v2.20 及以上，现在是 v2.19.0）。启动器用的 `--progress json` 与 `!override` 都要 v2.20+」。
- **三平台安装引导**由 Rust 按当前平台生成（只有它知道跑在哪个系统上），界面与 headless 共用同一份文案。
  Windows 那份包含 WSL2 检测（`wsl --status` 只看退出码 —— wsl.exe 的输出是 UTF-16，解析文本不可靠）、
  BIOS 虚拟化、`.wslconfig` 限内存、Clash/TUN 导致容器无网这四个常见坑（方案 §6 逐条落实）。
- Docker Desktop 的**商业授权提示**（250 人 / 1000 万美元）按方案 §6 写进引导末尾。

### 1.2 `config`（方案 §5.3、§7）

三个文件，各司其职：

| 文件 | 内容 | 权限 |
|---|---|---|
| `~/.hunter/launcher.toml` | 语言、自启、镜像源、tag、端口、模型模式、安装标记。**不含任何 key** | 644（目录 700） |
| `~/.hunter/app/.env` | Hunter 的配置，含 hunter key 与数据库口令 | **600** |
| `~/.hunter/app/docker-compose.launcher.yml` | 端口与镜像源覆盖 | 644 |

- **三个密钥首次生成后永不更换**：`JWT_SECRET`（48 字节）、`POSTGRES_PASSWORD`（24 字节）、
  `OPENCODE_PASS`（18 字节），全部取自操作系统 CSPRNG。换掉任何一个都会出真实的问题 ——
  JWT 换了用户掉登录、数据库口令换了连不上已初始化的卷、opencode 口令换了健康检查直接挂。
  重写 `.env` 前先把旧值读回来（`read_sticky`），有单测覆盖，用例 9 也实测了两次打开指纹不变。
- **端口冲突**：逐个 `TcpListener::bind` 试。web 按 `0.0.0.0` 试（它要对外），其余按 `127.0.0.1` 试。
  被占就往上找，最多 200 个。**本项目自己这一套正占着的端口不算冲突**（见第十一节的 bug 2）。
- **覆盖文件**：除 web 外全部 `!override ["127.0.0.1:x:y"]`（红线 4）。
  `!override` 标签是必须的 —— compose 默认对 `ports` 做**追加**合并，漏了标签会变成「既听 0.0.0.0 又听 127.0.0.1」。
  国内源时顺便把 postgres / redis 的 `image:` 也改写过去。
- **compose 文件**：按固定 tag 从 `raw.githubusercontent.com/agentpit-io/hunter-community/v<tag>/docker-compose.yml` 取，
  做三重校验（长度 ≥ 2000 字节、含 `services:` 与六个服务名、含 `hunter-community-web`），
  再比对内置副本的 sha256（`4732348f…62ee2`）；不一致或取不到就用**启动器内置的 1.2.0 副本**，并如实告诉用户用的是哪一份。
  方案 §5.2 说的「从 Release 资产下载」不成立（M0 §3.2 实测 Release 的 `assets` 是空数组）。

### 1.3 `gateway`（方案 §5.4、§8）

方案写的 `POST https://llm.agentpit.io/v1/keys/validate` **不存在**。真实接口（M0 §1 实测）：

```
GET https://hunter.agentpit.io/api/saas/llm/quota       → 额度
GET https://hunter.agentpit.io/api/saas/llm/v1/models   → 模型列表（OpenAI 兼容）
```

错误分类与文案：

| 情况 | 判定 | 错误码 | 文案要点 |
|---|---|---|---|
| 格式不对 | **本地判，不发请求**（`hunt_tools_` 开头、43 位、随机段是 ASCII） | `E_KEY_INVALID` | 「应该是 `hunt_tools_` 开头、一共 43 位的一串字符（你填的是 N 位）」+ 申请链接 |
| 网关 401 | HTTP 401 | `E_KEY_INVALID` | 「这把 key 网关不认（可能填错了，也可能已经被吊销）」 |
| 额度用尽 | HTTP 402 | `E_QUOTA_EXHAUSTED` | 「等明天 0 点（上海时间）重置，或者在下一步改用你自己的模型 key」 |
| 连不上 | 传输层失败 | `E_PROXY_BLOCK` | 「检查网络或代理；用 Clash 之类代理时把 hunter.agentpit.io 放行」 |

**没有假装能区分「已吊销」**：M0 §1.3 实测网关对「格式错 / 不存在 / 已吊销 / 未带 key」返回
**字节级完全相同**的 401，方案 §18 要求的分原因文案在网关侧做不到（红线 1，不编造诊断结论）。

**自带 key 模式的连通性检查是真的发请求**：先试 `GET {base}/models`；
有些兼容服务没开这个接口，再退而发一次 `max_tokens: 1` 的 `POST {base}/chat/completions`。
两条都不通才算失败。模型名不在 `/models` 列表里时如实说「列出的 N 个模型里没有它，名字可能写错了 —— 仍然可以继续」。
DeepSeek 按 **BASE_URL 的主机名**自动开 `LLM_SCHEMA_SANITIZE=1`（不猜模型名，路径里带 deepseek 不算）。
自带 key 模式下十个子智能体模型名（`AGENT_SUB_RESEARCH_MODEL` 等）也一并换成用户那个模型 ——
不换的话「对话能用、深度分析是坏的」（M0 §3.3）。

### 1.4 `registry`（方案 §5.5）

候选源两个，**只有真实探到的才参与**：

| id | 前缀 | postgres/redis 从哪来 | 界面文案 |
|---|---|---|---|
| `ghcr` | `ghcr.io/agentpit-io` | `docker.io/library`（GHCR 上没有它们） | GHCR · GitHub |
| `tencent` | `hkccr.ccs.tencentyun.com/agentpit` | 同前缀（国内拉 Docker Hub 不稳，已一并镜像） | 腾讯云 · 香港 |

探测走标准 registry v2 匿名流程：`GET /v2/<repo>/manifests/<tag>` → 401 拿 `WWW-Authenticate`
→ 换 token → 再取一次 → **解析响应确认真是个 manifest**（不是只看状态码）。
探不到就标「不可用」并写清 HTTP 状态或网络错误，**不做假的测速界面**。
一个都探不到时直接报错，不偷偷退回某个源让用户白等几分钟。

用户还可以在设置里手填自定义前缀（自建镜像仓库的内网用户）。

### 1.5 `compose`（方案 §5.2、§9）

- **进度流在 stderr 上**，不是 stdout。这是本轮最重要的一条实测修正，详见第十二节偏离 1。
- 按 `parent_id`（形如 `"Image <完整引用>"`）分组到镜像；层级 `current`/`total` 求和。
  `postgres:16-alpine` 这种不带 registry 前缀的 id 靠后缀匹配认出来。
- **分母是拉取前从 registry manifest 算好的压缩大小**，不是等层报上来 ——
  这样进度条从第一秒起就是对的。多架构 index 按 `platform.os == "linux"` 过滤掉
  buildx 塞的 `unknown/unknown` attestation 条目（M0 §4.1 的坑）。
- `Extracting` 行只有 `current` 没有 `total`，算不出解压百分比 → 这一段界面显示「解压中」（待办池 P1-1 的解法）。
- **速度与剩余时间只算真走过网络的层**：本机内容存储里已有的层会瞬间「完成」，
  把它们算进速度会显示 67 MB/s 这种一看就假的数字（第十一节 bug 1）。百分比里仍然算它们 —— 用户关心的是整体完成度。
- 失败重试 3 次，**没有指定源时自动换到另一个源**（重写 `.env` 与覆盖文件里的镜像地址后重来）。
- `up -d` 后每 2 秒轮询 `docker compose ps --format json` 的 `Health`，上限 180 秒；
  超时时**点名是哪几个服务没就绪**、各自处在什么状态；有容器非零退出就不傻等，立刻报出来。
- `down` **永远不带 `-v`**，绝不删用户的数据卷。
- 所有命令 `--project-name hunter` + `--project-directory ~/.hunter/app`，参数一律数组（红线 3）。

### 1.6 `flow` —— 界面版与 headless 共用的编排层

一次安装的真实顺序：

```
① 选镜像源（真实探测）→ ② 取 compose（固定 tag + 校验 + 兜底）
→ ③ 解端口冲突 → 写 .env(600) 与覆盖文件 → docker compose config 校验
   → 从渲染结果里**机器自查红线 4**（除 web 外必须绑 127.0.0.1）
→ ④ 读 manifest 算每镜像大小 → ⑤ pull（失败换源重试 3 次）
→ ⑥ up -d → 轮询健康 180 秒
```

第 ③ 步在拉取**之前**：compose 要靠 `.env` 的 `HUNTER_REGISTRY` / `HUNTER_VERSION`
才知道拉哪些镜像。方案 §4 的状态机把 `WriteConfig` 画在 `Pulling` 之后，那个顺序在真实
compose 工作流里走不通（偏离 2）。

**红线 4 的自查读的是 `docker compose config --format json`**，不是我们写的覆盖文件 ——
覆盖文件只是「意图」，`config` 给的是合并之后的**最终结果**，`!override` 漏了只有在这里才看得出来。

### 1.7 headless（方案 §6 Linux 一节）

```
hunter-launcher --headless [--key-file PATH] [--registry ghcr|tencent|<前缀>] [--tag 1.2.0] [--pull-only]
hunter-launcher --status | --start | --stop | --restart | --down | --logs [服务名] | --diagnose
```

- **和界面版跑的是同一套 `flow`**，不是另写一遍。两条路径只在「进度怎么显示」上不同。
- 交互式输入 key 时**不回显**（`rpassword`）；标准输入不是终端时明确要求用 `--key-file`。
- 终端里进度原地刷新，重定向到文件时改成每 10 秒一行（日志才读得下去）。
- `--pull-only` 是本轮新加的：只拉镜像不起容器。网速慢的机器可以先预下载，
  也让「换源重拉」「断网重试」这类测试不必碰已经装好的那一套。
- Windows 上 `windows_subsystem = "windows"` 的程序默认没有控制台，带 `--headless` 从 cmd 跑时
  先 `AttachConsole(ATTACH_PARENT_PROCESS)`，否则什么都看不见（只用一个 extern 声明，不引 windows-sys）。

### 1.8 日志与脱敏（方案 §7、§12.3 · 红线 2）

- `~/.hunter/logs/launcher.log`，5 × 5 MB 滚动。
- **`write_line` 是唯一的写盘出口，每一行都先过 `redact`** —— 这不是调用方的自觉，是写盘路径上的硬约束。
- 脱敏两道保险，顺序是**形状 → 登记 → 形状**：
  1. 形状匹配：`hunt_tools_…`、`sk-…`、`hk_…`、`Bearer …`、邮箱、手机号、IPv4 末段；
  2. 登记表：启动器手里真实拿到过的密文（hunter key、自带 key、数据库口令、JWT_SECRET）整段替换。
  形状跑两遍是因为登记表里可能存的是更长串的**前缀**，单靠登记会留一截尾巴。
- **`127.0.0.1` / `0.0.0.0` 不打码** —— 它们不是隐私，而且红线 4 的自查正靠这个串。
- 看门测试 `落盘的日志里找不到_key`：往临时目录真写三行含 key 的日志，
  再把文件读回来断言既搜不到整把 key 也搜不到 key 的片段。这条测试在 CI 里每次都跑。

### 3.2 真实冷拉（同一套代码路径，换一个本机没有的 tag）

为了拿到真实的下载耗时，用 `--pull-only --tag 1.1.0-rc1`（同样六个镜像、同样的解析器与聚合器）
先 `docker rmi` 掉再拉一遍。**网卡收字节是从 `/sys/class/net/<if>/statistics/rx_bytes` 读的，不是估的**：

| 项 | 实测 |
|---|---|
| 墙钟（含准备） | 68 秒 |
| 纯拉取 | **61 秒** |
| 网卡实际收到 | **408 MiB** |
| manifest 合计（进度条分母） | 851 MB |

各镜像耗时（六个是**并行**拉的，所以时间互相重叠，这里是各自从第一个字节到 `Pulled`）：

| 镜像 | 压缩大小 | 耗时 |
|---|---|---|
| `hunter-community-web` | 327 MB | 60 秒 |
| `hunter-community-api` | 218 MB | 37 秒 |
| `hunter-community-opencode` | 153 MB | 28 秒 |
| `hunter-community-llm-shim` | 20.6 MB | 7 秒 |
| `postgres:16-alpine` | 116 MB | 5 秒（本机已有） |
| `redis:7-alpine` | 16.2 MB | 4 秒（本机已有） |

> **为什么 408 MiB 而不是 851 MB**：1.1.0-rc1 与本机已有的 1.2.0 共用相当一部分基础层，
> 那些层报 `Already exists`，不过网。这也正是「速度只算真走过网络的层」这条修正的由来。
>
> **一次完全干净的机器上装 1.2.0 要多久，本轮「未测」**（红线 5）。
> 原因：这台机器上跑着的 hunter-community 旧栈正用着同样的六个镜像，要造出「本机没有任何层」
> 的条件必须把旧栈 `down` 掉再 `docker rmi`；而旧栈没有 `.env` 文件（不知道当初是怎么起的），
> `down` 之后不保证能原样恢复，风险不值得。按本轮实测的 6.7 MiB/s 有效吞吐推算约需 2 分钟量级，
> **这是推算不是实测**。

### 3.3 一个副产品结论：修正 M0 §5.1 的「`docker rmi` 不清内容存储」

M0 记的是「containerd 镜像存储下 `docker rmi` 不清内容，重拉是秒级」。本轮实测 **Docker 29.8.1 会清**：
删掉 1.1.0-rc1 四个镜像后 `docker system df` 的镜像占用从 17.31 GB → 14.86 GB，磁盘从 43G → 41G，
随后的重拉确实走了网络（408 MiB）。M0 那次大概是镜像仍被别的 tag / 容器引用着。

**第一次跑 CI 就被 Windows 抓到一个真 bug**（[运行 35455475016](https://github.com/agentpit-io/HunterLauncher/actions/runs/35455475016)）：

**这条 bug 只有把 `cargo test` 加进跨平台 job 才抓得到 —— 加这一步当天就回了本。**

修完之后 [运行 35455884153](https://github.com/agentpit-io/HunterLauncher/actions/runs/35455884153) **全绿**：

## 十一、本轮真实测试撞出来的 6 个 bug（都已修并补了单测）

这一节记的是「**只有真跑起来才会暴露**」的问题，每一个都对应一条新的单元测试。

### bug 1 · 进度流在 stderr 上，按 stdout 读等于没有进度

第一版按 M0 §5.1 的记载读 stdout，结果拉取过程中一行进度都收不到，
所有事件在进程结束后一次性涌出来 —— 界面表现为「进度条一直 0%，最后一瞬间 100%」，
每镜像耗时全是 0 秒或整段时长。抓了一次真实的 `--progress json pull` 才看明白：
**403 行进度全在 stderr**，stdout 一行都没有。已改成两个流都读（各起一个读线程，
经 `mpsc` 汇到主循环），并补了一条以真实行型为素材的解析测试。

### bug 2 · 第二次打开会把端口往上挪一格

`resolve_ports` 把「端口被占」一律当冲突，而第二次打开时 3101 正被**我们自己的 web 容器**占着，
于是每开一次启动器端口就往上挪一格（3101 → 3102 → 3103…），用户存的书签全会失效。
已改成先问一遍 `docker compose ps` 拿到本项目正在用的端口，这些不算冲突。
用例 9 复测：连开两次，端口与三个密钥都不变。

### bug 3 · 界面打码露出 12/32 个随机字符

视觉稿的打码是「前缀 + 8 位随机 + 圆点 + 末 4 位」，那是按 `hk_` 前缀画的。
照抄到 43 位的真 key 上，`head=19` 会露出 8 位随机段 + 末 4 位 = **12/32**。
用户把界面截图贴进 issue 就等于泄漏三分之一把 key。已把 `head` 改成前缀长度（11），
随机段只露末 4 位（保留它是为了让用户确认「我贴的是哪一把」）。
补了一条测试：随机段里任意 5 个连续字符都不许出现在打码结果里。

### bug 4 · 速度显示 67 MB/s 这种一看就假的数字

本机内容存储里已有的层会瞬间「完成」，把它们算进速度就会冒出远超链路能力的数字。
已改成速度与剩余时间**只算真走过网络的层**（`Downloading` 事件标记过的），
百分比仍然算上缓存层（用户关心整体完成度）。

### bug 5 · Windows 上 CRLF 让内置 compose 副本的校验和对不上

CI 在 windows-latest 上跑 `cargo test` 时抓到的：git checkout 把 LF 换成 CRLF，
`include_str!` 编进去的内容就和写死的 sha256 对不上。
`.gitattributes` 强制 LF + `bundled_compose()` 再归一化一次。详见第六节。

### bug 6 · Docker 页要点两次「下一步」

状态机里 `CheckDocker` 与 `CheckDaemon` 渲染的是**同一页**，而按钮只发一个事件，
用户点完页面纹丝不动，得再点一次。一次检测本来就同时得出「装没装」与「daemon 起没起」两个结论，
已改成两个事件一起发。这是用 xdotool 走真实流程时撞出来的 —— 只看代码不会发现。

另外两处不算 bug 但也是真跑才发现的：**`docker compose` 的报错藏在 JSON 进度行里**
（`text: "Error"`，原因在 `details`），只挑非 JSON 行的话用户看到的是「原话：」后面空一片，
已改成两种都挑；以及**单元测试里的全局状态竞争**（日志单例与 `HUNTER_HOME` 环境变量），
已各加一把测试锁，连跑 3 次无 flaky。
