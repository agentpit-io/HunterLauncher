## 零、一句话

0.1.5 把 macOS 的端口 P0 修好了，真机却卡在下一步：**六个公开镜像一个都拉不下来**，
界面上那句「原话：」后面还是空的，规则层把它当成「源不通」在两个镜像源之间换了三次。

真因只有一句话：**我们让启动器找到了 docker，但没让 docker 找到它自己的凭据助手。**

本轮把三件事修掉——子进程环境统一构造（PATH 补全）、错误原话不再丢、
新错误码 `E_CRED_HELPER` + 不再来回换源——并在测试机上
**用真的 0.1.5 二进制复现了那次失败**，再用新版在同一个现场零点击跑到 6 / 6。

macOS 真机**未验证**（测试机是 Linux）。见第七节。

## 一、根因：I4 修的是上一层，这一层没修

### 1.1 现场原话

```
docker compose pull 退出码 1。原话：                           ← 第一次，空的
…（换源到 GHCR）…
retry_pull → 原话：error getting credentials - err: exec:
  "docker-credential-osxkeychain": executable file not found in $PATH, out: ``
```

用户的 `~/.docker/config.json` 里有 `"credsStore": "osxkeychain"`——
这不是用户手写的，是 OrbStack / Docker Desktop 装的时候自己写进去的。
docker 每次访问 registry（**哪怕是公开仓库**）都会先执行
`docker-credential-osxkeychain` 去问一句「这个 registry 有没有存过凭据」。
那个程序在 `/usr/local/bin`（软链到 `/Applications/OrbStack.app/Contents/MacOS/xbin/`）。

### 1.2 为什么启动器找得到 docker、docker 却找不到助手

| 层 | 谁在找 | 用的是什么 | I4 之后 |
|---|---|---|---|
| 一 | 启动器找 `docker` | `runtime::which`：配置 → PATH → 平台已知位置 | **修好了** |
| 二 | docker 找 `docker-credential-*` | **子进程继承的 `$PATH`** | **没碰过** |

`Command::new("/usr/local/bin/docker")` 只解决了第一层。第二层里，
子进程继承的还是 GUI 那份 `/usr/bin:/bin:/usr/sbin:/sbin`，
`/usr/local/bin` 不在里面，docker 自然 ENOENT。

**实测**（用户 Mac）：同一条 `docker compose pull`，把 `/usr/local/bin` 补进 PATH 之后立刻成功。

> 0.1.4 那次 GUI 拉取成功，是因为那次是从终端 `open` 启动、继承了终端的 PATH。
> **它从来没有证明过「双击能成功」。**

### 1.3 另外两条（都是「该说的话没说」那一类）

| # | 现象 | 为什么 |
|---|---|---|
| 2 | 第一次失败的「原话」是**空的** | compose v5 的 `--progress json` 把顶层错误写成 `{"error":true,"message":"…"}`，而 0.1.5 的 `extract_error_text` 只认 `{"text":"Error","details":…}` 那种形状，于是整条原因被丢掉。`retry_pull` 走的是不带 `--progress json` 的 `compose::run`，纯文本 stderr，所以**只有它**带出了真话 |
| 3 | 规则层把它当成「下载源不通」 | 错误码是 `E_PULL_FAILED`，规则层第 ④ 条就是「换个测得通的源」。**这是本机配置的问题**，ghcr 和腾讯云都通（测速那一步实测 619 ms / 1797 ms），换一百次也是同一句原话 |

三条连起来的结果：**268 秒、3 个修复回合、0 token、0 个问题解决**。

### 1.4 这次真正的教训

**修好一层不等于修好一类。**「谁的 PATH」这件事，凡是会 `exec` 别人的程序都要问一遍：
docker 要 exec 凭据助手、要 exec `docker-compose` 这个 CLI 插件；
Windows 上 Docker Desktop 的 `docker-credential-desktop.exe` 同理。
I4 的报告里写的是「macOS GUI 程序的 PATH 问题已修」——**那句话的范围写大了**。

## 二、改了什么

### 2.1 子进程环境统一构造 · `src-tauri/src/runtime/env.rs`（新文件，475 行）

一处实现，所有调用点复用：[`proc::base_command`] 是全项目**唯一**建 `Command` 的地方，
钩子挂在那一行上，改一次就全盘生效（`compose.rs` 里流式跑 pull 的那段也走它）。

| 项 | 取值 |
|---|---|
| `PATH` | 原 PATH + docker 所在目录 + 它软链指向的目录 + `[runtime] search_paths` + 平台内置清单。**去重、保序、只加真实存在的目录** |
| `DOCKER_CONFIG` | 只有开了隔离配置时才设（见 2.3）；否则原样继承 |

三个刻意的选择：

- **补进来的目录排在原 PATH 后面**。我们要做的是把「一个都找不到」变成「找得到」，
  不是去抢用户 PATH 里已有的同名程序。
- **与 `runtime::which` 用同一份清单**（`builtin_dirs()` + `Policy::extra_dirs`），
  不另抄一份 —— 抄一份就一定会有哪天只改了一边。
- **只加真实存在的目录**。不存在的目录补进 PATH，除了让每次 `exec` 多一次无用的 `stat`，
  还会让日志里那行「补了哪些目录」变成一串谎话。

日志里一行（测试机实测）：

```
2026-09-21 15:20:27 [info] 子进程 PATH 补了 2 个目录：/usr/local/bin、/snap/bin
```

核心算法拆成了纯函数 `build_path(base, candidates, exists)`，
所以它能在**任何平台的 CI 上**测，不依赖跑测试的机器上装没装 docker。

### 2.2 「原话」不再是空的 · `compose::extract_error_text`

**测试机上真跑出来的三行**（`DOCKER_CONFIG` 里写一个找不到的 `credsStore`，
compose v5.5.1 / Docker 29.8.1）：

```
{"id":"Image ghcr.io/…-api:1.2.0","status":"Working","text":"Pulling"}
{"id":"Image ghcr.io/…-web:1.2.0","status":"Working","text":"Pulling"}
{"error":true,"message":"error getting credentials - err: exec: \"docker-credential-fakehelper\": executable file not found in $PATH, out: ``"}
```

现在三种 JSON 形状都认：

| 形状 | 取哪里 | 谁会发 |
|---|---|---|
| `{"text":"Error","details":"…"}` / `{"status":"Error"}` | `details`，退而取 `status` | compose 的逐镜像进度事件 |
| `{"errorDetail":{"message":"…"}}` / `{"error":"…"}` | 里面的 message | `docker pull` 的原生流 |
| `{"error":true,"message":"…"}` | `message` | **compose v5 的顶层错误** ← 0.1.5 漏的就是它 |

另外三处：

- **两个流都收**（原来只收 stderr），stderr 优先、它空了才看 stdout；
- 纯文本行与 JSON 挑出来的**都要**（纯文本排前面），只要有谁说了一句实话就不许「原话」是空的；
- 真的一个字都没输出时，说「退出码 1，而且 stdout / stderr 里一个字的错误都没有」，
  **不留「原话：」这种半截话**，并在 launcher.log 里记一条 warn。

### 2.3 新错误码 `E_CRED_HELPER` + 对症的动作

判据三条任一命中：`error getting credentials` / `docker-credential-` /
`executable file not found`（后者排掉「找不到 docker-compose」那种）。
`pull` 与 `up` 两张归类表都接了这一条，而且**排在网络那几条前面**——
它的原话里常常也带着别的关键词。

规则层（`assist/auto.rs`，零 token）：

```
E_CRED_HELPER
 ├─ 补全后的 PATH 上找得到助手 → retry_pull（用补全后的 PATH 重来）
 └─ 补全后仍然找不到         → use_isolated_docker_config + retry_pull
```

`use_isolated_docker_config`（`Safe` 级，新动作）做的是：在
`~/.hunter/docker-config/` 里生成一份**去掉 `credsStore` / `credHelpers` / `auths`**
的 docker 配置，之后所有 docker 子进程用 `DOCKER_CONFIG` 指过去。
Hunter 的六个镜像都是公开的，本来就不需要登录。

**不改用户的 `~/.docker/config.json`** —— 这不是「代码里我们没写那一行」，
是路径守卫拦得住，并且有一条单测钉着：

```rust
#[test]
fn 用户的_docker_配置写不进去() {
    assert!(writable_path(&home().join(".docker/config.json")).is_err());
    assert!(writable_path(&dockercfg::isolated_dir().join("config.json")).is_ok());
}
```

两个不显眼但要紧的细节：

- `contexts` 与 `cli-plugins` 两个目录做**软链指回原处**。不带 `contexts`，
  `currentContext`（Docker Desktop 是 `desktop-linux`、OrbStack 是 `orbstack`）
  就找不到，docker 会去连默认的 `/var/run/docker.sock`；不带 `cli-plugins`，
  `docker compose` 这个插件本身就没了。**这两条不处理的话，「修好拉取」会变成「连不上 daemon」。**
- `contexts` 没带过来时，`currentContext` 也跟着去掉——留着一个指不到的 context 更糟。

### 2.4 不再在两个源之间来回兜圈

两道闸门，一内一外：

| 位置 | 规则 |
|---|---|
| `flow::pull` 的三次重试 | `E_CRED_HELPER` **立刻停**，不换源、不重试；另外，换过一次源之后原话指纹没变，也停 |
| `assist::auto` 的修复回合 | **同一条原话只换一次源**（`switched_registry` 按指纹记）。第二次遇到同一条原话时规则层**让路**，把现场连同原话交给诊断员（模型），并在过程流上说一句「这不是下载源的问题」 |

「原话指纹」= 原话小写化、抹掉候选源的 prefix / host / label、把数字换成 `#`、
压平空白。作用只有一个：回答「换过源之后，失败的还是不是同一件事」。

送给模型的证据里也补了两件事（0.1.5 的模型什么都没被告知，只好去猜）：

```
子进程 PATH 补了 2 个目录：/usr/local/bin、/snap/bin
docker 凭据助手 docker-credential-fakehelper：**补全 PATH 之后仍然找不到**
总指挥补充：上一回合已经换过下载源了，失败的原话一个字都没变，说明这件事与下载源无关。
```

## 四、偏离与刻意的决定

| # | 决定 | 为什么 |
|---|---|---|
| 1 | `DOCKER_CONFIG` 隔离是**兜底**，不是默认。默认只补 PATH | 绝大多数机器上助手就在已知位置，补 PATH 就够了，用户那份配置连读都只读一次 |
| 2 | 隔离配置时把 `contexts` / `cli-plugins` 软链回原处，而不是写一份「最小配置」了事 | 不带它们会从「拉不动」变成「连不上 daemon」「没有 compose 插件」，比原问题更糟 |
| 3 | Windows 上软链建不了就**如实报「没能带过来」**，不提权、不降级去改用户文件 | 授权页第 4 条：不用管理员密码。记进待办池 P1-28 |

```bash
env -i HOME=$HOME PATH=/usr/bin:/bin:/usr/sbin:/sbin \
```
