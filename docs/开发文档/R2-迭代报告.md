## 零、一句话

一台真 Windows 的运行面板上出过这么一行红字（逐字）：

> 每日自动备份没有挂上，这台电脑上它一次都不会跑：**schtasks 三条路都没装上定时备份：/Create /XML 失败：错误: 未指定的错误；先删后建（/XML）还是失败：错误: 未指定的错误；/SC DAILY 也失败：错误: 拒绝访问**

**这一屏里最值钱的一句是「拒绝访问」。** 第三条路（`/SC DAILY`）**一个 XML 都不碰**，
它也失败了 —— 说明病根不在 XML 写得对不对，而在**这个进程有没有资格往 Windows
任务库里写**。三条路共享同一个前提，前提不成立就一起死，代码里没有第四条路。

**但「判出病根」需要一次真机对照实验**（同一台机器上以管理员身份再跑一次同一条命令），
而本轮手上**一台 Windows 都没有**。所以这一轮**不去猜**，改做**不依赖那个前提**的事：

| | 依赖什么 | 在这台机器上 |
|---|---|---|
| 系统定时任务（0.1.16 及之前唯一的路） | **有资格往任务库写** | ❌ 三条路全灭 |
| **启动器自己补跑（R2）** | 登录自启 `HKCU\...\Run` —— **一个权限都不要** | ✅ 立刻从「零」变成「有」 |

这一轮就是 B 层：**启动器启动满 2 小时后自己补跑**，外加一条跨进程锁、
一个新备份档 `Kind::Missed`、一行常驻状态说明、一个能改的等待时长。

**A 层（一键自检 + 一次提权把任务真装上）没做**，转记 `待办池.md` P1-46 ——
理由写在那一节里：它是 Windows 专属行为，判据（H1 权限 / H2 安全软件 / H3 任务库坏了）
只能靠真机的对照实验拿到，**没有数据就写提权代码是在猜**。

| | 0.1.16 | R2 之后 |
|---|---|---|
| 任务库那条路装不上时 | **这台电脑上一次都不会跑**（界面上红条如实说，但备份是零） | 启动器启动满 120 分钟后自己补跑一次，**标成「补跑的一次」** |
| 「该不该补跑」的判据 | 不存在 | 纯函数 `fallback::should_catch_up`，18 条单测钉死 |
| 同一时刻两份备份撞上 | 没有互斥（`backup.rs` 里一把锁都没有） | `~/.hunter/backup.lock`，拿不到就跳过 |
| 用户想改等待时长 | — | 设置页可改，默认 120、范围 5–720 |
| 面板上那行说明 | 只在红了之后出现 | **常驻**一行，说清两种机制的能力差别与两条上限 |

## 一、这一轮改了什么（按方案 §4.3 的三条）

### 1.1 触发点 ①：启动后延迟补跑（兜底主路）

新模块 `src-tauri/src/fallback.rs`。判据是一个**纯函数**（方案 §4.3 给的那个形状）：

```rust
should_catch_up(启动时刻, 现在, 最近一次成功备份时刻, 等待分钟, 间隔小时) -> bool
  = 现在 - 启动时刻 ≥ 等待分钟
    且（从未成功过 或 现在 - 最近一次成功备份时刻 ≥ 间隔小时）
```

**计时口径三条照方案写死**（这三条不照做就会出现「明明开着却永远不备份」）：

1. 基准是**启动器进程的启动时刻**（不是登录时刻），用**墙钟 Unix 秒**记，
   **不用单调时钟** —— `fallback::mark_started()` 在 `lib::run()` 的最开头调一次；
2. **睡眠 / 休眠的时间算在里面**：判据每次都用 `now_unix()` 现算，不靠 `Instant` 累加。
   睡前开着、早上唤醒 → 唤醒后第一拍（≤ 15 分钟）就补跑；
3. 沿用**每 15 分钟一拍**，所以**最坏晚 15 分钟** —— 界面文案里不承诺「准点」。

### 1.2 触发点 ②：运行中定时

同一个 `fallback::spawn_watch()`，`thread::sleep(TICK)` 之后 `tick_once()`。
**平台范围只 Windows**（`if !cfg!(windows) { return; }`）——
macOS 的 LaunchAgent 与 Linux 的 `systemd --user` 都不需要管理员、本来就是准时的，
**不该跟着一起降级**（方案 §4.3 末段）。

`lib.rs` 里那条 `schedule::sync` 的对齐**一字未动**，两条路并存。

### 1.3 触发点 ③：任务计划（本轮没动）

`schedule.rs` 里 macOS / Linux / Windows 三套机制与 `install_schtasks` 的三条路
**一个字节都没改**。方案 §4.3 说它是「增强」：装上了就用，它多了「错过会补跑」。

**它有 `Ready` 的时候不补跑**（方案 §8 风险 4 / P5 验收）：`tick_once` 先问
`schedule::status()`，只有「装着且 Ready」才让路 —— 两种机制不要同一天跑两遍。
（这一问只在 `should_catch_up` 已经为真时才发生，不会每 15 分钟起一个 `schtasks` 子进程。）

### 1.4 「最近一次成功备份」怎么取（不新加状态存储）

`fallback::last_success_unix()` **两份来源取更近的那个**：

* 备份目录里最新那一份的 `at`（`backup::list()`）—— 这是**盘上真有的东西**；
* `[backup] last_ok_at` —— 定时备份跑在没有界面的进程里，它成功时写的这一项。

之所以两份都要：用户可能把备份目录整个换到外接盘上，也可能手动删过目录里的几份 ——
任一来源单独看都可能偏老或偏新。**两份都不是新加的状态存储**（方案 §4.3 要求）。

### 1.5 新档 `Kind::Missed`

`--backup --missed` 走的是**同一条无界面路径**（`headless::cmd_backup`），
只有一处不同：记进 `meta.json` 的 `kind` 是 `missed` 而不是 `scheduled`。

**不许混**（方案 §4.3「如实标注」）：这台机器上定时任务根本没装上，
用户看到的必须是「这是补跑的一次」。界面上四档的来源是四句不同的话
（`你手动做的` / `定时备份` / `补跑的一次` / `升级前自动备份`），
有一条前端测试盯着它们两两不同、而且「补跑」那句里不许出现「定时」。

**真跑证据**：`--backup --missed` 在 Linux 上写到盘里的 `meta.json` 是
`"kind": "missed"`（`R2-证据/c-补跑写下的meta是missed.json`）。

### 1.6 跨进程锁（T2-4）

`~/.hunter/backup.lock`，三处入口一起用：

| 入口 | 抢不到锁时 |
|---|---|
| `--backup`（定时 / 补跑，`headless::cmd_backup`） | 打印 + 记一行日志，**退出码 0**（是「跳过」，不是失败） |
| 界面上的「立即备份」（`commands::create_backup`） | 返回新错误码 `E_BACKUP_BUSY`，**不记进 `fail_streak`** |
| 恢复前的保命备份 | 走 `create()`，同一时刻不会有第二份 |

**不排队、不重试**（方案 §4.3）：备份不是不能错过的实时交易，抢跑没有意义。

**陈旧锁必须能被抢走**（这一条不写就是 P0 级隐患）：一次强退 / 断电留下的锁文件，
超过 **2 小时**没动就被下一个进程抢过去 —— 否则**这台机器从此再也不会自动备份**，
而且界面上一切正常。那比重复备份一次严重得多。

### 1.7 三个配置项（方案 §4.3 配置表）

| 键 | 默认 | 谁改 | 说明 |
|---|---|---|---|
| `[backup] windows_fallback` | `true` | 设置页（**只在 Windows 上出现**） | 关掉回到 R2 之前 |
| `[backup] fallback_delay_mins` | `120` | 设置页，用户可改 | 范围 5–720 |
| `[backup] fallback_interval_hours` | `24` | 本轮不给用户改 | 两次成功备份之间最长多久 |

`fallback_delay_mins` 的**类型是 `i64` 而不是 `u32`**，这是有意的：配置文件可能被
手改成 `-1`，而 `u32` 遇到负数会让**整份配置**解析失败 ——
`LauncherConfig::load()` 对解析失败的处理是「这次用默认设置」，
用户会莫名其妙地丢掉**所有**设置。收窄交给 `fallback::clamp_wait_mins`（5–720）。
有一条单测专门钉这个（`等待时长被手写成负数也读得回来并收进_5`）。

**校验语义三条照方案 §4.3 实现**：

1. **不允许 0**：0 或负数一律按 5 算。**不静默夹取** —— 存进去的是收窄后的值，
   回给界面的 `fallbackDelayMins` 也是它，输入框里当场显示成 5，
   旁边那三句文案说明了为什么；
2. **改小立即生效**：判定每次都用当前配置值，所以「120 → 5」之后下一拍（≤ 15 分钟）就补跑；
3. **改大对本次也生效**：把 120 改成 300 而本次已跑 200 分钟 → 本次不再补跑。

### 1.8 界面（方案 §4.4 的 U3 / U6）

* **运行面板一行常驻说明**（`data-testid="auto-backup-status"`，**不是红了才说**）：
  按 `autoMode` 分成三种说法 —— `scheduler`（系统定时任务，**没赶上的会补跑**）/
  `fallback`（启动器启动满 N 分钟后补跑，**没赶上的不补**）/ `off`。
  走 `fallback` 时下面再跟**两条上限**：
  「电脑当天既没开机、启动器也没运行 —— 那天不会有备份」
  「启动器没撑到 N 分钟就退出了 —— 这一次不会补跑，下次启动重新计时」。
* **设置页一块只在 Windows 上出现的设置**（`data-testid="settings-fallback"`）：
  开关 + 数字输入 + 「恢复默认（120 分钟）」，配方案 §4.4 U6 要求的三句文案
  （为什么默认 2 小时 / 改小最多 15 分钟内生效 / 填 0 为什么按 5 算）。
* **备份列表**：`missed` 那一档显示「补跑的一次」，与「定时备份」分开。
* i18n 中英两份字典同步补齐（有一条测试盯着两份键完全一致）。

## 二、必须遵守的既有决定（用户 2026-09-28 拍板）逐条对照

| 项 | 决定 | 落在哪 |
|---|---|---|
| 默认开关 | **默认开** | `BackupSection::default().windows_fallback = true`，单测 `等待时长的默认值就是用户定的那个数` |
| **禁「登录/启动即备份」** | 绝对不许一开始就备 | 判据第一项就是 `现在 - 启动时刻 ≥ 等待分钟`；`spawn_watch` 先 `sleep(TICK)` 再查；单测 `不足等待时长时不补跑哪怕当天从来没备过`（含 119 分 59 秒） |
| 补跑触发时机 | **启动满 2 小时之后**才允许 | 默认 `fallback_delay_mins = 120`（是默认值不是写死值，见下一条） |
| 等待时长 | **必须可配置**，默认 120 分钟 | 配置项 + 设置页输入框；单测 `等待时长改了判据跟着变` |
| 计时基准 | **墙钟**，不是运行时长 / CPU 时间 | `fallback::mark_started` 记的是 `timefmt::now_unix()`；单测 `启动时记住的是墙钟秒` 断言它 > 16 亿（`Instant` 那种小数字当场就红） |

> 「启动器起来后先等满 120 分钟；若这期间已经备过（比如定时任务恰好跑了），就不补；
> 等满之后若当天还没备过，才补跑一次。」
> —— 对应的就是 `should_catch_up` 的两个条件，外加 §1.4 那两个「最近一次成功」来源。

## 三、能在本机（Linux）验的 —— 这些是真测试

### 3.1 纯函数单测：18 条（Rust 723 → **741**）

判据被抽成纯函数再测（总控规则 §五：纯函数就是真测试）。

**`fallback::should_catch_up` / `fallback::due` —— 15 条**：

| 任务书 §4.1 的要求 | 测试 | 断言 |
|---|---|---|
| 启动后不足 120 分钟 → 不补跑 | `不足等待时长时不补跑哪怕当天从来没备过` | 0 分 / 1 分 / 119 分 / 119 分 59 秒 —— **差一秒也是没到** |
| 满 120 分钟且当天没备过 → 补跑 | `满等待时长且从未成功过就补跑` | 120 / 121 分、9 小时都补 |
| 满 120 分钟但当天已备过 → 不补 | `满等待时长但当天已经备过就不补` | 60 分钟前 / 5 分钟前刚成功过 → 都不补 |
| 等待时长改成别的值时判据跟着变 | `等待时长改了判据跟着变` | 同一刻：120 分不补、**改成 5 分就补**、改成 720 分更不补；间隔改成 1 小时后 110 分钟前那次也算旧 |
| 跨天边界 | `跨天边界` | 昨天 00:05 备过 → 36 小时后补；今天 09:00 备过 → 中午不补；今天 00:00 备过 → 23 小时时还不补 |
| 时钟回拨 / 系统时间异常 | `时钟回拨与未来时间不误判也不崩` | `now < started_at` → 不补；`last_ok` 在未来 → 不补；`i64::MAX` / `i64::MIN` 三种极端组合不 panic 不回绕 |
| 开关关掉时全不触发 | `开关关掉时以上全不触发` | `windows_fallback=false` → 不触发；`enabled=false` → 不触发（哪怕从没备过、等待调到最小） |

### 3.3 跨进程锁的 CLI 实跑（真跨进程，不是模拟）

锁是**文件级、跨平台**的，走的正是产品里那条代码路径，**不需要伪造任何 Windows 场景**：

```
$ printf 99999 > $HUNTER_HOME/backup.lock     # 另一份备份正拿着锁（刚建的，是活的）
$ hunter-launcher --backup --missed
  ⚠ 跳过：已经有一份备份在跑，这一次不排队也不重试。
★ 退出码 = 0（0 = 跳过，不是失败）
```

原始输出见 `R2-证据/b-跨进程锁.log`。同一份日志里还看到「锁让开之后真的会往下走」
（第二次退出码 1 是因为本机没有 Hunter 那套 compose 文件，**与锁无关**）。

## 四、没做的：A 层（自检 + 提权）

方案 §4.1/§4.2 那一半**本轮一步都没做**，转记 `待办池.md` **P1-46**。理由照抄在那里：

1. 自检（建一个探针任务、收原话、立刻删）与提权（走系统 UAC 再试一次）
   **全是 Windows 专属行为** —— 在 Linux 上只能写判读表与探针 argv 的纯函数单测，
   而那部分**证明不了真机上能不能提权、能不能建成**；
2. **更关键的是「没有数据就写提权代码是在猜」**：那两条 `/XML` 报的
   `未指定的错误` 到底是 H1（权限）、H2（安全软件 / 组策略）还是 H3（任务库坏了），
   判据只有**同一台机器上用管理员身份跑一次同样的命令**这一个对照实验。
   H1 与 H2 的处置完全相反（一个提权一次就好，一个提权也没用）；
3. 总控规则 §五 与用户 2026-09-26 的要求都写着：**不许在 Linux 上构造 / 模拟 Windows 场景**。

**B 层的价值恰恰在这里**：它**不需要先判清 H1/H2/H3** 就能让那台机器上的备份
从「零」变成「有」—— 一个权限都不要。

### 八.1 一条要拍板的事：一直失败时会不会每 15 分钟重试一次

**会。** 判据（方案 §4.3）只以「最近一次**成功**」为基准，所以一台
「备份一直在失败」的机器上，`should_catch_up` 每拍都为真，**每 15 分钟会再试一次**
（`tick_once` 是同步跑子进程的，所以实际节奏是「等 15 分钟 → 试一次 → 再等 15 分钟」）。

三种情况的实际代价：

| 现场 | 每 15 分钟会发生什么 | 代价 |
|---|---|---|
| 运行环境没起（Hunter 停着） | 子进程走到「跳过」就返回，**什么也没做** | 一次 docker 探测（约 1 秒），可忽略 |
| 运行环境起了、备份本身失败（盘满、目录没权限…） | 真的再试一次 `pg_dump` | 一次完整尝试，失败通常在几十秒内结束；`fail_streak` 到 2 时运行面板上那两条既有横幅会出来 |
| 运行环境起了、备份很慢 | 上一拍还在跑，下一拍在它返回之后才开始 | 不会重叠（同一个 ticker 线程 + 跨进程锁双保险） |

**为什么本轮没有加退避**：方案 §4.3 给的判据写得很死（「距最近一次成功 ≥ 间隔小时」），
任务书也写着「具体照方案文档 §4.3 实现」；而方案里 T2-5 那条「失败退避」
说的是**装任务**失败后 24 小时不再重试（`schedule_failed_at`），
不是补跑。自己加一条「多久之内不再试」会偏离那份判据，
也没有一条验收标准能证明它该取多少。

**建议**（留给下一轮或用户拍板）：如果觉得这个节奏太密，
最小改动是在 `fallback::due` 里加一条「距上一次**尝试**（`[backup] last_run_at`）
不足 1 小时就不试」—— 它不改「成功」那条判据，只限制失败时的重试频率。
加之前要想清楚：这条会让「刚失败完、用户把盘清出来了、想立刻补一次」多等一小时。

### 10.1 这一轮最值得记住的一句

**「装不上」不等于「没法备份」。**

I16 把「任务装不上」这件事摆到了界面上（那是「看得见」修对了一半），
但**它仍然是一次都不会跑**。R2 换了一个角度问同一个问题：
**这件事非要用那条装不上的路不可吗？**

任务计划要的是「有资格往系统任务库里写」；而登录自启一个权限都不要，
启动器本来就靠在它起来。**把备份交给启动器自己**，这条路不依赖那个不成立的前提 ——
于是那台机器上的备份从「零」变成「有」，**不需要先判清病根**。

判病根（A 层）该做，但它要一台真 Windows 的对照实验；
**而在拿到那份数据之前，用户不该继续过没有备份的日子。**
