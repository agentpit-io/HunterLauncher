## 二、详解：P0 —— 随机口令里的一个 `/` 能让整套装不起来

### 2.1 怎么撞上的

I2 的 GUI 回归第一遍走到「启动」那一步停住了，界面是错误页
（截图见 §8 的说明，那一张已经被第二遍覆盖，日志与容器状态都留着）：

```
E_START_TIMEOUT: docker compose up -d 失败: dependency failed to start:
container hunter-api-1 is unhealthy
```

api 容器的日志一直在刷同一行：

```
2026-09-20 01:05:27 | INFO | 迁移 | 数据库还没起来，2 秒后重试（第 5 次）：
    invalid integer value "u3s9Ckg" for connection option "port"
```

`postgres` 容器本身是 healthy 的。所以问题不在数据库，在**连它的那串地址**。

### 2.2 原因

`secretgen::random_base64()` 用的是**标准 base64**，字母表里有 `+` 和 `/`。
生成出来的 `POSTGRES_PASSWORD` 会被上游拼成一个 DSN：

```
postgresql://hunter:<口令>@postgres:5432/hunter
```

按 RFC 3986，URL 的 authority **到第一个 `/`、`?` 或 `#` 为止**。口令里只要有一个 `/`，
authority 就在那里收尾了 —— 真正的主机名与端口全被甩进 path，解析出来的「端口」
是口令中间的一段乱码，正好对上日志里那个 `"u3s9Ckg"`。

当时那把口令的实测特征（**没有打印口令本身**，红线 2）：

```
长度 32 · 含 @ 0 处 · 含 : 0 处 · 含 / 1 处 · 含 + 0 处
非字母数字的字符：/
```

**这件事的概率有多大**：24 字节 base64 是 32 个字符，每个字符是 64 分之一。

| | 计算 | 概率 |
|---|---|---|
| 至少一个 `/` | `1 − (63/64)^32` | **39.6%** |
| 至少一个 `/` 或 `+` | `1 − (62/64)^32` | **63.5%** |

也就是说**每装三次就有一两次装不起来**。`+` 未必一定出事（要看解析器把不把它当空格），
`/` 是必然出事。M1–I1 一路装了很多次没撞上，是因为口令是 **sticky** 的
——`.env` 里已经有的不会被换掉，而那几次抽到的口令正好没有 `/`。

这也解释了 I1 报告里一句没深究的记录：M2 换工作目录时出现过
`password authentication failed`。那是另一个原因（数据卷跟项目名走），
但同一个函数本来就有这个雷。

### 2.3 怎么修的

`secretgen::random_token(n)`：字母表收成 `[A-Za-z0-9]`（62 个），拒绝采样
（丢掉 `>= 248` 的字节，否则直接 `% 62` 会让前 8 个字母略微偏多）。

* 损失的熵可以忽略：`log2(62)/log2(64) = 0.994`，32 个字符从 192 位降到 190 位；
* 换来的是「生成出来的东西放进 URL、shell、YAML 里都不用转义」；
* 返回的字符数与原来的 base64 一致（`n·4/3` 向上取整），升级上来的机器看起来没有变化。

三个 secret（`JWT_SECRET` / `POSTGRES_PASSWORD` / `OPENCODE_PASS`）全部改用它。
`OPENCODE_PASS` 同样会进一个 URL（web 的 BFF 反代 opencode 时要带用户名密码），
所以不是只改 postgres 那一个。

**已经装好的机器不受影响也不会被改**：口令是 sticky 的，换了就连不上已经初始化过的数据卷。
`config::read_sticky()` 现在会认出「旧口令里有 URL 特殊字符」并写一条 warn 日志，
说清「这套装起来过就不用管；本来就没装起来的话，最干净的办法是重装一次」，
**不悄悄改、更不删数据卷**。

四条新单测：

```
secretgen::tests::生成的口令里绝不出现会破坏_url_的字符   ← 跑 200 次，单次撞上的概率 40%
secretgen::tests::字母表用满且没有明显偏斜               ← 62 个字符都要出现过
secretgen::tests::生成的密钥长度对且两次不一样
config::tests::认得出会把_dsn_截断的旧口令               ← 用真实形状的口令验 authority 确实被截断
```

### 2.4 需上游配合（本项目不改它）

根因其实在两边：启动器不该生成需要转义的口令，**上游也该对 DSN 里的口令做 URL 编码**
（`urllib.parse.quote`）。按总控规则本项目只读引用 hunter-community，所以只修自己这一侧；
启动器这边**不依赖上游改**也能彻底不踩这个坑，但照着 `.env.example` 手工设口令的用户仍然会踩。
已记进「九、仍未解决的」。

## 三、详解：本轮自审抓出来的四条

### 3.1 「打开链接」的白名单**还能**被绕过（安全）

I1 修过一次这个函数（`http://localhost.example.com/` 被当成本机）。
I1 之后的写法是「主机名后面必须紧跟 `:`、`/` 或者结束」。这一版仍然漏：

```
http://localhost:1@evil.com/
```

`localhost:1` 在 URL 语法里是 **userinfo**，`@` 后面的 `evil.com` 才是主机。
`rest.strip_prefix("localhost")` 得到 `":1@evil.com/"`，以 `:` 开头 → 放行 →
交给系统浏览器 → 打开 evil.com。

改成整段解析 authority（到第一个 `/`、`?`、`#` 为止）：

```rust
let authority = rest.split(['/', '?', '#']).next().unwrap_or("");
if authority.contains('@') { return false; }          // userinfo 一律拒绝
let (host, port) = match authority.split_once(':') { … };
if !matches!(host, "localhost" | "127.0.0.1") { return false; }
match port { None => true, Some(p) => !p.is_empty() && p.bytes().all(|b| b.is_ascii_digit()) }
```

**实际可利用性**：和 I1 那次一样，不高 —— 这个函数的入参目前全部来自启动器自己算出来的
地址。它是一道纵深防御，存在的理由就是「万一前端被注入了什么」。补了 2 组共 8 条断言。

### 3.2 模型名 / 自定义镜像源里的换行会注入进 `.env`

`.env` 一行一个 `KEY=值`，值里有 `\n` 就等于**又定义了一个环境变量**，
而 compose 读 `.env` 时后定义的会盖掉先定义的。于是一个多出来的换行能把
`HUNTER_API_KEY` / `POSTGRES_PASSWORD` 这类关键项整个换掉。

三个来源里两个是被别的东西挡住的、一个是真通的：

| 字段 | 会不会被写进 `.env` | 原来挡得住吗 |
|---|---|---|
| 自带模型 key | 会 | 挡得住（带 `\n` 的值放进 HTTP 头，ureq 直接报错 → 连通性检查不过 → 不保存） |
| 模型 BASE_URL | 会 | 挡得住（URL 解析失败，同上） |
| **模型名** | 会 | **挡不住** —— 它只出现在 JSON 请求体里，`\n` 完全合法；而 `/models` 回 200 就算连通 |
| **自定义镜像源** | 会（还会进覆盖文件的 `image:` 行） | **挡不住** —— 原来只 `trim()` 了一下 |

**这不是一个别人能打的洞**（输入全来自用户自己的键盘或剪贴板），但从剪贴板里带出一个
尾随换行是非常常见的事，而它的后果是一套**装得起来但行为莫名其妙**的栈。

两道修：`render_env()` 对六个会原样上屏的值逐个查换行，有就当场报一句人话；
自定义镜像源另外过一遍形状校验 `registry::prefix_ok()`（`主机[:端口]/路径`，
不许带镜像名、tag、空格、换行、大写）。设置页与 headless 两条路都接上了。

### 3.3 `~/.hunter` 的子目录是 775

I1 把四个配置文件收成 600、根目录早就是 700，但**子目录跟着系统 umask 走**
—— 测试机的 umask 是 002，于是实测：

```
700 /home/support/.hunter
775 /home/support/.hunter/app        ← 这几个
775 /home/support/.hunter/backups
775 /home/support/.hunter/logs …
```

根目录 700 已经挡住了遍历，所以这只是纵深防御的一层；但「工作目录里的东西只有属主能碰」
要么是真的、要么就别写在文档里。`ensure_dirs()` 现在把六个子目录也收成 700，
单测逐个断言。实测修完之后八行全是 700 / 600（见 §5 用例 3）。

`app/VERSION` 仍然是 644（里面只有一个版本号）—— 记成待办池 P2-16，不在这一版动。

### 3.4 「复制」按钮可能什么都没复制，却照样显示「已复制」

待办池 P1-21 记的是「把安装命令做成点一下复制」。**查下来这一条记岔了** ——
M4 就已经有复制按钮了（`data-testid="copy-install-cmd"`）。真正的问题是它的写法：

```ts
void navigator.clipboard?.writeText(m.command)
setCopied(true)                  // ← 不管成没成，一律显示「已复制」
```

`navigator.clipboard` 只在**安全上下文**里存在。Tauri 在 Linux 上走 `tauri://localhost`
自定义协议，WebKitGTK 认不认它是安全上下文要看版本；认不出来时这个 API 直接是 `undefined`，
那句可选链于是什么都没做，而界面照样跳「已复制」。用户切到终端一粘，空的。
这正是红线 1 说的「不许假装成功」。

新的 `src/lib/clipboard.ts` 返回**真的成功了没有**：先试 `navigator.clipboard.writeText`，
不行退回 `document.execCommand('copy')`（老、被标记为废弃，但不要求安全上下文），
两条都不行就如实返回 `false`，界面显示「复制不了，请手动选中」。更新页与日志页两处都改了。

**实测结论要说清楚**（红线 5）：在测试机的 WebKitGTK 上这条路**本来就是通的** ——
Xvfb 里点一下「复制全部」，`xclip -o -selection clipboard` 真读到了 **3151 个字符**，
而且里面 **0 处 key 明文**。所以这不是一个「正在发生的故障」，修的是「万一不可用时会撒谎」。
按钮文字从「复制全部」变成「已复制」的那一张截图是
[`11c-日志-复制之后.png`](../screenshots/I2/11c-日志-复制之后.png)。

## 四、详解：待办池取的四条

### 4.1 P1-11 · 限流 429 真打出来了

**第一次没打出来**：`/v1/models` 连打 30 次全是 200。结论本身是有价值的 ——
限流不作用于这个路径。

**第二次也没打出来**：25 次 `POST /v1/chat/completions` 串行发，用了 64 秒，
正好被切在两个自然分钟上（前 18 次在 00:36、后 7 次在 00:37），两边都没到 20。

**第三次打出来了**：按并发 4（网关自报的 `max_concurrency`）分 7 批，28 次压进十几秒。
第 13 次起全部 429。实测的响应（**key 已打码**）：

```
HTTP/1.1 429 Too Many Requests
retry-after: 60
Content-Type: application/json

{"error":{"message":"请求太频繁了：每分钟最多 20 次，这一分钟已经第 21 次。等一分钟再试即可；
如果是脚本在批量跑，请自行加个间隔。","type":"rate_limit_error","code":"rate_limited",
"param":null,"retry_after":60}}
```

| 实测结论 | 值 |
|---|---|
| 限流作用于哪些路径 | **只有 `POST /v1/chat/completions`**。`/v1/models` 连打 30 次、`/quota` 在触发之后立刻查，都是 200 |
| 窗口 | **自然分钟**，不是滑动窗口（25 次摊在 64 秒里跨了两分钟就不触发） |
| 限额 | 20 / 分钟，与 `/quota` 自报的 `rate_per_min: 20` 一致 |
| 等多久 | 响应头 `retry-after: 60`，体里 `error.retry_after: 60` |
| 这一轮总共烧掉 | 三次尝试合计约 **3,500 token**（每次往返约 99 token），额度从 212,907 涨到 216,406 |

**对启动器的意义**：启动器只用 `/quota` 与 `/v1/models`，**碰不到限流**。
仍然补了处理，因为「key 好好的但这一刻问不出来」绝不能显示成「这把 key 无效」——
那会让用户去重新申请一把根本不需要的 key。新增错误码 `E_RATE_LIMITED`
（Rust 与前端 `machine.ts` 同步加），文案直说「这不是 key 的问题，等 N 秒再点一次」，
N 取自 `retry-after`（头没了就读体，都没有按 60 兜底）。两条单测用的是上面那段响应原文。

### 4.2 P1-19 · `.deb` 版本号改用 Debian 写法

dpkg 把 `-` 后面那一段当成「Debian 修订号」，修订号越大越新，于是 `0.1.0-rc.2` 在它眼里
比 `0.1.0` **新**，从 rc 升到正式版会被 apt 判成降级。M4 当时用 `--allow-downgrades` 绕过。

这一轮做了两侧：

* `selfupdate::deb_version()`：`0.1.0-rc.2` → `0.1.0~rc.2`（只换第一个 `-`），
  `deb_file_name()` / 两个下载地址都走它。**tag 段仍是 semver、文件名段是 Debian 版本号**，
  两段不一样是故意的，有一条测试专门盯着别写反。
* `release.yml` 的 Linux 打包步骤：版本号带 `-` 时用 `dpkg-deb -R` 拆包、改 `DEBIAN/control`
  的 `Version:`、再 `dpkg-deb --build` 打回去并改名。

真机验了三件事（`~/i2-deb.log`）：

| 检查 | 结果 |
|---|---|
| `dpkg --compare-versions 0.1.0 gt 0.1.0-rc.2` | **假** ← 原来的坑 |
| `dpkg --compare-versions 0.1.0 gt 0.1.0~rc.2` | **真** ← 修好了 |
| `dpkg --compare-versions 0.1.0~rc.1 lt 0.1.0~rc.2` | 真 |
| 拿真包演一遍重打（0.1.1 的 deb 改成 `0.1.3~rc.1`） | ✅ `dpkg-deb -f` 读出 `Version: 0.1.3~rc.1`，依赖三项没丢 |
| 重打出来的包装得上 | ✅ `Unpacking hunter-launcher (0.1.3~rc.1) over (0.1.1)`，退出码 0 |
| 反向装回 0.1.1（不带 `--allow-downgrades`） | ✅ 被 apt 挡住：`E: Packages were downgraded and -y was used without --allow-downgrades` |

`--allow-downgrades` **仍然留在安装命令里**：它只在 apt 真判成降级时起作用，
而「出了问题先退回上一版」是一条要留给用户的路。

测完把测试机上的包装回真实的 0.1.1。

### 4.3 P1-17 · COS 旧包清理

`scripts/cos-prune.py`。规则只有两条，都往「宁可留着」偏：

1. **正式版一个都不删**；
2. 预发布版**只在它的同号正式版已经发布、而且它不是最新的那个预发布版**时才删。

`launcher/latest.json` 不在任何版本目录里，代码里还显式排除一次；
`launcher/` 下看不懂的前缀连列都不列。`release.yml` 在上传完这一版之后跑一次
（顺序是有意的：先保证这一版在桶里，再动别的）。

规则本身有 `--self-test`（6 组用例），在 CI 的前端 job 里跑 —— 这个脚本会真删东西，
逻辑不能只靠眼看。

**本轮它实际删了什么**：见 §6.3（发布之后的实测）。

### 4.4 P2-15 · 命令行接管道会 panic

修之前在测试机上复现（0.1.1 的 deb）：

| 命令 | 修之前 | 修之后 |
|---|---|---|
| `hunter-launcher --status \| head -2` | 退出码 **134** + 一段 Rust backtrace | 安静结束 |
| `hunter-launcher --logs \| head -2` | stderr 里 `panicked at … Broken pipe` | 安静结束 |

Rust 运行时在 `main` 之前把 `SIGPIPE` 设成忽略，于是往已关闭的管道写不再是「安静结束」
而是 `println!` panic。**只在命令行模式下**恢复成系统默认（`signal(13, SIG_DFL)`，
一个 `extern "C"` 声明，不为这一行把 libc 拖进依赖树）；界面模式不碰它
——GUI 的 stdout 没人读，而进程被信号杀掉会比现在难查。

## 七、需要用户决定：web 端口默认绑哪里（待办池 P1-20）

**I1 提出、I2 把开关做完了，但默认值一个字节没动。**

### 7.1 I2 做了什么

| 做了 | 没做 |
|---|---|
| `launcher.toml` 加 `hunter.web_bind`（`all` / `local`），老配置读回来是 `all` | **没改默认值** |
| 设置页「部署」卡片里加一组「谁能打开 Hunter」：同一网络里的设备都可以 / 只有这台电脑 | 没有在升级时自动收紧已装机器 |
| 覆盖文件按它渲染（`"3101:3000"` 或 `"127.0.0.1:3101:3000"`） | |
| 端口探测跟着走（收紧之后 web 也只要 127.0.0.1 占得住就行） | |
| 完成页那条提示按真实配置二选一显示，不再写死 | |
| 3 条单测：默认必须是对外、老配置不被悄悄收紧、写错值按默认走 | |

截图 [`13-设置.png`](../screenshots/I2/13-设置.png) 里能看到这组控件，
选中的是「同一网络里的设备都可以」—— 那就是默认值。

### 7.2 还差什么（只差一个决定）

1. **默认该是哪一个？**「只有这台电脑」更安全，「同一网络」更方便（手机上也能开）；
2. **已经装好的机器要不要在升级时自动收紧？** 收紧会让「昨天手机上还能开」突然失效。

我的建议仍然是：**默认收成只有本机，设置页给开关（默认关），升级时不动已有配置，
只在运行面板上提示一次**。但这是建议，不是决定 —— 总控规则红线 4 明确把 web 排除在
「只绑 127.0.0.1」之外，改默认等于改产品决策。

I1 实测的那组数据仍然成立（从另一台机器不需要任何凭证就能进聊天界面并烧掉用户额度，
