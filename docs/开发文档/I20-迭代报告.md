## 一、背景与事故复盘

在 0.1.21 版本中，客户真机（Windows 环境，追踪码 HL-D9MCCQ / HL-5FQNHX）出现严重事故：
客户开着 Docker Desktop（开机快照清晰记录 `Docker: DockerDesktop · server 29.8.0`，且此前升级过程中已成功完成数据库备份与 compose config 校验），但在 0.1.21 下每一次点升级均在 1 秒内无条件失败，报错停在第 ⓪ 步：
`运行环境（Docker）现在用不了，这次升级先停在这里 —— 配置一个字节都没改。上面那几行是启动器替你把它拉起来的经过。（E_DAEMON_DOWN）`

### 根因分析
1. `src-tauri/src/upgrade.rs:672` 在第 ⓪ 步检查中调用了 `crate::runtime::effective::current().running`。
2. `runtime/effective.rs` 设计上为了防止与 `env::compute()` / `env::apply()` 形成循环依赖引发 stack overflow，严格限制为零子进程调用、纯查文件系统与 Unix domain socket。
3. 但在 Windows 系统上，Docker Desktop 与后台引擎通信走的是命名管道（`npipe://`），`effective.rs` 中的 `connectable()` 在非 Unix 分支硬编码返回 `false`，`user_running()` 亦直接返回 `None`。
4. 这导致在 Windows 上 `effective::current().running` 恒为 `false`。
5. 升级路径忽略了 `runtime/docker.rs` 中已有的、能够探测命名管道和 Docker daemon 真实状态的 `detect().daemon_running`，采用了错误的判据。
6. 此外，当启动器根本没有尝试拉起 Docker 时，提示文案中依然显示「上面那几行是启动器替你把它拉起来的经过」，属于虚假文案。

## 二、本轮改动

### 1. P0-1：建立统一引擎可用性判据（`runtime::engine`）
- 新建 `src-tauri/src/runtime/engine.rs`，暴露：
  - `is_engine_usable(eff_running, docker_daemon_running, os) -> bool`：纯函数，矩阵覆盖 Windows 与非 Windows 下的可用性判定；
  - `usable() -> bool`：对外唯一判定入口（Windows 取 `docker::detect().daemon_running`，非 Windows 取 `effective::current().running`）；
  - `format_engine_status(...)` 与 `summary() -> (bool, String)`：提供人话真话的引擎状态。
- 单测覆盖：4 组针对 `is_engine_usable` 矩阵的单测以及 1 组格式化真话测试，无 `cfg!` 宏剪裁，可在 Linux/Mac 及 Windows CI runner 上真实执行。

### 2. P0-2 & P0-3：升级第 ⓪ 步闸门修正与文案两态
- `src-tauri/src/upgrade.rs`：第 ⓪ 步改用 `crate::runtime::engine::usable()` 判定。若 Windows 上 Docker daemon 在跑则放行，真没跑时返回 `E_DAEMON_DOWN`，不搞一律放行。
- 提取纯函数 `format_runtime_down_message(ready_steps, stopped_state)`：
  - 若 `ready_steps` 非空（启动器确实尝试了拉起），保留「上面那几行是启动器替你把它拉起来的经过。」
  - 若 `ready_steps` 为空（未动手），说明真话 `运行环境（Docker）现在用不了（<具体原因>）...`，不谎称拉起经过。
- 附带单测验证两态文案。

### 3. P0-4：体检报文说真话
- `src-tauri/src/assist/probe.rs`：在体检报告中增加 `engine_usable` 与 `engine_status`（调用 `engine::summary()`），Windows 下如实报告 Docker 是否在运行，不把「没装」误报为「装了没跑」，不再误导用户与排查人员。

### 4. P1-5：同病同治审计与修正
逐一审查全仓将 `effective::current()` 当作引擎可用性判断的 5 个调用点：
1. `src-tauri/src/lib.rs:427`（开机自查容器拉起）：改用 `engine::usable()`。理由：该处意图为确认引擎可用后替用户拉起容器，改后 Windows 上开机自愈正常工作。
2. `src-tauri/src/assist/mod.rs:284`（`can_resume_install()`）：改用 `engine::usable()`。理由：安装断点续装依赖引擎可用性，改后 Windows 上断装后可正常续装。
3. `src-tauri/src/headless.rs:2523`（定时备份 headless）：改用 `engine::usable()`。理由：定时备份判断引擎是否在跑以决定是否跳过，改后 Windows 上不会再被误判跳过。
4. `src-tauri/src/config.rs:1667`（`runtime_label()`）：Windows 下若 Docker 已装或可用返回 `user`，否则 `none`。理由：Windows 上无内置运行时，存在 Docker 即为用户运行时，不再误写 `none`。
5. `src-tauri/src/commands.rs:976`（`ensure_runtime_up()` 提前返回）：改用 `engine::usable()` 提前返回。理由：引擎已经在跑时无需再做冗余拉起尝试。
- **严格未触碰**：`runtime/env.rs:242`（避免重新引入子进程循环调用）、`runtime/builtin.rs:402`、`assist/auto.rs:1070`、`tray.rs:248`。

### 5. P1-6：启动器自更新与 Hunter 升级互斥
- `src-tauri/src/commands.rs:1780`：在 `install_launcher_update` 中检查升级状态槽（`upgrade_slot().running`）与 `AppState::upgrade_in_flight()`。若升级进行中，直接拦截并返回人话提示「Hunter 升级正在进行中，请等待升级完成后再更新启动器」，防止自更新重启进程导致升级半路中断。

### 6. P0-8：编制《Windows 真机验收手册》
- 编写 `docs/开发文档/I20-Windows验收手册.md`，面向无桌面 Windows Server 2022 环境，包含避坑指南（PowerShell 5.1 编码、安装路径、重定向截流、Get-Content 乱码），以及 W1（无 Docker 拦截且无假文案）、W2（有真实 Docker 越过 ⓪ 步）、W3（诊断报文两种环境说真话）的完整可复制脚本与判据。
