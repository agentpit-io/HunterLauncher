## 一、三平台发布流水线（方案 §17、§16）

### 1.1 `.github/workflows/release.yml`

触发：tag `launcher-v*`（也可以 `workflow_dispatch` 指定一个已存在的 tag 重跑）。

```
build（矩阵，并行）
 ├─ ubuntu-22.04     deb + AppImage
 ├─ macos-latest     universal dmg + app.tar.gz   （--target universal-apple-darwin）
 └─ windows-latest   NSIS + MSI
        ↓ 每个 job 把产物改成不带空格的名字、连 .sig 一起上传成 artifact
release（汇总）
 ├─ 版本号与 tag 对账（对不上直接红，见 1.4）
 ├─ 生成两份 latest.json（GitHub 一份、COS 香港一份）
 ├─ 建 / 更新 GitHub Release（**一律 prerelease**）并上传全部产物
 └─ 把安装包同步到 COS /launcher/<版本>/，国内版清单到 /launcher/latest.json
```

每个平台 job 里都先跑 `cargo test` 与「发布产物里不许有演示数据」的自查，
编不过或测不过就不会有产物。

### 1.2 签名：写好了，但没有 secret 就整步跳过（总控规则红线 7）

| 步骤 | 有对应 secret 时 | 没有时（**当前就是这样**） |
|---|---|---|
| macOS 证书导入 | `security import` 进临时钥匙串 | `if: env.APPLE_CERTIFICATE != ''` → 整步 skipped |
| macOS 公证 | `notarytool submit --wait` + `stapler staple` | 同上 |
| Windows 代码签名 | `signtool sign` 每个 exe / msi | `if: env.WINDOWS_CERTIFICATE != ''` → 整步 skipped |
| **updater 签名** | 用 `TAURI_SIGNING_PRIVATE_KEY` 给每个可更新包出 `.sig` | **缺它直接红**，不跳过 —— 见 1.3 |

所以产出的是**未签名包**，Release 一律 `--prerelease`。要不要买证书由用户决定
（写在第十三节）。

### 1.3 updater 的密钥：这是另一回事，而且是必须的

两件事经常被混在一起，这里说清楚：

| | 代码签名 | updater 签名 |
|---|---|---|
| 谁在验 | 操作系统（SmartScreen / Gatekeeper） | 启动器自己 |
| 要花钱吗 | 要（CA / Apple，100–500 美元/年） | **不要**（minisign，自己生成，红线 7 明确允许） |
| 现在有吗 | 没有 → Release 标 prerelease | **有** |

本轮在开发机上生成了一对 minisign 密钥：

```
~/.hunter-launcher-keys/hunter-launcher-updater.key      私钥，600
~/.hunter-launcher-keys/hunter-launcher-updater.key.pub  公钥
~/.hunter-launcher-keys/updater-password.txt             私钥口令，600
```

私钥与口令已 `gh secret set` 进仓库（`TAURI_SIGNING_PRIVATE_KEY` /
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`），公钥写进 `tauri.conf.json` 的
`plugins.updater.pubkey`（编译进程序）。**私钥不在仓库里，也不在任何文档里。**

`release.yml` 在这个 secret 缺失时会**红**而不是跳过 —— 没有它产出的 `latest.json`
验不过签，自更新整个失效，那种「发出去了但更新是坏的」比构建失败糟糕得多。

### 1.4 版本号与 tag 对账

`release` job 第一件事是拿 tag 里的版本和 `tauri.conf.json` 对：

```bash
V="${TAG#launcher-v}"
CONF=$(node -p "require('./src-tauri/tauri.conf.json').version")
[ "$V" = "$CONF" ] || exit 1
```

因为 updater 比的是**编译进程序里**的版本号（`env!("CARGO_PKG_VERSION")`），
对不上就会出现「装了新版还提示有新版」的死循环。
配套加了 `scripts/set-version.sh`，一次把 `package.json` / `tauri.conf.json` /
`Cargo.toml` 三处改掉。

### 1.6 COS 上传：必须 virtual-hosted 寻址

`scripts/cos-upload.py` 用 boto3 走 COS 的 S3 兼容接口。**实测**：path-style 会被拒 ——

```
An error occurred (PathStyleDomainForbidden) when calling the PutObject operation:
The bucket you are attempting to access must be addressed using COS virtual-styled domain.
```

改成 `Config(s3={"addressing_style": "virtual"})` 后一次通过，上传 57 字节的探针
再 `curl` 回来 HTTP 200、内容一致（探针已删）。没配 secrets 时脚本打印一行说明并以 0 退出。

### 1.7 `ci.yml` 也加了三平台编译检查

M3 时 Windows / macOS 只跑 `cargo check`。本轮升级成**真编一次 release 二进制**
（`tauri build --no-bundle`）—— `cargo check` 走不到 `custom-protocol` 那条路径，
而正是那条路径出过问题（M1 §9：不带这个特性的产物会去连 devUrl，表现为白屏）。

同时把几个 action 升到大版本（待办池 P2-10）：`checkout` v4→v7、`setup-node` v4→v7、
`upload-artifact` v4→v7、`download-artifact`→v8、`pnpm/action-setup` v4→v6，
Node 20 弃用警告随之消失。

**`ci.yml` 里的 `tauri build` 要显式关掉 `createUpdaterArtifacts`**：配置里它是开的
（发布时要出 `.sig`），而签名要私钥 —— CI 不该、fork 的 PR 也拿不到那个 secret。
第一次跑 CI 就是栽在这里（见第九节 bug 1）。

## 二、启动器自更新（方案 §10）

### 2.1 端点与验签

`tauri.conf.json` 的 `plugins.updater.endpoints`，按顺序试：

```
1. https://hunter-dl-hk-1253756459.cos.ap-hongkong.myqcloud.com/launcher/latest.json
2. https://github.com/agentpit-io/HunterLauncher/releases/latest/download/latest.json
```

国内在前、GitHub 在后，是 `plan/国内镜像与下载源.md` 的要求。

> **第 2 个端点现在是死的，而且这是有原因的。**
> `releases/latest/download/…` 解析的是「最新的**正式** Release」，
> 而本项目的 Release 因为没有代码签名**一律标 prerelease**，所以那条路会 404。
> 它是留给「用户决定买证书、把某一版转成正式版」那天的 —— 到时候不用改代码就会自己活过来。
> 在那之前实际生效的只有 COS 那一个端点，也就是说**当前自更新只有一条链路**；
> COS 不可达时查更新会失败并如实报原因，**不会谎称「已是最新」**。
> 这一点写进了 `selfupdate.rs` 的模块头，免得以后有人把它当 bug 修。

### 2.2 检查节奏

启动 20 秒后查一次（让界面先出来），之后每 24 小时一次；设置里可以关（`check_update_hours = 0`）。
查到新版本：

* 发 `hunter://launcher-update` 事件 → 运行面板顶上出现一条金色横幅；
* 托盘 tooltip 多一行「启动器有新版本 vX」，「检查更新」那一项的文字也跟着变。

**任何情况下都不自动安装。**

托盘的「检查更新」一次查**两件事**（Hunter 与启动器）—— 用户点它的时候心里想的是
「有没有什么要更新的」，分成两个入口只会让人漏掉一个。

### 2.3 Linux 上的一个真实限制：`.deb` 装不了自己

Tauri 的 updater 在 Linux 上**只能替换 AppImage**（AppImage 是一个文件，换掉就完事）。
`.deb` 装在 `/usr/bin` 与 `/usr/lib` 下，换它要 root —— 一个桌面程序不该背着用户拿 root
改系统目录，也不该为此常驻一个提权 helper。

所以按安装形式分成两条路，**两条都做完整，都不假装**：

| 安装形式 | 点「立即更新」之后 |
|---|---|
| AppImage / Windows / macOS | 下载 → 验签 → 就地安装 → `app.restart()`，全自动 |
| `.deb`（以及别的包管理器装的） | 下载新包到 `~/.hunter/updates/` → 弹一个框给出**一条可以直接粘贴的命令**，并说明为什么最后一步得用户自己来 |

判断靠 `APPIMAGE` 环境变量（AppImage 运行时会设它，指向那个文件本身）——
这也正是 Tauri updater 自己用的判据，所以界面上说的「能不能装」和实际能不能装是一致的，
不会出现「说能装、点了才失败」。

`.deb` 的下载地址按固定规则拼（国内在前）：

```
{COS}/launcher/<版本>/hunter-launcher_<版本>_amd64.deb
https://github.com/agentpit-io/HunterLauncher/releases/download/launcher-v<版本>/hunter-launcher_<版本>_amd64.deb
```

`selfupdate.rs` 里有一条测试**专门盯住这个命名和 `release.yml` 的改名步骤一致**——
两边对不上就是 404，而那种错只有用户点更新的时候才会暴露。

## 三、Hunter 升级与回滚（方案 §5.6、§10）· **测试 3 / 4 在这里**

### 3.1 流程与「哪一步之后才需要回滚」

```
① 取新版 compose（严格模式，取不到就停）      ← 还没动任何东西
② 备份（pg_dump + .env + 两个 compose）        ← 同上
─────────────── 从这里开始，失败要回滚 ───────────────
③ 写新 compose / 新 .env（tag 换掉）/ 覆盖文件
④ docker compose config 校验 + 红线 4 的端口自查
⑤ pull（失败自动换源重试 3 次）
⑥ up -d + 等 180 秒健康
```

①② 失败时**如实报错，不谎称「已回滚」**——没动过的东西没有什么可回滚的。

两处与方案不同（第十节还会再列）：

* 方案说「替换 `OPENCODE_TAG`」，实际 hunter-community 的 compose 用的是**一个**
  `HUNTER_VERSION` 管全部四个镜像，没有单独的 `OPENCODE_TAG`。换的是它。
* 方案说「回滚 tag → `up -d`」，这里**还会把 `.env` 与两个 compose 文件一起写回**：
  只改 tag 不够 —— 新版本的 compose 可能加了新服务、新健康检查、新环境变量，
  拿新 compose 配旧镜像起出来的东西谁也说不清是什么。

### 3.2 备份（`~/.hunter/backups/<时间戳>-v<旧版本>/`）

`pg_dump --clean --if-exists --no-owner`，**输出直接落盘不进内存**（用户的库可能几百 MB，
先攒成 String 再写等于翻倍塞内存）。postgres 没在跑时会先单独 `up -d postgres` 并
`pg_isready` 等到能连。

**数据库没备份成功就不往下走。** 升级最坏的结果是数据出问题，没有转储等于没有后悔药。

**回滚默认只还原配置，不自动灌回数据。** 升级失败绝大多数发生在「镜像拉不下来」或
「容器起不来」，这两种情况下数据库根本没被动过；这时候灌回一份转储反而会抹掉升级中途
写进去的东西。真出现「数据被迁坏了」由用户在更新页显式点「从备份恢复数据库」
（破坏性操作，二次确认）。

### 3.3 测试 3：1.1.0 → 1.2.0，数据一条不少

造干净起点：先把**我们自己那套**（`-p hunter`）`down -v`，再装 1.1.0。
（`-p hunter-community` 的旧栈全程 6 个容器没动过，脚本里有断言。）
不是从现有的 1.2.0 往回降 —— Alembic 的迁移是往前做的，降级没有定义。

### 3.4 测试 4：指定一个「镜像不存在的版本」——结果是另一种正确行为

## 四、离线包（方案 §9）· **测试 5 在这里**

### 4.1 做了什么

* **导出**：`hunter-launcher --export-images <tar>`（`docker save` 六个镜像）。
  方案只写了「提供从文件导入的入口」，但没有导出端这个功能就只有消费者没有生产者，
  内网用户拿不到那个 tar —— 所以两头都做了。
* **导入**：界面（选择模型页底栏 / `E_PULL_FAILED` 错误页 / 设置页）或
  `--import-images <tar>`。`docker load` 之后：
  1. 从 docker 报出来的镜像名**反推**这一包是哪个源、哪个版本；
  2. 用 `docker image inspect` **逐个复核**六个镜像真的在本机
     （`docker load` 说成功不等于齐了）；
  3. 六个都齐了才置离线标志，缺哪个明说缺哪个。
* **安装**：离线标志为真时跳过镜像源测速与拉取，直接写配置 + `up -d`。

界面入口摆在「选择模型」页底栏，是因为下一步就开始拉镜像了 —— 连不上源的机器得在
**开始之前**就有地方导入。`E_PULL_FAILED` 错误页上也有一个，那正是方案 §18
给这个错误码规定的动作（「换源重试 / 离线导入」）。

### 4.2 测试 5：断开三个 registry，用 tar 装成

「断开」用 `/etc/hosts` 把 `ghcr.io` / `hkccr.ccs.tencentyun.com` /
`registry-1.docker.io` 等指到 `127.0.0.1`（**不动测试机的防火墙服务**，红线 9）。
`hunter.agentpit.io` 不挡 —— key 校验还是要连它，那是一次很小的 HTTPS 请求，
和拉 800 MB 镜像不是一回事（完全断网的环境目前用不了，已写进 README 与使用说明）。

| 步骤 | 实测 |
|---|---|
| 导出 `hunter-images-1.1.0.tar` | **797,517,312 字节（798 MB），58 秒** |
| 真删掉四个 1.1.0 的 hunter 镜像 | `Untagged: …web/api/opencode/llm-shim:1.1.0` ✓ |
| 拦截生效 | `ghcr.io` / `hkccr` 都连不上；`hunter.agentpit.io` HTTP 200 |
| **对照组**：不导入直接装 | `✗ E_PULL_FAILED: 1.1.0 这个版本在所有候选镜像源上都拉不到：GHCR · GitHub（… Connection refused）；腾讯云 · 香港（… Connection refused）` ✓ 正是想要的失败 |
| `docker load` 导入 | **19 秒**，六个镜像全部报出来，`缺 []`，`tag=Some("1.1.0")` ✓ |
| 第一次跑「断网安装」 | **✗ 失败**（见下） |

> `postgres:16-alpine` 与 `redis:7-alpine` **删不掉** —— 测试机上预先存在的
> hunter-community 旧栈正在用它们，删它会把旧栈弄坏（红线 9）。
> 所以这两个镜像的导入是 no-op，它们的「在不在」是靠 `docker image inspect` 确认的，
> 不是靠一次冷加载。四个 hunter 镜像是真删真导。

### 4.3 测试 5 第一次就挂了，而且挂得很对（第九节 bug 2）

导入明明成功，紧接着的安装还是去测速然后 `E_PULL_FAILED`。原因：

**`--import-images` 导完六个镜像就退出了，真正安装是下一个进程做的事** ——
离线标志只放在 `AppState` 的内存里，那个进程根本看不到它。
界面上同样会中招：导入之后用户完全可能先把启动器关了再开。

修法三处：

1. `install.offline` **写进 `launcher.toml`**（`#[serde(default)]`，老配置读回来是
   `false`），`AppState::new()` 从配置里读回它；
2. `flow::prepare` 在离线模式下**跳过镜像源测速** —— 那台机器多半根本连不上任何源
   （这正是用离线包的原因），去测速只会白等两个超时。第 ④ 步算大小也改读
   `docker image inspect`，不再去问 manifest；
3. 真的从网上拉成功过一次就把标志清掉 —— 留着它会让以后每次安装都跳过拉取，
   镜像永远停在导入时的那一版。

### 4.4 修完之后重跑，全绿

同一个脚本、同一个 tar、同样把三个 registry 挡掉：

| 步骤 | 实测 |
|---|---|
| 对照组（不导入直接装） | `✗ E_PULL_FAILED … Connection refused` ✓ 仍然装不上 |
| `docker load` 导入 798 MB | **20 秒**，`缺 []`，`tag=Some("1.1.0")` |
| **断网安装** | `离线模式：镜像已由离线包导入，跳过镜像源测速（源 ghcr.io/agentpit-io）` → `✓ 拉取完成，用时 0 秒` → `✓ 6 个服务全部就绪，用时 1 分 0 秒`，**退出码 0** |
| 日志 | `离线模式：六个镜像都在本机，跳过拉取` |

### 4.5 第三次跑：验「一次性标志」（bug 9 的修正）

把离线标志改成一次性之后，同一个脚本再跑一遍：

| 步骤 | 实测 |
|---|---|
| 对照组（不导入直接装） | `✗ E_PULL_FAILED … Connection refused` ✓ |

顺带验到另一条：这一轮开头（镜像已经被删掉、标志还留着的那一刻）日志里是

```

—— 标志为真但镜像不齐时**不会装作能跳过**，而是老老实实回去联网拉（然后因为断网而失败，

最后把测试机从离线测试留下的 1.1.0 升回 1.2.0，**这一次日志里是**：

05:48:24 [info] 离线模式：六个镜像都在本机，跳过拉取

```

正是 bug 9 要的效果：**离线包只管它那一轮，下一次升级照常去问 registry。**

## 九、本轮撞出来的问题

十条，**全部是真跑（或真读配置 / 真读日志）才暴露的**，没有一个是靠读代码想出来的。

### bug 1 · CI 的 `tauri build` 打不出包：找不到 updater 私钥

第一次跑 `ci.yml` 就红。日志：

```
Finished 2 bundles at: …/Hunter Launcher_0.1.0_amd64.deb / .AppImage
A public key has been found, but no private key.
Make sure to set `TAURI_SIGNING_PRIVATE_KEY` environment variable.
       Error …
```

**原因**：`tauri.conf.json` 里 `createUpdaterArtifacts` 是开着的（发布时要出 `.sig`），
于是**任何** `tauri build` 都会在打完包之后去签名。而 CI 不该拿到那个 secret
（fork 的 PR 更拿不到）。

**修**：`ci.yml` 的 `tauri build` 加 `--config '{"bundle":{"createUpdaterArtifacts":false}}'`。
CI 这一步要验的是「能不能打出装得上的包」，签名留给 `release.yml`。

### bug 2 · 离线包导入之后，安装还是去测速然后失败

见 4.3。**离线标志只在进程内存里**，而 `--import-images` 与真正的安装是两个进程。
修成落盘（`launcher.toml` 的 `install.offline`）+ 离线模式跳过测速 + 联网拉成功后自动清除。

### bug 3 · macOS 的 `tauri build` 拿一个空的签名身份去 codesign

rc.1 第一次发布，macOS job 红：

```
failed to bundle project: failed codesign application:
failed to run command security import: failed to import keychain certificate
```

**原因**：**空字符串不等于没设置**。为了让步骤的 `if:` 能读到，我把
`APPLE_SIGNING_IDENTITY` 等放在 job 级 `env` 里；没配的 secret 在那里会变成一个
**存在但为空**的环境变量，而 Tauri 判的是「这个变量在不在」——于是它认为要签名。

**修**：`tauri build` 之前把值为空的那几个显式 `unset`，它才会走「不签名」那条路。

### bug 4 · MSI 不接受 `0.1.0-rc.1`

同一次发布，Windows job 红：

```
failed to bundle project: `optional pre-release identifier in app version
must be numeric-only and cannot be greater than 65535 for msi target`
```

**原因**：WiX 只认纯数字的预发布段。NSIS 没这个限制。

**修**：Windows 上分两次打包 —— NSIS 用真实版本号，MSI 用
`bundle.windows.wix.version` 覆盖成去掉后缀的数字版本。第二次只是重新打包，很快。
**代价**：两个 rc 的 MSI ProductVersion 会一样，Windows 认不出「更新」。
对预发布可以接受（Windows 上推荐的是 NSIS），正式版没有后缀不受影响。

### bug 5 · `latest.json` 里**没有 macOS**，而流水线是绿的

rc.1 第二次发布：三平台构建全绿、Release 建出来了、12 个资产都在，
但 `latest.json` 的 `platforms` 只有 `linux-x86_64` 与 `windows-x86_64`。

**原因**：macOS 的 `.app.tar.gz` 是**唯一一个文件名里不带版本**的产物
（Tauri 只用 `productName` 命名它），改名后变成 `hunter-launcher.app.tar.gz`，
而 `make-latest-json.py` 找的是 `*_universal.app.tar.gz`。

这个 bug 最难受的地方是**它不会让任何一步失败** —— 发出去之后 mac 用户永远收不到更新，
而我们看到的是一条绿色的流水线。

**修**：改名时补上版本与 `universal`；另外加一道闸门 ——
生成完 `latest.json` 立刻检查四个 target 键（`linux-x86_64` / `windows-x86_64` /
`darwin-x86_64` / `darwin-aarch64`）一个都不能少，少了就红。

### bug 6 · COS 不支持 boto3 的分片上传

同一次发布的汇总 job：

```
botocore.exceptions.ClientError: An error occurred (MissingContentLength)
when calling the UploadPart operation: You must provide the Content-Length HTTP header.
Failed to upload staged/hunter-launcher_0.1.0-rc.1_amd64.AppImage
```

**原因**：boto3 默认超过 8 MB 就切成 multipart，而 COS 的 `UploadPart` 要求带
`Content-Length`，boto3 不带。所以**小文件都成功、只有 78 MB 的 AppImage 失败**。

**修**：`TransferConfig(multipart_threshold=5GiB)` 关掉分片，走单次 `PutObject`
（COS 单次支持到 5 GB，我们最大的包才 80 MB）。已用一个 60,000,000 字节的文件
真传真下验过（上传成功、`curl` 回来 HTTP 200、字节数一致）。

### bug 7 · headless 查不到启动器更新（不是 bug，是缺口）

`--check-update` 原来只打印「安装形式」和 Release 页地址 —— 因为 Tauri 的 updater
插件要 `AppHandle`，headless 没有。也就是说 **SSH 用户根本查不到启动器有没有新版本**。

**补**：`selfupdate.rs` 里加一套自己读清单 + 用同一把公钥验签的实现，
`--check-update` 真去读，另加 `--self-update`（AppImage 就地替换、`.deb` 只下载，
两条路都先验签）。三条测试盯住「公钥与端点写在两个地方不许各改各的」。

### bug 9 · 离线标志留太久，升级会**悄悄跳过拉取**

收尾时顺手看了一眼测试机的 `launcher.toml`：

```toml
[install]
offline = true      # ← 离线测试早就跑完了，后来还联网升级过
```

翻日志：

```
2026-09-20 04:44:06 [info] 离线模式：六个镜像都在本机，跳过拉取   ← 离线测试，正常
2026-09-20 05:37:14 [info] 离线模式：六个镜像都在本机，跳过拉取   ← **这是一次 --upgrade 1.2.0**
```

那次升级**一次 registry 都没碰**。容器最后是对的（1.2.0 的镜像确实在本机），
所以它不报错、看不出来 —— 但「升级」这件事的本意就是去取新版本，
悄悄用本地的不该是默认行为。

原来的清除条件是「真的从网上拉成功过一次」，而这一路根本没走到那个分支。

**修**：把离线标志改成**一次性** —— 一轮拉取结束就清掉，不管这一轮是跳过的还是真拉的。
语义因此和文档一致了：「导入离线包 → **紧接着的这一次**安装跳过拉取」。
air-gapped 的机器要重装就再 `--import-images` 一次（tar 就在手边，
`docker load` 一个已经加载过的包只要十几秒）。

> 这条是**读配置文件读出来的**，六个测试用例全绿的时候它就在那儿。
> 记在这里是因为「测试全过 ≠ 没有问题」——尤其是这种「结果碰巧是对的」的毛病。
>
> **这也是为什么 `launcher-v0.1.0` 打了两次**：第一次（21:33）四个 job 全绿、产物齐全，
> 但它是在这处修正**之前**的提交上打的。发出去只有十几分钟、是 prerelease、没有对外通知，
> 所以把那个 Release 与 tag 删掉，在修完的提交上重新打了一次 —— 留一个已知有缺陷的
> 构建在下载地址上不合适。第二次的产物见 7.3。

### bug 10 · 从 rc 升到正式版时，我们给的那条 apt 命令**装不上**

最后一次端到端验收（测试机上 rc.2 → 正式版 0.1.0）踩到的：

```
0 upgraded, 0 newly installed, 1 downgraded, 0 to remove and 0 not upgraded.
E: Packages were downgraded and -y was used without --allow-downgrades
```

**dpkg 对预发布版的排序和 semver 相反。** 实测（Ubuntu 24.04）：

```
dpkg --compare-versions 0.1.0 gt 0.1.0-rc.2   → 假   ← -rc.2 被当成「Debian 修订号」
dpkg --compare-versions 0.1.0 gt 0.1.0~rc.2   → 真   ← 波浪号才是 Debian 的预发布写法
```

**修**：`deb_install_command` 加 `--allow-downgrades`（只在真需要时起作用，正常升级不受影响），
并在使用说明与常见问题里把「为什么是 downgrade」讲清楚 —— 不然用户看到这个词会以为装错了。
加了一条测试盯住这个开关别被删掉。

> **这一条没有让 v0.1.0 再重发一次**，理由：它只在「从 rc 的 deb 升到正式版的 deb」时出现。
> 直接装 v0.1.0 的人不受影响；从 v0.1.0 升到 0.1.1 / 0.2.0 也是正常升级，dpkg 与 semver
> 在那些版本上意见一致。修正会随下一版发出去。
> 更彻底的修法（deb 版本号用 `~rc.2`）需要 Tauri 支持单独覆盖 deb 版本号，记在待办池 P1-19。

### bug 8 · 测试机 pnpm 12 又挡了一次（P2-9 复发）

改了 `package.json` 的 `version` 之后，pnpm 会重新核对锁文件，于是
`minimumReleaseAge` 策略再次拦下 `@rollup/rollup-*`——连 `pnpm exec` 都跑不了，
而 `tauri build` 的 `beforeBuildCommand` 正是 `pnpm build`。

**绕法**（已写进开发指南）：直接调 `./node_modules/.bin/vite` 与
`./node_modules/.bin/tauri`，并用 `--config '{"build":{"beforeBuildCommand":""}}'`
把那一步关掉。CI 用 pnpm 10，不受影响。

## 十、偏离方案的决策与原因

| # | 方案怎么说 | 实际怎么做 | 为什么 |
|---|---|---|---|
| 1 | §10「替换 compose 文件与 `OPENCODE_TAG`」 | 换的是 `HUNTER_VERSION` | hunter-community 的 compose 用**一个** `HUNTER_VERSION` 管四个镜像，没有单独的 `OPENCODE_TAG` |
| 2 | §10「失败 → 回滚 tag → `up -d`」 | 回滚**整套配置**（`.env` + 两个 compose）再 `up -d` | 只改 tag 不够：新版本的 compose 可能加了新服务 / 新健康检查 / 新环境变量，拿新 compose 配旧镜像起出来的东西说不清是什么。实测验证了回滚后两个文件与升级前**逐字节一致** |
| 3 | §10 只写了「提供从文件导入的入口」 | 导入 + **导出**都做了 | 只有消费端没有生产端，内网用户拿不到那个 tar |
| 4 | §10「用户点击下载安装，重启生效」（默认全自动） | `.deb` 改成「下载 + 给一条命令」 | Tauri updater 在 Linux 上只能替换 AppImage；`.deb` 装在 `/usr` 下要 root，桌面程序不该背着用户拿 root |
| 5 | §16「签名是必做项」 | **不签名**，Release 一律 prerelease | 用户已决定不购买证书（红线 7）。CI 里签名步骤写好了，配上 secrets 就自动生效 |
| 6 | §17「同步到 `dl.agentpit.io`」 | 同步到腾讯云香港 COS | `dl.agentpit.io` 不存在（M0 实测），`plan/国内镜像与下载源.md` 已改用 COS |
| 7 | §10 Release Notes「取前 500 字」 | 取前 500 **字符** | 按字节切会把中文切成乱码。有单测盯着 |
| 8 | 升级前只做 `pg_dump` | 还备份 `.env` + 两个 compose + `launcher.toml` | 回滚要回到升级前那**一整套**，只有数据库转储是回不去的 |
| 9 | — | 数据库没备份成功就**中止升级** | 方案没写这一条。没有转储等于没有后悔药，这时候继续是拿用户的数据赌运气 |
| 10 | — | 回滚**不自动恢复数据库** | 升级失败绝大多数发生在「镜像拉不到」或「容器起不来」，这两种情况下数据库根本没被动过；自动灌回转储反而会抹掉升级中途写进去的东西 |

## 十二、遗留问题（已进待办池）

| # | 事项 |
|---|---|
| **P1-14** | `.deb` 装的启动器不能就地自更新。要全自动只有两条路：装一个带 root 的 helper（政策上不该做），或者建 apt 源（要仓库 + GPG 签名 + 用户加源，一整套基础设施）。写进「需要用户决定」 |
| **P1-15** | updater 的**就地安装**只在 AppImage 上真验过；Windows 的 NSIS `installMode: passive` 与 macOS 的 `.app.tar.gz` 替换只有代码路径审阅 |
| **P1-16** | `latest.json` 里 macOS 两个 target 指向同一个通用包（Tauri 官方写法），Intel 机器要下整个通用包 |
| **P1-17** | COS 上的旧版本安装包不会被清理，发十几个 rc 之后会堆很多 |
| P0-5 | 两个工作目录抢同一个 compose 项目名（M2 起的老问题，M4 未做） |
| P0-6 | 上游 api 缺四条只读接口（M3 起的老问题，要上游配合） |
| P1-9 / P1-12 | 「完全干净的机器上首次安装要多久」仍然测不出（测试机上层都在） |
| P1-13 | 托盘图标在真实桌面上的目视确认 |
| P1-10 / P1-11 | 自带第三方 key 的完整安装、402 / 429 仍未实测 |
| P1-18 | **预发布版本的 MSI 认不出「更新」**：WiX 只认纯数字的预发布段，`rc.1` / `rc.2` 的 MSI ProductVersion 都被降成 `0.1.0`。正式版没有后缀，不受影响 |
| P2-9 | 测试机 pnpm 12 的 `minimumReleaseAge` —— 本轮**又撞了一次**：改了 `package.json` 的 version 就会触发重新校验锁文件。绕法是直接调 `./node_modules/.bin/vite` 与 `./node_modules/.bin/tauri`。CI 用 pnpm 10 不受影响 |

本轮新发现、**没进待办池但要记一笔**的：

* **MSI 不接受非数字的预发布后缀**。`0.1.0-rc.1` 会被 WiX 直接拒绝。现在的做法是
  MSI 单独用 `bundle.windows.wix.version` 覆盖成去掉后缀的版本 —— 代价是两个 rc 的 MSI
  ProductVersion 会一样，Windows 认不出「更新」。**对预发布可以接受**（Windows 上推荐的是
  NSIS），正式版没有后缀不受影响。
* **升级测试没有覆盖「跑了一次真实数据库迁移之后数据还对」**：1.1.0 → 1.2.0 在这个实例上
  `schema_migrations` 前后都是 23 条，没有新增迁移。要等一个真的带迁移的版本对。

## 十三、需要用户决定的事

1. **要不要买代码签名证书**（Windows OV/EV 100–500 美元/年 + Apple 99 美元/年）。
   现在：产出未签名包、Release 一律 prerelease、README 与常见问题里写了放行步骤。
   买了之后：把证书塞进 secrets，流水线里那三步会自动生效；同时**GitHub 那个 updater
   端点也会跟着活过来**（它解析的是「最新的正式 Release」）。
2. **0.1.0 要不要转成正式版**。功能完整、Linux 真机跑通，但没签名、Windows/macOS 没真机测过。
   按里程碑要求，本轮打的 `launcher-v0.1.0` **仍标 prerelease**。
3. **要不要给 `.deb` 建 apt 源**（见 P1-14）。有了它 `.deb` 用户也能一条命令升级。
4. 一把第三方模型 key（DeepSeek / OpenAI），用来端到端验「自带 key」那条路（P1-10）。
5. 一台带桌面的 Windows / macOS 机器，验托盘外观与就地自更新（P1-13、P1-15）。

## 十四、给迭代轮（I1）的交接

**能直接用的**：

* `scripts/set-version.sh <版本>` 改三个文件的版本号 → 提交 → `git tag launcher-v<版本>` → push，
  剩下的 `release.yml` 全包（三平台打包、Release、`latest.json`、COS 同步）。
  发版流程完整写在 [`docs/开发指南.md`](../开发指南.md) 第九节。
* `hunter-launcher --check-update` / `--upgrade <版本>` / `--backups` /
  `--import-images` / `--export-images` —— 和界面走同一套代码，适合脚本化回归。
* `scripts/m4-test-upgrade.sh` / `m4-test-rollback.sh` / `m4-test-offline.sh`
  （在 `/mnt/disk-119/hunter-launcher/scripts/`）可以整套重跑，输出带时间戳直接进报告。

**动之前要知道的**：

* `install.offline` 在 `launcher.toml` 里。它为真时**跳过测速与拉取**，而且是
  **一次性的**（一轮拉取结束就清，跳过的也算）。调试「为什么没去拉镜像」时先看它，
  再看日志里有没有「离线模式：六个镜像都在本机，跳过拉取」。
* 改安装包文件名要同时改三处：`release.yml` 的改名步骤、`selfupdate.rs` 的
  `deb_url_*`、`make-latest-json.py` 的 `TARGETS`。`selfupdate.rs` 里那条测试会拦住漏改。
* `tauri.conf.json` 的 `createUpdaterArtifacts` 是**开着**的，任何 `tauri build`
  都要么有 `TAURI_SIGNING_PRIVATE_KEY`、要么用 `--config` 关掉它。
* updater 的私钥丢了 = 已经装出去的启动器再也收不到更新（它们只认编译进去的公钥）。
  私钥在开发机 `~/.hunter-launcher-keys/` 与仓库 secrets 里，两份都别删。

**建议 I1 先做的三件**（都在待办池）：

1. **P0-5**（两个工作目录抢 compose 项目名）—— 它会让用户莫名其妙掉配置，是 P0；
2. **P1-14 / P1-15**：给 `.deb` 找一条能自动升级的路，或者至少在真机上验一遍
   Windows / macOS 的就地安装；
3. **P1-17**：COS 的旧版本清理，趁桶里东西还少。
