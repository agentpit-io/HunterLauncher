## 零、一句话

这一轮和 I10 是同一天、同一台 Mac 上的**同一次失败的两段**。

I10 修的是「为什么会失败」（虚拟机没有 DNS）。I11 修的是**失败之后的那 71 分钟**：

```
21:39  E_START_TIMEOUT，界面进「出错了」
22:05  根因在外部被修好 → 6/6 健康、web 127.0.0.1:3100 返回 200
22:42  AI 又读了一遍 opencode 日志，规则层 unknown —— 界面还挂着 21:39 那张卡片
22:46  用户点「重试」→ 重新取 compose、重写 .env、开始重新拉 849 MB（用户手动取消）
22:50  用户：「已经可以正常访问了，但系统安装还有错误提醒……」
```

三件事错了，而且是三种不同性质的错：

| # | 错在哪 | 性质 |
|---|---|---|
| 1 | **界面不看现状。** 服务好了 41 分钟，失败卡片一直挂着 | 产品缺口：没有人去问「现在怎么样了」 |
| 2 | **「重试」= 从头装一遍。** 这台机器上该有的一件不缺 | 设计缺陷：重试没有前置判断 |
| 3 | **那一页上只有「上一步」「重试」。** 用户想关掉都没处点 | 出口缺失 |

外加一条送给模型的**假前提**：用户导出的诊断里，五个正被 Hunter 自己占着的端口
全印着「空闲」—— 前提一错，后面的推理全是白做的。

本轮五件事（U1–U5），逐条对应用户原话；每一条都在测试机上真跑过，
其中 U1 与 U3 是在 **Xvfb 真界面 + 真 Docker + 真 key** 的会话里验的，不是演示模式。

## 一、U1 · 错误页会自己看现状

### 1.1 新模块 `selfcheck.rs`：只读地问一句「它到底在不在跑」

这件事必须**只看不改**，所以单独开了一个模块而不是塞进安装流程里。它做三件事：

| 步骤 | 手段 | 会不会改动机器 |
|---|---|---|
| 这个 compose 项目名现在是谁的 | `compose::guard_project_owner()`（读容器标签） | 否 |
| 六个服务各自什么状态 | `docker compose ps --all` | 否 |
| 网页打不打得开 | 对 `http://127.0.0.1:<web 端口>/` 发一次 GET，6 秒超时 | 否 |
| （只有安装前的深查才做）容器连不连得上模型网关 | I10 的 `netcheck::probe()`，一个 `--rm` 的一次性容器 | 不碰本项目任何容器 |

四种结论，对应四种做法：

| 结论 | 现场 | 该做什么 |
|---|---|---|
| `Absent` | 项目名不归我们 / 配置文件不在 / 一个容器都没有 | 完整安装 |
| `Incomplete` | 六个服务没建齐，**或者有容器「建出来过但一次都没跑起来」** | 完整安装 |
| `Partial` | 六个容器都在，但有的没就绪 / 网页打不开 | 只修不正常的那部分（见第二节） |
| `Healthy` | 6/6 就绪、网页真的应答 | 什么都不做 |

`Incomplete` 里那条「建出来过但没跑起来」是特意加的：那是上一次起到一半被打断
留下的残骸（用户 Mac 上 0.1.4 的现场就有 3 个），**它们身上冻着的是当时那一组端口**。
把它们当成「只差起一下」去 `up`，起来的还是旧端口，照样撞车 ——
这一档必须回到 I5 就有的那条路：清残骸 → 重算端口 → 重起。
（这一条是写代码时想到的，后来被 I10 场景 F 的回归验证了，见第五节。）

**关于「网页打得开」的判据**：任何 5xx 以下的状态码都算活着，不强求 200 ——
未登录时上游会 302 到 `/login`，那同样证明这个端口后面有 Hunter 在应答。

### 1.2 界面这一侧：低频复查 + 三个触发点

新 hook `useSelfCheck`，挂在错误页上。三个触发点缺一不可：

1. **挂载就查一次** —— 用户可能是刚打开启动器，服务早就好了；
2. **每 20 秒查一次** —— 外部把它修好这件事，没有人会来通知我们；
3. **窗口重新拿到焦点时查一次** —— 用户去别处折腾了一圈回来，第一眼就该是对的。

外加第四个：**AI 或规则层每跑完一个动作，立刻重查一次**
（`AssistPanel` 新增 `onActed` 回调，成功失败都叫）。
0.1.9 那次 AI 读了四遍日志、动作也跑过，界面自始至终**没有重新判断过现状**。

查到 `Healthy` 就发一条新的状态机事件 `ALREADY_RUNNING`，从任何状态都能进，
直接落到运行面板 —— **不经过完成页**：那一页会说「装好了」，而这一次一个字节都没下载。
切过去之后运行面板顶上出现一条绿色横幅说明刚才发生了什么，
否则那一跳会像是界面自己乱跳。

复查结论本身也常驻在错误卡片下面（「现在是什么情况」卡片，带「实测」角标），
数字全部来自后端实测：服务数、真实 HTTP 状态码、复查耗时。查不出来就说查不出来
（「这一次没问出来：<原话>」），**不拿上一次的结果冒充现在**（红线 1）。

### 1.3 实测：在 Linux 上把 0.1.9 那一幕重演了一遍

真界面、真 Docker、真 key，不是演示模式（`I11-证据/h-界面真机-错误页自己切回运行面板.txt`）：

现场怎么造的 —— 六个容器一直健康地跑着，把 `app/docker-compose.yml` 挪走、
把 tag 改成一个不存在的 `9.9.9`，于是安装在「挑下载源」那一步快速失败。


**从外部修好到界面跟上：≤ 30 秒，零点击。**

## 二、U2 ·「重试」先验证，不重装

### 2.1 总指挥开工前先复查

`Orchestrator::run()` 的第一件事不再是「检查 Docker」，而是一次只读复查，
然后按结论分三条路：

```
Healthy      → 什么都不做，直接收工（reused = true）
Partial      → 只修不正常的那几个服务，修好了同样直接收工
Absent /
Incomplete   → 走原来的四步：检查 Docker → 挑源写配置 → 下载 → 启动
```

**`Partial` 那条路碰什么、不碰什么，是逐条写死的：**

| 服务现在的状态 | 做什么 | 用的命令 |
|---|---|---|
| 在跑但健康检查不过 | 重启它的进程（容器不换，端口映射与数据卷都不动） | `docker compose restart <服务>` |
| 停着 / 退出了 | 起起来，**`--no-recreate`** | `docker compose up -d --no-recreate <服务>` |
| 健康的 | **一个字都不碰** | —— |

不取 compose、不写 `.env`、不拉镜像 —— 那三件事是「完整安装」的活，
不是「修一个服务」的活。`--no-recreate` 这个标志就是「点重试不能把正在跑的东西
推倒重来」这条要求的落点。

修完还要**再复查一次**才算数（验证员的老规矩：重跑一遍，不是问模型「好了吗」）。
还不行就把这一步交给「启动服务」那一步的修复回合（AI、规则层都在那条路上），
**照样不回头去取 compose、不重拉镜像**。

### 2.2 「自己那一套」和「用户另外装的那一套」必须分开

I8 定的规矩是「本机已有另一套 Hunter 就并存、换端口」。那条规矩只对
**用户自己另外装的**成立 —— 要是把我们上一次装的那一套也算进去，
点一次重试就会并出第二套，白占几个 G 的盘和内存。

代码里这条线一直在（`other_hunter_installs` 按 `project == "hunter"` 过滤），
本轮给它补了一条单测钉死：`ports::tests::自己上一次装的那一套不会被当成另一套_hunter`。
加上开工前的复查，「自己那一套」现在有两道保障：
**根本走不到并存那条路**（复查先接管），以及**就算走到了也不会把自己列进候选**。

### 2.3 实测（`I11-证据/a-容器创建时间前后比对.txt` 等）

判据用容器的 `CreatedAt`：compose 一旦重建容器，这个时间就会变。

| 场景 | 现场 | 结果 | 用时 | token |
|---|---|---|---|---|
| B · 六个服务全健康时点重试 | 6/6 healthy | **一条 compose 命令都没跑**，六个 `CreatedAt` 一字不差 | **4 秒** | 0 |
| C · 只停掉 opencode 再点重试 | 5 running + 1 exited | 只跑了 `up -d --no-recreate opencode`，六个 `CreatedAt` 一字不差（含 opencode） | 19 秒 | 0 |
| G · 配置缺了一半（compose 文件被挪走） | 容器健康、配置不全 | 走完整安装；跑完六个 `CreatedAt` 仍然没变，三把 sticky 口令也没换 | 17 秒 | 0 |
| 收尾复验 · 全新装好之后再点一次 | 6/6 healthy | 零重建 | **2 秒**（对比首装 72 秒） | 0 |

场景 B 的 launcher.log 原文，总共只有两行：

```
02:40:10 [info] 开工前复查：Hunter 已经在正常运行（6 / 6 健康，网页返回 HTTP 200）（4016 毫秒）
02:40:10 [info] 开工前复查发现这一套已经在正常运行，本次不做任何安装动作
```

场景 C 的 launcher.log，**只有一条会改动机器的命令**：

```
02:49:18 [info] 开工前复查：Hunter 在跑，但 opencode 还没就绪（2598 毫秒）
02:49:21 [info] docker compose up -d --no-recreate opencode 完成
02:49:34 [info] 开工前复查发现这一套已经在正常运行，本次不做任何安装动作
```

命令行的收尾那句话也跟着改了：**这一次什么都没装的时候不说「装好了」**——

```
✓ 没有重新安装：这一次没有重新下载任何镜像，健康的容器也一个都没重建。打开 http://localhost:3101
```

## 三、U3 · 错误页多了一个「关闭」

新 Tauri 命令 `window_hide`，和原来的 `window_close` 不是一回事：

| | `window_close`（标题栏那个 ×） | `window_hide`（本轮新增） |
|---|---|---|
| 语义 | 关窗口 = 请求退出 | 把窗口收回托盘 |
| 容器还在跑时 | 弹「保持后台运行 / 一起停止」 | 不弹，什么都不问 |
| 进程 | 退出 | 继续活着（托盘还在） |
| 正在跑的服务 | 看用户在对话框里怎么选 | **一个都不动** |

错误页底部与诊断卡片底部各加一个「关闭」走的是后者。
**复查说容器全绿时，它变成那一页的主按钮**，「重试」退成次按钮 ——
那种情形下「重试」本来就是错的那个选择。

实测（同一次真机会话）：点下去之后

```
$ xwininfo -id <窗口>  →  Map State: IsUnMapped     ← 窗口收起来了
$ ps -p <pid>          →  进程还在（etime 04:21）    ← 没退出
$ docker ps --filter label=com.docker.compose.project=hunter
  六个容器全部 Up … (healthy)                        ← 服务一个都没动
```

## 四、U4 · 端口那一栏不再骗人

### 4.1 根因：不是探测漏了，是**只有两档**

0.1.9 那份用户导出的诊断里，3100 / 8100 / 3921 / 5442 / 6479 五个端口全写着
「空闲」，而它们当时正被 Hunter 自己的服务占着（mac 上由 lima 的 ssh 端口转发
在宿主上监听）。查下去，错在 `Survey::verdict` 里的一行提前返回：

```rust
// 旧代码
if ignored_owner && occ.is_empty() {
    return Verdict::free(port);   // ← 连绑定探测与 lsof 都不跑了
}
```

对**安装**来说这个答案是对的（这个端口我们能用）；对**诊断**来说是错的。
根子是 `Verdict` 只有「空闲 / 被占用」两档，而「被我们自己占着」在安装那条路上
恰好也算「可用」，于是被直接写成了 `free = true`。

### 4.2 修法：把「能不能用」和「有没有人在听」分开

`Verdict` 现在有三档（`Kind::Free` / `Mine` / `Other`）：

* `free` —— 三路都说没人听。**它不再是「可用」的同义词**；
* `usable()` —— 这次安装能不能用（没人听，或者听着的就是我们自己）；
* `occupants` —— 挡在前面的占用者；`mine` —— 占着但属于 Hunter 自己的证据。

三路照常全跑，只是把「属于我们自己」的证据归到 `mine`。
所有问「能不能用」的调用点（端口分配、预检闸门）改成 `usable()`，
所有给人看 / 给模型看的地方拿到的是三档的人话。

诊断信息里的端口一节因此变成三类，而且**命令行的 `--diagnose` 与界面上的
「诊断报文」现在用的是同一个函数**（`Report::ports_section()`）——
原来 `--diagnose` 根本没有端口这一节，两边口径各写各的。

### 4.3 实测（`I11-证据/e-诊断的端口一节分三类.txt`）

```
## 端口（空闲 / 被 Hunter 自己占用 / 被其他程序占用）
web 3101 被 Hunter 自己占用（正常，不是冲突） · Docker 容器 hunter-web-1（compose 项目 hunter · 127.0.0.1:3101->3000/tcp）；绑 0.0.0.0 时被系统拒绝（Address already in use (os error 98)）；绑 127.0.0.1 时被系统拒绝（Address already in use (os error 98)）
api 8101 被 Hunter 自己占用（正常，不是冲突） · …
opencode 3922 被 Hunter 自己占用（正常，不是冲突） · …
postgres 5443 被 Hunter 自己占用（正常，不是冲突） · …
redis 6480 被 Hunter 自己占用（正常，不是冲突） · …
```

送给模型的那份证据也是同一份（场景 7 的 `--diagnose --ai` 输出里能看到同样的五行，
见 `I11-证据/r7-守卫越界八条全部被拒.log` 末尾）。

三条新单测钉住三档：`被自己占着的端口不许报成空闲`（现场按 mac 那一幕构造：
`docker ps` 报本项目发布端口 + lsof 报一个叫 `ssh` 的监听进程）、
`被别人占着时既不空闲也不可用`、`没人听就是空闲`。
另有一条 I5 留下的老测试被**有意改掉了**断言：它原来断言的正是 `.free`，
而那就是这次错的地方 —— 现在断言 `usable() && !free && kind == Mine`。

## 五、U5 · 手工敲 `docker compose` 也不会把端口开到局域网上

### 5.1 背景（真实事故，50 分钟）

2026-09-22 22:01，本地 Claude 在用户 Mac 上手工跑了一次
`docker compose -p hunter up -d`，**漏了启动器的覆盖文件** ——
容器被重建成 `0.0.0.0`，五个端口在局域网里可达了约 50 分钟（22:50 才恢复）。

### 5.2 两道：让手工命令自带覆盖文件 + 跑偏了自己收回来

**第一道 · `.env` 里写上 compose 自己的配置项。** compose 会读项目目录下的 `.env`
来取这几个值，所以在 `~/.hunter/app` 里直接敲 `docker compose up -d` 也会带上覆盖文件：

```
COMPOSE_PROJECT_NAME=hunter
COMPOSE_PATH_SEPARATOR=:          ← 分隔符写死，不赌 compose 的平台默认值（Windows 是 ;）
COMPOSE_FILE=docker-compose.yml:docker-compose.launcher.yml
```

启动器自己走的是命令行 `-f`，优先级更高，**所以这三行不会改变启动器的行为，只兜住手工操作**。
这三项和 key、端口一样进了「写完读回来逐项对账」的名单：漏写一项就不算写成功。

**第二道 · 跑着的容器绑在哪，和配置说的一不一样。** 启动器每次启动、
以及每次开工前复查都对一遍：`docker compose ps` 报的真实绑定地址 vs 磁盘上那份覆盖文件。
不一样就按覆盖文件把**那几个**容器重建回来（别的一个不碰）。

这不是替用户做新决定 —— 覆盖文件本来就写着 `127.0.0.1`，是现实跑偏了。
I7 那一档「老机器的 web 本来就对外」（`WebBind::LegacyLan`）**不在此列**：
那是用户的现状，启动器有意不悄悄改它。

### 5.3 实测（`I11-证据/f-手工敲compose也带上覆盖文件.txt`、`d-容器被重建成0.0.0.0-自动收回本机.log`）

```
$ cd ~/.hunter/app && docker compose config | grep -E '^name:|published'
name: hunter                          ← 项目名对了，不会并出第二套
        published: "8101" …           ← 端口是覆盖文件里那一组

$ docker compose up -d --force-recreate redis      # 不带任何 -f / -p
 Container hunter-redis-1 Recreated
$ docker ps --filter name=hunter-redis-1 --format '{{.Ports}}'
127.0.0.1:6480->6379/tcp              ← 覆盖文件被带上了
```

反面对照 —— 显式只给基础 compose（绕过 `.env` 里的 `COMPOSE_FILE`），复现那 50 分钟：

```
$ docker compose -p hunter -f docker-compose.yml up -d --force-recreate redis postgres
```

## 六、实测撞出来的三条（都当轮修了）

这三条都不是读代码读出来的，是真跑之后看着输出发现的。

### 6.1 收尾那句话在说假话

第一版 `Partial` 修完之后照样打印「这一次没有下载任何东西，**也没有动正在跑的容器**」——
可那一次明明重启过 opencode；收回端口绑定的那一次更明显，postgres 与 redis
是**真的被重建过**的。

改法：那句话现在逐条按刚才真做过的事拼出来（`fixed` / `rebound` 两份清单），
没做过任何事才会出现「正在跑的容器一个都没动过」。命令行的最后一行同理：
「✓ 装好了」在 `reused` 为真时换成「✓ 没有重新安装：这一次没有重新下载任何镜像，
健康的容器也一个都没重建」。

**教训和 I10 那条一样**：红线 1 不只管数字，也管动词。

### 6.2 `--diagnose` 根本没有端口这一节

改三档显示的时候才发现：**用户导出的那份「诊断信息」是界面上的诊断报文
（`Report::to_prompt()`），而命令行的 `--diagnose` 走的是另一段自己拼的文本，
里面连端口都没有**。代码注释里明明写着「和界面上『复制诊断信息』拿到的是同一份东西，
两边的口径必须一致」。

改法：抽出 `Report::ports_section()`，两边都调它。

### 6.3 「建出来过但没跑起来」差点被当成「只差起一下」

写 `Partial` 那条路时意识到的：六个 `Created` 状态的容器会被判成
「六个都在，只是没就绪」，于是 `up -d --no-recreate` 起它们 ——
而它们身上冻着的是**上一次那一组端口**，起来照样撞车。

改法见 1.1：`Created` 一律归到 `Incomplete`，走完整流程。
这一条随后被 I10 场景 F 的回归验证了（第七节）。

## 八、没做的 / 未验证的

* **macOS 真机未验证。** 本项目只有 Linux 测试机。本轮改的东西里，
  `.env` 那三行与端口三分类是平台无关的；「容器绑在 `0.0.0.0` 就收回来」
  在 mac 上多一层 lima 端口转发，`docker compose ps` 报的仍然是容器侧的绑定地址，
  代码路径相同，但**没有在 mac 上跑过**。等用户真机验收。
* **端口被 lima ssh 转发占着时的三分类**，靠的是 `docker ps` 那一路认出
  「这是项目 `hunter` 的容器」。单测里按 mac 那一幕构造了现场（含一个叫 `ssh`
  的监听进程），但**真机上没跑过**。
* **复查的轮询间隔 20 秒是拍的**，没有做成可配置 —— 它只在错误页上跑，
  一次是 `docker compose ps` + 一次本机 GET，代价很小。
* **没有给「关闭」加托盘气泡提示**（「启动器还在托盘里」）。三平台的气泡 API
  行为不一致，而且托盘图标本来就在那儿，这一轮先不做。
