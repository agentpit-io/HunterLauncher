## 零、一句话

用户 2026-09-22 那段原话里，I12 做掉了前四句（状态持久化、资源、启停、重装前检测），
剩下的三件事是这一轮的全部：

| 用户原话 | 本轮做的 |
|---|---|
| 「可以执行删除应用，但需要输入「删除应用」文字，避免用户错误点击按钮。删除前，还需要提醒，数据库是否需要保留，还是只删除应用。」 | **R4**：三步 —— 选范围（默认「保留数据」）→ 逐字输入 → 执行并逐条报告 |
| 「同时支持本地数据库文件备份和恢复，可以设置自动备份时间、备份目录……默认备份保留近 3 天」 | **R6**：`pg_dump -Fc` + 密钥卷 + 配置 + `meta.json`，**做完立刻校验**；三平台定时任务；恢复是六步的完整流程 |
| 「并可以分析硬盘、内存异常情况，给予提醒和智能分析解决」 | **R7**：七类监测项、两级阈值、结论 + 一键处理，判不了的把脱敏快照交给诊断助手 |

这一轮和 I12 有一处根本的不同：**I12 做的全是「看」，I13 做的全是「动」**——
而且动的是用户的数据。所以这份报告里关于守卫的篇幅比功能还多。

而验收也确实撞出了这一类里最该撞出来的那种问题：**守卫那三道门全都生效了，
错的是喂给它们的那张清单**（第 5.2 节 ①）。命令的形状对，不等于命令里的东西是对的。

## 一、R6 · 备份与恢复

### 1.1 一份备份是什么（与 0.1.12 的差别）

| | 0.1.12 及之前 | I13 |
|---|---|---|
| 数据库 | `pg_dump --clean --if-exists`（纯 SQL 文本） | **`pg_dump -Fc`**（自定义格式，自带压缩） |
| 数据卷 | **一个都不备份** | 密钥卷（必备）+ 自建技能 + 会话记录（可选，默认都备） |
| 校验 | 没有 | **`pg_restore --list` 读一遍目录，读不出来就判这次失败** |
| 位置 | 固定在 `~/.hunter/backups`（删除应用会波及） | 可配置，默认在文档目录，**一定在 `~/.hunter` 之外** |
| 保留 | 不删，无限堆 | 按天保留最近 N 天；升级前备份另算，单独留最近 2 份 |
| 元信息 | tag / 时间 / 字节数 | 加上**逐个文件的 sha256**、表数与**真数出来的**行数、校验结论 |
| 谁做的 | 只有升级流程 | 升级 / 手动 / **定时任务**，同一个函数、同一套格式 |

换 `-Fc` 有三个实在的理由，第二个才是关键：它自带压缩、
**`pg_restore --list` 能在不恢复的前提下把目录读出来**（校验靠它）、
以及恢复时可以只挑一部分对象。代价是必须用 `pg_restore` 而不是 `psql` ——
两者都在 postgres 容器里，用户什么都不用装。

### 1.2 「没校验过的不算备份」

这是本轮最该单独说的一条设计。`backup::create` 的失败定义是：

```
转储没做成  →  失败
转储做成了，但 pg_restore --list 读不出目录  →  也算失败
```

理由不是洁癖：**一份「看起来在那儿、其实恢复不了」的备份比没有备份更糟** ——
它会让人在真出事的那一天才发现自己什么都没有。

卷没打成**不算整次失败**（数据库在就还有救），但会如实记进 `meta.json`
与界面上那一行 —— 「会话记录没备上」和「数据库没备上」是两件事。

### 1.3 行数是数出来的，不是估的

`meta.json` 里的「表数与行数概况」用的是 `count(*)`，不是
`pg_stat_user_tables.n_live_tup`。后者是统计收集器的估算值，
备份里写「1,234 行」而实际是 1,180 行 —— 那就是编数字（红线 1）。

代价是表很多时要跑一会儿，所以超过 40 张表就只报表数、并说明
「这个库有 N 张表，超过 40 张就不逐表数行了」。

### 1.4 定时：三平台各一套，一条 `sudo` 都没有

| 平台 | 机制 | 错过了会怎样 |
|---|---|---|
| macOS | 用户级 LaunchAgent（`~/Library/LaunchAgents/io.agentpit.hunter-backup.plist`，`StartCalendarInterval`） | launchd 在**唤醒之后补跑**（它自己的语义，不是我们做的） |
| Linux | `systemd --user` 定时器，**`Persistent=true`** | systemd 记着上次跑的时间，开机 / 唤醒后补跑 |
| Windows | 任务计划程序，**`StartWhenAvailable`** | 「错过后尽快运行」 |

三条路跑的都是同一条命令：`hunter-launcher --backup --scheduled`。

**三件不做的事**，写在 `schedule.rs` 的模块注释里：不要 root、不装系统级服务、
不替用户开 `loginctl enable-linger`（那是一条会改变系统行为的命令，我们只如实报告它的状态）。

「装没装」一律**现查系统**（`launchctl print` / `systemctl --user is-enabled` /
`schtasks /Query`），不读配置里的备忘 —— 配置说「开着」而系统里根本没装，
正是最需要被看见的那种情况。

设置页每改一次备份设置，**当场**把系统里的任务改成一致的样子
（`write_backup_settings` 里两件事在同一个命令里完成，不给它们分开的机会）。
装完 Hunter 也会挂一次（`flow.rs`），开机还会再对一遍（`lib.rs` 的开机自查）。

### 1.5 Hunter 停着的时候怎么办

方案 R6 6.3 写了三档，代码里逐条对应：

| 现场 | 做法 |
|---|---|
| 运行环境（Docker / 虚拟机）都没起 | **记为「跳过」**，写进 `[backup] last_run_at`，下次打开启动器时提示。**不擅自把整套服务拉起来** |
| 运行环境在跑、Hunter 停着 | 只把 postgres 临时 `up -d` 起来，做完**停回去** |
| 一切正常 | 直接做 |

「跳过」的退出码是 0 而不是 1 —— 它不是失败。报成失败会让
「连续两次失败交给诊断助手」误触发。

### 1.6 恢复：六步，第一步不是客套

```
先给当前数据做一份备份 → 停 api/opencode/web/llm-shim
  → pg_restore --clean --if-exists → 恢复密钥卷与 JWT_SECRET
  → 启动 → 等六个服务健康
```

第一步（保命备份）**做不成就停下来，什么都不改** —— 恢复是不可逆的，
而用户挑错一份备份是完全可能的。

`JWT_SECRET` 那一步**只动那一行**：备份里的 `.env` 还有 hunter key 与数据库口令，
那些都该保持这台机器的现状（数据库口令换了 api 就连不上库了，待办池 P1-29 那个坑）。

恢复前有一次**只读体检**（`preflight`）：逐个核 `meta.json` 里的 sha256、
看备份的 tag 是不是比这台机器上的新（是就拦下来先提示升级）、
看有哪些卷、是不是 0.1.12 的老格式（那一档走 `psql`）。

### 1.7 换电脑迁移

`--restore` 与界面上的「从别的目录选一份备份」都认**任意目录**：
把整个备份文件夹拷过去，在新机器的启动器里指给它看就行。
判据是「这个目录里有没有 `meta.json`」，不是「它在不在备份目录下」。

## 二、R4 · 删除应用

### 2.1 三步

| 步 | 界面上是什么 | 代码里是什么 |
|---|---|---|
| ① 选范围 | 两张卡片，**默认选中后果最轻的那一张** | `Scope::default() == AppOnly`，有单测 |
| ② 逐字输入 | 「删除应用」/「删除应用和数据」，差一个字按钮一直灰着 | `check_confirm`（Rust）+ `confirmOk`（前端），**两处都核** |
| ③ 执行并报告 | 逐条：删了什么、留了什么、腾出多少 | `Report` 里 `removed_* / kept / failures` 分开列 |

第二步为什么要两句不同的话：**后果不一样的两件事不该打同一句话**。
范围 ② 多打四个字是值得的。

### 2.2 两档各自删什么

| | ① 只删应用，保留数据（默认） | ② 删除应用和全部数据 |
|---|---|---|
| 容器与网络 | 删（`compose down --remove-orphans`，**不带 `-v`**） | 删 |
| 数据卷 | **全留** | 删（逐个核标签之后） |
| 镜像 | 可选 | 可选 |
| `~/.hunter/app/.env` | **留** | 删 |
| `launcher.toml` | **重写成只剩 `[backup]` 那一段** | 删 |
| 日志 / 遥测 / 诊断包 / 更新缓存 | 删 | 删 |
| 定时备份任务 | 移除 | 移除 |
| 备份目录 | **永远不删** | **永远不删** |

两处值得单说：

**为什么 ① 一定要留 `.env`。** 它里面有 `POSTGRES_PASSWORD` 与 `JWT_SECRET`。
删掉它、而数据卷还在 —— 那正是待办池 P1-29 记的那个死局：
卷里的库还认旧密码，api 迁移重试 31 次全是 `password authentication failed`，
而唯一的出路（删用户的数据卷）是守卫写死不许做的事。

**为什么 `launcher.toml` 不是整个删掉。** 用户改过的备份目录要是跟着没了，
重装之后就找不到自己那些备份了。所以是「重写成只剩备份设置」，有单测钉着。

### 2.3 内置运行时那个陷阱

macOS 上数据卷在 Colima 虚拟机的磁盘镜像里 —— **删虚拟机 = 删数据**。
所以「保留数据」的同时勾「顺便删掉运行环境」是一个自相矛盾的选择：

* `plan()` 把它标成 `runtime_blocked`（附带一句人话的原因）；
* 界面禁用那个勾选，并把原因**写在勾选旁边**，不是藏在 tooltip 里；
* `run()` **再拒一次** —— 界面有 bug 也不该把用户的数据删掉。

### 2.4 只动本项目：五道判据

| 要删的东西 | 凭什么确定它是我们的 |
|---|---|
| 容器 | `docker compose --project-name hunter down`（compose 自己只动这个项目） |
| 数据卷 | 每一个都先过 `guard::own_volume`：`com.docker.compose.project` 标签必须是 `hunter`，**查不到也不删**；再过 `argv_volume_rm` |
| 镜像 | 只删 `config::images()` 算出来的那几个引用，走 `argv_image_rm`（`prune` 一律拒绝） |
| 文件 | 只删 `~/.hunter`，删之前 `guard_root` 核一遍它不是根目录、不是家目录 |
| 运行环境 | 走 I7 就有的 `builtin::uninstall()`，只动 `~/.hunter/runtime` |

按名字前缀匹配是不行的：用户机器上完全可能有
`hunter-fresh_hunter_pg_data`、`hunter-community_hunter_pg_data`（测试机上就有），
按前缀删会把别人的数据一起删掉。

## 三、R7 · 硬盘、内存与服务异常

### 3.1 七类监测项

方案 R7 那张表逐行落地，**阈值一条都没写死在代码里**（全在 `[monitor]`）：

| # | 监测项 | 提醒 | 严重 | 一键处理 | 只给建议 |
|---|---|---|---|---|---|
| 1 | 系统盘剩余 | < 20 GB | < 5 GB | 清本项目旧镜像 / 悬空卷 / 过期备份 | 你自己的文件要不要清，由你决定 |
| 2 | 运行环境虚拟机磁盘 | > 80% | > 95% | 同上 | 扩盘（要停机，不可逆，得你点头） |
| 3 | 备份目录所在盘 | 放不下 3 份 | 放不下 1 份 | 清过期备份 | 换目录 / 减少保留天数 |
| 4 | 这台电脑的内存压力 | 黄 | 红 | — | 停 Hunter 能还回多少内存（**先说清它占了多少**） |
| 5 | 运行环境内存 | > 85% | — | — | 电脑有富余才建议调大虚拟机内存 |
| 6 | 服务反复重启 / 被 OOM 杀掉 | 窗口内 ≥ 3 次 | `OOMKilled` | — | 交给诊断助手读日志 |
| 7 | 数据库单日增长 | > 1 GB | — | — | 看备份 `meta.json` 里的逐表行数 |

### 3.2 「重启了几次」是差值，不是累计值

`docker inspect` 给的 `RestartCount` 是**累计值**。一台跑了半年的机器上它可能是 200，
而这半年里一次问题都没有。所以 `monitor.rs` 存了一个跨进程的状态文件
（`~/.hunter/monitor-state.json`），记 `(时间, 那一刻的计数)` 的采样，
窗口内的重启次数 = **窗口内最后一次的计数 − 第一次的计数**。

同一个文件还存「数据库每天的大小」（算单日增长）与「哪条提醒什么时候说过」
（「24 小时内不重复」靠它，启动器关掉再开不会把昨天说过的话重说一遍）。

### 3.3 一键处理：只有三件事，而且每一件都先问「有没有人在用它」

```
旧镜像   仓库名是 hunter-community-{web,api,opencode,llm-shim}
         而且 tag 不是现在这一版
         而且**没有任何容器在用它**（docker ps -a 的镜像清单里没有）
悬空卷   带本项目标签、但不在 compose 声明的那六个卷里
         而且没有容器挂着、而且标签是读到的不是猜的
过期备份 按 [backup] keep_days 轮换
```

`postgres` 与 `redis` 刻意**不在**清理名单里：它们是公共基础镜像，
这台机器上别的项目很可能也在用同一份。

**一条 `docker image prune` / `volume prune` 都不跑**：那两条会删到别人的东西。
测试机上同时跑着 `hunter-community`、两套 `hca-*` 和本项目，
一条 `prune -a` 能把另外三套一起清掉。

### 3.4 交给诊断助手的是什么

规则层判不了的那几条（为什么被 OOM、为什么反复重启、数据库为什么长得快）
才 `needs_ai = true`。点了之后送出去的是 `snapshot_for_ai()` 给的那几行：

```
时间 2026-09-23 10:12:40
这台电脑内存 3159478272/8319729664 字节
内存压力 正常（PSI avg10 0.0%）
系统盘 剩 76836319232/206900281344 字节
服务 api · CPU 0.5% · 内存 103000000 · 重启 204 · OOM false
提醒 restart-api · Warn · api 在反复重启
```

**只有数字与服务名**：没有路径、没有主机名、没有 key，发之前还要再过一遍出口闸。
这一层**不给工具表** —— 真能动手的三件事已经在规则层了，
剩下那些本来就不允许自动做，给了工具表只是多一条本不该有的动手通路。

## 四、守卫：三道新窄门

I13 要做的三件事，每一件都要用到通用守卫（`guard::argv`）**明确禁止**的东西：

| 要做的事 | 大名单为什么禁 | 这道窄门凭什么放 |
|---|---|---|
| 装 / 卸定时备份任务 | `FORBIDDEN_PATH_HINTS` 里有 `/Library/LaunchAgents` | `argv_schedule`：只认**我们自己那一个** Label / 单元名 / 任务名，参数逐字写死 |
| 删本项目的数据卷 | `FORBIDDEN_DOCKER` 里有 `volume rm` | `argv_volume_rm`：调用方必须先用 `own_volume` 逐个核过标签 |
| 删本项目的旧镜像 | `FORBIDDEN_DOCKER` 里有 `image prune` | `argv_image_rm`：只删按引用指名的，`prune` 一律拒 |

**三道门都不改大名单。** 模型走的永远是 `argv`，它照样拒绝这三类命令 ——
有一条单测（`三道窄门没有把大名单撬开`）专门钉这件事。

能走窄门的只有启动器自己那几处调用点，参数是代码拼的，模型碰不到。
这和 I8 给 `scutil --proxy` / Homebrew 安装脚本开窄门是同一条原则：
**禁令针对的是「谁能提出这条命令」，不是「这个程序名本身有罪」。**

### 5.1 单测

| | I12 收尾 | 本轮 |
|---|---|---|
| Rust | 591 | **648**（+57） |
| 前端（vitest） | 95 | **106**（+11） |

新增的 57 条 Rust 单测：

| 模块 | 条数 | 钉的是什么 |
|---|---|---|
| `backup` | 13 | 目录名按方案的格式、同一分钟的第二份不覆盖第一份；新旧两种命名都读得出日期；**0.1.12 的 `meta.json` 读得出来而且算成升级前备份**；轮换四条（按天保留最后一份、升级前备份单独留 2 份、认不出日期的一份都不删、保留天数被手改成 0 时也至少留一天）；版本比较（`1.10.0 > 1.9.0` 不能按字符串比）；校验只数真正的目录项不数注释；**建议的备份目录一定在工作目录之外**；删除守卫只认备份根下面那一层 |
| `schedule` | 9 | plist 里跑的就是那条无界面命令、`RunAtLoad` 必须是 false、改了时间内容真的会变、路径要转义 XML；**systemd 定时器必须是 `Persistent=true`**（没有它睡过 00:00 那一次就永远不补跑）、时间两位数补零、**路径带空格也解析得了**、不提权；**Windows 任务必须带 `StartWhenAvailable`**、XML 是 UTF-16 带 BOM；三个平台的路径都在用户自己的地盘里（`LaunchAgents` 不是 `LaunchDaemons`） |

### 5.2 实测当场撞出来的四个问题

这一节排在实测表前面，因为**它比那张表更有信息量**。四条里有一条是真的会伤到用户的。

#### ① 一键清理会把用户自己本地构建的同名镜像算成「我们的旧镜像」

第一版的判据是「仓库名**末一段**在那四个服务名里」。测试机上跑出来的清单是这样的：

```
旧镜像 14 个 · 13.3 GB
  ghcr.io/agentpit-io/hunter-community-api:1.1.0-i13test · 898 MB
  ghcr.io/agentpit-io/hunter-community-web:1.1.0 · 1.7 GB
  hkccr.ccs.tencentyun.com/agentpit/hunter-community-opencode:1.1.0 · 619 MB
  …
  hunter-community-api:dev · 898 MB        ← **这不是我们的**
  hunter-community-api:p2 · 898 MB         ← **这不是我们的**
  hunter-community-web:dev · 1.7 GB        ← **这不是我们的**
  hunter-community-web:p2 · 1.7 GB         ← **这不是我们的**
  hunter-community-llm-shim:dev · 74.2 MB  ← **这不是我们的**
  hunter-community-opencode:dev · 619 MB   ← **这不是我们的**
```

后面那六个是**这台机器上别人用 `docker build` 造出来的本地镜像**，
仓库名恰好也叫 `hunter-community-api` / `hunter-community-web`。
启动器从来没有拉过它们 —— 它拉的一律带镜像源前缀
（`ghcr.io/agentpit-io/…` 或 `hkccr.ccs.tencentyun.com/agentpit/…`）。

「有容器在用它就跳过」那一道没挡住：那几个 tag 当时确实没有容器在用
（在跑的是别的 tag）。**清单是在我按下 `-y` 之后才印出来的**，
中止得及时，一个都没删掉（事后逐个 `docker image inspect` 核过，
六个都在，`hunter-community` 与两套 `hca-*` 共 17 个容器全部 healthy）。

修法：判据从「末一段匹配」收紧成「**仓库必须完整地等于
`<我们自己的某个镜像源前缀>/<那四个名字之一>`**」，前缀取自
`registry::CANDIDATES` 再加上用户当前配置里那一个。
新增单测 `旧镜像_用户自己本地构建的同名镜像一个都不碰` 把这一条钉死，
另加一条 `旧镜像_仓库集合是空的时候一个都不删`（配置读不出来时宁可什么都不清）。

**这一条值得单独记一笔**：守卫那三道门（`argv_image_rm` 只认指名道姓、
不认 `prune`）**全部生效了** —— 它们拦的是「命令的形状」。
而这一次错的是**上游那张清单本身**：拼进命令里的镜像名是错的，
形状再对也没用。「只删我们自己的东西」这句话，光靠命令层的守卫守不住，
还得有一道「这东西凭什么算我们的」的判据。

#### ② `--uninstall-plan all` 里那个 `all` 谁都没接住

两次输出一模一样才看出来 —— 范围默默落回默认的「只删应用」。
根子是 `--uninstall-plan` 被塞进了那张「不带参数的动作」表里，
而 `--uninstall` 在另一个分支里是带参数的。
修完补了一条单测（`删除应用的范围词要被接住`），顺带把 `--backup` / `--restore` /
`--schedule` 的开关也一并钉住。

**只影响命令行**：界面那一侧是 `uninstall_plan(scope, deep)` 显式传的。

#### ③ `docker restart` 不算「重启」

验收脚本第一版用 `docker restart hunter-llm-shim-1` 造「反复重启」的现场，
连跑四次之后 `RestartCount` 还是 **0**：

```
重启前的 RestartCount  0
  第 1 次重启后 RestartCount=0
  第 2 次重启后 RestartCount=0
```

`RestartCount` 只数**重启策略把它重新拉起来**的次数，手工重启一次都不算。
换成让容器真的崩（覆盖文件里给 llm-shim 塞一个 `entrypoint: ["sh","-c","exit 1"]`，
`restart: unless-stopped` 会把它一遍遍拉起来）之后才造得出这个现场。

**这是验收脚本的毛病，不是产品的**。记在这里是因为它说明一件事：
造现场和写判据一样容易造错，而造错的现场会让一条**本来是对的**规则看起来是坏的。

#### ④ 「库里 60 张表，合计 0 行」

表数超过上限（第一版是 40）时 `rows_total` 是 `None`，而打印那一行写的是
`m.rows_total.unwrap_or(0)` —— 屏幕上就成了「合计 0 行」。
**没数过却印了一个数**，正是红线 1 禁止的事。

两处一起改：上限从 40 提到 **80**（这套库实查是 60 张表，40 这个数让
`meta.json` 里的 `tables` 永远是空的 —— 这一项做了等于没做），
以及没数过时如实写「表太多，没有逐表数行」（命令行与界面各一处）。

#### `r6-persistent`：为什么只能近似造

`Persistent=true` 的语义是「**开机 / 用户 manager 重新起来时**，发现上一次该跑的时间
已经过去了就补跑」。而 systemd 把「上次什么时候触发过」同时记在两个地方：
盘上的 stamp 文件，**和自己进程的内存里**。

第一遍的做法是 `stop → 删 stamp → start`，不管用 —— `list-timers` 的 `LAST`
仍然是上一次真实触发的 11:18:26。第二遍改成另起一个**从来没触发过**的一次性单元，
也不管用：没有 stamp 的定时器 systemd 根本不会替它补跑（否则每装一个每日定时器
都会当场跑一次）。

第三遍才对：用启动器生成的那两份单元的**原文**另起一次性单元，
再**手工造一个 mtime 是昨天 00:00 的 stamp 文件** —— 这正是
「昨天跑过、今天 00:00 那一次错过了」的现场。`systemctl --user start` 之后
**立刻补跑**（11:54:19 触发，备份 6 → 7 份）。

真正走「重启机器」那条路在这台机器上做不了：它上面还跑着另外三套项目
（`hunter-community` 与两套 `hca-*`），总控规则红线 9 不许动它们。
**这一条如实记「近似造」**：`Persistent=true` 那一行本身有单测钉着，
补跑的行为是用同一份单元原文在真 systemd 上验的，但**不是从一次真实的关机里走出来的**。

**截图时当场改掉的两处（这两处只有看图才看得出来）：**

1. **禁用的勾选看不出是禁用的。** 「顺便删掉运行环境」在范围 ① 下点不动，
   但视觉上和能点的那一个一模一样 —— 用户只会觉得「我点了怎么没反应」，

2. **「备份与恢复」那一页的右卡被挤出屏幕。** systemd 那句
   「下次什么时候跑」很长且不含空格，而栅格子项的 `min-width` 默认是 `auto`

## 六、偏离方案的决策

| # | 方案写的 | 实际做的 | 为什么 |
|---|---|---|---|
| 1 | R6 6.2「备份目录名 `hunter-<YYYYMMDD-HHmm>-v<tag>`」 | 照做，但**同一分钟内的第二份加 `-2`** | 方案给的格式只到分钟，而「升级前备份 + 紧接着的手动备份」完全可能落在同一分钟里。不加后缀就是覆盖掉前一份 |
| 2 | R6 6.3 / R7「托盘通知」 | **托盘 tooltip + 一个托盘菜单项**，不是系统级弹窗 | 两条理由：① **能验** —— 本项目唯一的真机跑在 Xvfb 下，没有任何通知守护进程，系统弹窗在那台机器上既弹不出来也截不了图，做了只能在报告里写「未验证」；② 和「启动器有新版本」那一条（M4 起就是这么做的）保持同一套做法。详见 `tray::note_alert` 的注释 |
| 3 | R6 6.1「保留份数：最近 3 天」 | 加了一条 `keep_days_clamped()`（收进 1–30） | 配置文件是让人改的，手改成 0 的时候不能真的一份都不留 |
| 4 | R7「数据库体积增长异常 → 给出占用最大的几张表」 | 提醒里只说「去看备份的 `meta.json`」，**没有当场去数** | 「占用最大的几张表」要么用 `pg_total_relation_size`（那是磁盘占用，和「增长」不是一回事），要么重数一遍行数（大库上要跑很久）。而**每一份备份的 `meta.json` 里本来就有逐表行数** —— 指过去比当场再数一遍诚实，也便宜 |
| 5 | R4「删除应用 ① 删除：容器、镜像、**启动器配置**」 | `launcher.toml` **不是整个删掉**，重写成只剩 `[backup]` 那一段 | 用户改过的备份目录要是跟着没了，重装之后就找不到自己那些备份了。有单测 |
| 6 | 方案没提 | `.env` 在范围 ① 下**必须留** | 它里面有 `POSTGRES_PASSWORD`。删掉它而数据卷还在，正是待办池 P1-29 那个死局：卷里的库还认旧密码，api 永远起不来，而唯一的出路是删用户的数据卷 —— 守卫写死不许做的事 |
| 7 | R7 表里「系统盘剩余 < 5GB → 列出可安全释放的空间」 | 同时列，但**「构造盘剩余不足」这个现场是靠把阈值调到实测值之上造出来的** | 测试机的系统盘有 72 GB 空闲，真把它填到 5 GB 以下会波及同机另外三套项目。阈值本来就是 `[monitor]` 里的配置项，调它造出的现场里**每一个数字仍然是实测的** |
| 8 | 方案第四节 `[monitor]` 五项 | 多了六项（`vm_disk_crit_pct` / `restart_warn_count` / `restart_window_min` / `db_growth_warn_gb` / `backup_disk_min_copies` / `quiet_hours`） | R7 那张表里的阈值比第四节列的多。「一条都不写死在代码里」是这一轮自己定的规矩 |

## 七、没做的 / 未验证的

* **macOS 的 LaunchAgent 与 Windows 的任务计划没有真机验证。** 本项目只有一台 Linux 测试机。
  这两条路上写全了代码与单测（plist / 任务 XML 的每个字段逐条断言、守卫白名单逐条断言），
  但 `launchctl bootout/bootstrap` 与 `schtasks /Create /XML` **一次都没有在真机上跑过**。
  等用户在自己的 Mac 上跑 0.1.13，本地 Claude 查两样东西：
  `launchctl print gui/<uid>/io.agentpit.hunter-backup` 与
  `~/.hunter/logs/backup-schedule.log`。已进待办池（P1-37）。

* **`monitor::runtime()` 那一层仍然没在真虚拟机里跑过**（I12 就记着的 P1-33）。
  R7 里「运行环境磁盘 / 内存」两条规则因此**在这台机器上一次都没被触发过** ——
  `applicable()` 恒为假，走的是「不适用 + 说明原因」那一支。

* **「同一问题 24 小时内不重复」只验了一半。** 实测能验的是「紧接着再跑一次，
  `notify` 里没有它」；**跨 24 小时那一半没验** —— 那要么等一天，要么改测试机的系统时间，
  而后者会波及同机另外三套容器的证书与日志时间戳。判据本身（一行算术）有单测。
  已进待办池（P1-38）。

* **备份失败那一档只造了「盘满」这一个现场。** R6 6.3 列了三个常见原因
  （盘空间不足、外接盘未连接、权限）。本轮用一个 12 MB 的 loop 设备把第一个真验了，
  另外两个只有代码路径 —— 三条路的错误文案来自同一个 `map_err`。已进待办池（P1-39）。

* **R7 的「系统盘剩余不足」是靠调阈值造出来的现场**（见第六节第 7 条）。
  测试机系统盘有 70 多 GB 空闲，真把它填到 5 GB 以下会波及同机另外三套项目。
  调的是 `[monitor]` 里的配置项，**提醒里每一个数字仍然是实测的**。

* **`E_DATA_DOWNGRADE` 那一档的「从备份恢复」入口还是没做**（I12 留下的 P1-32）。
  I13 之后前提成立了（备份里真的有 `secrets.tar.gz`），`datacheck` 也开始数
  「有几份备份带着密钥卷」并在结论里说出来 —— 但界面上还是一句话 + 一个「继续」，
  不是两个可点的选项。理由与做法写在待办池 P1-37 那一条的隔壁（P1-32 已更新）。

* **系统级弹窗通知没做**（见第六节第 2 条）。这一版是托盘 tooltip + 托盘菜单项。

* **`cleanup::plan()` 在容器多的机器上不便宜**：「哪些卷有容器挂着」只能逐个容器
  `docker inspect`（`docker ps --filter volume=` 没有这个形状），测试机上二十几个容器
  就是二十几个子进程。本轮给它加了 5 分钟缓存（后台轮询走缓存、用户点「看看能腾出多少」
  走真值），够用但不优雅。已进待办池（P1-40）。

* **`assist::probe::human_bytes` 按 1024 进位却写成 `KB/MB/GB`**（I12 记的 P1-36）本轮没动。

### 等用户在 Mac 上跑 0.1.13，重点看五件事

1. **打开启动器之后，设置页「数据备份」那一节里「定时任务」写的是什么。**
