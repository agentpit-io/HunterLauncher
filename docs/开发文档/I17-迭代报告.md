## 零、一句话

客户那台 Windows 上，「打开页面是空白」其实是浏览器连不上 `localhost:3100`；
而启动器顶着绿点说「Hunter 运行中 · 已运行 1 小时 3 分」，还给了一个点过去打不开的
「打开 Hunter」。**三件事叠在一起**：面板的「在跑」是从「有一个容器活着」猜的（P0-1）、
那个活着的容器是备份流程留下的孤儿 postgres（P0-2）、而真的中间态
（配置已 1.2.3、镜像不齐、六个容器全停）恰好落在中断卡片看不见的那一格（P0-3）。
把他弄成这个样子的那一次点击是「正在拉取新版本的镜像…」时点了应用退出（P0-4）。

| | 0.1.17 | I17 之后 |
|---|---|---|
| **P0-1** 面板说「运行中」 | `any(state == "running")` —— 一个 postgres 活着就点亮大标题；时长读**已退出**容器的 `StartedAt`；地址跟着一起给 | `running` = web 在跑 **且本机 HTTP 探得通**；时长只在 web 真在跑时才有；地址只在探得通时才有。三样一起收紧 |
| **P0-2** 备份留孤儿 postgres | 备份会临时 `up -d postgres`，**从来不停回去**（注释承诺的 R6 6.3 从没落地） | `PostgresLease`：谁起谁收拾，靠 `Drop`，不是靠人记得接返回值 |
| **P0-3** 中断卡片静默 | 判据要「有容器在跑才读得出跑着的是哪一版」——**全停正是它看不见的那一格** | 判据换成 `.env` 的 `HUNTER_VERSION` vs `launcher.toml` 的 `hunter.tag` + 「配置那一版镜像齐不齐」，**与容器无关** |
| **P0-4** 升级中退出 | 静默退出，进程一死回滚不跑 —— 中间态就是这么来的 | 升级改完配置到收尾之间退出**先拦一下**（三条入口同一判定点）；**常规退出一个提示都没有** |
| **U1–U4** 界面 | 启动/停止/检查更新埋在卡片底部一堆 `size="sm"` 里，要滚动才看得见；退出要问「保持后台/一起停止」；镜像源叫「腾讯云 · 香港」 | 首页一级按钮（46px 同层高）；退出＝关窗口、不停容器、不问（**升级中那一次除外**）；显示名改「中国国内云服务」 |

发布那一环的诱因也补了一道自查：`scripts/verify-mirrors.sh`（两源 × 四镜像 × 指定 tag），
以及升级**改写配置之前**先探一次 manifest 的前置体检。

## 一、P0-1 · 「有一个容器活着」不等于「能用」

### 1.1 现场

客户第一张截图上是自相矛盾的一屏：标题「Hunter 运行中」、副行「v1.2.2 · 已运行 1 小时 3 分 ·
http://localhost:3100」，而服务行里 **只有 postgres 有内存（46 MB）**，web / api / opencode /
llm-shim / redis 全是 0 B；第二张截图是浏览器 `localhost:3100` → `ERR_CONNECTION_REFUSED`。

时长可以反推：`已运行 1 小时 3 分` 读的是 **web 容器最后一次启动**，
`container_uptime()` 读 `docker inspect hunter-web-1` 的 `.State.StartedAt` ——
**容器 exited 之后这个字段依然保留**，于是退出了一小时的容器还在贡献「运行中 X 分钟」。

### 1.2 改法：三样一起收紧，判据收进一个纯函数

`RuntimeStatus` 新增 `posture` 与 `web_ok`；`runtime_status` 里多一次**本机浅探**
`http://127.0.0.1:{web_port}/`（超时 2 秒，比 `selfcheck` 那 6 秒短 —— 面板是首屏路径）。
三条结论各自收紧：

| 字段 | 0.1.17 | 现在 |
|---|---|---|
| `running` | `services.iter().any(\|s\| s.state == "running")` | `running_now(posture, web_ok)`：**探不通就当没在跑** |
| `uptime_seconds` | 读 web 的 `StartedAt`（已退出也读） | **只在 web 容器 `running` 时**才给值，否则 `None` |
| `web_url` | `if running { Some(…) }` | **只在 `web_ok` 时**给 |

判据抽成纯函数（`flow::running_now`）：

```rust
pub fn running_now(posture: crate::selfcheck::Posture, web_ok: bool) -> bool {
    use crate::selfcheck::Posture::*;
    match posture {
        Healthy | Partial => web_ok,
        Stopped | RuntimeDown | Absent | Incomplete => false,
    }
}
```

**宁严不宽**：探不通却说「没在跑」，用户白点一次启动；说「在跑」却打不开，
用户拿到的是一个打不开的页面 —— 后者才是这次投诉的事。

前端跟着走（`Dashboard.tsx`）：

* 标题四档 —— `Healthy` → 「Hunter 运行中」；`Partial` → 「Hunter 运行中 · 有服务不正常」；
  `Stopped` / `RuntimeDown` → 「Hunter 已停止」；`Absent` / `Incomplete` → 「还没有装好」。
  **「在不在跑」认 `running`，「为什么不正常」才认 `posture`** —— 只 postgres 活着时
  `selfcheck` 给的是 `Partial`，纯按 posture 会写成「运行中 · 有服务不正常」，而 A1-1 要的是
  「Hunter 已停止」（网页打不开的时候说「运行中」正是客户被误导的那一句）。
* 副行只在健康时给「v… · 时长 · 地址」；`uptimeSeconds === null` 时**不显示这一截**
  （写 `?? 0` 会把「读不到」变成「已运行 0 秒」，那是编的）。
* 「打开 Hunter」按钮 `webUrl` 为空时**根本不出现**（不是变灰）——
  留一个灰按钮在那儿仍然在暗示「这里本该能点」。

### 1.3 验收（现场造景，见第七节 A1-1 / A1-3）

```
A1-1  docker compose stop web api opencode llm-shim redis（只留 postgres）
      PANEL running=false · posture=Partial · web_ok=false · web_url=None · uptime_seconds=None
      BOOT  headline=Hunter 没跑起来：web、api、opencode、llm-shim、redis 停着（需要启动）、网页打不开
A1-3  六个容器全停（客户 10:44 的现场）
      PANEL running=false · posture=Stopped · web_url=None · uptime_seconds=None
```

`selfcheck` 那句开机判定也一起改了（原来写的是「Hunter 在跑，但…」，而网页一个字节都回不来）；
新增单测 `selfcheck::tests::网页打不开时不说在跑`，正反两向都钉。

## 二、P0-2 · 备份把 postgres 留成孤儿

### 2.1 现场与根因

`backup.rs` 里 `ensure_postgres_up` 的注释写得很清楚：

```rust
/// 返回「这次是不是我们起的」—— 定时备份在 Hunter 已停止时要**做完再停回去**
/// （方案 R6 6.3），靠的就是这个返回值。
pub fn ensure_postgres_up(note: &mut impl FnMut(&str)) -> AppResult<bool> { ... }
```

而**两个调用方都把返回值丢了**（`dump_db` 与 `restore`），全仓没有任何地方停回去 ——
注释承诺的 R6 6.3 从未实现。备份是无需界面、无人看的流程（`--backup --missed` 子进程），
所以这条路径错了半年也不会有人报。客户日志里 09:44:53、09:45:31、10:13:02 三次备份之后的现场，
都是「postgres 在跑、其余全停」。

### 2.2 改法：把「谁起的谁收拾」变成一个不能忘的结构

新增 `struct PostgresLease { we_started, released }`：

* `PostgresLease::acquire(note)` → 内部调 `ensure_postgres_up`，把返回值存进 `we_started`；
* `fn disarm(self)` → 显式「不停回去」（`restore` 用，它后面紧接着 `compose::up()`）；
* `impl Drop` → 若 `we_started && !released`，`guard_project_owner()` 之后
  `compose stop postgres`，并在启动器日志里写一行「备份时临时起的 postgres 已停回去」。

`dump_db(out, note, lease: &PostgresLease)` 改为**收租约**而不是自己 `ensure` ——
拿不到租约就调不出这个函数（类型层面挡住「忘记接返回值」这件事）。
`create` 入口 acquire 一次，成功失败都靠 `Drop` 收拾；`restore` 在 `compose::up()` 前 `disarm()`。
**不做分叉**：`Kind::PreUpgrade` 也走同一条规则（少一个开关，少一类分叉）。

### 2.3 验收（A2-1 / A2-3）

```
A2-1  停止状态备份一次
      备份输出：备份前 Hunter 是停着的，现在把临时起来的 postgres 停回去
      日志：    备份时临时起的 postgres 已停回去（Hunter 本来就没在跑）
      之后 docker compose ps -a → 六个全 exited  ✓（不留孤儿 postgres）
A2-3  6/6 健康时备份一次 → 六个仍全 running，面板仍是「运行中」（lease 是空动作）✓
```

## 三、P0-3 · 中断卡片在自己最该出现的场景里沉默

### 3.1 根因：判据要求「必须有容器在跑」

```rust
// 0.1.17 · upgrade.rs
if config_tag.is_empty() || running_tags.is_empty() || missing_images.is_empty() {
    return None;   // ← 全停时 running_tags 为空，直接判成「没有中间态」
}
```

`running_tags` 来自 `docker compose ps` 里 `state == "running"` 的容器 ——
**它要读「跑着的是哪一版」，就必须有容器在跑**。全停正是最需要这张卡片的状态，
恰好也是它看不见的状态。客户那台于是被面板判成「装好了，点『启动』就能用」，
而点下去只会再卡一次拉取。

### 3.2 改法：换一个与容器无关的判据

启动器里已经躺着两个天然对不上的字段：

| 字段 | 是什么 | 什么时候写 |
|---|---|---|
| `.env` 的 `HUNTER_VERSION` | **配置意图的版本** | 升级第 ③ 步就写，**在拉取之前** |
| `launcher.toml` 的 `hunter.tag` | **上一次真正成功的版本** | 只有整轮升级成功后才写 |

新的 `judge_interrupted(config_tag, last_good_tag, running_tags, missing_images)` 三条缺一不可：

1. `config_tag` 非空；
2. **`missing_images` 非空** —— 这一条是**防误报的主防线**（每一台正常机器每次开机都会走到这里，
   误报会天天弹一个吓人的问句）；镜像齐了直接 `up -d` 就完事，那不是一个需要打断用户的现场；
3. 配置版 ≠ 上一次成功的版本，**且**跑着的（如果有）也不是配置那一版。

`running_tags` 退居**只影响文案与出路**：有容器在跑就回它那一版，一个都没跑就回 `last_good_tag`。
`Interrupted` 新增 `last_good_tag`，`running_tag` 变成 `Option<String>`；全停时的 headline
与「回退到 vX」的措辞都另起一档（全停时说「回退到正在跑的 vX」是假话）。

`selfcheck` 的 `Stopped` 分支同步加了一道「配置那一版镜像齐不齐」：

```
有缺镜：Hunter 装好了，但 v1.2.2 的镜像本机还缺 4 个 —— 先补齐再启动，别急着点「启动」
        · 但配置那一版 v1.2.2 的镜像本机还缺 4 个：web、api、opencode、llm-shim
        · 所以现在点「启动」会先去拉这几个镜像 —— 上一次升级多半就是卡在这一步。
```

另外 `catch_up_config_tag`（`flow::start` 里）补了 A3-4 那一档：配置超前 + 镜像齐 ⇒
起来之后把 `hunter.tag` 补齐（**缺镜就一个字都不改** —— 那正是中间态，该由卡片去问人）。

### 3.3 验收（A3-1 / A3-2 / A3-3 / A3-4 / A3-5）

五条全过，原始输出见 `I17-证据/现场造景-全场景.log`。其中 A3-1 的现场**不是手摆的**：
起一次真的 `--upgrade`，等它写完配置、正在拉镜像时**把进程组强杀掉** ——
这就是客户 10:38 那一次点击的位置（脚本里 `scene_interrupted()` 有注释说明为什么不能用 `sed` 摆：
手改 `.env` 能造出「配置超前」，但**没有升级前那份备份**，而 A3-3 的回退正是从它里面写回去的）。

| 用例 | 结果 |
|---|---|
| A3-1 | 出卡片；`config_tag=1.2.2` / `running_tag=None` / `last_good_tag=1.2.0` / 列出 4 个缺镜；**不出现**「点『启动』就能用」 |
| A3-2 | `--upgrade 1.2.2` 真拉真起（六个镜像合计约 881 MB、实下 483 MB）→ `hunter.tag=1.2.2`、卡片消失、面板「运行中」 |
| A3-3 | 从同一个现场点回退 → `.env` 回到 1.2.0（从 `hunter-…-v1.2.0` 那份升级前备份写回）、卡片消失 |
| A3-4 | 配置超前但镜像齐、全停 → **不出卡片**（主防线生效）；`--start` 能起来、面板「运行中」 |
| A3-5 | 容器跑在 1.2.0 上、配置超前、1.2.2 镜像摘掉 → 卡片照旧出现，`running_tag=Some("1.2.0")` |

**A3-4 有一条边界要写清楚**（`case_a34` 的输出里也原样打了出来）：
「起来之后补齐 `hunter.tag`」的执行点是 `flow::start`（界面上的「启动服务」按钮走的就是它），
而命令行 `--start` 与托盘「启动」走的是 `compose::up()`，**不经过它**，所以补不上。
**本机没有跑 `flow::start`** —— 它会顺带调 `schedule::sync()`，在这台机器上会真去写
`~/.config/systemd/user/hunter-backup.{service,timer}` 并 `systemctl --user daemon-reload`，
违反总控规则红线 3（不动 systemd）。所以「界面上点一次启动服务能不能补齐」进未验证清单（第十节）。

## 四、P0-4 · 升级进行中的退出拦截

### 4.1 客户的中间态不是「拉取失败」留下的

0.1.17 有「取消升级」而且取消会走完整回滚，但他点的是**应用退出** ——
那条路上没有任何拦截，进程一死回滚不会跑。日志里 10:38:12–10:38:41 只有「写配置 → 拉镜像 →
国内源 not found → 切 GHCR」，**没有任何「拉取完成」记录**，然后就重启了。

### 4.2 改法：三条入口，一个判定点，只有一个窗口会说话

* `AppState` 新增 `upgrade_armed: Mutex<Option<String>>`；
  `do_upgrade` 在**写完 `.env` 与 compose 之后**（第 ③ 步）`arm_upgrade(target)`，
  三个分支（成功 / 取消回滚 / 失败回滚）走完在**同一处** `disarm_upgrade()` ——
  回滚本身也是改配置，回滚到一半被退掉同样会留下说不清的现场。
* 纯判据 `upgrade::quit_guard(armed_tag) -> Option<QuitGuard>`：
  没有升级在跑 → `None`（**A4-6 的判据层**）；升级中 → `Some`，句子里带上是哪一版。
* `commands::request_quit` 是**三条退出入口唯一的判定点**：右上角红点（`window_close` →
  `CloseRequested` → `request_quit`）、托盘「退出」、面板上的「退出启动器」。
  判据为 `None` 就 `exit_now`（**容器一个都不动**）；为 `Some` 就把窗口叫到前面并发事件。
* 前端 `UpgradeQuitGuard`（`App.tsx`）收到事件才弹，两个动作：
  **继续退出**（`quitApp(true)` 绕过后端那道判定）与
  **取消升级并回滚后再退出**（置 `state.cancel`，等升级线程把配置写回去再退，兜底 420 秒）。

### 4.3 与 U2 的张力（方案 §8 风险 9）

U2 要的是「退出不要再提醒用户选择」；P0-4 要的是「升级拉取中退出提醒一句」。
本轮按方案的建议**只在这一个窗口里提示**，A4-6 专门防回归：非升级状态一律不弹。

### 4.4 验收

```
A4-6  非升级状态：  QUIT_GUARD armed=None · guard=None  → 直接退出，不弹任何提示  ✓
      （对照）quit_guard 的两条单测都过：升级中给一句话并带上版本；没有升级在跑时不弹
A4-5  未验证 —— 见第十节（要 GUI 上在拉取途中点一次退出）
```

## 五、U1–U4 · 用户 2026-09-29 提的四条界面需求

> 用户原话：*「1）启动和关闭 服务 在首页有明显大按钮；2）关闭应用 需要有个明显按钮，
> 关闭应用，默认不关闭服务，不要再提醒用户选择；3）检查更新和升级，需要在首页也明细一级按钮…
> 4）部署镜像源选择 腾讯云香港，名称修改为中国国内云服务。并完成测试后，发布」*

### 5.1 U1 / U3 · 首页一级按钮

头部标题区右侧是一组**同一视觉层高**的按钮（`h-[46px] px-6 text-lg`，与原来那个
「打开 Hunter」一模一样）：

```
[停止服务]  或  [启动服务]        ← 主色，一次只出现一个（两个方向相反的按钮并排会让用户点错）
[重启]
[检查更新 · v1.2.4] 或 [检查更新]  ← 查到 Hunter 有新版本时按钮本身变强调态并带上版本号
[打开 Hunter]                     ← 只在 webUrl 有值（＝网页真能打开）时出现
   退出后 Hunter 继续在后台运行，下次打开还在      [退出启动器]
   想让它不再占内存，用旁边的「停止服务」，不是退出启动器。
```

日志 / 备份 / 反馈 / 上传日志 / 更多 **留在下方次要区，语义一个都没动**；
起停 / 重启 / 检查更新 不再在下面重复放一遍（同一件事两个入口、其中一个还要滚动才看得见，
正是用户提的那条问题）。`runtimeDown` 时启动按钮文案沿用 `t.dashboard.runtimeDownStart`（「启动运行时」），没新造词。

**新增的那两行小字**是「不再询问」的代价换来的知情（方案 §8 风险 3）；
第二行原本只有文案（`t.quit.stopHint`）没接上界面，本轮补上并删掉了重复的 `dashboard.quitHint`。

### 5.2 U2 · 退出＝关窗口

* `quit_app` 的 `stop_containers` 参数**整个删掉**了 —— 不是「传 false」，是**没有地方能传 true**
  （少一个开关就少一类「有时问、有时不问」）；
* 右上角红点、托盘「退出」、面板按钮三条入口走同一个 `request_quit`；

（注释也算），而那个字**永远不会上屏**。所以没有为一句注释去重跑字体子集（那会让子集白长一个字），
把注释改成「它**盖**在运行面板上」就绿了。**顺带说明这条检查的口径**：它宁可从严（注释也算），
触发时先看一眼那个字到底会不会上屏，再决定是改字还是重跑子集 —— 别把「注释里的生僻字」
当成「界面上要出豆腐块」。

### 9.3 这一轮自己发现并修掉的两处「做了一半」

* **两个演示页没登记**（`dashboard-interrupted-stopped` / `update-no-tag`，外加 `quit-guard`）——
  `check-shots.sh` 抓出来的（截图和开机屏一模一样）。见第八节 8.2。
* **`i17-verify.sh` 有三处「照原样跑不出正确的现场」**（见第七节末）：手改 `.env` 造中间态没有升级前备份、
  `docker rmi` 不带 `-f` 删不掉镜像、`all` 的顺序会让 A3-4 拿不到镜像。三处都改了，而且每条场景现在都能单独跑。

### 9.4 没查出来的那一个

**演示模式自动打开前置体检弹窗没做成**（8.3）：试了两种写法都不弹，用「把 `demoPage()` 与 `DEMO` 渲染进页面标题」

## 十一、没做的、要用户拍板的

### 11.1 国内源同步（方案 §4.2① 的另一半）

**本轮的产出只有「发现并拦一下」**：`scripts/verify-mirrors.sh`（缺了就非零退出）
+ 写进发布清单「两源齐了才算这次发布完成」。**同步本身没做**，用户 2026-09-29 已明确
「由其它链路负责」。所以：

* 这次实测国内源上 **1.2.3 四个镜像仍全 404**（2026-09-29 13:20 上海时间）；
* 结构性原因没变：同步是每 6 小时的定时作业，而**升级按钮在 Release 出现那一刻就亮了** ——
  即使窗口缩到 1 小时，客户那 8 分钟照样会撞。要根治得在发布侧做「镜像先就位、再点亮升级入口」，
  那是发布流程改造，不在本轮。

### 11.2 托盘「启动」与命令行 `--start` 不补 `hunter.tag`

这两条走的是 `compose::up()`，不经过 `flow::start`，所以 A3-4 那个「起来之后补齐版本记录」
在它们上面不生效 —— 后果是：**用托盘启动**一台「配置超前 + 镜像齐」的机器，
面板会显示一个比实际旧的版本号（跑着的其实是新版本），而中断卡片（正确地）不出现。

本轮**没有动它**，理由：在没有「等健康」的前提下补记录＝在不知道有没有真起来的情况下改记账，
那是猜（红线 1）。正确的改法是让托盘那条路也走 `flow::start`（它已经在后台线程上，
等 180 秒不会冻界面），但那会顺带把 `schedule::sync()` 拉进托盘路径 —— 属于行为扩大，
不在本轮方案的文件清单里。**建议下一轮做，并配一条 A3-4 的 GUI 验收。**

### 11.3 「界面文案里没有 Markdown 渲染器」这条检查只覆盖 i18n 字典

这一轮顺手去掉了 `quit_guard` 弹窗正文里的两个反引号（`\.env\`` → `.env`，同 P0-3 那次
「四个星号」的道理），也在 `demo.ts` 里同步改了。但**全仓还有 95 处 Rust 字符串字面量里
带 `**` 或反引号**，其中一部分会直接上屏（错误卡片、助手提示）。

`i18n.test.ts` 那条「文案里不许出现渲染不出来的标记」只扫 `src/i18n/` 两份字典，
**扫不到 Rust 侧**。要收口得写一条类似 `check-wording.py` 的检查（复用 `rust_strings.py` 的

### 12.2 下一轮开工前要知道的

1. **本机 `src-tauri/target/release/hunter-launcher` 现在是「演示态」产物** ——
   截图脚本要的是 `VITE_DEMO=1 tauri build --no-bundle`，而 `i17-verify.sh` 要的是不带演示数据的
   那个。两者**共用同一个路径**，切换时记得重新构建（`cargo build --release` 那一条**不能用**来出图：
   没有 `custom-protocol` 特性时产物会去连 devUrl，窗口一片白 —— M1 踩过）；
2. **本机那套 `hunter` 测试栈的 `.env` 里有一把占位 key**（`HUNTER_API_KEY=hunt_tools_i17…`）。
   脚手架 `examples/i17_make_stack.rs` 当初写的是空 key，而升级路径 `rewrite_env_and_override`
   **没有 key 就拒绝写 `.env`**（那是刻意的安全行为）—— 于是 A3-2 那种「真升级」在本机跑不起来。
   **这不是产品缺陷，是脚手架没造全一台机器的样子**；下一轮造景时直接用现在这份 `.env`；
3. **本机的 `flow::start` 不能随便跑**（它会 `schedule::sync()` → 在这台机器上会真写
   `~/.config/systemd/user/` 下的定时器 + `systemctl --user daemon-reload`，违反红线 3）。
   凡是验收要经过 `flow::start` 的，先在脚本里把 `backup.enabled` 关掉或改用别的路径，
   别默认「跑一下没关系」；
4. **`scripts/i17-verify.sh` 的 `TAG` / `AHEAD` 是本机镜像决定的**（默认 `1.2.0` / `1.2.2`）。
   换机器要把它设成「本机有镜像的那一版」与「本机没有、但 GHCR 上有的一版」；
5. 本轮**没有发布**：不 bump 版本号、不打 tag、不建 Release、不上架。
   `feat/i17` 合并进 `main` + CI 四绿就是本轮的终点。

### 12.3 这一轮最值得记住的一句

**「有一个东西活着」不是「这个东西能用」，「程序退出了」不是「这件事结束了」。**

P0-1 说的是前者：一个孤儿 postgres 点亮了整块面板，而用户点过去是
`ERR_CONNECTION_REFUSED`。P0-2 与 P0-4 说的是后者：备份跑完了但那一次操作没结束
（postgres 还开着），用户退出了但那次升级没结束（中间态留在了机器上）。

这四条 P0 和 I16 那三条是同一种病：**不是「功能没做」，是「做了，但状态说的不是真的」**——
只不过 I16 是「没说出来」，这一轮是「说错了」。而它们能被发现，
靠的都是**用户本机那份日志里的一条原始读数**（`docker compose ps` 六个 `exited`、
服务行里五个 0 B）—— 不是我们的自动化测试。
