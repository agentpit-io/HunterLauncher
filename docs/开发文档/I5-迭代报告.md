## 零、一句话

用户在自己的 Mac 上装 0.1.4，启动那一步报「port is already allocated」。
本轮先修掉造成它的确定性缺陷（**端口探测在 macOS 上把被占死的端口判成了空闲**），
再把整个安装从「出错了给你看诊断面板」改成「一次授权，AI 自己干完，过程实时直播」。

测试机上七个场景全部按「授权后零点击」验收：
**GUI 真机实测，从点下「授权 AI 自动安装」到六个服务健康，54–94 秒，中间 0 次点击。**

macOS 真机**没有验证**（测试机是 Linux）—— 代码里的 macOS 分支、CI 的 macOS 回归测试、
打出来的 dmg 都在，但「真机跑通」这件事要由用户本机的 Claude 来做，见第八节。

## 一、这次失败的根因：一行 `TcpListener::bind`

### 1.1 现场

用户电脑上早就跑着一套 Hunter（compose 项目 `hunter-fresh`，占 3100 / 8100 / 3921 / 5442 / 6479）。
启动器装第二套（项目 `hunter`），**只把 web 3100 改成了 3101，其余四个照原样用**，
`docker compose up` 随后报：

```
Bind for 0.0.0.0:6479 failed: port is already allocated
Bind for 0.0.0.0:8100 failed: port is already allocated
```

### 1.2 为什么只有 web 查对了

0.1.4 的探测是一行 `std::net::TcpListener::bind(addr)`，`addr` 按红线 4 分两种：
web 探 `0.0.0.0`（它要对外），其余四个探 `127.0.0.1`（它们只绑本机）。

`std::net::TcpListener::bind` 在 Unix 上**默认给监听套接字开 `SO_REUSEADDR`**。
macOS 的 BSD 语义下，这个选项会让「绑 `127.0.0.1:P`」在「`*:P` 已被别人占着」时**照样成功**：

| 绑法 | macOS（`*:8100` 已被 OrbStack 占着） | Linux |
|---|---|---|
| 带 `SO_REUSEADDR` 绑 `127.0.0.1:8100` | **成功** ← 0.1.4 走的就是这条 | 失败 |
| 带 `SO_REUSEADDR` 绑 `0.0.0.0:8100` | 失败 ← web 走的是这条，所以只有它查对了 | 失败 |
| 不带 `SO_REUSEADDR` 绑 `127.0.0.1:8100` | 失败 | 失败 |

Linux 内核对 `SO_REUSEADDR` 的处理不一样（只影响 `TIME_WAIT`，不允许活跃监听共存），
所以同一份代码在测试机上四个场景全过、一上真机就炸。**I4 的测试覆盖不到这一类缺陷。**

### 1.3 连锁的四条

| # | 现象 | 为什么 |
|---|---|---|
| 2 | 失败被归类成 `E_START_TIMEOUT`（「180 秒没就绪」） | `compose::up` 里所有失败一律 `Code::StartTimeout`，不看原话 |
| 3 | 规则层「认不出来」 | 因为错误码错了，`ports-taken` 规则根本没被匹配 |
| 4 | AI 执行的「重新分配端口」没用 | 它调的还是同一个有缺陷的探测，结果不变 |
| 5 | AI 把原因猜成「残留容器」 | 送给它的诊断里**没有「这个端口被谁占着」**，模型只会把空白填满 |
| 6 | 用户要自己点「让 AI 帮我看看」、自己确认、自己读结论 | 产品设计问题 |

## 二、改了什么（对应设计文档哪一节）

### 2.1 端口探测三重确认（设计文档 §六.1）· `src-tauri/src/ports.rs`（新文件，587 行）

任何一路说「占用」就算占用，并记下**占用者是谁**：

| # | 手段 | 抓得住 | 抓不住 |
|---|---|---|---|
| 1 | `socket2` 显式构造、**不设 `SO_REUSEADDR`**，`0.0.0.0` 与 `[::]` 各绑一次 | 本机任何进程的 TCP 监听 | 占用者是谁 |
| 2 | `docker ps --format '{{.Names}}\t{{.Image}}\t{{.Label "com.docker.compose.project"}}\t{{.Ports}}'` | Docker/OrbStack 转发的端口，**且知道是谁** | Docker 之外的进程 |
| 3 | `lsof -nP -iTCP -sTCP:LISTEN`（Windows 用 `netstat -ano`） | 占用者的进程名 | 没装 lsof 的精简系统 |

两个刻意的选择：

- **探测一律按通配地址来**，不按「这个服务将来绑哪」。通配绑定和任何具体地址上的监听都冲突，
  是三种绑法里最保守的一种。漏判的代价是装完起不来（0.1.4 的现场），误判的代价只是多换一个端口 ——
  两者不对称。
- **`docker ps` / `lsof` 一次 survey 查一批端口**（`ports::Survey`），
  不是每个端口各起两个子进程。

`config::port_free` 与 `config::resolve_ports` 现在都走它；旧的 `all_interfaces` 参数留着只为兼容，
两种取值结果相同。

### 2.2 起容器前的预检闸门（设计文档 §六.2）· `compose::preflight_gate`

`docker compose up` 之前，从 `docker compose config --format json` 取**渲染后**的端口表
（不是我们以为写下去的 `launcher.toml`），再对一遍现场。有冲突就现在说，不等 Docker 报错。

这一条在场景 6 里真的响了：算好端口之后、起容器之前，有别的进程抢走了 3101。

### 2.3 错误归类（设计文档 §六.3）· `err::Code::PortConflict` + `compose::classify_up_error`

新错误码 `E_PORT_CONFLICT`（带端口号与服务名）。`compose::up` 不再把所有失败归成
`E_START_TIMEOUT`，而是按原话分：

| 原话 | 归到 |
|---|---|
| `port is already allocated` / `address already in use` / `Ports are not available` | `E_PORT_CONFLICT`（带端口 + 服务名） |
| `no space left` | `E_PULL_FAILED`（「磁盘满了」） |
| `pull access denied` | `E_PULL_FAILED`（「仓库不让拉，多半是 tag 写错了」） |
| `TLS handshake timeout` / `i/o timeout` / `context deadline exceeded` | `E_PULL_FAILED`（超时） |
| `Cannot connect to the Docker daemon` | `E_DAEMON_DOWN` |
| 其他 | `E_START_TIMEOUT`，**但带上原话与退出码** |

### 2.4 认得出本机已有的其他 Hunter（设计文档 §六.4）· `ports::other_hunter_installs`

判据：至少有一个容器用 `hunter-community-*` 镜像、且 compose 项目名不是 `hunter`。
**认定之后把那个项目的全部容器都算进来** —— postgres 与 redis 用的是官方镜像
（`postgres:16` / `redis:7`），名字里没有 `hunter-community-`，
只按镜像名筛会漏报一半端口（首轮实测界面上写成「占着 3 个端口」，实际是 5 个）。

默认处置：**并存换端口**。界面上明说「启动器不会停它、不会删它」。

### 2.5 清残留容器（设计文档 §六.5）· `compose::remove_own_stale_containers`

只删本项目 `hunter` 里状态为 `created` 的容器，**不带 `-v`**，
删之前逐个 `docker inspect` 核对 `com.docker.compose.project` 标签。

### 2.6 CI 的 macOS 回归（设计文档 §9.3）· `.github/workflows/ci.yml`

`cross` 这个 job 的 macOS runner 上真跑一条：先起一个**带 `SO_REUSEADDR` 的 `*:port` 监听**
（这正是 OrbStack / Docker 的端口转发进程在宿主上的样子），断言探测判它为「占用」。
`cargo test` 本来就包含它，这里单独再跑一次 `ports::tests -- --nocapture`，
是为了它红的时候一眼看得出是**这一条**红了。

```rust
#[test]
fn 带_so_reuseaddr_的通配监听必须被判为占用() { … }
```

> 0.1.4 的 `TcpListener::bind("127.0.0.1", port)` 在 macOS 上会**通过这个断言的反面**。

### 2.7 一次授权（设计文档 §三）· `src/pages/Consent.tsx` + `config` `[assist] mode`

向导改成：**欢迎 → 输入 key → 一次授权 → 自动安装 → 完成**。

三档存 `launcher.toml [assist] mode`：`auto` 自动驾驶（授权页上推荐）/
`confirm` 逐步确认 / `off` 关闭。**配置文件里的默认值是 `confirm` 而不是 `auto`** ——
自动驾驶要用户在授权页上亲自点，不能靠一个默认值替他同意。
授权时间与档位写进日志、写进 `launcher.toml [assist] consented_at`、写进审计日志。

「选择模型」从主路径上挪走了：默认走 Hunter 网关，想换自带 key 的人点授权页左下角
那条「我要用自己的模型 key」，或者装好之后在设置里改。
**这是为了「授权之后一次都不用点」这条硬指标** —— 中间插一页让用户点「下一步」就不算数。

### 2.8 多智能体（设计文档 §四）· `src-tauri/src/assist/auto.rs`（1300 行）

| 角色 | 实现 | 调模型 |
|---|---|---|
| 总指挥 `Orchestrator` | Rust 状态机：推进 4 个步骤、管回合上限与 token 预算、失败进修复回合 | 否 |
| 侦察员 `Orchestrator::scout` | 只读采证：端口三重确认的结果（**含占用者**）、本机其他 Hunter、本项目残留容器、完整诊断报文 | 否 |
| 诊断员 `rule_plan` → `ask_model` | 先规则后模型。规则认得出来的一个 token 都不花 | 仅兜底 |
| 守卫 `assist/guard.rs` | 路径 / 容器 / 命令三道硬校验 + 审计 | 否 |
| 执行员 `actions::execute_as` | 动作表内执行，捕获输出，写审计 | 否 |
| 验证员 | **重跑失败的那一步**（不是问模型「好了吗」）。跑过了才算解决 | 否 |
| 讲解员 `narrate_issue` / `narrate_detail` | 模板化人话，**数字只来自真实值** | 否 |

复核员（第二模型）按分期留给 I6。

### 2.9 动作表 v2（设计文档 §五）· `assist/actions.rs`

风险分三级（`guard::Level`）：`ReadOnly` / `Safe` / `Sensitive`。
`auto` 档下 `Safe` 直接执行，`Sensitive` **在任何档位下都要先问**，表外一律拒绝。

新增：`probe_network` · `read_container_logs` · `list_other_hunter_installs` · `wait_daemon`
（只读）；`retry_pull` · `compose_down_own` · `remove_own_stale_containers` ·
`restart_own_service` · `raise_timeouts` · `export_feedback_bundle`（Safe）。

**本轮不含 `install_runtime` 与 `reuse_existing_hunter`**（按分期留给 I6）。
I4 就有的 `brew_install` 留着，但级别定为 `Sensitive` —— 它是装新软件，任何档位下都要问。

### 2.10 守卫（设计文档 §3.3）· `src-tauri/src/assist/guard.rs`（新文件，600 行）

授权页上写给用户的每一条「绝不会做」，这里各有一条对应的硬校验：

| 承诺 | 实现 |
|---|---|
| 不删你的任何文件 | `writable_path`：`canonicalize` 之后必须落在 `~/.hunter/` 内（解开 `..` 与软链）；`deletable_path` 再限定到「启动器自己生成的那几个文件」的白名单 |
| 不删不停你别的容器 | `own_container`：执行前 `docker inspect` 查 `com.docker.compose.project`，不是 `hunter` 一律拒绝；`argv` 强制会改动状态的 docker 命令带 `--project-name hunter` |
| 不改你的网络设置 | `argv`：`networksetup` / `scutil` / `pfctl` / `iptables` / `netsh` / `/etc/hosts` 等一律拒绝 |
| 不用管理员密码 | `argv`：`sudo` / `su` / `doas` / `pkexec` / `runas` 一律拒绝 |
| 不执行它自己编的命令 | 动作表机制 + `argv` 拦 `sh` / `bash` / `python` / `osascript` / `node` 等 |
| 不删数据卷 | `argv`：`volume rm` / `volume prune` / `system prune` / `image prune` / `down -v` / `rm -v` 一律拒绝 |

审计日志 `~/.hunter/logs/assist-audit.log`（权限 600），一行一条 JSON：
时间、动作、参数、由谁提出（rule / model / orchestrator / user）、级别、结果。
**通过和拒绝都写** —— 只记拒绝的话，「它到底做了什么」就查不出来了。
设置页里能直接看最近 20 条。

### 场景 1 · 启动器探不到 docker

**怎么造的现场**：给启动器一个只有必需工具、**没有 docker** 的 PATH
（`/tmp/i5-nodocker-bin`），并 `HUNTER_USE_BUILTIN_PATHS=0` 关掉内置已知位置清单。
这样连兜底也找不到 —— 和「用户的 mac 上 GUI 程序拿不到 `/usr/local/bin`」是同一类现场。

```
× 检查 Docker　这台机器上找不到 docker 可执行文件。
! 发现问题：找不到 Docker
   ✓ 分析中…　查了 5 个端口
   … 问一下模型            ← 规则层给不出办法（探测确实一个位置都没探到）
   ✓ 正在处理：重新按已知位置找一遍 docker　没找到 docker（探了 1 个位置）
   …（第 2 回合）
   ✓ 正在处理：把 docker 的路径写进设置
       已写入 docker_path = "/usr/bin/docker"，重新探测的结果：/usr/bin/docker（配置）
   … 重新试一次刚才失败的那一步　检查 Docker
✓ 检查 Docker　Docker Engine 29.8.1 正在运行
…
✓ 完成　打开 http://localhost:3101 就能用了
统计：自动解决 1 个问题 · 2 个修复回合 · 8632 token · 用时 50 秒
```

模型给的路径 `/usr/bin/docker` 被 `path_arg()` **真的验了一遍**（存在且可执行）才让它执行 ——
这一层校验就是「模型编一条路径」的兜底。

**没测到的**：docker 真的一个字节都没装的机器。测试机上 docker 是装着的，
造不出这种现场而不弄坏机器。那条路径由 `manual_step()` 覆盖（场景 2 证明了这个机制真的会触发）
与单元测试覆盖。

### 场景 2 · 装了但 daemon 没起

`sudo systemctl stop docker.socket docker.service`，测完立刻起回来（已恢复，6 个旧栈容器 running）。

```
× 检查 Docker　docker 命令在，但连不上后台服务（daemon 没起）。
   ✓ 找到原因　systemd 的 docker 服务 装着但没在运行，把它启动起来再等它就绪。
   × 正在处理：启动 systemd 的 docker 服务
       「启动 systemd 的 docker 服务」没成功（退出码 Some(1)）：See system logs and 'systemctl status docker.service' for details.
   ? Docker 后台服务要用管理员权限才能启动　请在终端里执行：sudo systemctl start docker
✗ E_DAEMON_DOWN: docker 命令在，但连不上后台服务（daemon 没起）。
  Docker 后台服务要用管理员权限才能启动：在终端里执行 sudo systemctl start docker，然后重试。
```

这是设计文档 §3.3 第 4 条的落地：动作表里**没有**任何需要 `sudo` 的动作，
撞上要管理员权限的事就老老实实请用户出手，**不替他提权，也不假装做过了**。
界面上是一张「需要你」卡片，两个按钮：「我执行完了，继续」/「先不弄了」
（截图 `i5-auto-need-user.png`）。命令行下没有人能点，当场按「不」处理并说明原因。

> **首轮跑出来的两个真 bug，已修**：
> 1. `run_argv` 原来对**任何**退出码都返回 `Ok`，于是 `systemctl start docker` 退出码 1
>    照样显示「✓ 已处理」，总指挥以为修好了 → 接着白等 90 秒 `wait_daemon` → 再原样重试三个回合。
>    **4 分 39 秒全花在这上面。** 现在改动类动作退出码非 0 一律 `Err`（只读动作例外：
>    `docker version` 在 daemon 没起时退出码本来就是 1，那本身就是答案）。
> 2. 规则层每一回合都原样再提一次同一个失败过的动作。现在 `failed_actions` 记着，不提第二次。
>
> 同一个场景从 **279 秒 → 3 秒**。

### 场景 3 / 5 · 端口被占 & 本机已有另一套 Hunter

测试机上的 `hunter-community` 旧栈正好占满 5 个端口，这两个场景是同一个现场的两个角度。

## 五、偏离设计文档的决策

| # | 决策 | 原因 |
|---|---|---|
| 1 | 「选择模型」从主路径挪到授权页的一条支线链接 | 设计文档 §二的流程图里本来就没有它；而留着它就意味着授权之后还要点一次「下一步」，与「授权后零点击」直接冲突。默认（Hunter 网关）不用点，要换自带 key 的人点那条链接或装完去设置里改 |
| 2 | `[assist] mode` 的**配置默认值**是 `confirm`，不是 `auto` | 授权页上 `auto` 是推荐项、写在主按钮上；但「用户还没点过任何东西」时程序里存的那一档必须是保守的那一个 —— 默认值不能替用户同意 |
| 3 | 多了一种「需要你」：**AI 没有权限做的事** | 设计文档列了三种必问情况。Linux 上 `systemctl start docker` 要 root，而动作表里刻意没有任何 sudo 动作（§3.3 第 4 条）。这时候既不能替他提权、也不能假装做过了，只能请他执行一条命令。做成了同一种「需要你」卡片 |
| 4 | I4 就有的 `brew_install` 留在表里，级别定为 `Sensitive` | 设计文档说本轮不含 `install_runtime`。`brew_install` 是 I4 已有的能力，删掉是功能回退；定成 `Sensitive` 之后任何档位下都要用户先同意，等于没有新增自动能力 |
| 5 | 场景 1 造的是「探不到 docker」而不是「一个字节都没装」 | 测试机上 docker 装着且旧栈在跑它，造不出「真没装」而不弄坏机器。这个现场与用户 mac 上「GUI 程序拿不到 `/usr/local/bin`」是同一类，而且**更接近**真实失败模式 |
| 6 | 场景 6 额外加了「起容器前端口被抢」 | 端口探测修好之后，光有残留 `Created` 容器已经不会让安装失败（compose 自己会重建）。不加这一手就证明不了清理动作真的会跑 |
| 7 | `net_bytes`：把「真的过了网的字节」和「进度条分子」分开 | `downloaded_bytes` 把本机已有的层也算进去（那是整体完成度）。拿它去说「下载了 849 MB、用时 1 秒」是在骗人（红线 1） |
