## 零、一句话

客户 2026-09-25 点「升级 Hunter 1.2.0 → 1.2.2」，界面卡在
**「正在拉取新版本的镜像…」一个多小时不动**，最后他自己把应用关了。
我们想查 —— **手上一份日志都没有**。

这一轮做的就是这两件事，外加强退之后留下的那个中间态：

| | 0.1.15 | I16 之后 |
|---|---|---|
| **P0-1** 拉取卡死 | `compose pull` 不报错就一直等下去。「报错 → 换源重试」一次都没触发 | 90 秒没有新进展就判定卡死、杀掉它、换另一个源；两个源都卡死才算失败。新错误码 `E_PULL_STALLED` |
| **P0-2** 拿不到日志 | 让用户导诊断包 → 发文件 → 我们人工翻。他一休息这条链子就断 | 他点一下，脱敏后的日志直接进我们的库，他只要念一个 8 位追踪码 |
| **P1-1** 卡住只能强退 | 升级过程中没有「取消」 | 点了就杀子进程、把配置写回升级前那一份，并明说容器一个都没动 |
| **P1-2** 强退后的中间态 | 下次打开照着新配置 `up`，去拉一个还没下完的镜像 —— **又卡一次** | 开机自查认得出「上次升级没做完」，给「继续升级 / 回退到正在跑的那一版」两个按钮 |

## 一、P0-1 · 「没有新字节 = 卡住」

### 1.1 那个数字是关键线索

客户截图里能确定的：打包三个卷 → 写新 compose 与 `.env`（`HUNTER_VERSION=1.2.2`）
→ `docker compose config` 校验通过 → 六个服务端口都在 `127.0.0.1` →
**算出「六个镜像合计约 748 MB」** → 然后就停在「正在拉取新版本的镜像…」。

「748 MB」这个数只有**逐个读镜像 manifest** 才算得出来 ——
说明到镜像仓库的元数据请求是通的，卡住的是**拉层（blob）**那一步。

对照：同一个升级在另一台 Mac 上走腾讯云香港，**52 秒**拉完
（`08:27:48 第 1 次拉取` → `08:28:41 拉取完成，用时 52 秒`）。

### 1.2 为什么原来发现不了

原来的逻辑是「`docker compose pull` 报错 → 换源重试」。
可这种连接**不报错**：TCP 连上了、进程活着、就是不传字节。
compose 不退出，`pull_streaming` 就一直在读那个管道。

> 同一个病在 Hunter 那边（0.1.22 修的「国内直连 npm 官方源碰上卡死的连接
> 没有总超时」）刚犯过一次。所以这一轮**治在 `proc` 层**，不是在拉镜像这一处打补丁。

### 1.3 两种超时，分清楚

`proc.rs` 现在有两套超时，用途不重叠：

| | 谁在管 | 什么时候用 |
|---|---|---|
| **总超时** | `run_timeout` | 短命令。「这条命令最多允许跑 N 秒」 |
| **静默超时** | `run_streaming` 的 `StreamOpts::silence` | 长跑且有进度流的：拉镜像、起容器、导入离线包 |

**为什么必须有第二种**：长跑的命令给不出一个合理的总超时 ——
748 MB 在好网上 52 秒、在慢网上二十分钟，写死哪个数都是错的。
而「多久没有任何新进展」是一个**与网速无关**的量。

`run_streaming` 的形状：

```rust
pub enum Ev<'a> { Line { text: &'a str, is_err: bool }, Poll }
pub enum Fresh { Yes, No }
pub enum Ended { Exited(Option<i32>), Stalled { silent_secs: u64 }, TimedOut { secs: u64 }, Cancelled }

pub fn run_streaming(
    program: &str, args: &[&str], opts: &StreamOpts,
    on_event: impl FnMut(Ev) -> Fresh,
) -> AppResult<Streamed>
```

### 1.4 判据不是「管道上有没有字节」

这一条是实测撞出来的，也是整条功能里最要紧的一个决定。

测试机上 `docker compose --progress json pull` 对着一个「blob 不吐字节」的 registry，
吐出来的是这些（原文留在 `I16-证据/compose-pull-stalled.jsonl`）：

```json
{"id":"Image …/hunter-community-web:1.2.2","status":"Working","text":"Pulling"}
{"id":"d4f147ee4233","parent_id":"Image …/hunter-community-web:1.2.2","status":"Working","text":"Pulling fs layer","details":"0B"}
{"id":"d4f147ee4233","parent_id":"Image …/hunter-community-web:1.2.2","status":"Working","text":"Pulling fs layer","details":"0B"}
{"id":"d4f147ee4233","parent_id":"Image …/hunter-community-web:1.2.2","status":"Working","text":"Pulling fs layer","details":"0B"}
```

**同一句话重复吐。** 按「管道上有没有字节」判，这个现场永远判不出卡死。

所以判据是**解析之后**的状态：`PullAggregator::progress_token()` ——
把「每一层的已下载字节 + 完成标志 + 层数 + 每个镜像的状态」压成一个数，
这个数变了才算有进展。调用方通过 `Fresh::Yes / No` 把这个判断交回 `proc`。

不关心这件事的调用方一律回 `Yes`，等价于「管道有字节 = 有进展」。

### 1.5 为什么是 90 秒

正常拉取里两条进度之间是亚秒级的。真实的对照是 2026-09-25 另一台 Mac 上那一次
—— 同样 1.2.0 → 1.2.2、同样走腾讯云香港，**整整 52 秒**就全部拉完了。
也就是说 **90 秒的静默比整次拉取还长**：一条正常的连接不可能在中间空这么久，
一条卡死的连接会一直空下去。

可以用 `~/.hunter/launcher.toml` 的 `[hunter] pull_stall_secs` 改（夹在 20–1800 秒）。

### 1.6 杀进程的两个细节

**先 `SIGTERM` 再 `SIGKILL`。** `docker compose pull` 收到 TERM 会自己把已经起的
拉取协程收掉；直接 KILL 来不及做这件事，会在 daemon 那边留下半截的下载任务。
给它 2 秒，不走再硬杀。

**被杀的那一路不 `join` 读线程。** 杀掉的是我们 spawn 的那一个进程，
但它可能已经 fork 出孙子进程（`sh -c '… ; sleep 600'` 就是），
孙子继承着同一个管道写端 —— 父进程死了管道不会关，读线程永远等不到 EOF。
join 它就等于把「杀掉卡死的进程」换成「自己也卡死」，**那比原来的病还糟**。
原文从 `Arc<Mutex<Vec<String>>>` 里取，不需要线程结束就拿得到。

### 1.7 文案：说清楚卡在哪

不是「拉取失败」，而是（测试机实测原文）：

```text
✗ E_PULL_STALLED: 从「自定义镜像源」拉了 20 秒，一个字节都没下到。
  这个源试过了 —— 连得上、就是不给数据。这多半是这台机器到镜像仓库的路被掐在
  半路上了（运营商、公司网关、代理）。可以换个网络再试（手机热点最快验），
  或者用离线包安装。
```

三种说法对应三种真实情况，**不知道的就说不知道**（红线 1）：

| 现场 | 说法 |
|---|---|
| 一个字节都没来 | 「一个字节都没下到」 |
| 分母读到了、下了一半（客户那台就是这一档） | 「已下载 120 MB / 共 748 MB」 |
| 下到了字节但 manifest 没读到 | 「已下载 5.0 MB，总量没读到」 |

### 1.8 换源：两个源都卡死才算失败

卡住这一档**不走**既有的「原话指纹」判断（它的原话里带着源的名字，指纹本来就不同），
另起一条：记下「哪些源卡过」，`flow::stall_decision` 三条规则 ——

* 用户点名了源 → 不换（他说了算）；
* 没有别的源可换 → 不换；
* 下一个源**已经卡过一次** → 不换（再换就是在两条死路之间兜圈，I6 那次「268 秒
  在两个源之间来回」就是这么来的）。

这个判定做成了**纯函数**，理由和 `runtime::effective::decide` 一样：
真造那种现场要起一个假 registry，而它一次只造得出**一个**卡死的源 ——
「两个源都卡死」在真机上根本摆不出来，只能靠单测考（见第六节）。

### 1.9 同一套超时复用到别处

任务书要求「凡是长跑且有进度流的子进程都走它」。**三处都走了：**

| 谁 | 静默阈值 | 总上限 | 判据 |
|---|---|---|---|
| **拉镜像** `compose --progress json pull` | **90 秒**（`pull_stall_secs` 可改） | 无 | `PullAggregator::progress_token()` —— 它会重复吐同一行，管道字节不作数（1.4） |
| **起容器** `compose --progress plain up -d` | **60 秒**（`compose::UP_SILENCE`） | 300 秒 | 管道上有字节就算有进展 —— `up -d` 的进度是一行一个新状态，不重复 |
| **导入离线包** `docker load -i` | **60 秒** | 1800 秒 | 同上 |

后两处的阈值比拉镜像短，理由是**它们都不跨网络**：起容器是本机的活
（建网络、建容器、挂卷、起进程），`docker load` 是读盘。
正常情况下每一步之间都是亚秒级；真静默一分钟，那是守护进程或者那块盘出问题了，
再等下去没有意义。

**这不只是「顺手加一下」** —— `docker load` 原来的写法是
`run_timeout(…, 1800 秒)`：一个坏掉的 tar（拷贝没拷完是最常见的一种）
会让用户对着「正在从 … 导入镜像…」干等**半小时**，和客户在拉镜像上等的那一个多小时
是同一个病。现在 60 秒就说得出「这个 tar 可能是坏的，先核对一下文件大小」。

起容器那两处（`up_services` / `start_services`）**保留**原来的 300 秒总上限：
静默超时是加进来的第二道，不是替换。卡住与超时都归到「非 0 退出」并把原因写进
stderr 的**最后一行**（`Ran::err_line()` 取的就是那一行，写成两行前半句会丢），
上层的 `classify_up_error` 照旧按原话分类。

`E_PULL_STALLED` 是一个新错误码，前端 `ERROR_CODES`、`RETRY_TARGET`、
两份 i18n、规则层（`pull-stalled-switch-registry`，说法和「源不通」那一套**不同** ——
说错原因比不说更糟）、错误页的「离线导入」出口都跟着补齐了。
离线导入卡住也报这个码（那一档的出路是「换一份 tar」，错误页上本来就有「从文件导入」）。

## 二、P0-2 · 一键上传日志（本轮重点）

### 2.1 它解决的是哪一段

排障原来的链条是：让用户导诊断包 → 他把 zip 发给我们 → 我们人工翻。
**三步里有两步要他在场。** 9 月 25 日那次，客户点完「关闭应用」就去休息了，
链子断在第一步。

现在：他点一下 →「上传日志给我们（不含 key 与口令）」→ 看一眼要传什么 →
确认 → 拿到一个追踪码，念给我们。

### 2.2 三条底线，写在代码里不靠自觉

**① 默认不传。** 只有用户亲手点了才发请求。设置页那个「出错时自动上传日志」
默认关，而且打开之后**只在出错时**传 —— 判据只有 `logship::should_auto_upload`
一个入口，它拿不到错误码时一律返回 false。正常安装、正常运行一个字节都不出门。

**② 传之前给他看。** `logship_preview` 返回的 `body` 会被存进
`AppState::upload_preview`，`logship_upload` 传的就是它 ——
**界面上看到的和送出去的是同一串字节**，不存在两套。
没有预览过就不给传（这不是防御性编程，是这条路的设计：不给看就传等于替用户做决定）。

**③ key 一个字节都不传。** 服务端接受一个可选的 `hunterKey`（原文，它只存
sha256 前 16 位，用来把同一用户的多次上报串起来）。**我们不填它。**
总控规则红线 2 写的是「hunter key 只存 `~/.hunter/app/.env`（权限 600）与内存；
**不写日志、不进遥测**、不进诊断包」—— 一键上传日志就是一次上报。
这个字段本来就是可选的，不填不影响任何功能；串同一个用户靠 `machineId`。

> **这是一处与任务书的偏离，写在这里请用户过目**：任务书把 `hunterKey` 列为
> 可选项。我们选择不填。真要按 key 串同一个用户，那是一个需要明确松口红线 2 的决定，
> 不该由代码默默做掉。

### 2.3 `machineId`

首次要用到时生成一个随机 UUID v4（系统 CSPRNG，和 `install_id` 同一个生成器），
写进 `launcher.toml` 的 `[support] machine_id`。

**不碰任何硬件信息** —— MAC、序列号、主机名一律没读。那种东西一旦发出去，
就不再是「一个用来串起同一台机器几次上报的随机数」，而是一个跨应用可关联的指纹。
用户删掉 `launcher.toml` 就换一个，本来就该这样。

拿不到系统随机源时**不退回一个可预测的值**（时间戳、主机名哈希…），
宁可这一次不带 `machineId` 上传。

### 2.4 脱敏：走现有的闸，外加两条新形状

正文就是现有诊断包里那份东西，三道闸一道没新写：

1. `feedback::collect` —— 每一节出来时已经过了 `redact::redact` 与 `mask_home`；
2. `redact::mask_names_here` —— 把用户名与主机名**换掉**（I7 起 `assert_clean_strict`
   只会**发现**它们，发现之后只能拒绝出门；上传这条路要的是「抹掉之后照样送得出去」，
   拒绝上传等于让用户回到「自己导 zip 再发文件」，那正是这一轮要解决的事）；
3. `feedback::assert_clean_strict` —— 出门前整份再扫一遍，扫出东西就**不给传**
   （界面上连「确认上传」那个按钮都不给）。

**这一轮给 `redact` 补了两条形状**，都是写单测时当场撞出来的：

| 形状 | 例子 | 为什么原来漏了 |
|---|---|---|
| `XXX_PASSWORD=…` / `SECRET=` / `PASS=` / `TOKEN=` / `API_KEY=` | `POSTGRES_PASSWORD=Sup3rSecretPw` | 原来靠另外两道：诊断包里的 `.env` 只留白名单四项，启动器自己生成的口令在生成那一刻就 `register_secret` 了。两道都管用，但都**只覆盖它们自己那条路** —— 用户手改过的 `.env`、容器日志里打出来的连接串、`compose config` 的输出，三道之外没人管 |
| 连接串里的 userinfo | `postgres://hunter:Sup3rSecret@127.0.0.1:5432/h` → `postgres://hunter:****@…` | 那里的口令前面没有键名，只有一个冒号 |

已经抹过的值不再抹第二遍：`hunt_tools_****` 里那个前缀是**有用的信息**
（「这是哪一家的 key」），`<已移除>` 是诊断包白名单主动删的，两个都原样留着。

### 2.5 失败要说人话，而且给第二条路

| 情况 | 说法 | 还做什么 |
|---|---|---|
| 429 | 「今天传得有点多，服务端暂时不收了（同一台机器每小时最多 5 次、每天 20 次），过一个小时再点一次就行。」+ 服务端原话 + 日志在本机哪个路径 | 不导包（日志本来就在他机器上，路径也给了） |
| 413 | 「这一份日志太大，服务端不收（上限 2 MB）。」 | **当场导一个诊断包**并给出路径 |
| 5xx | 「我们这边的服务器出错了（HTTP 5xx），**不怪你**。」 | 同上 |
| 压根没连上 | 「传不上去（原因）。已经给你把诊断包导到 …，把这个文件发给我们也一样管用。」 | 同上 |
| 200 但没有 `traceCode` | 「服务端回了 200，但没给追踪码。这一份到底有没有收下说不准」 | **不谎称成功**（红线 1） |

路径这两处**故意不脱敏**：它们是给用户看的「你的东西在哪」，
抹成 `<用户目录>/.hunter/logs/launcher.log` 他就找不到那个文件了。
它们不会被上传（`Outcome` 只回给界面），也不会进上传正文。

### 2.6 界面

按钮在三个地方，文案统一「上传日志给我们（不含 key 与口令）」：
**错误页**、**设置页**（隐私那一节）、**运行面板**的按钮区。

传完那一屏：追踪码一行大字（34px 琥珀金）+ 复制按钮 +
「把这个码发给我们，我们就能查到这份日志。它也已经写进了本机日志，
关掉这个窗口也找得回来」。追踪码同时写进 `launcher.toml`，
设置页上能看到「上一次上传：HL-XXXXXX（时间）」。

### 2.7 出站地址清单

设置页那份「启动器真的会连哪些主机」加了 `www.agentpit.io`。
只有用户点了按钮、或者开了自动上传并且真的出了错才会连它 ——
但它确实会连，所以那份清单里必须有。

## 三、P1 · 取消与自愈

### 3.1 升级过程中可以取消

客户那次只能强退，而强退发生在「`.env` 已经写成 1.2.2、镜像还没拉全」之后 ——
**没有走到回滚**，机器就停在一个说不清的中间态。

现在升级页上有「取消升级」。点了之后：
`state.cancel` 置位 → `run_streaming` 当场杀掉 `docker compose pull` →
`upgrade()` 认出这是取消（不是失败）→ 从升级前那次自动备份里把
`.env` 与两份 compose 原样写回 → 说一句：

> 已取消。Hunter 还是 v1.2.0，正在跑的 6 个容器一个都没动，配置也写回了升级前那一份。
> 升级前的备份留在 …。

`UpgradeResult` 多了一个 `cancelled` 字段，界面靠它把「取消」和「失败」分开说 ——
**把用户的主动选择显示成一条红色错误，会让他以为自己把机器点坏了。**

### 3.2 下次启动自愈

开机自查（`boot_state`，以及命令行的 `--boot-state`）现在多问一句：

```text
配置（.env / compose）说的版本  ≠  正在跑的容器的版本
                 且
        新版本的镜像本机并不齐
```

三个条件缺一不可（`upgrade::judge_interrupted`，纯函数）：

* 配置说的版本与正在跑的版本不一样；
* **真的有容器在跑**（一个都没有 = 那是「还没装」或「停着」，不是「升级没做完」）；
* 配置那一版的镜像**本机不齐** —— 齐了的话直接 `up -d` 就完事，
  那不是一个需要打断用户的现场。

判定为真时，运行面板顶上出现一张卡片（排在所有提醒的**最前面**：
在用户选定之前，面板上其它关于版本的数字都要打个问号），两个按钮：

* **继续升到 v1.2.2** → 打开更新页走正常升级；
* **回退到正在跑的 v1.2.0** → 只把配置写回去，**不碰容器、不碰卷、不拉镜像**
  （那六个容器本来就在正常跑，为了「让配置对上」去重建它们是完全不必要的风险）。

回退优先从**升级前那次自动备份**里把配置原样写回（它就是当时那一份，而且不需要网络）；
找不到对得上的备份才去重新取一份那一版的 compose，取不到就停 ——
宁可什么都不改，也不要写一份来路不明的配置。写完还要**复核一遍**
`.env` 里的 `HUNTER_VERSION` 到底改成了没有，才敢说「已回退」。

**不许默默按新配置 `up`** —— 那会去拉一个还没下完的镜像，用户又看到一次「卡住」。

## 四、Windows 客户那份诊断包撞出来的四条

镜像源 GHCR**（`plan/win-0.1.15-20260926/`）。

这位客户替我们验了一件挂在待办池里很久的事 ——「Windows 从未真机验证」。
四条问题里**三条只在 Windows 上暴露**，其中两条是 P0。

> **这一节里凡是标「未验证」的，就是真的没验过。** 我们手上一台 Windows 都没有，
> 用户 2026-09-26 明确要求：**不许在 Linux 上构造、模拟、伪装 Windows 场景做自动化测试**
> —— 假的 `schtasks`、假的 GBK 控制台，跑绿了也不等于真机能用。
> 所以这一节分得很清楚：**纯函数级的单测在 Linux 上是真测试**（第七节），
> **其余 Windows 行为全部列进 6.4 那张「待人工验证」清单**。

### 4.1 选源只探 manifest、不探层数据（本地 Claude 已修，本轮真机验了一次）

这一条 `24f11b8` 已经修完：`probe()` 在 manifest 通过之后，挑镜像里**最小的一层**
发 `Range: bytes=0-262143` 真下一段回来，下不来就判这个源不可用；
排序改成「能不能用 → 层数据下得多快 → 元数据多快」。

**为什么这条在 Windows 客户那里要命**：他机器上 GHCR 的 manifest 又快又通，
于是每次选源都选中 GHCR；可 GHCR 的层数据根本不在 `ghcr.io` 上 ——
`ghcr.io/v2/…/blobs/sha256:…` 回的是 **HTTP/2 307**，`location` 指向
`pkg-containers.githubusercontent.com`。**探的东西和真正要下载的东西不是同一样东西。**

本轮在测试机上真机验了一次（`scripts/i16-probe-test.sh`，原始输出
`I16-证据/probe-test.log`）。造现场的办法不是造假 registry，而是**只把层那一侧堵掉**：
`/etc/hosts` 里把 `pkg-containers.githubusercontent.com` 指到 `198.51.100.1`
（TEST-NET-2，不可路由），`ghcr.io` 一个字不动，退出时写回。实测：

| | 判定 | 实测 |
|---|---|---|
| `probe(ghcr)` | **不可用** ✓ | manifest 那一步走通了（`elapsed_ms = 443`），`data_ok = false`，`data_ms = None`（没测成就不给数字），detail 写「元数据能拿到，但层数据下不来」 |
| `probe(tencent)` | 可用 ✓ | `data_ok = true`、`data_ms = 6205`（**实测值**）、`elapsed_ms = 1704` |
| `choose()` | 选腾讯云 ✓ | 排序键「能不能用 → data_ms → elapsed_ms」 |

**真机跑这一条时当场撞出一个更要命的 bug**，而 13 条单测全是绿的：
`probe_data_plane` 原来用 `http::get` 读层数据，而那个函数把正文
`read_to_string().unwrap_or_default()` —— 对着 gzip 二进制**永远返回空串**。
于是「连上了，但一个字节都没给」对**每一个真实镜像源**都成立，
一台干净机器上什么都装不了。修法是新开一个按字节读的 `http::get_bytes_headers`。

> 这件事值得单独记一笔：**把真 TLS、真 HTTP、真 307 mock 掉就等于不测** ——
> 而「探的东西和要下的东西不是同一样」恰恰是 mock 永远发现不了的那一类。

### 4.2 P0-3 · Windows 上定时备份从第一天起就没装上

客户日志里这一行出现了**两次**（安装时、每次开机自查）：

```text
装完挂定时备份没成（不影响安装）：schtasks /Create 失败：����: δָ���Ĵ���
```

**那串东西不是乱码而已，是 GBK 字节被当成 UTF-8 解的结果。**
按 GBK 解回来是 **`错误: 未指定的错误`**。后果有两层，第二层更严重：

1. 真正的失败原因我们**从来没看见过**；
2. **客户以为自己有每日自动备份，实际上一次都没跑过。**

#### ① 解码按平台走（`proc.rs`）

`decode_output` 取代了两处 `String::from_utf8_lossy`：先按 UTF-8 严格解，
解不动才按这台机器的**控制台输出代码页**（`GetConsoleOutputCP`，拿不到再 `GetACP`）
重解一遍。代码页 → 编码的映射交给 `encoding_rs`（只在 `cfg(windows)` 下启用），
**不自己手写码表**；代码页不认识（例如 OEM 437）就老实退回 `from_utf8_lossy`。

拆出一个纯函数 `decode_console(bytes, codepage)` 只为一件事：
让「给一段 GBK 字节流，断言解出来是中文」这条单测**在 Linux 上跑得了**。
把这段逻辑关进 `cfg(windows)` 就等于永远不测它。

**顺带修掉一个更隐蔽的**：`run_streaming` 原来是
`reader.lines().map_while(Result::ok)` —— `Lines` 碰到一行不是合法 UTF-8 会返回
`Err`，而 `map_while(Result::ok)` 见 `Err` 即**整条流就此停读**。
在中文 Windows 上，子进程随便吐一句 GBK 的提示，后面所有输出
（**包括拉取进度**）就全丢了，而且丢得悄无声息。改成按字节读、自己切行、再解码。

#### ② schtasks 到底为什么失败：三条路，不赌一个猜想

解码修好只是让我们**以后**能看见原因。这一次的原因仍然查不出来 ——
「未指定的错误」就是任务计划服务说「我不告诉你」，而我们没有 Windows 机器。

所以这里**不赌某一个猜想**，而是把三条路都走一遍，前一步不成才走下一步：

| | 做法 | 代价 |
|---|---|---|
| ① | `schtasks /Create /TN … /XML … /F` | 无。带 `StartWhenAvailable`（错过后补跑） |
| ② | 先 `/Delete` 掉可能存在的同名任务，再试一次 `/XML` | 多一次调用。四次失败里唯一与那一次成功不同的地方就是「任务已存在」，值得排除 |
| ③ | **完全不用 XML**：`/Create /TN … /TR … /SC DAILY /ST HH:MM /F` | **没有「错过后补跑」** —— 电脑在那个时刻关着，那一天就没有备份。**界面上如实说出来**（红线 1） |

XML 本身照规范修了两处（都**不是**「我们确认的根因」，而是「本来就该这么写」）：

* 补上 `<Principals>`：原先 `<Actions Context="Author">` 指向一个 **XML 里根本不存在的
  principal**，而 schema 要求 `Context` 与某个 `<Principal id=…>` 对得上；
* `<Settings>` 的子元素按 schema 里的顺序排。

**另外查出并修掉一处真 bug（这条不用 Windows 也能确认）**：临时 XML 文件名原先是写死的
`~/.hunter/hunter-backup-task.xml`。安装收尾（`flow.rs`）与开机自查
（`lib.rs` 里那个 spawn 出来的线程）都会调 `schedule::sync`，
两边撞上时**一边的 `remove_file` 会把另一边正在读的那份删掉** ——
schtasks 于是报一句什么都没说的「未指定的错误」。
现在每次调用各用各的文件名（`pid` + 自增序号），外加一把进程内的互斥锁。
**客户日志里那两行恰好就是这两处同时在跑**，所以这个猜想不是凭空来的；
但它到底是不是那一次的根因，**没有 Windows 机器就确认不了，报告里不写「已修复」，写「已排除这个可能」。**

#### ③ 装不上要说出来

`schedule::install` 现在把失败原话记进 `[backup] schedule_error`，
运行面板上出一条**红色横幅**：「每日自动备份没有挂上，这台电脑上它一次都不会跑：<原话>」
+ 一个「再挂一次」按钮 + 「打开备份设置」。它排在「上一次备份失败」那条**之前** ——
「某一次没成」和「一次都不会跑」是两件事，后者严重得多。
用户自己把自动备份关掉时，这条横幅跟着消失（那是他的决定，不是故障）。

> I14 的教训在这里又应验了一次：**代码里那件事其实做了（它真的去装了），缺的是「说出来」。**

### 4.3 P0-4 · 把 `exited` 说成「在跑但还没就绪」

客户 `ps.txt` 里六个容器**全是 `exited`**，0.1.15 的开机判定却说：

```text
开机判定：Hunter 在跑，但 web、api、opencode、llm-shim、postgres、redis 还没就绪、网页打不开
```

界面上于是出现自相矛盾的一屏：**「Hunter 运行中」＋「v1.2.2 · 容器已停止」**。

`exited`（容器退出了）和「起来了但健康检查没过」**处置完全相反**：
前者点「启动」，后者等一等或看日志。把前者说成后者，是把用户往错误的方向引。

改法：

* `Posture` 多一档 **`Stopped`**（六个容器都建齐了、但一个在跑的都没有）。
  判定做成纯函数 `judge_containers`，三档的顺序不能换：
  **`created` 的残骸先接走**（I5 §六.5：那些容器身上冻着上一次那组端口）→
  再看「一个在跑的都没有」→ 剩下的才是「有在跑的，但有的不正常」。
  `restarting` **不算**停着 —— 那是正在挣扎，处置是看日志；
* `Stopped` 这一档**不去探 web**：那个端口上本来就不会有人应答，探它只是白等 6 秒，
  再多报一句「网页打不开」把话说重了。也**不给网页地址** —— 给出去就是一个点不开的链接；
* `Partial` 那一档把「停着的」和「没就绪的」**分开说**：
  「web、api 停着（需要启动）」＋「opencode 还没就绪」；
* **界面顶上那行大字跟着「现在到底有没有容器在跑」走，不跟状态机的名字走。**
  0.1.15 只在 `state.name === 'Stopped'` 时才写「已停止」，
  于是客户那台（状态机停在 `Ready`、六个容器全 `exited`）出现了那一屏自相矛盾。
  还没拿到 `docker ps` 结果的那几秒说「正在检查 Hunter 状态…」——
  那时候说「已停止」是冤枉自己。

**这一条在 Linux 上验得了**（`docker compose stop` 在哪个系统上都造得出同一个现场），
真机结果见 5.5。

### 4.4 P2-5 ·「拉取完成，用时 4 秒」是误导

客户首装时这一行：

```text
第 1 次拉取，镜像源 ghcr.io/agentpit-io
拉取完成，用时 4 秒
```

4 秒拉完 849 MB 当然不可能 —— 他机器上**本来就装过一套 Hunter**（日志里五个端口全冲突），
镜像是现成的。可这句话让他以为「下载成功了」，于是后面升级真要下载时卡住，
就显得莫名其妙。

`PullAggregator` 加了 `net_bytes()`（真的过了网络的字节）与 `images_downloaded()`，
那句话改成 `done_line()` 的三档：

| 现场 | 说法 |
|---|---|
| 一个字节都没过网 | 「6 个镜像本机都已有，没有下载（核对用时 4 秒）」 |
| 下了一部分 | 「拉取完成，用时 52 秒：2 / 6 个镜像下载了 210 MB，其余本机已有」 |
| 全下了 | 「拉取完成，用时 52 秒：6 个镜像共下载 748 MB」 |

命令行那一路（`headless.rs`）同一个判据、同样三档。真机结果见 5.6。

### 6.2 `hunterKey` 我们不填（与任务书的偏离，请过目）

服务端接受一个可选的 `hunterKey`（原文，它只存 sha256 前 16 位，
用来把同一用户的多次上报串起来）。**我们不填它。**

总控规则红线 2：「hunter key 只存 `~/.hunter/app/.env`（权限 600）与内存；
**不写日志、不进遥测**、不进诊断包」——一键上传日志就是一次上报。
这个字段本来就是可选的，不填不影响任何功能；串同一个用户靠 `machineId`。

**真要按 key 串同一个用户，那是一个需要明确松口红线 2 的决定，不该由代码默默做掉。**

### 6.3 `schtasks` 的根因仍然没查出来

第 4.2 节说得很清楚：解码修好只是让我们**以后**看得见原因，
这一次的原因（「未指定的错误」= 任务计划服务说「我不告诉你」）**仍然不知道**。
三条路是为了「不赌某一个猜想」，不是「已经找到根因」。

那个临时 XML 文件名撞车的 bug 是**真 bug、也真修了**，而且客户日志里那两行
（安装时一条、开机自查一条）恰好就是两处同时在跑 —— 但**它到底是不是那一次的根因，
没有 Windows 机器就确认不了**。W1–W5 验完才知道。

### 9.3 这一轮最值得记住的一句

**「不报错」不等于「没出事」。**

P0-1 的那种连接不报错、`compose pull` 不退出、进程活着 —— 于是 0.1.15 陪着它等了
一个多小时。P0-3 的 `schtasks` 也一样：它**报了**错，可那句话被解成了乱码，
等于没报；而界面上写的是「不影响安装」。P0-4 更直接：状态查到了、说反了。

三条都不是「功能没做」，是**「做了，但没把真相说出来」**。
