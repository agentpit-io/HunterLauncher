## 零、一句话

0.1.13 在用户的 Mac 上被逐条真跑了一遍：**七项通过，四项有问题**。
这一轮做的就是那四条，外加一条从来没在真机上验过的升级路径。

| | 0.1.13 在用户 Mac 上的样子 | I14 之后 |
|---|---|---|
| **F1**（P0）自更新 | 在 macOS 上**下了一个 Linux 的 `.deb`**，然后 `dpkg: command not found` | 按 `latest.json` 里这台机器那一项取包；macOS 解 `.app.tar.gz` 就地换掉那个 `.app` |
| **F2** 删除计划的体积 | 「工作目录 86.1 GB / 运行环境 86.1 GB」，而 `du -sh` 是 **5.8 GB**；警告连印两遍 | 按**实占块数**算；两行来自两处；警告只说一遍 |
| **F3** 重装时的 key | 刚承诺过「重装会直接沿用」，`--auto -y` 却报「标准输入不是终端」 | 要 key 之前先读 `.env`，验得过就沿用并说一句；界面同理 |
| **F4** 定时备份 | 删除应用把它一并移除了，重装之后**看不出来它回来没有** | 装完那一步把结论印在过程流与完成页上；删除时就说清「重装后会自动装回」 |
| **F5** Hunter 升级 | `--upgrade` 这条路**从来没在真机上验过** | 见第五节 |

这四条里有三条的共同点值得单独记一笔：**代码里那件事其实做了，缺的是「说出来」**。
F4 尤其典型 —— `flow::start` 装完本来就会挂定时任务，但它只往日志里写了一行，
而 `--uninstall` 刚刚把日志目录删掉了。**用户看不见的事等于没做**。

## 一、F1 · macOS 上的自更新

### 1.1 它当时是怎么坏的

用户 Mac 上 2026-09-23 23:34 的原话：

```text
已下载并验签 hunter-launcher_0.1.13_amd64.deb
E_NOT_IMPLEMENTED: /bin/sh: dpkg: command not found (127)
```

`self_update_headless` 里的 `match` 只单独处理了 AppImage：

```rust
match kind {
    InstallKind::AppImage => { …按清单取包，就地替换… }
    _ => { …下 .deb，走系统授权框跑 dpkg -i… }
}
```

`InstallKind::MacOS` 与 `InstallKind::Windows` 全落进那个 `_`。
而 `can_self_install()` 对这两个平台返回的是 **true** ——
也就是说界面那一侧（Tauri 的 updater）一直是对的，
**只有命令行这条路是错的**，而用户正好走的是命令行。

顺带还有一句话要纠正：那个分支无条件说

> 这台机器上的启动器是 **macos** 形式装的，换包要管理员权限。

两处都不对：macOS 上不是「换包」，而且**通常一个密码框都不用弹**。

### 1.2 现在怎么选包

**不再按安装形式去拼文件名。** `latest.json` 的 `platforms` 里，
每个平台本来就写着该下哪个 URL 与它的签名，按 `target_key()` 取就行
（`selfupdate::fetch_asset`）。选的不是我们拼的名字，是发布流水线自己写进清单的那一条。

| `target_key()` | 清单里那一项 | 怎么装 | 要不要管理员 |
|---|---|---|---|
| `darwin-x86_64` / `darwin-aarch64` | `*_universal.app.tar.gz`（两个键指同一个通用包） | 解包 → 两次 `rename` 就地换掉那个 `.app` | 目录写得了就**不要** |
| `windows-x86_64` | `*_x64-setup.exe` | 被动模式 `/P` 跑一遍 | 安装器自己按需要弹 UAC |
| `linux-x86_64` | `*.AppImage` | 写临时文件 → `rename` 换掉自己 | 不要 |
| （清单里没有 `.deb`） | — | 下到 `~/.hunter/updates/` → 系统授权框 → `dpkg -i` | 要 |

`.deb` 从来就不在 `latest.json` 里（updater 换不了它），所以它那条路是
**Linux 专属的兜底分支**，macOS / Windows 再也落不进来。

### 1.3 macOS 上那两次 `rename`

```text
下 *_universal.app.tar.gz → 验签
  → 在 .app 旁边建一个隐藏的临时目录（这一步同时是「写权限实测」）
  → tar -xzf 解到那里
  → rename(旧 .app → 同目录下的 .hunter-launcher-old-<pid>)
  → rename(新 .app → 旧 .app 的位置)
  → 删掉临时目录与旧包
```

三个选择各有各的理由：

**为什么不写死 `/Applications/Hunter Launcher.app`。**
从**正在跑的这个可执行文件**往上找第一个 `.app`（`app_bundle_path()`）。
用户完全可能把它放在 `~/Applications`、外接盘或者下载文件夹里。
写死路径的后果不是「更新失败」，是**把新版本装到一个他根本没在用的位置上，
而界面还报「已更新」** —— 那比失败糟得多。

**为什么用「能不能在旁边建个目录」当权限判据，而不是看路径是不是 `/Applications`。**
建得起来，后面那两次 `rename` 就一定做得成（同一个目录、同一个文件系统，
`rename` 在同一文件系统上是原子的）。按路径猜则两头都可能错：
`/Applications` 默认是 `drwxrwxr-x root:admin`，管理员账号自己就写得了 ——
**macOS 上的自更新通常一个密码框都不弹**；而被 MDM 管起来的机器上它可能真的写不了。

**为什么失败要把旧的搬回来。** 第二次 `rename` 没成时 `rename(备份 → 原位)`。
宁可这次没更新成，也不能让用户下次打不开启动器。

写不了的那一档才走 macOS 自己的授权框，一条命令：

```text
rsync -a --delete <刚解出来的新 .app>/ <正在跑的那个 .app>/
```

它是这一轮给守卫新开的一道窄门 —— `argv_privileged` 那张表上的第三条形状
（前两条是 `dpkg -i <启动器的 .deb>` 与 `systemctl start docker`），两头都钉死：

* 源必须解析到 `~/.hunter/updates/` 里面，而且以 `.app` 结尾；
* 目标必须**等于 `app_bundle_path()` 算出来的那个包** —— 不是命令行里说了算。

少了第二条，这条命令就成了「以 root 身份把任意目录镜像成另一个目录、还带 `--delete`」，
那是这张表里最不该出现的东西。

### 1.4 Windows 那一条

下清单里的 `*_x64-setup.exe`，验签，然后 `setup.exe /P`。
`/P` 是 Tauri 的 NSIS 模板认的「被动模式」开关，
和 `tauri.conf.json` 里 `plugins.updater.windows.installMode = "passive"` 是同一档 ——
界面版走 Tauri 的 updater 也是这个模式，两条路的行为得一致。

**不带 `/R`**（装完把程序重新拉起来）：命令行这条路的调用方要的是一个退出码，
不是一个突然弹出来的窗口。

## 二、F2 · 那个虚高 15 倍的数字

### 2.1 两个错叠在一起

`--uninstall-plan` 在用户 Mac 上报的是：

```text
工作目录  86.1 GB
运行环境  86.1 GB
```

而同一时刻 `du -sh ~/.hunter` 是 **5.8 GB**。两行还一模一样。

**第一个错：按表观长度算。** `dir_size()` 数的是 `metadata().len()`。
内置运行时那台虚拟机的磁盘镜像是**稀疏文件** —— 它对外宣称自己有几十 GB
（那是虚拟机磁盘的上限），实际落在盘上的只有一两 GB。
用户那台机器上的实测是「表观 20 GB、实占 1.7 GB」。

现在数的是**实占块数**（`st_blocks × 512`，`du` 用的就是它）。
Windows 上 std 拿不到这个数（稀疏 / 压缩文件要 `GetCompressedFileSize`），
退回文件长度 —— 那个平台上没有内置运行时，不存在这一类文件。

**第二个错：两行数的是同一堆东西。** 运行环境是 `~/.hunter/runtime`，
它就在工作目录里面。两行都从 `~/.hunter` 整个算一遍，自然一模一样。
现在「工作目录」那一行把 `runtime` 刨掉（`dir_size_excluding`），
命令行上也直接写明「（不含运行环境）」。

### 2.2 那段连说两遍的警告

「不能同时删运行环境」这段话在 `Plan` 里本来就有一个自己的字段（`runtime_blocked`），
而 `plan()` 又把它 `push` 进了 `warnings`。命令行与界面都是「先印前者、再遍历后者」，
于是同一段话连着说两遍。

改法是在源头去掉那次 `push` —— 命令行与界面因此一起修好，
不用两边各改一次。有一条单测钉着它不会再被塞回去。

## 三、F3 · 重装时沿用留下来的 key

### 3.1 承诺与现场

「只删除应用，保留数据」那一档的界面原话是：

> 容器与启动器的配置会被删掉；数据库、密钥卷、历史对话、自建技能全都留着。
> **以后重新安装会直接沿用，登录也不会失效。**

`~/.hunter/app/.env` 确实被留下来了（里面有 hunter key 与 `JWT_SECRET`），
但重装时 `--auto -y` 报的是：

```text
E_KEY_INVALID: 标准输入不是终端，没法交互式问 key。用 --key-file <路径> 指一个文件。
```

—— 留是留下了，**没有人去读它**。

### 3.2 现在的顺序

```text
--key-file 给了？        → 用它（显式的永远优先）
否则 .env 里有一把吗？   → 格式对得上就当场验一次：
                             验得过 → 用它，并说一句「沿用上次保留的 key（hunt_tools_****）」
                             验不过 → 如实说为什么，继续往下
标准输入是终端吗？       → 是就问，不是就如实报（原来那句话保持不变）
```

三处细节：

* **只在格式对得上时才当「留下来的 key」**（`config::kept_hunter_key`）。
  格式都不对的东西不值得拿去问网关，更不该先说一句「沿用上次保留的 key」再被网关打回来 ——
  那就是在骗人（红线 1）。
* **验过的结果直接交给调用方**（`read_key` 返回 `(key, Option<KeyCheckResult>)`），
  同一把 key 不会连问网关两次。
* **key 明文不进输出**，只印打码后的样子（红线 2）。

### 3.3 界面那一侧

新增一个命令 `kept_key`：读 `.env` → 核格式 → 问一次网关。
验得过就**直接放进内存**，key 页上出现一张卡片
「沿用上次保留的 key（`hunt_tools_****`）」+ 一个「换一把别的 key」的链接，
输入框收起来，「下一步」直接可点。验不过就照常让他填，
**并且把网关给的原因摆在上面**。

**完整的 key 不返回给前端**，只给打码后的样子与校验结论。

判据抽成了 `src/lib/keptkey.ts` 的纯函数，四条前端单测钉着。
其中一条专门钉「额度用完了**不算**用不了」：
`reason === 'exhausted'` 时 `valid` 仍然是 true，这把 key 照样能装、照样能登录，
所以还是沿用它，只是界面上要另外说一句额度的提醒。

## 四、F4 · 定时备份任务什么时候回来

### 4.1 它其实一直会回来

`flow::start` 装完那一步本来就有这么一段（I13 写的）：

```rust
if cfg.backup.enabled {
    match crate::schedule::sync(…) { … }
}
```

问题是它**只往日志里写一行**，而 `--uninstall` 刚刚把 `~/.hunter/logs` 整个删掉了。
命令行的过程流里没有它，界面的完成页上也没有它。
于是用户重装完之后，以为定时备份再也不会回来，自己去手工 `--schedule install` 了一遍。

### 4.2 改了什么

* 装完那一步的结论存进 `AppState::post_install`，走 `RuntimeStatus` 到两个地方：
  命令行的第 6 步过程流、界面的完成页（排在那几条静态提示之前，因为它是**实测结论**）。
* 三种结局各说各的话，一句都不含糊：
  * 挂上了 → 「已按你的备份设置把每天 00:00 的自动备份重新挂上（systemd --user 定时器）」
  * 挂了但系统里查不到 / 报错 → 「自动备份的定时任务没挂上：<原因>。Hunter 本身不受影响，可以到设置页重试。」
  * 配置里关着 → 「配置里自动备份是关着的，所以没有装定时任务（设置页可以打开）」
* **删除应用那一侧也把话说全**：计划里那一行从「装着（会一并移除）」改成
  「装着（会一并移除；重装完成后按你的备份设置自动装回）」，
  执行报告里那一条同理，界面的删除对话框上多一行同样的话。

「装了但系统里查不到」那一档单独拎出来是有理由的：
`schedule::sync` 返回的 `Status` 是**现查系统**的结果，
`installed == false` 的时候把它当成成功，就是在界面上报一个假状态。
