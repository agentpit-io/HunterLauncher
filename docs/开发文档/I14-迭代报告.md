## 零、一句话

0.1.13 在用户的 Mac 上被逐条真跑了一遍：**七项通过，四项有问题**。
这一轮做的就是那四条，外加一条从来没在真机上验过的升级路径。

| | 0.1.13 在用户 Mac 上的样子 | I14 之后 |
|---|---|---|
| **F1**（P0）自更新 | 在 macOS 上**下了一个 Linux 的 `.deb`**，然后 `dpkg: command not found` | 按 `latest.json` 里这台机器那一项取包；macOS 解 `.app.tar.gz` 就地换掉那个 `.app` |
| **F2** 删除计划的体积 | 「工作目录 86.1 GB / 运行环境 86.1 GB」，而 `du -sh` 是 **5.8 GB**；警告连印两遍 | 按**实占块数**算；两行来自两处；警告只说一遍 |
| **F3** 重装时的 key | 刚承诺过「重装会直接沿用」，`--auto -y` 却报「标准输入不是终端」 | 要 key 之前先读 `.env`，验得过就沿用并说一句；界面同理 |
| **F4** 定时备份 | 删除应用把它一并移除了，重装之后**看不出来它回来没有** | 装完那一步把结论印在过程流与完成页上；删除时就说清「重装后会自动装回」 |
| **F5** Hunter 升级 | `--upgrade` 这条路**从来没在真机上验过** | 见第五节 |

这四条里有三条的共同点值得单独记一笔：**代码里那件事其实做了，缺的是「说出来」**。
F4 尤其典型 —— `flow::start` 装完本来就会挂定时任务，但它只往日志里写了一行，
而 `--uninstall` 刚刚把日志目录删掉了。**用户看不见的事等于没做**。

## 一、F1 · macOS 上的自更新

### 1.1 它当时是怎么坏的

用户 Mac 上 2026-09-23 23:34 的原话：

```text
已下载并验签 hunter-launcher_0.1.13_amd64.deb
E_NOT_IMPLEMENTED: /bin/sh: dpkg: command not found (127)
```

`self_update_headless` 里的 `match` 只单独处理了 AppImage：

```rust
match kind {
    InstallKind::AppImage => { …按清单取包，就地替换… }
    _ => { …下 .deb，走系统授权框跑 dpkg -i… }
}
```

`InstallKind::MacOS` 与 `InstallKind::Windows` 全落进那个 `_`。
而 `can_self_install()` 对这两个平台返回的是 **true** ——
也就是说界面那一侧（Tauri 的 updater）一直是对的，
**只有命令行这条路是错的**，而用户正好走的是命令行。

顺带还有一句话要纠正：那个分支无条件说

> 这台机器上的启动器是 **macos** 形式装的，换包要管理员权限。

两处都不对：macOS 上不是「换包」，而且**通常一个密码框都不用弹**。

### 1.2 现在怎么选包

**不再按安装形式去拼文件名。** `latest.json` 的 `platforms` 里，
每个平台本来就写着该下哪个 URL 与它的签名，按 `target_key()` 取就行
（`selfupdate::fetch_asset`）。选的不是我们拼的名字，是发布流水线自己写进清单的那一条。

| `target_key()` | 清单里那一项 | 怎么装 | 要不要管理员 |
|---|---|---|---|
| `darwin-x86_64` / `darwin-aarch64` | `*_universal.app.tar.gz`（两个键指同一个通用包） | 解包 → 两次 `rename` 就地换掉那个 `.app` | 目录写得了就**不要** |
| `windows-x86_64` | `*_x64-setup.exe` | 被动模式 `/P` 跑一遍 | 安装器自己按需要弹 UAC |
| `linux-x86_64` | `*.AppImage` | 写临时文件 → `rename` 换掉自己 | 不要 |
| （清单里没有 `.deb`） | — | 下到 `~/.hunter/updates/` → 系统授权框 → `dpkg -i` | 要 |

`.deb` 从来就不在 `latest.json` 里（updater 换不了它），所以它那条路是
**Linux 专属的兜底分支**，macOS / Windows 再也落不进来。

### 1.3 macOS 上那两次 `rename`

```text
下 *_universal.app.tar.gz → 验签
  → 在 .app 旁边建一个隐藏的临时目录（这一步同时是「写权限实测」）
  → tar -xzf 解到那里
  → rename(旧 .app → 同目录下的 .hunter-launcher-old-<pid>)
  → rename(新 .app → 旧 .app 的位置)
  → 删掉临时目录与旧包
```

三个选择各有各的理由：

**为什么不写死 `/Applications/Hunter Launcher.app`。**
从**正在跑的这个可执行文件**往上找第一个 `.app`（`app_bundle_path()`）。
用户完全可能把它放在 `~/Applications`、外接盘或者下载文件夹里。
写死路径的后果不是「更新失败」，是**把新版本装到一个他根本没在用的位置上，
而界面还报「已更新」** —— 那比失败糟得多。

**为什么用「能不能在旁边建个目录」当权限判据，而不是看路径是不是 `/Applications`。**
建得起来，后面那两次 `rename` 就一定做得成（同一个目录、同一个文件系统，
`rename` 在同一文件系统上是原子的）。按路径猜则两头都可能错：
`/Applications` 默认是 `drwxrwxr-x root:admin`，管理员账号自己就写得了 ——
**macOS 上的自更新通常一个密码框都不弹**；而被 MDM 管起来的机器上它可能真的写不了。

**为什么失败要把旧的搬回来。** 第二次 `rename` 没成时 `rename(备份 → 原位)`。
宁可这次没更新成，也不能让用户下次打不开启动器。

写不了的那一档才走 macOS 自己的授权框，一条命令：

```text
rsync -a --delete <刚解出来的新 .app>/ <正在跑的那个 .app>/
```

它是这一轮给守卫新开的一道窄门 —— `argv_privileged` 那张表上的第三条形状
（前两条是 `dpkg -i <启动器的 .deb>` 与 `systemctl start docker`），两头都钉死：

* 源必须解析到 `~/.hunter/updates/` 里面，而且以 `.app` 结尾；
* 目标必须**等于 `app_bundle_path()` 算出来的那个包** —— 不是命令行里说了算。

少了第二条，这条命令就成了「以 root 身份把任意目录镜像成另一个目录、还带 `--delete`」，
那是这张表里最不该出现的东西。

### 1.4 Windows 那一条

下清单里的 `*_x64-setup.exe`，验签，然后 `setup.exe /P`。
`/P` 是 Tauri 的 NSIS 模板认的「被动模式」开关，
和 `tauri.conf.json` 里 `plugins.updater.windows.installMode = "passive"` 是同一档 ——
界面版走 Tauri 的 updater 也是这个模式，两条路的行为得一致。

**不带 `/R`**（装完把程序重新拉起来）：命令行这条路的调用方要的是一个退出码，
不是一个突然弹出来的窗口。

## 二、F2 · 那个虚高 15 倍的数字

### 2.1 两个错叠在一起

`--uninstall-plan` 在用户 Mac 上报的是：

```text
工作目录  86.1 GB
运行环境  86.1 GB
```

而同一时刻 `du -sh ~/.hunter` 是 **5.8 GB**。两行还一模一样。

**第一个错：按表观长度算。** `dir_size()` 数的是 `metadata().len()`。
内置运行时那台虚拟机的磁盘镜像是**稀疏文件** —— 它对外宣称自己有几十 GB
（那是虚拟机磁盘的上限），实际落在盘上的只有一两 GB。
用户那台机器上的实测是「表观 20 GB、实占 1.7 GB」。

现在数的是**实占块数**（`st_blocks × 512`，`du` 用的就是它）。
Windows 上 std 拿不到这个数（稀疏 / 压缩文件要 `GetCompressedFileSize`），
退回文件长度 —— 那个平台上没有内置运行时，不存在这一类文件。

**第二个错：两行数的是同一堆东西。** 运行环境是 `~/.hunter/runtime`，
它就在工作目录里面。两行都从 `~/.hunter` 整个算一遍，自然一模一样。
现在「工作目录」那一行把 `runtime` 刨掉（`dir_size_excluding`），
命令行上也直接写明「（不含运行环境）」。

### 2.2 那段连说两遍的警告

「不能同时删运行环境」这段话在 `Plan` 里本来就有一个自己的字段（`runtime_blocked`），
而 `plan()` 又把它 `push` 进了 `warnings`。命令行与界面都是「先印前者、再遍历后者」，
于是同一段话连着说两遍。

改法是在源头去掉那次 `push` —— 命令行与界面因此一起修好，
不用两边各改一次。有一条单测钉着它不会再被塞回去。

## 三、F3 · 重装时沿用留下来的 key

### 3.1 承诺与现场

「只删除应用，保留数据」那一档的界面原话是：

> 容器与启动器的配置会被删掉；数据库、密钥卷、历史对话、自建技能全都留着。
> **以后重新安装会直接沿用，登录也不会失效。**

`~/.hunter/app/.env` 确实被留下来了（里面有 hunter key 与 `JWT_SECRET`），
但重装时 `--auto -y` 报的是：

```text
E_KEY_INVALID: 标准输入不是终端，没法交互式问 key。用 --key-file <路径> 指一个文件。
```

—— 留是留下了，**没有人去读它**。

### 3.2 现在的顺序

```text
--key-file 给了？        → 用它（显式的永远优先）
否则 .env 里有一把吗？   → 格式对得上就当场验一次：
                             验得过 → 用它，并说一句「沿用上次保留的 key（hunt_tools_****）」
                             验不过 → 如实说为什么，继续往下
标准输入是终端吗？       → 是就问，不是就如实报（原来那句话保持不变）
```

三处细节：

* **只在格式对得上时才当「留下来的 key」**（`config::kept_hunter_key`）。
  格式都不对的东西不值得拿去问网关，更不该先说一句「沿用上次保留的 key」再被网关打回来 ——
  那就是在骗人（红线 1）。
* **验过的结果直接交给调用方**（`read_key` 返回 `(key, Option<KeyCheckResult>)`），
  同一把 key 不会连问网关两次。
* **key 明文不进输出**，只印打码后的样子（红线 2）。

### 3.3 界面那一侧

新增一个命令 `kept_key`：读 `.env` → 核格式 → 问一次网关。
验得过就**直接放进内存**，key 页上出现一张卡片
「沿用上次保留的 key（`hunt_tools_****`）」+ 一个「换一把别的 key」的链接，
输入框收起来，「下一步」直接可点。验不过就照常让他填，
**并且把网关给的原因摆在上面**。

**完整的 key 不返回给前端**，只给打码后的样子与校验结论。

判据抽成了 `src/lib/keptkey.ts` 的纯函数，六条前端单测钉着。
其中一条专门钉「额度用完了**不算**用不了」：
`reason === 'exhausted'` 时 `valid` 仍然是 true，这把 key 照样能装、照样能登录，
所以还是沿用它，只是界面上要另外说一句额度的提醒。

### 3.4 验收时自己撞出来的第三档：留着东西、但它不是一把 key

跑 `f3-bad-key` 那个场景时看到的原话是这样的：

```text
✗ E_KEY_INVALID: 标准输入不是终端，没法交互式问 key。用 --key-file <路径> 指一个文件。
```

—— 没有谎称「沿用」，这一条是对的。**但它一个字都没提 `.env` 里那把 key。**

根子在 `kept_hunter_key()` 只有两种结果：给得出一把，或者 `None`。
而 `None` 底下压着两件完全不同的事：

| `.env` 里 | 该说什么 |
|---|---|
| 根本没有 `HUNTER_API_KEY` 这一项 | 一个字都不用说（第一次装、或者选了「删除应用和全部数据」） |
| 有，但它不是一把 hunter key 的样子（手改过、粘贴时少了一截） | **要说**，否则用户看到的就是「我明明留着 key，它却让我重新输」 |

这就是 F4 那个坏法的另一个版本：**事情做了（读了），只是没说出来（为什么没用上）**。
于是拆成三档 `config::KeptKeyState`（`Absent` / `BadShape` / `Usable`），
命令行多印一行、界面多一张 `key-kept-shape` 的说明，前端判据多一档 `'shape'`。

### 3.5 `BadShape` 那一支里**不能**登记密文

第一版在 `BadShape` 里顺手 `redact::register_secret` 了一下，
理由是「它可能是一把真 key 被截断了一截，剩下那一截也不该出现在日志里」。
一跑单测当场红了五个（`redact` / `err` / `log` / `feedback`）：

```text
预期  LLM_API_KEY=hunt_tools_**** 写入 .env
实际  LLM_API_KEY=hun******** 写入 .env
```

登记表是**整个进程共用**的，而形状不对最常见的坏法恰恰是
`HUNTER_API_KEY=hunt_tools_`（key 正文被删干净了）。
把它登记进去，`hunt_tools_` 这个**前缀本身**就成了密文 ——
此后每一行日志里的 `hunt_tools_****` 都会被再替换一次，
`mask_key("hunt_tools_")` 回的是 `hun****`，于是变成 `hun********`：
**打码函数把自己的输出打成了看不出是什么的东西**。

不登记也不漏：`redact::mask_shapes` 本来就按前缀整段打掉 `hunt_tools_…`，
一把被截断的真 key 照样盖得住。新增一条单测专门钉这件事
（`看过形状不对的值之后打码函数还是好的`）。

## 四、F4 · 定时备份任务什么时候回来

### 4.1 它其实一直会回来

`flow::start` 装完那一步本来就有这么一段（I13 写的）：

```rust
if cfg.backup.enabled {
    match crate::schedule::sync(…) { … }
}
```

问题是它**只往日志里写一行**，而 `--uninstall` 刚刚把 `~/.hunter/logs` 整个删掉了。
命令行的过程流里没有它，界面的完成页上也没有它。
于是用户重装完之后，以为定时备份再也不会回来，自己去手工 `--schedule install` 了一遍。

### 4.2 改了什么

* 装完那一步的结论存进 `AppState::post_install`，走 `RuntimeStatus` 到两个地方：
  命令行的第 6 步过程流、界面的完成页（排在那几条静态提示之前，因为它是**实测结论**）。
* 三种结局各说各的话，一句都不含糊：
  * 挂上了 → 「已按你的备份设置把每天 00:00 的自动备份重新挂上（systemd --user 定时器）」
  * 挂了但系统里查不到 / 报错 → 「自动备份的定时任务没挂上：<原因>。Hunter 本身不受影响，可以到设置页重试。」
  * 配置里关着 → 「配置里自动备份是关着的，所以没有装定时任务（设置页可以打开）」
* **删除应用那一侧也把话说全**：计划里那一行从「装着（会一并移除）」改成
  「装着（会一并移除；重装完成后按你的备份设置自动装回）」，
  执行报告里那一条同理，界面的删除对话框上多一行同样的话。

「装了但系统里查不到」那一档单独拎出来是有理由的：
`schedule::sync` 返回的 `Status` 是**现查系统**的结果，
`installed == false` 的时候把它当成成功，就是在界面上报一个假状态。

## 五、F5 · Hunter 版本升级（第一次真跑）

`--upgrade` 这条路从 M4 就写在那里，**一次都没有在真机上跑过**。
这一轮补上了，而且顺手把它的失败分支也跑了两种。

### 5.1 顺利那一次：1.2.0 → 1.2.1

测试机上装的正好是 1.2.0，而上游 2026-09-22 发了 1.2.1
（补丁级，Release Notes 自己写着「无数据库变更、无新环境变量」）。

```text
升级 Hunter v1.2.0 → v1.2.1
  正在取 v1.2.1 的 docker-compose.yml…
  已取到（来自 raw.githubusercontent.com，23990 字节）
  正在备份（数据库 + 配置）…
  备份放到 <用户目录>/Hunter-backups/hunter-20260924-2327-v1.2.0
  已备份配置：.env、docker-compose.yml、docker-compose.launcher.yml、launcher.toml
  数据库已转储（144 KB）
  校验通过 · pg_restore --list 读出 391 条目录项
  已打包 hunter_secrets（303 B）/ hunter_user_skills（87 B）/ hunter_opencode_data（15.2 KB）
  已写入新的 compose 与 .env（HUNTER_VERSION=1.2.1，端口不变）
  docker compose config 校验通过，六个服务的端口全部绑在 127.0.0.1（红线 4）
  要拉的六个镜像合计约 850 MB（已有的层不会重复下载）
  正在拉取新版本的镜像… → 正在用新镜像重建容器… → 6 个服务全部就绪
  已升级到 v1.2.1
```

**实测：144 秒**。`launcher.toml` 的 `tag` 与 `.env` 的 `HUNTER_VERSION` 都变成 1.2.1，
6/6 健康，**升级前后都是 61 张表**。升级前那份备份自己就带着校验结论
（`pg_restore --list` 读出 391 条目录项），不是「做完就算」。

一处**实测与方案不符**已在 `upgrade.rs` 文件头记着，这一轮当场核实：
方案说「替换 `OPENCODE_TAG`」，而 hunter-community 的 compose 用的是
**一个** `HUNTER_VERSION` 管全部四个镜像，没有 `OPENCODE_TAG` 这个东西。

### 5.2 失败那两次：停在哪一步，决定该不该说「回滚」

`upgrade.rs` 文件头把顺序写死了：

```text
① 取新版 compose（严格模式，取不到就停）      ← 还没动任何东西
② 备份                                        ← 同上
─────────────── 从这里开始，失败要回滚 ───────────────
③ 写新 compose / 新 .env / 覆盖文件
④ docker compose config 校验 + 红线 4 的端口自查
⑤ pull（失败自动换源重试 3 次）
⑥ up -d + 等 180 秒健康
```

**①② 失败时不许说「已回滚」** —— 没动过的东西没有什么可回滚的，
说了就是在编（红线 1）。所以这两种失败要分开验。

**`f5-nosuch`：一个根本不存在的 tag。** 停在第 ① 步：

```text
✗ E_COMPOSE_FETCH: 取不到 v9.9.9-i14-不存在 的 docker-compose.yml：
  raw.githubusercontent.com HTTP 400；hunter-dl-hk-…myqcloud.com HTTP 404。这个版本可能不存在。
```

退出码 1、**输出里一个「回滚」字样都没有**、`tag` 原样是 1.2.1。这一档要断言的恰恰是「没提回滚」。

**`f5-rollback`：走到第 ⑤ 步再倒下来。** 这一档的造法费了点事，两次没造成：

| 造法 | 结果 |
|---|---|
| 不存在的 tag（`9.9.9-…`） | 停在 ①，compose 根本取不到 —— 这是上面那一档 |
| 真实存在的旧 tag `1.0.0` / `1.0.1` | 也停在 ①：tag 在 GitHub 上是真的、compose 也取得到，但那一版的 compose 里**没有 `hunter-community-web` 这个镜像引用**，`config::validate_compose` 当场拦下 |

而 hunter-community **已发布的每一个 tag，四个镜像都在 ghcr 上**
（`1.2.0-rc1` / `1.1.0-rc1` / `1.1.0-rc2` 逐个 `docker manifest inspect` 核过）——
「compose 合格、镜像却拉不到」这个组合在上游根本不存在，造不出来。

于是改成造**拉取本身失败**，用的是 **I6 在用户 Mac 上真撞过的那个失败**：
`DOCKER_CONFIG` 指向一份写着不存在的 `credsStore` 的配置，docker 客户端连凭据都取不到。
这条失败 `flow::pull` 判定为「与下载源无关」（`Code::CredHelper`），**不换源、直接返回** ——
正好落在第 ⑤ 步。那份配置只挂在这一条命令的环境变量上，**机器上的 docker 配置一个字节都没动**。

```text
  已写入新的 compose 与 .env（HUNTER_VERSION=1.2.0，端口不变）      ← ③ 做了
  docker compose config 校验通过，六个服务的端口全部绑在 127.0.0.1  ← ④ 过了
  正在拉取新版本的镜像…  0% 0 B / 849 MB
  升级失败：Docker 要用本机的凭据助手去取登录信息，但在这个程序看得到的 PATH 上找不到它。
            这和下载源无关，换源修不好。
  正在回滚到 v1.2.1…
  已写回升级前的 .env、docker-compose.yml、docker-compose.launcher.yml
  已回滚到 v1.2.1，6 个服务重新就绪。
```

**实测 15 秒**，逐条核过：

| 断言 | 结果 |
|---|---|
| 如实失败（退出码 1），没有谎称成功 | ✅ |
| 走到了第 ③ 步（新 compose 真写下去了）—— 这一次是真的需要回滚 | ✅ |
| 动手之前先备份了一次 | ✅ `hunter-20260924-2334-v1.2.1` |
| `launcher.toml` 的 `tag` 回到 1.2.1 | ✅ |
| `.env` 的 `HUNTER_VERSION` 回来了 | ✅ |
| **覆盖文件逐字节回到升级前**（md5 相同） | ✅ |
| 回滚之后 6/6 健康 | ✅ |
| 数据没动（仍然 61 张表） | ✅ |
| **六个容器一个都没重建**（容器 ID 全同） | ✅ |

最后一条是意外之喜：回滚时 `up -d` 用的是写回去的旧 compose，
docker 发现「期望状态和现状一样」，**一个容器都没动**。
也就是说这一次失败的升级对正在用 Hunter 的人是**完全无感**的。

## 七、没做的 / 未验证的

### 7.1 macOS 的自更新：**这一轮修的那条路，本轮没有在 macOS 上跑过**

这是本轮最大的一个洞，写在最前面。

F1 改的是「macOS 上 `--self-update` 该下哪个包、下完怎么装」，
而这个项目只有一台 Linux 测试机。本轮在 Linux 上真跑的是**选包那一半**
（`fetch_asset` 按 `target_key()` 取、四个平台的后缀断言、`latest.json` 的实物核对），
以及**换包那一半里和 macOS 无关的部分**（`swap_bundle` 的两次 `rename`
与「搬不进去把旧的放回原位」，它们是纯文件系统操作，单测在 Linux 上真跑）。

**没跑过的是把这些串起来的那一次**：在一台真 Mac 上下 `*_universal.app.tar.gz`、
`tar -xzf` 解开、换掉 `/Applications/Hunter Launcher.app`、再打开它看版本号。
按总控规则的「默认决策」，这一条记为「未真机测试」。

验法由本地 Claude 在用户 Mac 上做，三步：
**降级到 0.1.13 → `--self-update` → 核版本号与包的改动时间 → 打开它**。
结果**待本地 Claude 回填**。待办池 P1-15 保持开着，直到那一次回来。

### 7.2 Windows 的两条路仍然只有单测

`windows_install` 的 `setup.exe /P`（F1）与 I13 的 `schtasks /XML`（待办池 P1-41）
都只有单测与代码路径审阅。这个项目没有 Windows 机器，用户手上是 Mac。
CI 的 `windows-latest` 能保证它编得过、纯逻辑单测过得了，仅此而已。

### 7.3 「重装之后定时任务自己回来」在 macOS 上还没看见过

F4 在 Linux 上真跑通了（`systemd --user` 那一套），但用户 0.1.13 那次现场是 macOS 的
LaunchAgent。**当时到底有没有回来，现在说不清** —— 那一版一个字都不印，
而日志目录刚被 `--uninstall` 删掉了。0.1.14 在用户 Mac 上再走一遍
「删除应用（保留数据）→ 重装」就能看见那句话。已记为待办池 **P1-42**。

### 7.4 `/Applications` 写不了那一档（走系统授权框）没有真机

F1 里 macOS 分两档：目录写得了就两次 `rename`（**常见情况**，`/Applications`
默认是 `drwxrwxr-x root:admin`），写不了才走 macOS 自己的授权框跑一条
`rsync -a --delete`。第二档要一台被 MDM 管起来、或者 `.app` 装在别人账号下的机器才触发。
守卫那一侧（`argv_privileged` 的第三条形状）有单测逐条钉死，
**但那条 `rsync` 本身一次都没有以 root 身份真跑过**。

这一档的设计取向是「宁可不更新，也不乱动」：判据不是「路径像不像 `/Applications`」，
而是**真去它旁边建一个目录试试**——所以判错的方向只会是「本来不用密码却弹了一次框」，
不会是「以为写得了、结果把包换坏了」。

### 7.5 本轮没碰、因此也没重测的

I5 / I7 的场景 1–4（Docker 缺失 / daemon 没起 / 端口被占 / 拉取失败）这一轮没跑，
理由和 I12、I13 一样：场景 2 要 `systemctl stop docker`、场景 4 要 `iptables` 拦 ghcr，
两者都会波及测试机上另外三套在跑的项目（红线 9）。本轮代码没有碰到它们那几条路。
