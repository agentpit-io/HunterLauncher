## 二、详解：P0-5 —— 两个工作目录会互相顶掉

### 2.1 问题

`docker compose` 是**按项目名**认容器的，而启动器把项目名固定成 `hunter`（总控规则要求，
为的是和用户手工部署的 `hunter-community` 分开）。于是：

```
HUNTER_HOME=~/.hunter    装一套  → 容器 hunter-web-1 … 的配置指向 ~/.hunter/app
HUNTER_HOME=~/.hunter-b  再装一套 → docker compose -p hunter up -d
                                    → **同一批容器名**被按 ~/.hunter-b/app 的配置重建
```

结果是先装好的那一套**连配置带端口一起被顶掉**：书签失效、`.env` 指向的不再是它、
运行面板显示的端口对不上真实容器。数据卷不会被 `up -d` 删掉，但用户得重装一次才能回到原样。

M2 换工作目录做测试时真撞到过一次，M3 用 `HUNTER_HOME=~/.hunter-cnpull` 跑国内源测试时
又擦边一次（那次只 `--pull-only`，没真 `up -d`，所以侥幸没顶掉）。

### 2.2 怎么修的

`docker ps -a` 给得出每个容器的两个 compose 标签：

```
com.docker.compose.project.config_files   /home/u/.hunter/app/docker-compose.yml,/home/u/.hunter/app/docker-compose.launcher.yml
com.docker.compose.project.working_dir    /home/u/.hunter/app
```

`compose::guard_project_owner()` 在动容器之前查一次 `project=hunter` 的全部容器（**含已停止的**），
只要有一个的这两个标签都对不上我们这次要用的路径，就停下来报 `E_PROJECT_CONFLICT`。

判定「是我们的」两条满足其一即可 —— `config_files` 里有我们的 `docker-compose.yml`，
**或者** `working_dir` 就是我们的 `~/.hunter/app`。做成「沾边就算我们的」是有意的：
**宁可漏报也不能误报**，误报会把一次正常安装整个拦死。同样地，标签读不到
（老版本 docker、手工 `docker run` 起的容器）一律放行；`docker` 本身起不来也放行 ——
这是一道保险，不是必经的关卡。

闸门装在五个地方，覆盖所有会动容器的入口：

| 位置 | 为什么要单独一道 |
|---|---|
| `flow::prepare` | 拦得最早，别让用户白等 850 MB 的拉取 |
| `compose::up` | 真正的收口：安装、`--start`、托盘「启动」、升级都走它 |
| `compose::up_services` | 切模型模式会 `--force-recreate` 三个容器，落到别人那套上就是事故 |
| `backup::ensure_postgres`（`up -d postgres`） | 备份跑在升级**之前**，比 `compose::up` 更早 |
| —— | （`down` 不拦：用户就是要停掉别人那套，拦了反而没有出路） |

报错文案给两条**可以直接照做**的出路，并且说清数据没丢：

```
这台机器上已经有一套 Hunter 在用 compose 项目名「hunter」，它的工作目录是 /home/u/.hunter（容器 hunter-web-1）。
现在这个工作目录是 /home/u/.hunter-b。继续下去会把那一套的配置和端口一起顶掉，所以先停在这里。
想接着用那一套：把工作目录改回去（环境变量 HUNTER_HOME=/home/u/.hunter，或者直接不设这个变量）。
想换成这一套：先把旧的停掉再来 —— HUNTER_HOME=/home/u/.hunter hunter-launcher --down。
（数据卷不会被 up -d 删掉，顶掉的是配置与端口。）
```

新增错误码 `E_PROJECT_CONFLICT`（方案 §18 没有这一条，是实测补的，前端 `machine.ts`
与两份 i18n 同步加了）。

### 2.3 一处偏离方案

方案 §7 默认「一台机器只有一个 `~/.hunter`」，所以没有这个错误码，也没有项目名归属的概念。
实测这个假设不成立（`HUNTER_HOME` 是我们自己为了测试提供的口子，用户换工作目录也很自然），
按「与实测冲突时以实测为准」补上，已记在这里。

## 三、详解：本轮自审抓出来的三个问题

这三条谁都没记过，是通读代码时发现的。

### 3.1 「打开链接」的白名单能被绕过（安全）

`commands.rs` 的 `open_url_checked` 是启动器唯一「让操作系统去打开点什么」的口子
（运行面板的「打开 Hunter」、托盘、反馈页的「去 GitHub 提 issue」都走它）。原来的判断是：

```rust
let allowed = url.starts_with("https://")
    || url.starts_with("http://localhost")     // ← 这里
    || url.starts_with("http://127.0.0.1");    // ← 和这里
```

只比前缀，于是 `http://localhost.example.com/x`、`http://127.0.0.1.example.com/`、
`http://localhost-evil.test` 全都**算本机**，会被当成可信地址交给系统浏览器。
`http://127.0.0.10:80` 也一样（`127.0.0.1` 是 `127.0.0.10` 的前缀）。

改成：主机名后面必须紧跟 `:`（端口）、`/`（路径），或者就此结束。

```rust
pub fn url_allowed(url: &str) -> bool {
    if url.starts_with("https://") { return true; }
    let Some(rest) = url.strip_prefix("http://") else { return false; };
    ["localhost", "127.0.0.1"].iter().any(|h| {
        rest.strip_prefix(h).is_some_and(|after| {
            after.is_empty() || after.starts_with(':') || after.starts_with('/')
        })
    })
}
```

**实际可利用性有多高**：不高。这个函数的入参目前全部来自启动器自己算出来的地址
（`http://localhost:<端口>` 与几个写死的 https 链接），没有一条来自网络。
所以这是一道**纵深防御被打穿**，不是一个能直接打的洞。但这道防御存在的全部理由就是
「万一前端被注入了什么」，漏成这样等于没有，所以本轮修掉并补了 4 组单测
（含 4 个必须被拒的假冒本机域名）。

### 3.2 把中文粘进「自带模型 key」框可能让脱敏函数崩掉

`redact::mask_key` 给登记过的密文做短打码。原来的兜底分支是：

```rust
_ if key.len() > 3 => format!("{}****", &key[..3]),
```

`key.len()` 是**字节数**，`&key[..3]` 是**字节切片**。`"a密码…"` 这种串
（1 字节 + 3 字节的汉字）切在第 3 个字节上，正好落在汉字中间 → Rust 直接 panic。

谁会把中文放进 key？`register_secret` 登记的东西里有一项是**用户在「自带模型 key」
那个框里填的字符串** —— 填错框、粘错剪贴板都很常见。之后只要有任意一条日志里
出现这串字符，脱敏就会走到这里。

改成按**字符**取前三个（`char_indices().nth(3)`），并补了一条单测，
里面直接断言 `mask_key("a密码钥匙串") == "a密码****"` 以及整条日志过一遍脱敏不崩。

### 3.3 最小化 / 最大化按钮的提示是两个符号

标题栏三个圆点里，只有「关闭」有中文提示，另外两个的 `title` / `aria-label` 是
`—` 和 `⤢`。鼠标悬停上去看到一个破折号，屏幕阅读器念出来更莫名其妙。
两份 i18n 补了 `minimize` / `maximize`。

## 四、详解：其余三条

### 4.1 `~/.hunter` 下的文件统一 600（待办池 P2-11）

之前只有 `.env` 是 600（红线 2 的硬要求），`launcher.toml`、`docker-compose.yml`、
`docker-compose.launcher.yml` 都是 644。这三个文件里确实没有 secret，
但「工作目录里的东西只有属主能读」是更省心的口径，何况目录本身已经是 700。

`config.rs` 的四个写文件函数后面都补了 `paths::chmod_600`，并加了一条单测
把四个文件一次写出来、逐个断言权限位是 `0o600`。Windows 上 `chmod_600` 本来就是
空实现（没有 POSIX 权限位，靠用户目录的 ACL），如实返回 `Ok`。

**对已装机器的影响**：升级之后不会自动改已有文件的权限 —— 要等下一次
「重新安装 / 改一次设置 / 升级 Hunter」触发那几个写函数才会收紧。这是有意的，
启动器不在启动时扫一遍用户目录改权限。

### 4.2 Windows 上的三个窗口按钮（待办池 P1-7）

视觉稿把三个点画在**左上角**、顺序是「关闭 / 最小化 / 最大化」（mac 风格）。
M1 按稿 1:1 实现，三平台一致。问题是 Windows 用户点关闭是**右上角**的肌肉记忆，
照搬过去每次都会点错。

本轮按平台分开：

| 平台 | 位置 | 顺序 |
|---|---|---|
| macOS | 不自绘，用系统原生红绿灯（左上），只留 70px 空位 | 系统决定 |
| Linux | 左上角（**与视觉稿一致，没动**） | 关闭 / 最小化 / 最大化 |
| Windows | **右上角**（版本号右侧） | 最小化 / 最大化 / 关闭 |

**这一条没有 Windows 真机验证**（没有真机），只有代码路径审阅与 CI 编译。
Linux 上的截图可以证明「非 Windows 分支没被改坏」，Windows 分支只能等真机。

### 用例 6 · 额度用尽（402）实测 —— 待办池 P0-2

做法（总控规则红线 6）：只动**本项目自己在 M0 签发的那一把测试 key**（`id=49` ·
`launcher-m0` · 账号 hangeaiagent），把日额度临时压到 1 token，测完用 `--quota 49 0`
恢复成「不单独设置、用默认值」—— 那正是它原来的状态，所以是一次精确可逆的往返。
动手前先 `--show 49` 核对过账号与名字，**没有碰任何别的记录**。

**实测结论，两个接口的行为不一样**：

| 接口 | 状态码 | 响应体（节选） |
|---|---|---|
| `GET /api/saas/llm/quota` | **200** | `{"ok":true,"used_today":170206,"limit_daily":1,"remaining":0,"exhausted":true,"reset_at":"2026-09-21T00:00:00+08:00",…}` |
| `POST /api/saas/llm/v1/chat/completions` | **402** | `{"error":{"message":"HunterCode 内置模型额度今天用完了（已用 170,206 / 上限 1 token）。…","type":"insufficient_quota","code":"daily_quota_exceeded","used_today":170206,"limit":1,"reset_at":"2026-09-21T00:00:00+08:00","retry_after":60939}}` |

`code=daily_quota_exceeded` / `type=insufficient_quota` 与 M0 从 hermes 代码里读到的一致，
这一条终于有实测背书了。

**但实测顺手抓出一个真问题**：`gateway::check_key` 打的是 `/quota`，而 `/quota`
在额度用尽时回的是 **200**，所以 `check_key` **永远收不到 402** ——
`KeyReason::Exhausted` 这条分支此前是死代码。表现就是：额度早就用光了，
key 校验一路绿灯、一个字都不提，用户装完之后在 Hunter 里发第一句话才被拒。

修法：`QuotaInfo` 加 `exhausted`（网关字段优先，没有就按 `remaining` 兜底，
但**上限读不到时不算「用完」**—— 那是「不知道」，不是「用完」）。`check_key` 在
exhausted 时仍然返回 `valid: true`（key 确实是好的，第二天 0 点重置，下一步也能换自带 key），
但把 `reason` 置成 `exhausted` 并给一句话，**不挡住「下一步」**。

修完之后重新压了一次额度验证（`~/i1-t-402b.log`）：

```
[2/6] hunter key
  从 /home/support/.hunter-launcher-test/key 读到一把 key（hunt_tools_****）
  ⚠ 这把 key 是好的，但今天的额度已经用完了（已用 170206 / 上限 1）。额度在 2026-09-21 00:00（上海）重置。
    装可以照装，装完之后对话会被网关挡住，直到额度重置。现在就想用的话，下一步改用你自己的模型 key。
  ✓ key 有效 · 今日已用 170206 / 1 · 剩 0 · 每分钟 20 次 · 并发 4
```

界面上是琥珀色的提醒（不是红色的错误），截图 [`16-输入key-额度已用尽.png`](../screenshots/I1/16-输入key-额度已用尽.png)：
「今日剩余 **0** tokens」「今日模型额度 **1**」，「下一步」仍然可点。

测完立刻恢复，并复核 `--show 49` 回到「(未单独设置，用默认值)」。

## 七、需要用户决定：web 端口对公网开放

**这是本轮自审里最重要的一条，也是唯一一条「发现了但没有自己改掉」的。**

### 7.1 实测

启动器生成的覆盖文件里，web 那一行是：

```yaml
  web:
    ports: !override ["3101:3000"]      # 没有 127.0.0.1: 前缀 = 绑所有网卡
```

这是**按总控规则做的**：红线 4 的原话是「除 web 之外的端口（api / opencode / postgres / redis）
一律绑定 127.0.0.1」，并且在测试机防火墙那一节明确写着「启动器新栈的 web 端口不在拦截名单里
（按设计对外）」。所以这不是 bug，是既定设计。

本轮实测了它的实际后果 —— 从**开发机**（另一台机器，走公网 IP）打 `http://34.133.8.3:3101`：

| 试的东西 | 结果 |
|---|---|
| 打开聊天界面 | ✅ 直接进，没有任何登录 / 口令 |
| 提问并调用行情工具 | ✅ 真答出来了（用例 2 就是这么跑的） |
| 消耗的是谁的额度 | **用户的** —— 网关 `used_today` 跟着涨 |
| `/api/setup/status` | ❌ 401 `no_token_public`（上游 api 对公网访问**有**保护） |
| `/api/setup/env-check`、`/api/setup/llm/quota` | ❌ 同上 401 |
| `/api/health` | ✅ 200（只有 `status` 与 `hunter_api_key: configured`，不算敏感） |

也就是说：**上游保护住了「配置面」，但没有保护「使用面」**。
启动器写的 `HUNTER_SINGLE_USER=1` / `HUNTER_SETUP_TOKEN=`（留空）也都不构成登录墙。

对桌面用户来说，这意味着：只要这台机器的 3100 端口能被别人访问到
（公网 IP、公司内网、咖啡馆 WiFi、路由器上做过端口映射……），
**任何人都能用他的 Hunter、烧他的额度**。

### 7.2 本轮做了什么、没做什么

**做了**：完成页的提示列表里加了一条，把这件事直说：

> 这个地址绑在本机所有网卡上：同一网络里的人打开它就能直接用，并且用的是你的额度。只想自己用就给这台机器的防火墙加一条规则

**没做**：没有改默认绑定。理由是这属于产品决策，不是本项目单方面能定的 ——
总控规则把 web 明确排除在「只绑 127.0.0.1」之外，改它等于改规则。

### 7.3 要用户定的是什么

技术上一轮就能做完（`launcher.toml` 加一项 `hunter.web_bind`、设置页一个开关、
覆盖文件里写成 `127.0.0.1:{port}:3000`、加几条单测），真正的问题只有两个：

1. **默认值该是哪一个？** 「只有本机」更安全，「所有网卡」更方便（手机上也能开）；
2. **已经装好的机器要不要在升级时自动收紧？** 收紧会让「昨天手机上还能开」突然失效。

我的建议：**默认收成只有本机，设置页给一个「允许同一网络里的其他设备访问」的开关（默认关），
升级时不动已有配置，只在运行面板上提示一次**。但这是建议，不是决定。
已记为待办池 **P1-20**。
