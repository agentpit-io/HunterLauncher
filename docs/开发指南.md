## 一、环境

| 东西 | 版本 | 备注 |
|---|---|---|
| Node | 22+ | |
| pnpm | 10（CI 用的） | pnpm 12 有坑，见下 |
| Rust | stable | `rustup` 装 |
| Python | 3.8+ | 只有几个脚本用（字体、COS、清单生成） |

Ubuntu 22.04 / 24.04 的系统依赖：

```bash
sudo apt install -y libwebkit2gtk-4.1-dev libgtk-3-dev libayatana-appindicator3-dev \
                    librsvg2-dev libsoup-3.0-dev libjavascriptcoregtk-4.1-dev \
                    libssl-dev build-essential curl wget file pkg-config xdg-utils
```

> **`xdg-utils` 不在 Tauri 官方依赖清单里**，但 AppImage 打包要把 `xdg-open` 塞进 AppDir，
> 缺了会在打包的**最后一步**才失败。别问我们怎么知道的。

### pnpm 12 的 `minimumReleaseAge`

pnpm 12 默认拒绝 24 小时内发布的包。锁文件里只要有一个当日发布的传递依赖
（`@rollup/rollup-*` 经常中招），**任何** pnpm 命令都会红，包括 `pnpm exec`：

```
ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION
The lockfile contains entries that the active policies reject.
```

更麻烦的是 `tauri build` 的 `beforeBuildCommand` 是 `pnpm build`，所以连打包都被卡住。
绕法（按麻烦程度排）：

```bash
# 1. 直接调本地二进制，绕开 pnpm 这一层
./node_modules/.bin/vite build
./node_modules/.bin/tauri build --config '{"build":{"beforeBuildCommand":""}}' …

# 2. 或者在机器上把这条策略放宽（长期方案）
```

CI 用 pnpm 10，不受影响。等锁文件里的包都过了 24 小时问题会自动消失。
**改了 `package.json` 的 version 会重新触发校验**（pnpm 会重新核对锁文件），
所以每次发版都可能在这台机器上撞一次。

macOS 上打通用二进制要两个 target：

```bash
rustup target add aarch64-apple-darwin x86_64-apple-darwin
```

## 二、跑起来

```bash
pnpm install

pnpm tauri dev          # 开发，前端热重载
pnpm tauri build        # 出当前平台的安装包

# 只跑前端的检查，不需要 Rust
pnpm lint && pnpm typecheck && pnpm test && pnpm build

# Rust
cargo fmt   --manifest-path src-tauri/Cargo.toml
cargo test  --manifest-path src-tauri/Cargo.toml
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

**演示数据模式**（浏览器里预览界面、和视觉稿做截图比对）：

```bash
VITE_DEMO=1 pnpm dev
HUNTER_DEMO_PAGE=dashboard VITE_DEMO=1 pnpm tauri dev   # 直接打开某一页
```

界面右上角会有「演示数据」角标。**发布构建里进不去这个模式**：`VITE_DEMO` 是编译期常量，
`vite.config.ts` 里有断言（`HUNTER_CHANNEL=release` 时不许带 `VITE_DEMO=1`），
CI 里还会 grep 产物确认没有演示数据的标记，并且反过来验证一次"演示构建里确实有这个标记"——
否则那个检查可能是空跑。

## 四、几条不能破的规矩

这几条不是风格偏好，是这个项目的底线。改代码时对照一下：

### 1. 不用假数据冒充功能

真实环境里所有数字（额度、镜像大小、进度、服务状态、端口）都来自真实调用。
**拿不到就显示 `—` 并给原因**，不要填 0、不要填"约"、不要写一个看起来合理的值。

演示数据只在 `VITE_DEMO=1` 的开发构建里生效，界面上有角标，发布包里进不去。

有疑问时问自己：*"如果用户照着这个数字做决定，他会不会被误导？"*

### 2. key 只在两个地方

`~/.hunter/app/.env`（权限 600）和进程内存。**不进日志、不进遥测、不进诊断包、不进仓库和文档。**

任何可能被打印的字符串都要过 `redact::redact()`。新增一把 secret 时记得
`redact::register_secret()`。`err.rs` 的 `Display` 已经自动脱敏了，测试里有看门狗盯着这一条。

### 3. 子进程一律参数数组

`proc.rs` 只暴露"程序名 + 参数数组"的接口，**连一个接受整串命令行的函数都不提供**，
想拼字符串也没有地方拼。新增外部命令调用走 `proc::run` / `proc::run_timeout`，
或者 `compose::run` / `compose::argv`。

### 4. 除 web 外的端口只绑 127.0.0.1

api / opencode / postgres / redis 一律 `127.0.0.1`。覆盖文件里的 `!override` 标签是必须的：
compose 对 `ports` 默认做**追加**合并，漏了标签会变成"既听 0.0.0.0 又听 127.0.0.1"。

写完配置之后 `flow::verify_bindings()` 会读 `docker compose config --format json` 复核一遍 ——
读的是**合并之后的最终结果**，而不是我们自己写进去的那份"意图"。

### 5. 数字都是实测的

文档、注释、报告里写的每个数字都要有出处。没测过就写"未测"和原因。

## 五、Rust 侧模块地图

| 模块 | 方案节 | 干什么 |
|---|---|---|
| `runtime::which` | — | **可执行文件定位**（I4 的 P0）。配置 → PATH → 平台已知位置，按顺序探，全过程留痕。所有调 docker 的地方都从它拿绝对路径。已知位置清单**只写在这一处** |
| `runtime::docker` | §5.1 | Docker / daemon / compose 检测，三平台安装引导 |
| `compose` | §5.2、§9 | `--progress json` 的流式解析、up、健康轮询、logs |
| `config` | §5.3、§7 | `launcher.toml`、`.env`、端口冲突、覆盖文件、compose 文件 |
| `gateway` | §5.4、§8 | key 校验、额度、模型列表、自带 key 连通性 |
| `registry` | §5.5 | 候选源探测与测速、从 manifest 读压缩大小 |
| `flow` | — | 把上面串成一次完整安装。**GUI 与 headless 共用它** |
| `headless` | §6 | 纯命令行版 |
| `selfupdate` | §10 | 启动器自更新（两个端点 + minisign 验签 + deb 的手动路径） |
| `upgrade` | §5.6、§10 | Hunter 版本检查与升级，失败自动回滚 |
| `backup` | §10 | 升级前的 `pg_dump` 与配置备份 |
| `offline` | §9 | 离线包导入 / 导出 |
| `redact` / `log` | §7、§12.3 | 滚动日志与脱敏 |
| `tray` / `autostart` | §5.8 | 托盘、开机自启 |
| `telemetry` / `feedback` / `zip` | §11、§12 | 本地事件队列、诊断包 |
| `upstream` | §13 | 从本机 api 读面板要的数字 |
| `assist::probe` | — | 采一份**结构化诊断**（已脱敏 + 用户名已换掉），给界面与模型共用 |
| `assist::rules` | — | **第一层**：确定性规则。零延迟、零 token、不联网。认出来的情况到此为止 |
| `assist::actions` | — | **动作白名单**。模型只能从这张写死的表里挑，参数逐项校验，表外一律拒绝并记日志 |
| `assist::ai` | — | **第二层**：AI 兜底。最多 3 轮，8 条降级路径，出口闸扫 key 形状 |
| `assist`（mod） | — | 把两层串起来，**顺序不能反**；会话状态（用户确认动作发生在两轮之间） |

**加一个 Tauri command**：写在 `commands.rs`，在 `lib.rs` 的 `generate_handler!` 里注册，
在 `src/lib/ipc.ts` 里加对应的函数（顺手加 `DEMO` 分支），类型写进 `src/lib/types.ts`。
阻塞的活儿用 `blocking()` 包一层挪到工作线程。

**要几分钟的操作**（安装、升级）不要阻塞 command：起一个线程，用事件推进度，
另外给一个 `*_status` 命令让前端轮询（事件可能在页面挂载前就发过了）。

## 六、前端

设计令牌全部量自 `docs/design/` 下的三张视觉稿，逐项列在
[`docs/design/设计令牌.md`](design/设计令牌.md)，实现在 `src/styles/tokens.css`。
**视觉稿是 2 倍图**（2360×1520 ↔ 约 1180×760 逻辑像素），量到的像素值要 ÷2。

### 字体

Noto Sans SC + JetBrains Mono 的**子集**，随程序打包（离线可用），SIL OFL 1.1。
子集只含**仓库里出现过的字形**，所以：

```bash
# 加了新的中文文案之后必须重新生成，否则界面上会多出豆腐块
python3 -m venv /tmp/fonttools-venv && /tmp/fonttools-venv/bin/pip install fonttools brotli
/tmp/fonttools-venv/bin/python scripts/build-fonts.py
python3 scripts/check-fonts.py    # CI 里跑的就是这个，会拦住忘记生成的情况
```

`check-fonts.py` 只盯"能显示出来的字"（前端全文 + Rust 的**字符串字面量**），
改注释不会触发重新生成。

### 截图

涉及界面的改动要在测试机上用 Xvfb 真启动、逐张与视觉稿比对，截图存
`docs/screenshots/<里程碑>/`。**API 通 ≠ 界面通。**

```bash
bash scripts/screenshot.sh docs/screenshots/M4
python3 scripts/compare-mockup.py    # 与视觉稿逐项比像素
```

## 七、测试

* **Rust 单测**：`cargo test`。当前 188 个。纯逻辑（解析、版本比较、脱敏、状态文字、
  文件名规则）都有测试；碰真实 docker / 网络的部分靠真机跑。
* **前端单测**：`vitest`。状态机、格式化、打码。
* **真机测试**：只有 Linux 有环境。Windows / macOS 以「CI 能编译 + 打包 + 代码审阅」为准，
  报告里必须写明"未真机测试"。

写测试时的一个习惯：**测试名用中文一句话说清它在盯什么**。
`fn 下载地址与_release_yml_的命名一致()` 比 `fn test_deb_url()` 有用得多 ——
半年后有人想改文件名时，红掉的测试名直接告诉他为什么不能改。

## 八、CI

`.github/workflows/`：

| 文件 | 触发 | 干什么 |
|---|---|---|
| `ci.yml` | push main / PR / 手动 | 前端 lint+typecheck+vitest+build、Rust fmt+test+clippy+真打 deb/AppImage、Windows 与 macOS 真编一次 release 二进制 |
| `release.yml` | tag `launcher-v*` / 手动 | 三平台打包 → GitHub Release（prerelease）→ latest.json → 同步 COS |
| `cn-mirror.yml` | 每 6 小时 / 手动 | 把 hunter 镜像与 compose 同步到腾讯云香港 |

`ci.yml` 里几道自己给自己设的闸门：

* **不许出现已停用的国内源地址**（`scripts/check-retired-mirrors.sh`）——
  广州区的仓库和桶已经删了，代码里再引用就是 404。
* **字体子集要覆盖所有会上屏的字**。
* **发布产物里不许有演示数据标记**，而且**反过来**验证一次演示构建里确实有这个标记。
* **deb 的依赖里必须有 `libayatana-appindicator3-1`**，漏了托盘在很多桌面上直接不出现。

`cargo check` **不等于** `tauri build`：前者不带 `custom-protocol` 特性，
产物会去连 devUrl 而不是用内嵌的前端，表现是一个白屏窗口。所以 CI 的三平台都真编一次 release 二进制。

## 九、发版

```bash
# 1. 改版本号（三个文件一起改：package.json / tauri.conf.json / Cargo.toml）
scripts/set-version.sh 0.1.0-rc.1

# 2. 让 Cargo.lock 跟上，否则 CI 的 --locked 会报锁文件过期
cargo check --manifest-path src-tauri/Cargo.toml

# 3. CHANGELOG 里加一节（release-notes.sh 会把对应小节抄进 Release 说明）
$EDITOR CHANGELOG.md

# 4. 提交、打 tag、推
git commit -am "chore(release): 0.1.0-rc.1"
git tag launcher-v0.1.0-rc.1
git push && git push --tags
```

`release.yml` 接手之后：

1. 三平台并行 `tauri build`（macOS 用 `--target universal-apple-darwin`）；
2. 产物统一改成**不带空格**的文件名 —— Tauri 默认用 `productName`（"Hunter Launcher"）当文件名，
   带一个空格，下载地址会变成 `%20`。`selfupdate.rs` 里 `.deb` 的地址是按
   `hunter-launcher_<版本>_amd64.deb` 硬拼的，两边对不上就是 404
   （`selfupdate.rs` 里有一条测试专门盯这个）；
3. 建 / 更新 GitHub Release（**一律 prerelease**，因为没有代码签名），上传全部产物与 `.sig`；
4. `scripts/make-latest-json.py` 生成两份 updater 清单：一份地址指向 GitHub Release，
   一份指向 COS 香港；
5. `scripts/cos-upload.py` 把安装包传到 `/launcher/<版本>/`，国内版清单传到 `/launcher/latest.json`。

**版本号与 tag 必须对得上**：`release.yml` 会拿 tag 里的版本和 `tauri.conf.json` 对账，
对不上直接红。因为 updater 比的是**编译进程序里**的版本号，落后了就会出现
"装了新版还提示有新版"这种死循环。

预发布版本号要写成 `0.1.0-rc.1` 而不是 `0.1.0-rc1`：semver 按点号分段比较，
`rc.10 > rc.9` 才成立；写成 `rc10` 就变成字符串比较，`rc10 < rc9`。

## 十、updater 的密钥

**这和"安装包的代码签名"是两件事**，别混：

| | 代码签名 | updater 签名 |
|---|---|---|
| 谁在验 | 操作系统（SmartScreen / Gatekeeper） | 启动器自己 |
| 要花钱吗 | 要（CA / Apple，100–500 美元/年） | 不要（minisign，自己生成） |
| 现在有吗 | **没有**，所以 Release 标 prerelease | **有**，而且是必须的 |

生成一对新密钥：

```bash
pnpm exec tauri signer generate -w ~/.hunter-launcher-keys/hunter-launcher-updater.key
```

* 私钥放开发机 `~/.hunter-launcher-keys/`（600），**绝不进仓库**；
* 私钥与口令存进仓库 secrets：`TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`；
* 公钥写进 `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`。

**私钥丢了 = 已经装出去的那些启动器再也收不到更新**（它们只认编译进去的那个公钥）。
换密钥的唯一办法是让用户手动装一次带新公钥的版本。

`release.yml` 里这个 secret 缺失时会**红**，不像代码签名那样跳过 ——
没有它产出的 `latest.json` 验不过签，自更新整个失效，那种"发出去了但更新是坏的"
比构建失败糟糕得多。

## 十一、踩过的坑

留档，省得再踩一遍。完整的在各里程碑报告里。

| 坑 | 结论 |
|---|---|
| `docker compose --progress json pull` 的进度流在 **stderr** 上 | 不是 stdout |
| `Extracting` 行只有 `current` 没有 `total` | 算不出解压百分比，界面显示"解压中"而不是画假进度条 |
| `docker pull`（不带 compose）在非 TTY 下完全没有逐层进度 | 只有三行结果，所以必须走 compose |
| `compose ps --format json` 无容器时 stdout 是空字符串、退出码 0 | 解析器要吃空输入 |
| `cargo build --release` ≠ `tauri build` | 前者不带 `custom-protocol`，产物白屏 |
| WebKit 会把 `<button>` 的内容盒垂直居中 | 卡片被网格拉高后文字跑中间，改用带 role 的 `div` |
| compose 对 `ports` 默认**追加**合并 | 覆盖文件必须写 `!override` |
| Tencent COS 拒绝 path-style 寻址 | 必须 virtual-hosted（`PathStyleDomainForbidden`） |
| Tauri updater 在 Linux 上只能更新 AppImage | `.deb` 走"下载 + 一条命令"的路 |
| GitHub 未认证接口每小时 60 次 | 版本检查缓存 6 小时，否则开着面板十分钟就用光 |
| Windows 上 CRLF 会让内置 compose 副本的校验和对不上 | `.gitattributes` 里钉死 LF |
